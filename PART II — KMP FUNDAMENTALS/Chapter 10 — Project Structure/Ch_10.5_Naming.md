# Chapter 10 — Project Structure

## Part 5 — Naming

Naming is one of the least discussed parts of architecture.

Yet naming is one of the first things developers encounter.

Before reading an implementation, a developer sees:

```text
Module
Package
Class
Function
Interface
File
```

The names create an architectural expectation.

If the project says:

```text
core:network
```

developers expect network infrastructure.

If it says:

```text
core:utils
```

developers have no idea what belongs there.

If the package says:

```text
orders.domain.policy
```

the ownership is immediately clearer.

If the class is:

```text
OrderCancellationPolicy
```

the behavior is clearer than:

```text
OrderManager
```

Naming is therefore not cosmetic.

> **Naming is architecture expressed in words.**

---

# 1. Why Naming Matters

Good naming improves:

```text
Discoverability
Readability
Architecture communication
Code review
Team communication
Onboarding
Debugging
Ownership
Refactoring
API design
```

Poor naming creates:

```text
Ambiguity
Wrong dependencies
Misplaced code
Duplicated concepts
Architecture drift
```

---

# 2. The Naming Mental Model

Think about naming at multiple levels:

```text
Repository
    ↓
Application
    ↓
Module
    ↓
Package
    ↓
Type
    ↓
Function
    ↓
Variable
```

Every level should communicate a progressively more specific meaning.

For example:

```text
features/
└── orders/
    └── domain/
        └── policy/
            └── OrderCancellationPolicy
```

The entire path tells a story.

---

# 3. Naming Is a Hierarchy of Context

Consider:

```text
OrderCancellationPolicy
```

The name itself is useful.

But:

```text
features/orders/domain/policy/OrderCancellationPolicy.kt
```

is much more powerful.

The context tells us:

```text
Feature → Orders
Layer → Domain
Responsibility → Policy
Type → OrderCancellationPolicy
```

Good architecture uses all four levels.

---

# 4. The Naming Principle

A useful rule:

> **The closer code is to the business, the more its name should reflect business meaning.**

For example:

```text
CancelOrder
RefundPayment
TrackShipment
UpdateCustomerAddress
```

are stronger than:

```text
OrderProcessor
PaymentManager
ShipmentService
CustomerHandler
```

---

# 5. Technical Names vs Semantic Names

Technical:

```text
Manager
Helper
Handler
Processor
Service
Utils
Common
Base
Provider
```

Semantic:

```text
OrderCancellationPolicy
PaymentAuthorizer
ShipmentTracker
CustomerAddressUpdater
SecureStorage
```

Technical names describe implementation patterns.

Semantic names describe responsibility.

---

# 6. Business Language Should Drive Names

If the product calls something:

```text
Order
Payment
Shipment
Customer
Subscription
```

use those terms consistently.

Avoid creating alternative names:

```text
Purchase
Transaction
Delivery
Account
Membership
```

unless they represent genuinely different concepts.

---

# 7. Ubiquitous Language

In domain-driven systems, the same business concept should ideally have a consistent name across:

```text
Product
Architecture
Code
Documentation
Tickets
Monitoring
```

For example:

```text
Order Cancellation
```

should not become:

```text
Order Abort
Purchase Reversal
Order Termination
```

unless those are distinct concepts.

---

# 8. Naming as a Shared Team Language

A good name becomes part of team communication.

For example:

> “The issue is in the OrderCancellationPolicy.”

Everyone should know:

```text
What it does
Where it belongs
Who owns it
```

Naming reduces communication overhead.

---

# 9. Module Naming

A Gradle module name should communicate:

```text
Capability
Feature
Infrastructure
Platform
```

Examples:

```text
:features:orders
:features:payments
:core:network
:core:security
:platform:notifications
:design-system
```

---

# 10. Good Module Names

Good:

```text
:features:orders
:features:checkout
:core:network
:core:database
:core:security
:core:observability
:platform:secure-storage
:design-system
```

These names communicate responsibility.

---

# 11. Weak Module Names

Avoid:

```text
:common
:shared
:utils
:base
:core2
:module1
:library
:stuff
```

These names create ambiguity.

---

# 12. Module Naming Pattern

A useful enterprise convention:

```text
:category:capability
```

For example:

```text
:features:orders
:features:payments
:core:network
:core:security
:platform:storage
```

The exact taxonomy depends on the repository.

Consistency is more important than the specific prefix.

---

# 13. Feature Module Names

Feature modules should use business capabilities:

```text
orders
payments
profile
inventory
authentication
checkout
subscriptions
```

Avoid:

```text
order-feature
orders-module
orders-screen
orders-manager
```

unless those distinctions are architecturally meaningful.

---

# 14. Feature vs Screen Naming

A feature is larger than a screen.

Therefore:

```text
:features:orders
```

is usually stronger than:

```text
:features:order-list-screen
```

A feature may contain:

```text
List
Details
Create
Edit
Cancel
Tracking
```

---

# 15. Screen Names

Screens should describe user intent or business context.

Good:

```text
OrderListScreen
OrderDetailsScreen
PaymentHistoryScreen
ProfileScreen
```

Weak:

```text
Screen1
MainScreen
CommonScreen
GenericScreen
```

---

# 16. Feature Names vs UI Names

Prefer:

```text
orders
```

for the feature.

Then:

```text
OrderListScreen
OrderDetailsScreen
```

inside presentation.

This separates:

```text
Business capability
```

from:

```text
UI representation
```

---

# 17. Package Naming

Package names should be:

```text
lowercase
semantic
stable
predictable
```

Example:

```text
com.company.app.orders.domain
```

Avoid:

```text
com.company.app.CommonUtils
com.company.app.Misc
com.company.app.Helpers
```

---

# 18. Package Naming Pattern

A common structure:

```text
com.company.product.<feature>.<responsibility>
```

For example:

```text
com.acme.shop.orders.domain
com.acme.shop.orders.data
com.acme.shop.orders.presentation
```

---

# 19. Package Names Should Be Boring

This may sound strange.

But good package names are predictable:

```text
orders
payments
security
network
database
```

Do not try to make package names clever.

Clever names increase cognitive load.

---

# 20. Package Names and Context

Consider:

```text
com.example.orders.domain.model.Customer
```

versus:

```text
com.example.common.models.Customer
```

The first provides context.

The second hides ownership.

---

# 21. Package Naming and Bounded Contexts

Different contexts can own similar concepts:

```text
orders.domain.model.Customer
payments.domain.model.Customer
profile.domain.model.Customer
```

The package communicates:

```text
Which Customer?
```

This is useful in domain-driven architecture.

---

# 22. Naming Modules and Packages Together

Example:

```text
:features:orders
└── com.company.app.orders
    ├── domain
    ├── data
    └── presentation
```

The module and package reinforce the same concept.

That is desirable.

---

# 23. Avoid Naming Mismatch

Bad:

```text
Module:
:features:orders

Package:
com.company.app.purchase
```

Now the developer must learn that:

```text
orders = purchase
```

without a good reason.

Keep naming aligned.

---

# 24. Naming Source Sets

KMP source sets have established names:

```text
commonMain
commonTest
androidMain
androidUnitTest
iosMain
```

Use standard source-set naming unless the build architecture requires something else.

---

# 25. KMP Platform Naming

For platform-specific packages, prefer capability-oriented names:

```text
platform.storage
platform.camera
platform.notifications
```

rather than broad:

```text
androidStuff
iosStuff
```

---

# 26. `expect / actual` Naming

A common pattern:

```kotlin
expect class SecureStorage
```

and:

```kotlin
actual class SecureStorage
```

The conceptual name stays the same.

The source set tells you:

```text
Which implementation?
```

---

# 27. Why Matching `expect / actual` Names Matter

The goal is to communicate:

```text
One capability
Multiple implementations
```

instead of:

```text
AndroidSecureStorage
IosSecureStorage
```

everywhere.

The implementation can still have internal platform-specific names when useful.

---

# 28. Platform Implementation Naming

If a platform-specific implementation needs a distinct class:

```kotlin
internal class AndroidSecureStorage
```

or:

```kotlin
internal class KeychainSecureStorage
```

can be appropriate.

The public abstraction remains:

```text
SecureStorage
```

---

# 29. Interface Naming

Kotlin generally does not require interface names to begin with:

```text
I
```

Avoid:

```text
IOrderRepository
IPaymentGateway
ISecureStorage
```

Prefer:

```text
OrderRepository
PaymentGateway
SecureStorage
```

---

# 30. Why `I` Prefix Is Usually Unnecessary

The usage already tells you the type:

```kotlin
private val repository: OrderRepository
```

The important information is:

```text
What capability does it provide?
```

not:

```text
That it is an interface.
```

---

# 31. Implementation Naming

If there is one obvious implementation:

```kotlin
class DefaultOrderRepository : OrderRepository
```

can be useful.

Other options:

```text
SqlDelightOrderRepository
RemoteOrderRepository
CachedOrderRepository
```

when implementation differences matter.

---

# 32. Avoid `Impl` by Default

This:

```kotlin
class OrderRepositoryImpl : OrderRepository
```

is common but often not informative.

If there is a meaningful implementation name:

```kotlin
class CachedOrderRepository
```

is clearer.

---

# 33. When `Impl` Is Acceptable

`Impl` is acceptable when:

```text
There is genuinely one default implementation
+
No better semantic name exists
```

For example:

```text
DefaultClock
```

may be better than:

```text
ClockImpl
```

---

# 34. Default Implementation Naming

Prefer:

```kotlin
class DefaultLogger : Logger
```

over:

```kotlin
class LoggerImpl : Logger
```

because:

```text
Default
```

communicates why the implementation exists.

---

# 35. Repository Naming

Good:

```text
OrderRepository
PaymentRepository
ProfileRepository
```

Implementation:

```text
DefaultOrderRepository
CachedOrderRepository
RemoteOrderRepository
```

depending on architecture.

---

# 36. Data Source Naming

Good:

```text
OrderRemoteDataSource
OrderLocalDataSource
```

or:

```text
OrderApi
OrderDao
```

when those terms accurately represent the abstraction.

---

# 37. API Naming

Good:

```text
OrderApi
PaymentApi
ProfileApi
```

Avoid:

```text
ApiManager
ApiServiceManager
NetworkService
```

when the class is specifically an API client.

---

# 38. Network Client Naming

Infrastructure:

```text
NetworkClient
HttpClientFactory
NetworkConfig
NetworkError
```

Feature API:

```text
OrderApi
PaymentApi
```

Keep generic and feature-specific names separate.

---

# 39. DTO Naming

A transport model can use:

```text
OrderDto
PaymentDto
CustomerDto
```

if the DTO distinction is meaningful.

But if the type is already clearly scoped to a remote package, the suffix may sometimes be unnecessary.

For example:

```text
orders.data.remote.Order
```

may be clear enough depending on conventions.

---

# 40. Entity Naming

Database entities can use:

```text
OrderEntity
PaymentEntity
```

when that helps distinguish them from domain models.

Again:

```text
orders.data.local.OrderEntity
```

already provides context.

---

# 41. Domain Model Naming

Prefer business names:

```text
Order
Payment
Customer
Shipment
```

rather than:

```text
OrderModel
PaymentModel
CustomerModel
```

when the type represents the actual domain concept.

---

# 42. UI Model Naming

If the presentation model is different:

```text
OrderUiModel
OrderDetailsUiModel
OrderListItemUiModel
```

can clearly communicate presentation ownership.

---

# 43. UI State Naming

Good:

```text
OrderListUiState
OrderDetailsUiState
PaymentHistoryUiState
```

These names tell you:

```text
Screen/feature
Purpose
Layer
```

---

# 44. UI Event Naming

Good:

```text
OrderDetailsEvent
OrderListEvent
PaymentEvent
```

or more specific:

```text
OrderDetailsAction
OrderDetailsIntent
```

Choose one vocabulary and use it consistently.

---

# 45. MVI Naming

If the project uses MVI:

```text
OrderDetailsIntent
OrderDetailsState
OrderDetailsEffect
```

can be clear.

If it uses another terminology:

```text
Event
UiState
Effect
```

remain valid.

Consistency matters more than the exact terms.

---

# 46. MVVM Naming

For MVVM:

```text
OrderDetailsViewModel
OrderDetailsUiState
```

is straightforward.

Avoid:

```text
OrderDetailsVM
```

unless the project has a strong abbreviation convention.

---

# 47. Avoid Excessive Abbreviations

Avoid:

```text
OrdRepo
PayVM
UsrMgr
NetCfg
SecStore
```

Prefer:

```text
OrderRepository
PaymentViewModel
UserManager
NetworkConfig
SecureStorage
```

Code is read far more often than it is typed.

---

# 48. Naming and Readability

Compare:

```kotlin
val ordRepo = ordRepoProvider.get()
```

with:

```kotlin
val orderRepository = orderRepositoryProvider.get()
```

The second is longer.

It is also easier to understand.

---

# 49. Function Naming

Functions should describe actions or transformations.

Good:

```kotlin
cancelOrder()
loadOrders()
refreshOrders()
calculateTotal()
mapToDomain()
```

Avoid:

```kotlin
doStuff()
process()
handle()
execute()
run()
```

unless the context makes the meaning unambiguous.

---

# 50. Command Naming

Commands should usually use verbs:

```text
CreateOrder
CancelOrder
SubmitPayment
UpdateAddress
RefreshOrders
```

This makes intent clear.

---

# 51. Query Naming

Queries can use:

```text
GetOrders
GetOrderDetails
ObserveOrder
FindCustomer
LoadPaymentHistory
```

Choose a consistent vocabulary.

---

# 52. Use Case Naming

A use case should express user/business intent:

```text
CreateOrder
CancelOrder
TrackOrder
RefundPayment
```

Avoid:

```text
OrderUseCase
PaymentUseCase
```

because these names hide the actual operation.

---

# 53. One Use Case, One Intent

A class named:

```text
OrderUseCase
```

may eventually contain:

```text
create
cancel
update
delete
track
```

This becomes a god object.

Prefer:

```text
CreateOrder
CancelOrder
UpdateOrder
TrackOrder
```

when each represents meaningful behavior.

---

# 54. Service Naming

If a domain service exists, its name should express the business capability:

```text
OrderPricingService
PaymentAuthorizationService
ShippingRateCalculator
```

Avoid:

```text
OrderService
PaymentService
CommonService
```

when the responsibility can be named more precisely.

---

# 55. Manager Naming

`Manager` is often a smell.

Instead of:

```text
OrderManager
```

ask what it actually does:

```text
OrderCache
OrderSynchronizer
OrderRepository
OrderCoordinator
OrderCancellationPolicy
```

The precise name often reveals the correct architecture.

---

# 56. Helper Naming

`Helper` also hides responsibility.

Instead of:

```text
DateHelper
```

use:

```text
DateFormatter
DateParser
DateRangeCalculator
```

depending on behavior.

---

# 57. Processor Naming

`Processor` can also be vague.

Instead of:

```text
PaymentProcessor
```

consider:

```text
PaymentAuthorizer
PaymentCaptureService
PaymentRefundProcessor
```

if those are distinct operations.

---

# 58. Handler Naming

`Handler` can be appropriate for actual event/message handling:

```text
OrderCreatedEventHandler
PushNotificationHandler
DeepLinkHandler
```

But:

```text
OrderHandler
```

is too vague.

---

# 59. Coordinator Naming

`Coordinator` can be useful for orchestration:

```text
CheckoutCoordinator
NavigationCoordinator
SyncCoordinator
```

when the class actually coordinates multiple operations.

Do not use it as a generic replacement for:

```text
Manager
```

---

# 60. Controller Naming

`Controller` may be appropriate for:

```text
UI/controller
network controller
hardware controller
```

depending on architecture.

Avoid generic:

```text
OrderController
```

if it does not have a clear controller responsibility.

---

# 61. Provider Naming

`Provider` should mean:

```text
Provides something
```

Examples:

```text
ClockProvider
TokenProvider
DispatcherProvider
```

If it simply performs business logic:

```text
Provider
```

is misleading.

---

# 62. Factory Naming

A factory should actually create objects.

Good:

```text
OrderFactory
HttpClientFactory
ViewModelFactory
```

Avoid:

```text
OrderFactory
```

that also validates, saves, and sends analytics.

---

# 63. Builder Naming

Use `Builder` when the object is actually constructed incrementally.

Avoid:

```text
RequestBuilder
```

for a class that simply maps:

```text
RequestMapper
```

---

# 64. Adapter Naming

Adapters translate one boundary into another.

Good:

```text
StripePaymentAdapter
FirebaseAnalyticsAdapter
AndroidSecureStorageAdapter
```

The name communicates:

```text
What it adapts
```

---

# 65. Mapper Naming

Mappers transform between representations.

Good:

```text
OrderDtoMapper
OrderEntityMapper
OrderUiModelMapper
```

or concise extension functions:

```kotlin
fun OrderDto.toDomain(): Order
```

Choose one consistent approach.

---

# 66. Parser Naming

A parser should parse:

```text
DeepLinkParser
OrderNumberParser
JwtParser
```

Avoid:

```text
StringHelper
```

for parsing behavior.

---

# 67. Formatter Naming

A formatter should format:

```text
CurrencyFormatter
DateFormatter
OrderStatusFormatter
```

This is more precise than:

```text
DisplayHelper
```

---

# 68. Validator Naming

A validator validates:

```text
EmailValidator
OrderCancellationValidator
PaymentRequestValidator
```

But distinguish:

```text
Syntax validation
```

from:

```text
Business policy
```

For example:

```text
EmailValidator
```

versus:

```text
OrderCancellationPolicy
```

---

# 69. Policy Naming

Policy names are excellent for business rules:

```text
CancellationPolicy
RefundPolicy
PricingPolicy
EligibilityPolicy
```

They communicate:

```text
Decision-making responsibility
```

---

# 70. Strategy Naming

Strategy is useful when multiple interchangeable algorithms exist:

```text
TaxCalculationStrategy
PricingStrategy
RetryStrategy
```

Avoid adding `Strategy` just to make a class sound architectural.

---

# 71. Specification Naming

If the project uses the Specification pattern:

```text
OrderEligibilitySpecification
```

can be meaningful.

But do not create a generic:

```text
Specification
```

for simple predicates.

---

# 72. Repository Naming and Ownership

A repository should represent a data/domain boundary:

```text
OrderRepository
```

not:

```text
DataManager
```

The name communicates what the abstraction owns.

---

# 73. Cache Naming

Good:

```text
OrderCache
ProfileCache
TokenCache
```

If the cache has policy:

```text
OrderCachePolicy
```

may be appropriate.

---

# 74. Synchronizer Naming

Good:

```text
OrderSynchronizer
InventorySynchronizer
ProfileSynchronizer
```

if the class coordinates synchronization.

Avoid:

```text
SyncManager
```

unless the responsibility truly spans multiple domains.

---

# 75. Worker Naming

For background work:

```text
OrderSyncWorker
UploadWorker
CacheRefreshWorker
```

when the concept is specifically a worker.

KMP platform-specific implementations can sit behind shared capabilities where appropriate.

---

# 76. Scheduler Naming

Good:

```text
BackgroundTaskScheduler
NotificationScheduler
SyncScheduler
```

when the object schedules work.

---

# 77. Gateway Naming

Gateways are useful for external boundaries:

```text
PaymentGateway
IdentityGateway
AnalyticsGateway
```

They communicate:

```text
External capability
```

---

# 78. Client Naming

Clients usually represent technical communication:

```text
HttpClient
PaymentClient
MapsClient
```

Be careful:

```text
PaymentClient
```

could mean either business or vendor communication.

A more precise name may be:

```text
StripePaymentClient
```

inside an integration boundary.

---

# 79. API vs Gateway vs Client

A useful distinction:

```text
Api
→ Feature-specific remote endpoint contract

Client
→ Technical communication mechanism

Gateway
→ Application-facing boundary around an external capability
```

These are conventions, not absolute rules.

Consistency is the goal.

---

# 80. Naming External Integrations

Good:

```text
StripePaymentGateway
FirebaseAnalyticsAdapter
GoogleMapsLocationProvider
```

The vendor name can appear at the integration boundary.

Do not leak it into the entire application.

---

# 81. Vendor Naming Boundary

```text
features/payments
       │
       ▼
PaymentGateway
       │
       ▼
integrations/stripe
       │
       ▼
Stripe SDK
```

The vendor name belongs near the vendor boundary.

---

# 82. Naming Shared Infrastructure

Shared infrastructure should use stable capability names:

```text
NetworkClient
SecureStorage
Logger
Analytics
Database
Clock
```

Avoid:

```text
CommonManager
SharedProvider
GlobalService
```

---

# 83. Naming Platform Abstractions

Good:

```text
SecureStorage
BiometricAuthenticator
NotificationSender
Camera
LocationProvider
```

These describe capabilities.

Avoid:

```text
PlatformManager
PlatformService
DeviceHelper
```

---

# 84. Naming `expect / actual` APIs

The common declaration should be platform-neutral:

```kotlin
expect class NotificationSender
```

not:

```kotlin
expect class AndroidNotificationSender
```

The abstraction should describe the capability.

---

# 85. Naming Platform Implementations

Inside `androidMain`:

```kotlin
actual class NotificationSender
```

or:

```kotlin
internal class AndroidNotificationSender
```

Inside `iosMain`:

```kotlin
actual class NotificationSender
```

or:

```kotlin
internal class IosNotificationSender
```

depending on the implementation approach.

---

# 86. Naming Interfaces by Capability

Good:

```text
TokenProvider
Clock
Logger
SecureStorage
PaymentGateway
OrderRepository
```

These are capabilities.

---

# 87. Naming Interfaces by Implementation

Weak:

```text
KtorNetwork
FirebaseLogger
SqlDelightRepository
```

when those names become the public abstraction.

These names expose implementation choices.

---

# 88. Naming and Dependency Inversion

The abstraction should be named after:

```text
What consumers need
```

not:

```text
What implementation happens to provide it
```

For example:

```text
PaymentGateway
```

instead of:

```text
StripeService
```

at the application boundary.

---

# 89. Naming Domain Models

Domain models should usually use nouns:

```text
Order
Payment
Shipment
Customer
Address
Subscription
```

They represent business concepts.

---

# 90. Naming Value Objects

Value objects should be precise:

```text
Money
Currency
EmailAddress
OrderId
CustomerId
PostalCode
```

Avoid generic:

```text
Value
Data
Identifier
StringValue
```

when a business concept exists.

---

# 91. Strongly Typed IDs

Instead of:

```kotlin
typealias OrderId = String
```

or:

```kotlin
val orderId: String
```

a domain model may use:

```kotlin
@JvmInline
value class OrderId(
    val value: String
)
```

The name communicates semantics.

The exact representation depends on platform and architecture.

---

# 92. Naming Enums

Use domain language:

```text
OrderStatus
PaymentStatus
ShipmentStatus
```

Values:

```text
Pending
Confirmed
Cancelled
Completed
```

Avoid:

```text
StatusType
StatusEnum
OrderStatusEnum
```

The type already communicates that it is an enum/sealed hierarchy.

---

# 93. Naming Sealed Hierarchies

Use the concept:

```kotlin
sealed interface PaymentResult
```

rather than:

```kotlin
sealed interface PaymentResultType
```

The type itself is enough.

---

# 94. Naming Errors

Good:

```text
OrderError
PaymentError
AuthenticationError
NetworkError
```

More specific:

```text
OrderCancellationError
PaymentAuthorizationError
```

Avoid:

```text
GenericError
CommonError
BaseError
```

when the domain is known.

---

# 95. Naming Error Cases

Prefer semantic cases:

```kotlin
sealed interface OrderError {
    data object NotFound : OrderError
    data object CancellationNotAllowed : OrderError
    data object Unauthorized : OrderError
}
```

over:

```text
Error1
Error2
Error3
```

---

# 96. Naming Results

A result should describe the operation:

```text
PaymentResult
OrderCreationResult
AuthenticationResult
```

rather than:

```text
CommonResult
BaseResult
GenericResult
```

unless it is genuinely generic.

---

# 97. Naming Events

Events should describe something that happened:

```text
OrderCreated
PaymentAuthorized
ProfileUpdated
ShipmentDelivered
```

This is clearer than:

```text
OrderEvent
PaymentEvent
UpdateEvent
```

when the exact event is known.

---

# 98. Naming Commands

Commands describe requested actions:

```text
CreateOrder
CancelOrder
AuthorizePayment
UpdateProfile
```

This distinguishes:

```text
Intent
```

from:


# 255. Naming and `expect / actual`

# 334. Naming and Architecture Smells

Common naming smells:

```text
🚨 Manager
🚨 Helper
🚨 Utils
🚨 Common
🚨 Base
🚨 Global
🚨 Generic
🚨 Processor
🚨 Handler
🚨 Service
🚨 Provider
```

These words are not forbidden.

They simply deserve scrutiny.

---

# 335. Naming Smell: `Manager`

Ask:

```text
What exactly does it manage?
```

Then replace with the actual responsibility.

---

# 336. Naming Smell: `Helper`

Ask:

```text
What does it help with?
```

Name the operation.

---

# 337. Naming Smell: `Utils`

Ask:

```text
What capability do these utilities represent?
```

Split by semantic ownership.

---

# 338. Naming Smell: `Service`

Ask:

```text
What does this service actually do?
```

Use:

```text
Repository
Gateway
Policy
Calculator
Validator
Authorizer
Synchronizer
```

when those are more accurate.

---

# 339. Naming Smell: `Base`

Base classes should represent a genuine shared abstraction.

Avoid:

```text
BaseManager
BaseService
BaseRepository
BaseViewModel
```

unless the shared behavior is substantial and meaningful.

---

# 340. Naming Smell: `Common`

If the only reason is:

```text
"Used by multiple places"
```

that is not enough.

Find the actual semantic capability.

---

# 341. Naming Smell: `Global`

Global names often indicate hidden shared state.

Ask:

```text
What lifecycle?
Who owns it?
Why is it global?
```

---

# 342. Naming Smell: `Generic`

Names such as:

```text
GenericRepository
GenericManager
GenericService
```

often hide the actual domain.

---

# 343. Naming Smell: `Processor`

Ask:

```text
What does it process?
What transformation happens?
```

Then name the behavior.

---

# 344. Naming Smell: `Handler`

Ask:

```text
What event/message/input does it handle?
```

Then make that explicit:

```text
OrderCreatedEventHandler
DeepLinkHandler
```

---

# 345. Naming Smell: `Provider`

Ask:

```text
What does it provide?
```

If the answer is:

```text
Everything
```

the abstraction is too broad.

---

# 346. Naming Smell: `Factory`

Ask:

```text
What does it create?
```

If it also validates, stores, and sends analytics, split responsibilities.

---

# 347. Naming Smell: `Manager` Replacement Example

Before:

```kotlin
class OrderManager
```

After analyzing responsibilities:

```text
OrderRepository
OrderSynchronizer
OrderCancellationPolicy
OrderAnalytics
```

The names reveal the architecture.

---

# 348. Naming Smell: `Service` Replacement Example

Before:

```kotlin
class PaymentService
```

After:

```text
PaymentAuthorizer
PaymentCapturer
PaymentRefundProcessor
PaymentHistoryReader
```

depending on actual responsibilities.

---

# 349. Naming Smell: `Utils` Replacement Example

Before:

```text
core/utils/
├── DateUtils
├── CurrencyUtils
├── OrderUtils
```

After:

```text
core/time/DateFormatter
core/money/CurrencyFormatter
features/orders/domain/OrderCalculator
```

Ownership becomes explicit.

---

# 350. Naming Smell: `Common Models` Replacement

Before:

```text
common/models/
├── User
├── Order
├── Payment
```

After:

```text
features/orders/domain/model/Order
features/payments/domain/model/Payment
features/profile/domain/model/Profile
```

or intentionally shared contracts/value objects.

If the name is:

# 378. Naming Golden Rules

```text
1. Name by responsibility.
2. Use business language for business concepts.
3. Name abstractions by capability.
4. Name implementations by mechanism.
5. Keep platform-neutral names in common APIs.
6. Keep vendor names near integration boundaries.
7. Avoid generic dumping-ground names.
8. Avoid unnecessary abbreviations.
9. Avoid redundant suffixes such as Model, Manager, Impl, Enum.
10. Use package context to provide additional meaning.
11. Keep public API names stable.
12. Prefer precise names over clever names.
13. Let names expose ownership.
14. Let names reveal architectural boundaries.
15. Use consistent terminology across the repository.
16. Rename vague legacy types during migration when practical.
17. Name events as facts.
18. Name commands as intentions.
19. Name policies as decisions.
20. Name mappers as transformations.
21. Name platform APIs as capabilities.
22. Name vendor adapters as vendor + capability.
23. Keep names aligned with package and module structure.
24. Treat naming as part of architecture, not formatting.
25. If a class is difficult to name, reconsider its responsibility.
```

# 382. Final Takeaways

Naming is not the last step after architecture.

Naming is part of architecture.

A strong KMP project should make the following relationships obvious:

```text
Feature
    ↓
Package
    ↓
Responsibility
    ↓
Capability
    ↓
Implementation
    ↓
Platform / Vendor
```

The most useful naming principle is:

> [!IMPORTANT]
> **Name the thing according to the responsibility it owns, not the technical mechanism it currently uses.**

Prefer:

```text
PaymentGateway
```

over:

```text
StripeService
```

at the application boundary.

Prefer:

```text
OrderCancellationPolicy
```

over:

```text
OrderManager
```

Prefer:

```text
SecureStorage
```

over:

```text
AndroidKeyStoreManager
```

in common KMP APIs.

Prefer:

```text
core:network
```

over:

```text
core:ktor
```

when the module represents networking rather than one specific implementation.

Prefer:

```text
orders/domain/model
```

over:

```text
common/models
```

when the model belongs to Orders.

The ultimate goal is not to make names longer.

It is to make them **predictable, semantic, stable, and architectural**.

```text
Good Name
    ↓
Clear Responsibility
    ↓
Clear Ownership
    ↓
Clear Dependency
    ↓
Clear Architecture
```

That is why naming is not just style.

**Naming is one of the mechanisms through which a KMP architecture explains itself.**
