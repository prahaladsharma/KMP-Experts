# Chapter 10 — Project Structure

## Part 6 — Scaling

A project structure that works for five developers may become painful for fifty.

A module structure that works for three features may become expensive when the product grows to thirty.

A dependency that feels harmless today can become a build bottleneck, ownership problem, or architectural constraint later.

This is where **scaling** becomes an architectural concern.

> [!IMPORTANT]
> **Scaling project structure is not about creating more modules. It is about creating boundaries that allow code, teams, builds, releases, and ownership to grow without becoming tightly coupled.**

A scalable KMP architecture must scale several dimensions at the same time:

```text
                KMP PROJECT
                    │
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
    CODE           TEAMS         BUILDS
      │             │             │
      ▼             ▼             ▼
  FEATURES       OWNERSHIP     PERFORMANCE
      │             │             │
      └─────────────┼─────────────┘
                    ▼
                RELEASES
                    │
                    ▼
                PLATFORMS
```

The goal is not maximum modularization.

The goal is **controlled growth**.

---

# 1. What Does Scaling Mean?

When developers say:

> “The application needs to scale.”

they often mean runtime scalability:

```text
More users
More traffic
More data
More requests
```

Project architecture has another form of scaling.

A codebase must scale with:

```text
More developers
More teams
More features
More modules
More platforms
More dependencies
More releases
More tests
More build work
More business rules
```

This chapter focuses on that dimension.

---

# 2. The Six Dimensions of Project Scaling

A mature KMP project should consider:

| Dimension | Question |
|---|---|
| Code | Can the codebase grow without becoming confusing? |
| Teams | Can multiple teams work independently? |
| Build | Can developers build and test efficiently? |
| Ownership | Is responsibility clear? |
| Release | Can parts evolve independently where needed? |
| Platform | Can Android, iOS and other targets evolve without polluting shared code? |

A structure that solves only one of these dimensions is incomplete.

---

# 3. The Scaling Problem

Imagine the project starts like this:

```text
app/
├── common/
├── utils/
├── services/
└── models/
```

With five developers, it may feel manageable.

After several years:

```text
app/
├── common/
│   ├── models/
│   ├── utils/
│   ├── managers/
│   └── services/
│
├── services/
│   ├── payment/
│   ├── order/
│   ├── profile/
│   └── ...
│
├── models/
│   ├── User
│   ├── Order
│   ├── Payment
│   └── ...
│
└── utils/
    └── ...
```

Now everyone depends on everyone.

The problem is not code volume alone.

The problem is **lack of boundaries**.

---

# 4. The Scalable Alternative

A scalable architecture introduces ownership boundaries:

```text
project/
│
├── apps/
│
├── features/
│   ├── authentication/
│   ├── orders/
│   ├── payments/
│   └── profile/
│
├── core/
│   ├── network/
│   ├── database/
│   ├── security/
│   └── observability/
│
├── platform/
│   ├── storage/
│   ├── notifications/
│   └── device/
│
├── integrations/
│   ├── payments/
│   ├── analytics/
│   └── identity/
│
├── design-system/
├── testing/
└── build-logic/
```

The important property is not the number of directories.

It is:

```text
Clear ownership
Clear dependency direction
Clear change boundaries
```

---

# 5. Scaling Is About Change

A useful architectural question is:

> **What changes together?**

If two pieces of code almost always change together, keeping them close may make sense.

If they evolve independently, separating them may make sense.

This is more useful than asking:

> “Should everything be a separate module?”

---

# 6. The Change-Coupling Principle

Suppose:

```text
Orders
Payments
Profile
```

change independently.

Then:

```text
features/orders
features/payments
features/profile
```

can provide useful boundaries.

But if:

```text
Orders
OrderDetails
OrderHistory
OrderTracking
```

always change together and belong to the same business capability, splitting each screen into a Gradle module may create unnecessary complexity.

---

# 7. Scale by Business Boundary

A strong default:

```text
Feature = Business capability
```

Examples:

```text
orders
payments
checkout
profile
subscriptions
inventory
```

Each feature becomes a potential unit of:

```text
Ownership
Testing
Architecture
Change
Release
```

---

# 8. Feature Modules as Scaling Units

```text
                    APPLICATION
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       ORDERS         PAYMENTS        PROFILE
          │              │              │
          ▼              ▼              ▼
       TEAM A          TEAM B          TEAM C
```

This allows teams to work in parallel.

---

# 9. Team Scaling

A project structure should make it possible for:

```text
Team A → Orders
Team B → Payments
Team C → Profile
Team D → Platform
```

without every change requiring coordination across the entire repository.

This is one of the strongest reasons to modularize.

---

# 10. Conway's Law

A useful organizational observation:

> **Systems tend to reflect the communication structures of the organizations that build them.**

If ten teams all directly modify one giant module:

```text
:app
```

the architecture may become a reflection of that shared ownership.

If teams have clear capabilities:

```text
Orders
Payments
Identity
Platform
```

the module structure can reinforce those boundaries.

---

# 11. Architecture Should Support Team Boundaries

A scalable KMP project can align:

```text
Business capability
        ↓
Feature module
        ↓
Package boundary
        ↓
Team ownership
        ↓
CODEOWNERS
        ↓
CI checks
```

This is much stronger than simply organizing folders.

---

# 12. Module Ownership

Each important module should ideally have:

```text
Owner
Purpose
Public API
Dependencies
Consumers
Testing strategy
Release responsibility
```

Example:

```text
:features:payments

Owner:
Payments Team

Purpose:
Payment lifecycle

Public API:
PaymentAuthorizer

Dependencies:
core:network
core:security
integrations:payments
```

---

# 13. The Ownership Test

Ask:

> “If something breaks in this module, who should I contact?”

If the answer is:

```text
Everyone
```

the ownership boundary is weak.

---

# 14. CODEOWNERS

Repository ownership can reinforce module boundaries:

```text
/features/orders/**        @orders-team
/features/payments/**      @payments-team
/features/profile/**       @profile-team
/core/security/**          @security-team
/design-system/**          @design-system-team
```

The exact Git hosting syntax depends on the platform.

The architectural principle is:

```text
Code path → Ownership
```

---

# 15. Scaling Module Boundaries

Not every package needs to become a Gradle module.

Use:

```text
Package
```

for organization within a boundary.

Use:

```text
Module
```

when stronger isolation is valuable.

---

# 16. Package vs Module at Scale

| Need | Package | Module |
|---|---|---|
| Organize files | Yes | Yes |
| Naming boundary | Yes | Yes |
| Visibility isolation | Limited | Strong |
| Dependency restriction | Weak | Strong |
| Independent build unit | No | Yes |
| Team ownership | Possible | Strong |
| API surface | Convention | Enforceable |
| Build caching | Limited | Stronger |
| Gradle dependency control | No | Yes |

The goal is not:

```text
Maximum modules
```

The goal is:

```text
Useful boundaries
```

---

# 17. The Cost of a Module

Every module introduces some cost:

```text
Gradle configuration
Dependency management
Build logic
Testing
CI configuration
Documentation
Ownership
Developer navigation
```

Therefore:

> **A module should earn its existence.**

---

# 18. Module Economics

Think of each module as:

```text
Value of isolation
        -
Cost of isolation
```

If:

```text
Isolation benefit > complexity
```

the module is useful.

If:

```text
Isolation benefit < complexity
```

the module may be unnecessary.

---

# 19. The Wrong Way to Scale

A team discovers modular architecture and creates:

```text
:order-model
:order-api
:order-dto
:order-repository
:order-screen
:order-viewmodel
:order-utils
:order-mapper
```

for a small feature.

Now one simple change requires:

```text
9 modules
```

This is **module explosion**.

---

# 20. Module Explosion

Symptoms:

```text
Too many tiny modules
Long dependency chains
Hard-to-understand build graph
Excessive Gradle configuration
Frequent API changes
High cognitive load
```

Modularity has crossed the point of diminishing returns.

---

# 21. The Opposite Problem: Monolith

The other extreme:

```text
:app
```

contains:

```text
Everything
```

Symptoms:

```text
Large build surface
Weak ownership
High coupling
Difficult testing
Frequent merge conflicts
Slow refactoring
```

---

# 22. The Scaling Sweet Spot

A healthy architecture often looks like:

```text
             Application
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     Feature    Feature    Feature
        │         │         │
        └────┬────┴────┬────┘
             ▼         ▼
            Core     Platform
               \      /
                \    /
                Integration
```

Not:

```text
Everything → Everything
```

and not:

```text
Every class → Module
```

---

# 23. Dependency Graph Scaling

A project should keep dependencies directional.

Example:

```text
Application
    ↓
Features
    ↓
Core abstractions
    ↓
Platform / Integrations
```

Avoid:

```text
Feature A ↔ Feature B
Feature B ↔ Feature C
Feature C ↔ Core
Core ↔ Feature A
```

This creates cycles and coordination problems.

---

# 24. Dependency Graph Complexity

If every module can depend on every other module:

```text
N modules
```

can create a potentially large number of relationships.

A bounded architecture tries to reduce the number of meaningful edges.

```text
More nodes
+
Fewer unnecessary edges
=
More scalable graph
```

---

# 25. Dependency Direction

A useful default:

```text
App
 ↓
Features
 ↓
Contracts / Core
 ↓
Implementations
 ↓
Platform / Vendors
```

The exact architecture may differ, but the important property is:

```text
Predictable direction
```

---

# 26. Feature-to-Feature Dependencies

At scale, direct dependencies between features can become dangerous.

Example:

```text
Orders
  ↓
Payments
  ↓
Profile
  ↓
Orders
```

Now a cycle exists.

---

# 27. Prefer Contracts

Instead of:

```text
Orders → Payments implementation
```

use:

```text
Orders
  ↓
PaymentAuthorizer
  ↓
Payments implementation
```

The contract controls coupling.

---

# 28. Capability-Oriented Dependencies

A feature should depend on:

```text
What it needs
```

not:

```text
Everything another feature owns
```

For example:

```text
Checkout → PaymentAuthorizer
```

rather than:

```text
Checkout → PaymentFeature
```

---

# 29. Shared Contracts

At larger scale, a contract module may help:

```text
:contracts:payments
```

containing:

```text
PaymentAuthorizer
PaymentResult
PaymentError
```

Then:

```text
Checkout → contracts:payments
Payments → contracts:payments
```

This can reduce feature-to-feature coupling.

---

# 30. Do Not Create Contract Modules Everywhere

Contract modules also have costs.

Avoid:

```text
contracts:orders
contracts:payments
contracts:profile
contracts:search
contracts:settings
contracts:...
```

unless there is a real need for independent contract ownership or dependency isolation.

---

# 31. Shared Module Scaling

Shared modules are useful when they provide stable capabilities:

```text
core:network
core:security
core:database
core:observability
```

They become dangerous when they become:

```text
everything shared
```

---

# 32. The Shared Module Trap

A module called:

```text
:shared
```

often becomes:

```text
models
utils
extensions
network
security
analytics
feature code
```

Eventually:

```text
Everyone depends on shared.
```

That creates a new monolith.

---

# 33. Shared Does Not Mean Central

A capability can be shared without being placed into one giant module.

Instead:

```text
core:network
core:security
core:time
core:observability
```

This creates semantic boundaries.

---

# 34. Scaling the Core

A core module should have:

```text
High reuse
Stable API
Low feature coupling
Clear responsibility
```

A useful rule:

> **Core should depend on capabilities, not product features.**

---

# 35. Core Dependency Direction

Good:

```text
features
   ↓
core
```

Suspicious:

```text
core
   ↓
features
```

A core module depending on a feature often indicates that the boundary is wrong.

---

# 36. Core as a Dependency Hub

Core modules naturally become highly depended upon.

Therefore:

```text
Core API stability
```

has high impact.

A change to:

```text
core:network
```

may affect:

```text
20 features
```

This is why core APIs should be deliberately designed.

---

# 37. Stable Dependencies

A highly reused module should be:

```text
Stable
Predictable
Backward-compatible
Well-tested
Small in concept
```

This is more important than simply making it reusable.

---

# 38. Stable Dependencies Principle

A module that many modules depend on should change less frequently than its consumers.

Conceptually:

```text
High fan-out
      ↓
Higher stability requirement
```

---

# 39. Dependency Fan-Out

If:

```text
core:network
```

is consumed by:

```text
orders
payments
profile
checkout
inventory
search
```

then changing it has broad impact.

Measure:

```text
Who depends on me?
```

not only:

```text
Who do I depend on?
```

---

# 40. Fan-In and Fan-Out

Two useful metrics:

```text
Fan-in
→ Number of modules depending on this module.

Fan-out
→ Number of modules this module depends on.
```

A high fan-in module should be carefully governed.

A high fan-out module may be overly broad.

---

# 41. Dependency Metrics

A practical architecture review can track:

```text
Module count
Dependency count
Fan-in
Fan-out
Cycles
Build time
Test time
API surface
Change frequency
Ownership count
```

These metrics provide evidence for refactoring.

---

# 42. Change Frequency

Suppose:

```text
core:network
```

changes:

```text
Daily
```

while:

```text
50 modules
```

depend on it.

This may indicate:

```text
Unstable shared abstraction
```

or:

```text
Implementation leakage
```

---

# 43. Stable Core vs Fast Features

A useful architecture can separate:

```text
Stable capabilities
```

from:

```text
Rapidly changing business features
```

Example:

```text
Stable:
core:security
core:network

Fast-changing:
features:checkout
features:orders
```

---

# 44. Scaling Through Encapsulation

The more teams and modules a system has, the more important encapsulation becomes.

Prefer:

```text
Public API
+
Internal implementation
```

over:

```text
Everything public
```

---

# 45. Public API as a Scaling Boundary

Example:

```kotlin
public interface PaymentAuthorizer {
    suspend fun authorize(request: PaymentRequest): PaymentResult
}
```

Internal:

```kotlin
internal class StripePaymentClient
internal class PaymentMapper
internal class PaymentRetryPolicy
```

Consumers do not depend on implementation details.

---

# 46. Why Public API Matters at Scale

If implementation details leak:

```text
20 consumers
    ↓
Depend on internal classes
```

then a small implementation change becomes a repository-wide migration.

If only the contract is public:

```text
20 consumers
    ↓
Depend on stable API
```

the implementation can evolve independently.

---

# 47. `api` vs `implementation`

Gradle dependency configuration can reinforce boundaries.

Conceptually:

```kotlin
dependencies {
    api(project(":contracts:payments"))
    implementation(project(":core:network"))
}
```

Use `api` when consumers genuinely need the dependency as part of the module's exposed API.

Use `implementation` when the dependency is internal.

---

# 48. Avoid Accidental API Leakage

If:

```kotlin
api(project(":core:network"))
```

is used unnecessarily, consumers may become coupled to network types.

Prefer:

```kotlin
implementation(project(":core:network"))
```

when network details should remain internal.

---

# 49. API Surface and Scaling

A useful rule:

> **Every public symbol is a future compatibility responsibility.**

Therefore:

```text
Small public API
=
Lower long-term coupling
```

---

# 50. Scaling KMP Source Sets

KMP introduces multiple targets:

```text
commonMain
androidMain
iosMain
desktopMain
wasmJsMain
```

As targets grow, source-set organization becomes increasingly important.

---

# 51. Platform Growth

A project may begin:

```text
commonMain
androidMain
iosMain
```

and later add:

```text
desktopMain
wasmJsMain
webMain
```

A good architecture should allow target growth without moving platform assumptions into common code.

---

# 52. Platform-Specific Growth

Bad:

```text
commonMain
└── AndroidStuff
└── IOSStuff
```

Better:

```text
commonMain
    capability
        ↓
androidMain
    implementation

iosMain
    implementation
```

The platform boundary remains explicit.

---

# 53. Shared Source Sets

KMP can also use intermediate source sets where appropriate:

```text
commonMain
    ↓
appleMain
    ├── iosMain
    ├── macosMain
    └── tvosMain
```

The exact hierarchy depends on supported targets.

The architectural principle is:

```text
Share only where semantics are genuinely shared.
```

---

# 54. Source Set Explosion

A project can also over-engineer source sets:

```text
common
platform
apple
ios
iosSimulator
iosDevice
...
```

Only introduce intermediate source sets when they reduce meaningful duplication or represent a real compatibility boundary.

---

# 55. Scaling Shared Code

A shared implementation should be:

```text
Semantically portable
Testable
Stable
Platform-neutral
```

Avoid moving code into `commonMain` simply because:

```text
"Both platforms currently need it."
```

The deeper question is:

```text
Does the behavior have the same meaning on both platforms?
```

---

# 56. Scaling Platform Differences

If behavior differs meaningfully:

```text
Common API
+
Platform-specific implementation
```

may be appropriate.

If the semantics differ fundamentally:

```text
Separate platform capability
```

may be clearer.

---

# 57. Scaling Feature Modules

As features grow, avoid turning one feature into another monolith.

Example:

```text
features/orders/
├── domain/
├── data/
├── presentation/
├── navigation/
└── ...
```

If Orders becomes huge, consider meaningful sub-capabilities:

```text
features/orders
features/order-history
features/order-tracking
```

only if they have independent ownership or change boundaries.

---

# 58. Feature Splitting Decision

Ask:

```text
Does this area have independent:
- ownership?
- lifecycle?
- release cadence?
- dependencies?
- domain rules?
- testing needs?
```

If several answers are yes, extraction may be justified.

---

# 59. Do Not Split by Screen Automatically

Avoid:

```text
orders-list
orders-details
orders-history
```

as separate modules merely because they are screens.

Screens are UI units.

Modules should generally represent stronger architectural boundaries.

---

# 60. Vertical Slice Scaling

A vertical slice groups the code required to deliver a business capability:

```text
orders/
├── domain/
├── data/
├── presentation/
└── navigation/
```

This improves:

```text
Ownership
Change locality
Feature delivery
```

---

# 61. Horizontal Layer Scaling

An alternative:

```text
domain/
data/
presentation/
```

across the whole application.

This can work for smaller systems.

At larger scale, feature-oriented organization often improves ownership.

---

# 62. Hybrid Scaling

Many mature systems use:

```text
Feature modules
    +
Layered packages
```

For example:

```text
features/orders/
├── domain/
├── data/
└── presentation/
```

This provides:

```text
Feature boundary
+
Layer boundary
```

---

# 63. Scaling Architecture by Team Topology

If one team owns everything:

```text
Feature modules
```

may still help code organization.

If many teams exist:

```text
Feature boundaries
+
Ownership rules
+
Dependency contracts
```

become much more important.

---

# 64. Team Independence

A scalable architecture tries to allow:

```text
Team A changes Orders
```

without requiring:

```text
Team B to modify Payments
Team C to modify Profile
Team D to modify Core
```

unless the change genuinely crosses those boundaries.

---

# 65. Team Dependency Smell

If every feature change requires:

```text
Platform team
Core team
Design team
Payments team
```

then the architecture may have too much shared coupling.

---

# 66. Shared Platform Team

Platform teams can provide stable capabilities:

```text
Networking
Security
Observability
Storage
Build tooling
```

Feature teams consume those capabilities.

The platform team should avoid owning business logic for every feature.

---

# 67. Platform Team Boundary

Good:

```text
Platform Team
├── Network
├── Security
├── Storage
├── Observability
└── Build Logic
```

Feature teams:

```text
Orders
Payments
Profile
Checkout
```

This creates a scalable organizational model.

---

# 68. Platform as a Product

A useful mindset:

> **Shared platform modules are internal products.**

They should provide:

```text
Documentation
Stable APIs
Versioning
Migration guidance
Support
Observability
```

not simply:

```text
Reusable code
```

---

# 69. Internal Platform API

Example:

```text
SecureStorage
```

should have:

```text
README
Usage example
Security guarantees
Supported platforms
Testing strategy
Migration policy
```

This reduces support load.

---

# 70. Scaling Documentation

As the project grows, documentation becomes part of architecture.

At minimum:

```text
README.md
ARCHITECTURE.md
MODULES.md
CONTRIBUTING.md
```

and ADRs for important decisions.

---

# 71. Module Documentation

A useful module README:

```markdown
# Orders

## Responsibility

Owns the order lifecycle.

## Public API

- OrdersEntryPoint
- OrderReader

## Dependencies

- core:network
- core:database

## Consumers

- checkout
- profile

## Owner

Orders Team
```

This is especially useful in large repositories.

---

# 72. Scaling Architecture Decisions

Architectural decisions should be recorded when they are expensive to rediscover.

Examples:

```text
Why Orders owns Order?
Why Payments is isolated?
Why network implementation is hidden?
Why iOS uses native UI?
Why shared UI is limited?
```

---

# 73. ADR Example

```text
ADR-001
Feature modules represent business capabilities.

Decision:
Use feature-oriented Gradle modules.

Reason:
Improve team ownership and reduce cross-feature coupling.

Consequence:
Features expose small public APIs.
```

---

# 74. Scaling Through Rules

A large repository needs automated rules.

Examples:

```text
Feature cannot depend on another feature's internal package.
Core cannot depend on feature modules.
Domain cannot depend on presentation.
Platform code cannot leak into common domain.
Vendor SDKs remain inside integrations.
```

---

# 75. Architecture Tests

Architecture rules can be checked automatically.

Conceptually:

```text
Build
  ↓
Unit tests
  ↓
Architecture tests
  ↓
Dependency checks
  ↓
API checks
  ↓
Release
```

The exact tooling may vary.

---

# 76. Architecture Enforcement

Documentation says:

```text
Core must not depend on features.
```

Architecture enforcement ensures:

```text
A developer cannot accidentally introduce the dependency.
```

This is more scalable than relying only on code review.

---

# 77. Dependency Constraints

A repository can maintain a dependency policy:

```text
apps
  ↓
features
  ↓
core
  ↓
platform/integrations

integrations
  ↓
vendor SDKs
```

Unexpected edges should fail validation.

---

# 78. Dependency Graph as an Architectural Artifact

Generate or maintain a graph:

```text
                  app
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
      orders    payments    profile
        │          │          │
        └────┬─────┴─────┬────┘
             ▼           ▼
          network      security
             │
             ▼
           ktor
```

The graph makes architecture visible.

---

# 79. Scaling Build Performance

More modules can improve build isolation.

But more modules also increase Gradle configuration overhead.

Therefore:

```text
Modularization
≠
Automatically faster builds
```

Build performance depends on:

```text
Module graph
Source changes
Incremental compilation
Caching
Configuration
Kotlin compilation
Annotation processing
Code generation
Test execution
```

---

# 80. Build Impact of a Shared Module

Suppose:

```text
core:network
```

changes.

If:

```text
30 modules
```

depend on its API, many consumers may require recompilation.

This is why highly shared APIs should be stable.

---

# 81. Minimize Unnecessary API Changes

Changing:

```text
public class
public function
public interface
```

can have broad build impact.

Prefer:

```text
internal implementation
```

when consumers do not need direct access.

---

# 82. Build Graph Depth

A deep chain:

```text
A → B → C → D → E → F
```

can increase reasoning complexity.

A flatter graph:

```text
Features → Core
```

is often easier to maintain.

This does not mean every graph must be flat.

The goal is:

```text
Intentional depth
```

---

# 83. Build Graph Cycles

Cycles are especially harmful:

```text
A → B
↑   ↓
└───┘
```

They make:

```text
Build ordering
Ownership
Testing
Refactoring
```

harder.

A scalable architecture should prevent cycles.

---

# 84. Dependency Cycle Example

Bad:

```text
orders
   ↓
payments
   ↓
orders
```

Possible solution:

```text
orders
   ↓
contracts:payment
   ↑
payments
```

or:

```text
application orchestration
```

depending on the business relationship.

---

# 85. Build Logic Scaling

As Gradle configuration grows, centralize conventions:

```text
build-logic/
├── kmp-library
├── android-library
├── compose-library
├── testing
└── publishing
```

This prevents every module from repeating:

```kotlin
plugins {
    ...
}
```

and configuration.

---

# 86. Version Catalog Scaling

Centralize dependency versions where appropriate:

```toml
[versions]

coroutines = "..."
serialization = "..."
```

But avoid turning the version catalog into an undocumented dumping ground.

The exact naming depends on the build system.

The principle is:

```text

    ↓
```

# 102. Why Composition Matters at Scale

If modules construct their own dependencies:


```text
   ↓
Dependency graph
   ↓
```

# 103. Dependency Injection Scaling

Example:



Feature:

```kotlin
class CheckoutUseCase(
    private val paymentGateway: PaymentGateway
)
```

The feature does not know how the gateway is constructed.

# 212. Scaling Through Bounded Contexts

When a system becomes large:

```text
"Shared model"
```

often becomes less useful than:

```text
"Shared concept with explicit contract"
```

This preserves autonomy.

---

# 213. Scaling Cross-Context Communication

Use:

```text
Events
Queries
Commands
Capability interfaces
Read models
Contracts
```

rather than direct access to another context's internals.

---

# 214. Event-Driven Scaling

Example:

```text
Orders
   │
   └── OrderCreated
             │
       ┌─────┼─────┐
       ▼     ▼     ▼
   Payments Analytics Inventory
```

This can reduce direct dependencies.

But event-driven architecture introduces its own complexity.

Use it when the decoupling benefit is real.

---

# 215. Event-Driven Tradeoffs

Benefits:

```text
Loose coupling
Independent consumers
Asynchronous processing
```

Costs:

```text
Debugging complexity
Ordering concerns
Failure handling
Event versioning
Observability
```

Do not introduce events simply to avoid a small dependency.

---

# 216. Scaling Commands and Queries

A feature can expose:

```text
OrderReader
OrderWriter
```

instead of its entire internal repository.

This is a form of capability-oriented architecture.

---

# 217. Scaling Read Models

For cross-feature dashboards:

```text
Orders
    ↓
OrderSummary
    ↓
Dashboard
```

rather than:

```text
Dashboard → Orders internal database
```

The contract controls coupling.

---

# 218. Scaling Data Ownership

The database should not become the architecture.

Bad:

```text
Every feature
    ↓
Shared database tables
```

Better:

```text
Feature
    ↓
Repository
    ↓
Owned persistence
```

when the business boundary warrants it.

---

# 219. Shared Database Trap

A shared database can create hidden coupling:

```text
Orders writes table
Payments reads table
Analytics reads table
Profile updates table
```

Now database schema becomes a cross-feature API.

---

# 220. Scaling Persistence Ownership

Prefer clear ownership:

```text
Orders
  → Order storage

Payments
  → Payment storage

Profile
  → Profile storage
```

Cross-feature access should use explicit contracts where possible.

---

# 221. Scaling Database Migrations

Database changes should have:

```text
Owner
Migration
Compatibility plan
Rollback/forward strategy
Testing
```

Large shared schemas require especially careful coordination.

---

# 222. Scaling API Ownership

Remote APIs can also become organizational boundaries.

A feature should ideally know:

```text
Its API contract
```

without exposing the entire backend client to unrelated features.

---

# 223. Scaling Backend Contract Changes

When a backend changes:

```text
DTO
→ Mapper
→ Domain
```

should absorb many transport changes.

This is another reason not to use DTOs as domain models.

# 224. Scaling DTO Boundaries

Bad:

```text
UI
  ↓
OrderDto
```

Better:

```text
API
 ↓
OrderDto
 ↓
Order
 ↓
OrderUiModel
 ↓
UI
```

The representation boundaries reduce blast radius.

---

# 225. Scaling With Multiple Backend Versions

If multiple backend versions exist:

```text
OrderApiV1
OrderApiV2
```

can be hidden behind:

```text
OrderRepository
```

or a suitable gateway.

The feature need not know transport version details.

---

# 226. Scaling Backward Compatibility

A compatibility layer can translate:

```text
V1 DTO
V2 DTO
```

into the same domain concept:

```text
Order
```

when semantics remain compatible.

---

# 227. Scaling API Evolution

Public feature API:

```text
OrderReader
```

can remain stable while:

```text
backend API
database
vendor
platform
```

change internally.

This is the power of a good boundary.

---

# 228. Scaling Release Trains

A large organization may have:

```text
Feature teams
Platform teams
Mobile release team
```

The architecture should reduce the number of reasons they must synchronize.

---

# 229. Scaling Release Coordination

Good:

```text
Platform API stable
Feature implementation independent
```

Risky:

```text
Feature A requires simultaneous internal changes in Feature B and Core
```

unless the change genuinely crosses those boundaries.

---

# 230. Scaling Deprecation

At scale, old APIs accumulate.

A healthy lifecycle:

```text
Introduce
    ↓
Adopt
    ↓
Deprecate
    ↓
Migrate
    ↓
Remove
```

Without the final step, architecture accumulates permanent complexity.

---

# 231. Deprecation Ownership

Every deprecated API should ideally have:

```text
Owner
Migration target
Reason
Removal criteria
```

This prevents “temporary” architecture from becoming permanent.

---

# 232. Scaling Architecture Debt

Architecture debt should be visible:

```text
Legacy module
Temporary adapter
Deprecated API
Migration boundary
Feature flag
Compatibility layer
```

Explicit names and documentation make debt manageable.

# 233. Scaling With Migration Modules

```text
├── orders
└── payments
```

Migration path:

```text

      ↓
```

# 234. Scaling Repository Size

```text
Clear documentation
```

# 235. Scaling Searchability

Consistent prefixes and semantic packages improve:

# 236. Scaling Through Predictability

# 237. Scaling Through Standardization

Standardize:

```text
Documentation
Ownership
```

# 238. Standardization vs Flexibility

Potentially excessive:


Standards should reduce cognitive load, not create ceremony.

# 239. Scaling and Architectural Simplicity

The paradox:

> **A scalable architecture is often simpler for developers, even though it contains more structure.**

Why?

Because the structure answers:

```text
Where?
Who?
Why?
What can I depend on?
```

---

# 240. Complexity Budget

Every architectural mechanism has cost:

```text
Modules
Interfaces
Adapters
Events
DI
Source sets
Contracts
Versioning
```

Spend complexity where it reduces a larger cost.

---

# 241. Scaling Principle

A useful formula:

```text
Architectural complexity
        should be
proportional to
organizational + technical complexity
```

Do not build enterprise architecture for a tiny prototype.

Do not run a giant enterprise product like a prototype.

---

# 242. Scaling and Evidence

Introduce a boundary when evidence shows:

```text
Build is too slow
Ownership conflicts
Dependencies are too broad
Teams block each other
Vendor leakage is spreading
Feature changes have large blast radius
```

Architecture should respond to observed constraints.

---

# 243. Scaling Architecture Review Questions

Ask:

```text
Where is the largest coupling?
Which module changes most often?
Which module has the most consumers?
Which team owns the most code?
Where are merge conflicts?
Which build tasks are slow?
Which public APIs are unstable?
Which modules are deprecated?
```

These questions reveal where scaling work is needed.

---

# 244. Scaling Smell: One Team Owns Everything

If:

```text
Platform Team
```

owns:

```text
Network
Security
Orders
Payments
Profile
Checkout
```

then platform ownership has become product ownership.

Reconsider boundaries.

---

# 245. Scaling Smell: Everyone Owns Core

If every team can change:

```text
core
```

then:

```text
core
```

may be too broad.

Split by stable capabilities and establish ownership.

---

# 246. Scaling Smell: Shared Model Dependency

If every feature imports:

```text
common.models.Order
```

ask:

```text
Is this truly a shared domain contract?
```

If not, localize the model.

---

# 247. Scaling Smell: Feature-to-Feature Internals

Bad:

```kotlin
import com.company.payments.internal.StripePaymentClient
```

inside:

```text
orders
```

This bypasses the boundary.

---

# 248. Scaling Smell: Platform Leakage

Bad:

```kotlin
class CancelOrderUseCase(
    private val context: Context
)
```

if the use case does not genuinely need Android context.

The platform dependency has crossed too far inward.

---

# 249. Scaling Smell: Vendor Leakage

Bad:

```kotlin
class CheckoutUseCase(
    private val stripeClient: StripeClient
)
```

Better:

```kotlin
class CheckoutUseCase(
    private val paymentGateway: PaymentGateway
)
```

with:

```text
StripePaymentGateway
```

at the integration boundary.

---

# 250. Scaling Smell: Global Utility

Bad:

```text
core/utils
```

contains:

```text
DateUtils
OrderUtils
PaymentUtils
StringUtils
NetworkUtils
```

This is not a scalable ownership model.

---

# 251. Scaling Smell: Global App Module

If every feature must modify:

```text
AppModule.kt
```

for ordinary changes, the composition root may be too centralized.

Use feature-level modules and explicit registration mechanisms where appropriate.

---

# 252. Scaling Smell: Giant DI Graph

A giant DI module with:

```text
500 providers
```

becomes difficult to reason about.

Split DI configuration by capability:

```text
NetworkModule
SecurityModule
OrdersModule
PaymentsModule
```

while keeping the composition root clear.

---

# 253. Scaling Smell: Giant Navigation Graph

If every feature directly edits one giant navigation file:

```text
AppNavigation.kt
```

ownership becomes difficult.

Feature-owned navigation contracts can reduce coordination.

---

# 254. Scaling Smell: Giant Analytics File

Avoid:

```text
AnalyticsEvents.kt
```

with thousands of feature-specific events.

Prefer feature ownership:

```text
orders/analytics/OrderAnalyticsEvent
payments/analytics/PaymentAnalyticsEvent
```

and map them through shared infrastructure.

---

# 255. Scaling Smell: Giant Error Model

Avoid:

```text
CommonError
```

with every business error in the application.

Prefer:

```text
OrderError
PaymentError
AuthenticationError
```

and map infrastructure failures appropriately.

---

# 256. Scaling Smell: One Repository for Everything

Bad:

```text
AppRepository
```

with:

```text
orders
payments
profile
inventory
analytics
```

This is a giant coupling point.

Prefer capability/domain-specific repositories.

---

# 257. Scaling Smell: One Service for Everything

Bad:

```text
AppService
```

with hundreds of methods.

This is usually a sign that business boundaries have not been modeled.

---

# 258. Scaling Smell: Copy-Paste Architecture

If every feature has slightly different conventions:

```text
Orders uses Repository
Payments uses Service
Profile uses Manager
Checkout uses Gateway
```

developers must relearn the architecture repeatedly.

Standardize vocabulary where responsibilities are equivalent.

---

# 259. Scaling Smell: Architecture by Team Preference

One team:

```text
MVI
```

another:

```text
MVVM
```

another:

```text
Redux
```

This is not automatically wrong.

But at scale, teams should understand:

```text
Which choices are flexible?
Which boundaries are mandatory?
```

---

# 260. Scaling Guardrails vs Implementation Freedom

Standardize:

```text
Module boundaries
Dependency direction
Public API rules
Security boundaries
Vendor isolation
Ownership
```

Allow flexibility in:

```text
Internal implementation
State management details
Mapping style
Testing style
```

where reasonable.

---

# 261. Scaling Architecture Contracts

A good architecture contract says:

```text
Feature modules cannot access another feature's internal packages.

Core cannot depend on features.

Vendor SDKs remain inside integrations.

Platform APIs cannot leak into common domain logic.
```

It does not say:

```text
Every feature must contain exactly 12 classes.
```

---

# 262. Scaling Through Internal APIs

Kotlin visibility can help:

```kotlin
internal class StripePaymentClient
```

while exposing:

```kotlin

```

This creates compiler-enforced boundaries.

---

# 263. Scaling With `internal`

`internal` is particularly valuable in modular Kotlin projects because it limits implementation visibility to the module.

Use it deliberately for:

```text

DTOs
Database entities
Vendor adapters
Internal helpers
```

when consumers do not need them.

---

# 264. Scaling API Exposure

Think in layers:

```text
Public
    ↓
Internal
    ↓
Private
```

The smaller the public surface, the easier the module is to evolve.

# 265. Scaling With Explicit APIs

Explicit API mode can help library-style modules expose intentional declarations.

The broader principle:

> **Make public API a deliberate decision rather than an accident.**

# 266. Scaling Module APIs

Example:

```text

├── api/
│   └── PaymentAuthorizer.kt
│
└── internal/
    ├── StripePaymentGateway.kt
    ├── PaymentMapper.kt
    └── PaymentRetryPolicy.kt
```

---

# 267. Scaling API Contracts

The contract:

```kotlin
interface PaymentAuthorizer {
    suspend fun authorize(
        request: PaymentRequest
    ): PaymentResult
}
```

should avoid exposing:

```text
StripeRequest
KtorResponse
DatabaseEntity
AndroidContext
```

unless those are genuinely part of the public contract.

---

# 268. Scaling Through Minimal Interfaces

A small interface:

```text
PaymentAuthorizer
```

is easier to:

```text

Fake
Test
Document
Version
Replace
```

than:

```text
PaymentService
```

with 40 methods.

---

# 269. Scaling and Interface Segregation

At scale:

```text
Consumer needs 2 methods
```

should not automatically mean:

```text
Consumer depends on 25 methods.
```

Small capability interfaces reduce coupling.

---

# 270. Scaling and Dependency Inversion

The scalable pattern remains:

```text
High-level feature
       ↓
Stable abstraction
       ↓
Low-level implementation
       ↓
Platform/vendor
```

This is especially powerful in KMP because platform implementations can evolve independently.

---

# 271. Scaling and Source Set Boundaries

```text
commonMain
    │
    ├── domain
    ├── application
    └── shared infrastructure
            │
            ▼
      platform abstraction
            │
      ┌─────┴─────┐
      ▼           ▼
 androidMain   iosMain
```

The source-set boundary becomes part of the architecture.

# 272. Scaling and New KMP Targets

If a new target arrives:

```text

```

the question should be:

```text

```

rather than:

```text
Where do we put Wasm-specific code everywhere?
```

A good architecture localizes the impact.

```text
├── multiple apps
├── multiple platforms

```

The architecture should evolve with the organization.

# 280. Do Not Predict the Future Too Precisely

Architecture should prepare for plausible change.

It should not implement every hypothetical future requirement today.

Bad:

```text
We may support 12 platforms someday,
so let's create 40 abstraction modules now.
```

Better:

```text
Keep platform boundaries clean
and add implementations when required.
```

Prepare for:

```text
Likely change
```

without implementing:

```text
Imaginary complexity
```

This is one of the most important architecture skills.

# 318. Closing Perspective

Project structure becomes truly important when the project becomes larger than the individual developer's mental model.

At small scale, you can remember:

```text
Where everything is.
```

At large scale, you cannot.

The architecture must remember for you.

That is what modules, packages, naming, ownership, dependency rules, source sets and contracts are really doing.

They create a map.

A scalable KMP project should let a developer answer:

```text
Where does this capability belong?

Who owns it?

What can I depend on?

What should I not depend on?

Where is the platform-specific implementation?

Where is the vendor integration?

What is public?

What is internal?

What will change if I modify this?
```

without understanding the entire repository.

That is the real purpose of scaling project structure.

> [!TIP]
> **A scalable architecture does not eliminate complexity. It puts complexity behind boundaries so that each developer, team, and feature only needs to understand the part they are responsible for.**

The strongest KMP mental model is therefore:

```text
                BUSINESS
                   │
                   ▼
                FEATURES
                   │
                   ▼
              CAPABILITIES
                   │
                   ▼
              ABSTRACTIONS
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
     PLATFORM             INTEGRATION
        │                     │
        ▼                     ▼
    Android/iOS/etc.      Vendors/SDKs
```

And around all of it:

```text
                 OWNERSHIP
                     +
                DEPENDENCY RULES
                     +
                 API BOUNDARIES
                     +
                BUILD BOUNDARIES
                     +
                TEAM BOUNDARIES
```

That is what allows a KMP project to grow from:

```text
One developer
```

to:

```text
Multiple teams
Multiple features
Multiple applications
Multiple platforms
Multiple releases
```

without turning the repository into one giant dependency graph.

**Scaling is not about making the project bigger.**

**Scaling is about making growth predictable.**
