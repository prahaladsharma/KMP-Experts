# Chapter 10 — Project Structure

## Part 2 — Feature Modules

Feature modules are one of the most important structural decisions in a growing KMP application.

A feature module answers a simple question:

> **What business capability does this module own?**

Instead of organizing a large project only by technical layers:

```text
presentation/
domain/
data/
network/
database/
```

we can organize it around business capabilities:

```text
features/
├── authentication/
├── orders/
├── payments/
├── profile/
└── inventory/
```

Each feature becomes a meaningful architectural boundary.

```text
                    APPLICATION
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
     Orders           Payments          Profile
        │                │                │
        └────────────────┼────────────────┘
                         ▼
                       Core
```

> [!IMPORTANT]
> **A feature module is not merely a folder containing feature-related files. It is a boundary around a business capability, its ownership, its dependencies, and the code that changes together.**

---

# 1. What Is a Feature Module?

A feature module is a self-contained unit representing a meaningful product capability.

Examples:

```text
Authentication
Orders
Payments
Inventory
Search
Profile
Notifications
```

A feature module may contain:

```text
Presentation
Domain
Data
Tests
Platform-specific implementations
```

For example:

```text
features/orders/
├── src/
│   ├── commonMain/
│   ├── commonTest/
│   ├── androidMain/
│   └── iosMain/
└── build.gradle.kts
```

The exact physical structure can vary.

The important idea is:

```text
Feature = Business Boundary
```

---

# 2. Why Feature Modules Matter

Imagine an application with:

```text
Orders
Payments
Profile
Inventory
Search
Notifications
```

If everything exists inside one shared module:

```text
shared/
├── orders/
├── payments/
├── profile/
├── inventory/
├── search/
└── notifications/
```

the project may initially be manageable.

As the project grows:

```text
More developers
More dependencies
More tests
More build work
More ownership conflicts
```

the single module becomes increasingly expensive.

Feature modules introduce stronger boundaries:

```text
:features:orders
:features:payments
:features:profile
:features:inventory
:features:search
:features:notifications
```

---

# 3. Feature Module Mental Model

Think of each feature as a small product inside the application:

```text
┌───────────────────────────────┐
│          Orders               │
│                               │
│  Presentation                │
│  Domain                      │
│  Data                        │
│  Tests                       │
│  Platform adapters           │
│                               │
└───────────────────────────────┘
```

It should have:

```text
A responsibility
An owner
A public boundary
A dependency boundary
A testing boundary
```

---

# 4. Feature Modules Are About Ownership

Suppose the application has an Orders team.

A natural relationship is:

```text
Orders Team
     │
     ▼
:features:orders
```

The team owns:

```text
Order business rules
Order data access
Order presentation state
Order tests
Order-specific integrations
```

Other teams consume only the public capability they need.

---

# 5. Feature Modules and Team Scaling

Without feature boundaries:

```text
Developer A
Developer B
Developer C
Developer D
        │
        ▼
     shared/
```

Everyone edits the same large module.

This creates:

```text
Merge conflicts
Code ownership ambiguity
Long reviews
Unclear dependencies
```

With feature modules:

```text
Developer A → Orders
Developer B → Payments
Developer C → Profile
Developer D → Inventory
```

The architecture begins to support team autonomy.

---

# 6. Feature Modules and Business Capabilities

A feature should represent something meaningful from the product perspective.

Good:

```text
orders
payments
profile
inventory
```

Less useful:

```text
network-feature
repository-feature
models-feature
utils-feature
```

The first group represents business capabilities.

The second group represents technical implementation details.

Technical infrastructure usually belongs in core/platform modules rather than feature modules.

---

# 7. Feature Module vs Screen

A feature is not necessarily a screen.

For example:

```text
Orders
```

may contain:

```text
Order List
Order Details
Order History
Order Cancellation
Order Tracking
Order Returns
```

Therefore:

```text
Feature
   ├── Screen
   ├── Screen
   ├── Screen
   └── Screen
```

A feature is generally a broader business capability than a single UI screen.

---

# 8. Feature Module vs Use Case

Likewise, a feature is not simply one use case.

For example:

```text
Orders
```

may contain:

```text
CreateOrder
GetOrder
CancelOrder
TrackOrder
ReturnOrder
```

These are behaviors inside the feature.

The feature owns the larger capability.

---

# 9. Feature Module vs Domain Module

A domain module might contain:

```text
shared domain concepts
```

while a feature module owns:

```text
feature-specific business behavior
```

For example:

```text
core/domain/
└── Money
```

while:

```text
features/payments/
└── PaymentCalculator
```

The distinction depends on the business model.

---

# 10. Feature Module vs Core Module

A useful rule:

```text
Feature
    ↓
Business-specific

Core
    ↓
Cross-feature capability
```

For example:

```text
OrderRepository
    → Orders

NetworkClient
    → Core

PaymentGateway
    → Payments or shared contract

SecureStorage
    → Platform/Core
```

---

# 11. A Typical Feature Module

A KMP feature can look like:

```text
features/orders/
│
├── src/
│   ├── commonMain/
│   │   └── kotlin/
│   │       └── orders/
│   │           ├── domain/
│   │           ├── data/
│   │           └── presentation/
│   │
│   ├── commonTest/
│   │
│   ├── androidMain/
│   │
│   └── iosMain/
│
└── build.gradle.kts
```

This gives the feature:

```text
Shared business logic
+
Shared tests
+
Platform-specific implementations
```

---

# 12. Why `commonMain` Matters

Feature business logic should be placed in `commonMain` when it does not require platform APIs.

Examples:

```text
Order
OrderRepository
GetOrderUseCase
CancelOrderUseCase
OrderValidator
OrderState
```

This allows Android and iOS to share the same behavior.

---

# 13. Example Domain Model

```kotlin
@JvmInline
value class OrderId(
    val value: String
)

data class Order(
    val id: OrderId,
    val status: OrderStatus,
    val total: Money
)
```

This belongs naturally inside:

```text
features/orders/
```

when the model is owned by Orders.

---

# 14. Example Repository Contract

```kotlin
interface OrderRepository {

    suspend fun getOrder(
        id: OrderId
    ): Order

    suspend fun cancelOrder(
        id: OrderId
    )
}
```

This contract belongs to the feature's business boundary.

The implementation can remain internal.

---

# 15. Example Use Case

```kotlin
class CancelOrderUseCase(
    private val repository: OrderRepository
) {

    suspend operator fun invoke(
        orderId: OrderId
    ) {
        repository.cancelOrder(orderId)
    }
}
```

The use case knows:

```text
OrderRepository
```

It does not need to know:

```text
Retrofit
SQLDelight
Room
Android SDK
iOS SDK
```

---

# 16. Feature Data Layer

The data layer can contain:

```text
OrderRepositoryImpl
OrderApi
OrderDto
OrderMapper
OrderLocalDataSource
```

For example:

```text
features/orders/
└── data/
    ├── OrderRepositoryImpl.kt
    ├── OrderApi.kt
    ├── OrderDto.kt
    └── OrderMapper.kt
```

These implementation details should not automatically become part of the feature's public API.

---

# 17. Feature Presentation Layer

Presentation may contain:

```text
OrderViewModel
OrderState
OrderAction
OrderEffect
```

For example:

```kotlin
data class OrderState(
    val isLoading: Boolean = false,
    val order: Order? = null,
    val error: String? = null
)
```

This is feature-specific presentation state.

---

# 18. Feature UI

If using Compose Multiplatform:

```text
commonMain/
└── presentation/
    └── OrderScreen.kt
```

If using native UI:

```text
androidMain/
└── OrderScreen.kt

iosMain/
└── OrderView.swift
```

The feature boundary remains the same.

Only the UI sharing strategy changes.

---

# 19. Feature Module with Native UI

A feature can use:

```text
Shared:
- Domain
- Use cases
- Repository
- State

Android:
- Compose UI

iOS:
- SwiftUI
```

Architecture:

```text
             Orders Feature
                   │
       ┌───────────┴───────────┐
       ▼                       ▼
  Shared Logic             Native UI
       │                 ┌─────┴─────┐
       │                 ▼           ▼
       │              Android       iOS
       │              Compose     SwiftUI
       │
       ▼
    Domain/Data
```

This is a common KMP strategy.

---

# 20. Feature Module with Shared UI

Alternatively:

```text
Orders
   │
   ▼
Compose Multiplatform
   │
 ┌─┴─────────────┐
 ▼               ▼
Android          iOS
```

Now more presentation code can live in:

```text
commonMain
```

The feature module structure does not fundamentally change.

---

# 21. Feature Public API

A feature should expose only what other modules need.

For example:

```kotlin
interface Orders {
    suspend fun getOrder(
        id: OrderId
    ): Order
}
```

Internal classes remain:

```kotlin
internal
```

where possible.

---

# 22. Public API vs Internal Implementation

Think of a feature as:

```text
┌─────────────────────────────────┐
│         Orders Module            │
│                                  │
│  ┌───────────────────────────┐   │
│  │       Public API          │   │
│  │                           │   │
│  │ Orders                    │   │
│  │ OrderId                   │   │
│  └──────────────┬────────────┘   │
│                 │                │
│        ┌────────▼────────┐       │
│        │ Internal        │       │
│        │ Repository      │       │
│        │ API             │       │
│        │ Mapper          │       │
│        │ DataSource      │       │
│        └─────────────────┘       │
└─────────────────────────────────┘
```

This is information hiding at module level.

---

# 23. Why Small Public APIs Matter

Suppose a feature exposes:

```text
OrderRepository
OrderRepositoryImpl
OrderApi
OrderDto
OrderMapper
OrderDatabase
OrderEntity
OrderViewModel
OrderState
```

Other modules can now depend on implementation details.

A better public surface might be:

```text
Orders
OrderId
```

Everything else remains internal.

---

# 24. Feature API as a Contract

The public API should describe:

```text
What the feature provides
```

not:

```text
How the feature implements it
```

For example:

```kotlin
interface PaymentGateway {
    suspend fun authorize(
        request: PaymentRequest
    ): PaymentResult
}
```

is a capability contract.

---

# 25. Avoid Leaking Framework Types

A feature API should avoid unnecessarily exposing:

```text
Android Context
Activity
UIViewController
Retrofit Response
Room Entity
Vendor SDK types
```

when the feature is intended to be cross-platform.

Prefer domain or capability types.

---

# 26. Feature Dependencies

Suppose:

```text
Orders
```

needs:

```text
Payments
```

Do not immediately add:

```text
Orders → Payments
```

Ask what Orders actually needs.

Maybe it needs:

```text
Payment authorization capability
```

rather than the entire Payments feature.

---

# 27. Feature-to-Feature Dependency

A simple relationship:

```text
Orders
   │
   ▼
Payments
```

can be valid if the business relationship is real.

But the dependency should cross:

```text
Public API
```

not:

```text
Internal implementation
```

---

# 28. Feature Contract Pattern

A better design may be:

```text
Orders
   │
   ▼
PaymentGateway
   ▲
   │
Payments
```

Now Orders depends on a capability rather than the internal Payments module.

This can reduce coupling.

---

# 29. Feature Event Pattern

Another option:

```text
Orders
   │
   ▼
OrderCreated
   │
   ├── Payments
   ├── Notifications
   └── Analytics
```

This is useful when consumers do not need synchronous feature calls.

However, events introduce:

```text
Asynchrony
Retries
Ordering
Debugging
Observability
```

so they should be used intentionally.

---

# 30. Feature Dependency Decision

When Feature A needs Feature B, ask:

```text
Does A need a direct response?
        │
       Yes
        │
        ▼
Can a small capability interface work?
        │
       Yes
        │
        ▼
Use a contract

       No
        │
        ▼
Is this naturally an event?
        │
       Yes
        │
        ▼
Use an event
```

This keeps feature boundaries explicit.

---

# 31. Feature Cycles

Avoid:

```text
Orders → Payments
Payments → Orders
```

This creates a cycle.

Cycles make:

```text
Ownership
Testing
Builds
Releases
Refactoring
```

more difficult.

---

# 32. Breaking Feature Cycles

Possible solutions:

```text
Contract
Event
Shared stable capability
Move common concept
Redesign ownership
```

Do not automatically create:

```text
core/feature-cycle-helper
```

just to break the compiler cycle.

Fix the architectural relationship.

---

# 33. Feature Modules and Dependency Direction

A common direction is:

```text
Application
     ↓
Feature
     ↓
Core / Contracts
     ↓
Infrastructure
     ↓
Platform
```

Avoid:

```text
Core
  ↓
Feature
```

when the core module is intended to be reusable across features.

---

# 34. Feature Modules and Core

Feature modules can consume:

```text
core:network
core:database
core:security
```

but Core should not depend on:

```text
features:orders
features:payments
```

Otherwise:

```text
Core
```

stops being a stable foundation.

---

# 35. Feature Modules and Platform

A feature may need:

```text
SecureStorage
Scanner
Notifications
```

Prefer:

```text
Feature
   ↓
Platform Capability
   ↓
Platform Implementation
```

rather than:

```text
Feature
   ↓
Android SDK
```

for cross-platform capabilities.

---

# 36. Feature Module Dependency Matrix

Example:

| Feature | Network | Database | Security | Payments | Profile |
|---|---:|---:|---:|---:|---:|
| Orders | ✓ | ✓ | ✓ | Contract | - |
| Payments | ✓ | ✓ | ✓ | - | - |
| Profile | ✓ | ✓ | ✓ | - | - |
| Inventory | ✓ | ✓ | - | - | - |

The matrix makes dependencies visible.

If every feature depends on every other feature, investigate the architecture.

---

# 37. Feature Dependency Graph

A healthy graph might look like:

```text
             Application
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    Orders     Payments    Profile
       │          │          │
       └──────┬───┴──────────┘
              ▼
             Core
```

A problematic graph:

```text
Orders ↔ Payments
  ↕        ↕
Profile ↔ Inventory
  ↕        ↕
Search ↔ Notifications
```

The second graph creates high coordination cost.

# 40. Feature Module and Team Ownership

A feature module can become a natural:

```text
Team Boundary
```

For example:

```text
Orders Team
     │
     ▼
:features:orders
```

This does not mean only one team can ever touch the module.

It means there is clear accountability.

# 41. Feature Modules and Code Review

A change to:

```text
:features:orders
```

can usually be reviewed primarily by:

```text
Orders owners
```

If the change modifies:

```text
core:security
```

additional ownership may be required.

Module boundaries therefore support review boundaries.

---

# 42. Feature Modules and CODEOWNERS

A repository can define ownership:

```text
/features/orders/       @orders-team
/features/payments/     @payments-team
/core/security/         @platform-security
```

This makes ownership explicit.

---

# 43. Feature Modules and Testing

A feature should own its tests.

For example:

```text
features/orders/
├── src/
│   ├── commonMain/
│   ├── commonTest/
│   ├── androidMain/
│   └── iosMain/
```

Tests can validate:

```text
Business rules
Use cases
Repositories
State transitions
Mappers
Platform behavior
```

---

# 44. Feature Unit Tests

Business logic should be testable without:

```text
Android emulator
iOS simulator
Network
Real database
```

Example:

```kotlin
@Test
fun `cancel order invokes repository`() = runTest {
    val repository = FakeOrderRepository()
    val useCase = CancelOrderUseCase(repository)

    useCase(OrderId("123"))

    assertTrue(repository.cancelledOrders.contains(
        OrderId("123")
    ))
}
```

This is one of the biggest benefits of good feature boundaries.

---

# 45. Feature Fakes

A feature can define:

```text
FakeOrderRepository
FakePaymentGateway
FakeSecureStorage
```

for tests.

The real implementations remain outside the business test.

---

# 46. Feature Integration Tests

Some behavior requires:

```text
Database
Network
Platform adapter
```

These can be tested separately.

For example:

```text
OrderRepository
    ↓
Fake API
    ↓
Test Database
```

The test boundary is explicit.

---

# 47. Feature UI Tests

UI tests can remain closer to the platform:

```text
Android UI Tests
iOS UI Tests
```

while business tests remain common.

This avoids duplicating business test logic across platforms.

---

# 48. Feature Modules and Build Performance

Feature modules can improve build isolation.

Suppose:

```text
Orders
Payments
Profile
```

are separate modules.

A change in:

```text
Profile
```

does not necessarily require rebuilding all feature implementation code.

The exact behavior depends on the Gradle dependency graph.

---

# 49. Feature Modules and Incremental Builds

The benefit is strongest when dependencies are:

```text
Directional
Minimal
Stable
```

If:

```text
Every feature → Giant Core
```

then changing the core can still affect many modules.

Modularization must therefore be combined with dependency discipline.

---

# 50. Feature Modules and Build Graphs

Think of:

```text
Feature Module
```

as both:

```text
Business Boundary
```

and:

```text
Compilation Boundary
```

This is why feature modules can provide architectural and build benefits simultaneously.

---

# 51. Feature Module Size

A feature module should be large enough to represent a meaningful capability.

For example:

```text
Orders
```

can contain multiple screens.

Avoid splitting:

```text
OrderListModule
OrderDetailsModule
OrderHistoryModule
```

unless those parts truly need:

```text
Independent ownership
Independent release
Independent reuse
```

---

# 52. Feature Module Granularity

A useful scale:

```text
Too Small
    ↓
Screen-level modules

Good
    ↓
Business capability modules

Too Large
    ↓
Entire application module
```

The middle usually provides the best balance.

# 53. Feature Modules and Product Boundaries

Some products naturally define features:

```text
Banking
├── Accounts
├── Transfers
├── Payments
├── Cards
└── Profile
```

Each can become a feature module.

The business domain itself guides the architecture.

---

# 54. Feature Modules and Enterprise Boundaries

In enterprise systems:

```text
Identity
Payments
Orders
Inventory
Reporting
```

may correspond to:

```text
Teams
Services
Business units
```

This can make feature modules especially useful.

---

# 55. Feature Modules and Bounded Contexts

A feature does not always equal a bounded context.

But some feature boundaries can become context boundaries.

For example:

```text
Payments
```

may have its own:

```text
Payment
Transaction
Refund
Authorization
```

models.

Orders should not necessarily share every Payments internal model.

---

# 56. Context-Specific Models

For example:

```kotlin
data class PaymentTransaction(
    val transactionId: String,
    val amount: Money
)
```

belongs to Payments.

Orders might only need:

```kotlin
data class PaymentStatus(
    val orderId: OrderId,
    val status: Status
)
```

This prevents large cross-feature models.

---

# 57. Feature Modules and Shared IDs

Sometimes sharing a small value object is reasonable:

```kotlin
@JvmInline
value class OrderId(
    val value: String
)
```

But sharing an entire:

```text
Order
```

model between unrelated contexts may be unnecessary.

Prefer sharing stable concepts.

---

# 58. Feature Modules and Domain Duplication

A little duplication can be healthier than tight coupling.

For example:

```text
OrderCustomer
PaymentCustomer
```

may intentionally differ.

Do not create a global:

```text
CustomerEverything
```

just to avoid duplicated fields.

---

# 59. Feature Modules and Reuse

Reuse a feature module when:

```text
Same capability
+
Same ownership
+
Same behavior
+
Same lifecycle
```

If two products merely have similar screens but different business rules, they may not need the same feature module.

---

# 60. Feature Modules and Product Variants

Suppose:

```text
Consumer App
Employee App
Partner App
```

all need:

```text
Authentication
```

Authentication may be shared.

But:

```text
Orders
```

might differ significantly.

The architecture should allow selective reuse.

---

# 61. Feature Modules and Multi-App Architecture

A repository can contain:

```text
apps/
├── consumer/
├── employee/
└── partner/

features/
├── authentication/
├── orders/
├── inventory/
└── profile/
```

Each app chooses its feature set.

```text
Consumer
 ├── Authentication
 ├── Orders
 └── Profile

Employee
 ├── Authentication
 ├── Inventory
 └── Reporting
```

This is more flexible than one universal application module.

---

# 62. Feature Modules and Feature Composition

An application can compose features:

```text
Application
    │
    ├── Authentication
    ├── Orders
    ├── Payments
    └── Profile
```

The application becomes the composition layer.

Features remain focused on their own responsibilities.

---

# 63. Feature Modules and Navigation

Feature modules should not automatically own the entire application navigation graph.

A better relationship can be:

```text
Feature
   │
   └── Exposes Destination / Entry Point

Application
   │
   └── Owns Navigation Composition
```

This reduces navigation coupling.

---

# 64. Feature Entry Points

A feature can expose a semantic entry point:

```kotlin
data class OrderDestination(
    val orderId: OrderId
)
```

The application decides how to render or navigate to it.

This keeps platform navigation outside the core feature API.

---

# 65. Feature Modules and Deep Links

A deep link:

```text
myapp://orders/123
```

can resolve to:

```text
OrderDestination(OrderId("123"))
```

The Orders feature handles the business meaning.

The application handles platform navigation.

---

# 66. Feature Modules and Shared State

Avoid putting every feature's state into:

```text
GlobalAppState
```

Instead:

```text
Orders
    → OrderState

Payments
    → PaymentState

Profile
    → ProfileState
```

Only truly global state should be centralized.

---

# 67. Feature Modules and Authentication

Authentication is often cross-cutting.

A feature may consume:

```kotlin
interface AuthenticationState {
    val isAuthenticated: Boolean
}
```

instead of implementing authentication itself.

This keeps:

```text
Authentication
```

as an owned capability.

---

# 68. Feature Modules and Permissions

A feature may require:

```text
Camera
Location
Bluetooth
```

The feature should express the capability it needs.

For example:

```kotlin
interface BarcodeScanner {
    suspend fun scan(): Barcode
}
```

Platform implementation handles:

```text
Camera permission
Native scanner SDK
Lifecycle
```

---

# 69. Feature Modules and Platform Capabilities

The architecture becomes:

```text
Orders
  │
  ▼
BarcodeScanner
  ▲
  │
Platform
  │
 ├── AndroidScanner
 └── IosScanner
```

This keeps the feature portable.

Suppose Payments uses:

```text
Vendor SDK
```

The feature should preferably depend on:

```text
PaymentGateway
```

while:

```text
integrations/payments
```

contains:

```text
Vendor adapter
```

Architecture:

```text
Payments Feature
       │
       ▼
PaymentGateway
       ▲
       │
Payment Integration
       │
```

# 163. Feature Modules and Feature Lifecycle

A feature can have:

```text
Created
Active
Inactive
Destroyed
```

depending on UI/navigation architecture.

The module itself should not own lifecycle globally.

The application and platform frameworks control lifecycle.

---

# 164. Feature Modules and Resource Cleanup

Platform resources such as:

```text
Camera
Bluetooth
Location
```

need explicit cleanup.

The platform adapter should own:

```text
Start
Stop
Close
Release
```

The feature should consume a semantic capability.

---

# 165. Feature Modules and Dependency Minimization

A feature should ideally depend on:

```text
Only what it needs
```

For example:

```text
Orders
 ├── core:network
 ├── core:database
 └── platform:secure-storage
```

rather than:

```text
Orders
 ├── core:network
 ├── core:database
 ├── core:security
 ├── core:analytics
 ├── core:logging
 ├── core:notifications
 ├── core:config
 └── 10 other modules
```

A large dependency list is a signal worth investigating.

---

# 166. Feature Modules and Dependency Fan-Out

Fan-out means:

```text
How many dependencies does this feature have?
```

High fan-out may indicate:

```text
Too many responsibilities
```

or:

```text
Too many cross-cutting dependencies
```

The solution may be better boundaries, not merely removing dependencies.

---

# 167. Feature Modules and Dependency Fan-In

Fan-in means:

```text
How many modules depend on this feature?
```

A feature with many consumers needs:

```text
Stable API
Documentation
Compatibility discipline
```

It may also indicate that some of its capability should become a separate shared contract.

---

# 168. Feature Modules and API Stability

A widely consumed feature should expose:

```text
Small
Stable
Semantic
```

APIs.

Avoid exposing implementation classes simply because they are convenient.

---

# 169. Feature Modules and Consumer-Driven APIs

Ask:

```text
What do consumers actually need?
```

If consumers only need:

```kotlin
suspend fun getOrder(
    id: OrderId
): Order
```

do not expose:

```text
OrderApi
OrderDao
OrderMapper
```

This keeps the contract focused.

---

# 170. Feature Modules and Interface Segregation

Avoid:

```kotlin
interface OrdersService {
    fun getOrder()
    fun createOrder()
    fun cancelOrder()
    fun returnOrder()
    fun trackOrder()
    fun exportOrder()
}
```

if different consumers need unrelated capabilities.

Consider:

```text
OrderQuery
OrderCommand
OrderTracking
```

when the business and ownership model supports it.

---

# 171. Feature Modules and Capability Interfaces

Capability interfaces can be useful:

```kotlin
interface OrderReader {
    suspend fun getOrder(
        id: OrderId
    ): Order
}

interface OrderCanceller {
    suspend fun cancel(
        id: OrderId
    )
}
```

Consumers depend only on the capability they need.

Do not create tiny interfaces mechanically.

Use them when they reduce meaningful coupling.

---

# 172. Feature Modules and Feature Entry APIs

A feature may expose one primary facade:

```kotlin
interface Orders {
    suspend fun getOrder(id: OrderId): Order
    suspend fun cancelOrder(id: OrderId)
}
```

Internally:

```text
OrdersImpl
 ├── GetOrderUseCase
 └── CancelOrderUseCase
```

This is a simple pattern for controlled feature access.

---

# 173. Feature Modules and Facades

A facade can hide:

```text
Multiple use cases
Multiple repositories
Multiple integrations
```

behind:

```text
One feature API
```

But do not make the facade a giant "everything service."

Keep it focused.

---

# 174. Feature Modules and Dependency Inversion

Feature business logic should depend on abstractions:

```text
Use Case
   ↓
Repository Interface
   ▲
   │
Repository Implementation
```

This allows:

```text
Fake
Real
Offline
Remote
Test
```

implementations.

---

# 175. Feature Modules and Platform Inversion

Similarly:

```text
Feature
   ↓
SecureStorage
   ▲
   │
Android / iOS
```

The feature depends on the capability.

The platform provides the implementation.

---

# 176. Feature Modules and Composition Root

The application can assemble:

```text
Orders
   ↓
OrderRepositoryImpl
   ↓
OrderApi
   ↓
HttpClient
```

The feature itself does not need to know how these objects are constructed.

---

# 177. Feature Modules and Configuration Injection

Instead of:

```kotlin
object GlobalConfig
```

prefer:

```kotlin
data class OrdersConfig(
    val pageSize: Int
)
```

provided by composition.

This keeps feature dependencies explicit.

---

# 178. Feature Modules and Environment Variants

The application may provide:

```text
DevelopmentOrdersConfig
ProductionOrdersConfig
```

without changing the feature implementation.

This is another benefit of dependency inversion.

---

# 179. Feature Modules and Test Configuration

Tests can provide:

```text
FakeOrderRepository
TestOrdersConfig
FakePaymentGateway
```

without changing production code.

The feature boundary supports test isolation.

---

# 180. Feature Modules and Architecture Enforcement

A feature module should ideally not import:

```text
another feature's internal package
```

Architecture checks can enforce this.

For example:

```text
features/orders
    ❌ features/payments/internal

features/orders
    ✓ features/payments/public-api
```

---

# 181. Feature Modules and Gradle `api` vs `implementation`

Gradle dependency exposure matters.

Prefer:

```kotlin
dependencies {
    implementation(project(":core:network"))
}
```

when the dependency should remain internal.

Use:

```kotlin
api(project(":core:domain"))
```

only when the dependency genuinely forms part of the module's public API.

This distinction helps control dependency leakage.

---

# 182. Why `api` vs `implementation` Matters

With:

```kotlin
api(...)
```

consumers may see the dependency transitively.

With:

```kotlin
implementation(...)
```

the dependency remains an implementation detail.

Therefore:

```text
Public API
    ↓
api

Internal dependency
    ↓
implementation
```

Use the narrowest visibility appropriate.

---

# 183. Feature Modules and Dependency Leakage

Bad:

```text
Orders
  api → Retrofit
```

if consumers do not need Retrofit.

Better:

```text
Orders
  implementation → Network Infrastructure
```

The feature's public API remains domain-oriented.

---

# 184. Feature Modules and Public Models

Be careful with public data classes.

If:

```kotlin
data class OrderDto(...)
```

is public, consumers may begin depending on its fields.

Later backend changes become consumer changes.

Prefer exposing:

```kotlin
Order
```

when the domain model is the intended contract.

---

# 185. Feature Modules and Binary Compatibility

If a feature becomes a reusable library, public API changes may affect:

```text
Binary compatibility
Source compatibility
Consumer builds
```

This is another reason to keep public APIs small.

---

# 186. Feature Modules and Internal Constructors

Even public types can limit construction:

```kotlin
class Order internal constructor(
    val id: OrderId
)
```

This prevents consumers from creating invalid instances when construction rules belong to the feature.

Use this carefully.

---

# 187. Feature Modules and Invariants

A feature can protect business invariants.

For example:

```text
Order cannot transition:
DELIVERED → CREATED
```

The feature owns the rule.

Consumers should not bypass the rule by constructing arbitrary states.

---

# 188. Feature Modules and Domain Encapsulation

Domain invariants should live near the model and business behavior.

For example:

```kotlin
class Order(
    val id: OrderId,
    private var status: OrderStatus
) {

    fun cancel() {
        check(status == OrderStatus.CREATED)
        status = OrderStatus.CANCELLED
    }
}
```

The exact model style depends on the project.

The architectural point is:

```text
Business rule belongs to business owner.
```

---

# 189. Feature Modules and State Transitions

A feature can model:

```text
CREATED
   ↓
CONFIRMED
   ↓
SHIPPED
   ↓
DELIVERED
```

with controlled transitions.

This prevents other modules from manipulating feature state arbitrarily.

---

# 190. Feature Modules and Business Events

A state transition can produce:

```text
OrderConfirmed
OrderShipped
OrderDelivered
```

Other systems can react through contracts or events.

This is useful for reducing direct feature coupling.

---

# 191. Feature Modules and Notifications

For example:

```text
OrderDelivered
       ↓
Notification
```

Orders does not need to know:

```text
Android notification API
APNs
Push provider
```

The notification system handles delivery.

---

# 192. Feature Modules and Analytics

Similarly:

```text
OrderDelivered
       ↓
Analytics
```

The analytics infrastructure translates it to the required provider.

---

# 193. Feature Modules and Search

Search may query multiple capabilities:

```text
Orders

Customers
```

Avoid making Search depend directly on internal implementations.

Use stable contracts:

```text
OrderSearchSource
ProductSearchSource
CustomerSearchSource
```

when the architecture benefits from that separation.

---

# 194. Feature Modules and Aggregator Features

Some features are naturally aggregators.

For example:

```text
Dashboard
```

may display:

```text
Orders
Payments
Inventory
```

Dashboard can depend on public contracts:

```text
Dashboard
 ├── OrderSummary
 ├── PaymentSummary
 └── InventorySummary
```

It should not reach into feature internals.

---

# 195. Feature Modules and Dashboard Design

A dashboard may create:

```text
DashboardState
```

from:

```text
Orders API
Payments API
Inventory API
```

This is a legitimate cross-feature composition.

The important boundary is:

```text
Public capability
```

rather than:

```text
Internal implementation
```

---

# 196. Feature Modules and Composite Features

Some features combine multiple capabilities:

```text
Checkout
```

may depend on:

```text
Cart
Payments
Inventory
Profile
```

This is acceptable when Checkout is itself a meaningful business capability.

The key is distinguishing:

```text
Orchestration
```

from:

```text
Shared implementation
```

---

# 197. Feature Modules and Orchestration

A Checkout feature may coordinate:

```text
Validate Cart
      ↓
Reserve Inventory
      ↓
Authorize Payment
      ↓
Create Order
```

The underlying features remain independently owned.

Checkout owns the orchestration flow.

---

# 198. Feature Modules and Transaction Boundaries

If the operation crosses multiple features:

```text
Checkout
 → Inventory
 → Payment
 → Orders
```

do not assume one local database transaction can cover everything.

Distributed business operations need explicit consistency strategies.

The feature architecture should make those boundaries visible.

---

# 199. Feature Modules and Saga-Like Workflows

A long-running business workflow may look like:

```text
Checkout
  ↓
Reserve Inventory
  ↓
Authorize Payment
  ↓
Create Order
```

Failure may require compensation:

```text
Payment fails
    ↓
Release Inventory
```

This orchestration belongs to the appropriate business capability.

---

# 200. Feature Modules and Business Ownership

A useful question:

> **Which team owns the business decision?**

If Checkout decides:

```text
When inventory is reserved
When payment is authorized
```

then Checkout may own the orchestration.

Do not distribute one business decision arbitrarily across modules.

---

# 201. Feature Modules and Dependency Direction

The direction should reflect business ownership.

For example:

```text
Checkout
   ↓
Payment Contract
   ↓
Payment Capability
```

rather than:

```text
Checkout
   ↔
Payment
```

with mutual internal access.

---

# 202. Feature Modules and Shared Contracts

Sometimes a separate contract module can be useful:

```text
contracts/
└── payment/
```

when:

```text
Multiple applications
Multiple consumers
Independent ownership
```

require a stable contract.

Do not create contract modules for every interface automatically.

---

# 203. Feature Modules and Contract Extraction

A feature may start:

```text
:features:payments
```

Later, if many systems consume the API:

```text
:contracts:payments
:features:payments
```

The contract becomes independently consumable.

This is an evolutionary step.

---

# 204. Feature Modules and API Ownership

Even if the contract is separate:

```text
Payments Team
```

should usually own:

```text
Payment Contract
```

because the contract describes its capability.

---

# 205. Feature Modules and Shared Contracts vs Shared Models

A contract can be:

```text
Small
Stable
Semantic
```

while a shared model can become:

```text
Large
Coupled
Difficult to evolve
```

Prefer sharing the smallest useful representation.

---

# 206. Feature Modules and Data Transfer

Instead of exposing:

```text
PaymentTransaction
```

to Orders, Payments may expose:

```kotlin
data class PaymentStatus(
    val orderId: OrderId,
    val status: PaymentStatusType
)
```

This is a narrower contract.

---

# 207. Feature Modules and Anti-Corruption Layers

If Payments uses an external provider:

```text
Provider Model
     ↓
Adapter
     ↓
Payment Domain
```

Orders sees:

```text
Payment Contract
```

not:

```text
Provider Model
```

This protects the architecture.

---

# 208. Feature Modules and Legacy Integration

The same pattern applies to legacy systems:

```text
Legacy API
     ↓
Adapter
     ↓
Feature Contract
```

Legacy terminology remains outside the feature's internal model.

---

# 209. Feature Modules and Migration

A feature can migrate incrementally:

```text
Legacy Orders
       ↓
Orders Contract
       ↓
New Orders Implementation
```

Consumers remain stable during the migration.

---

# 210. Feature Modules and Strangler Pattern

A legacy feature can be replaced capability by capability:

```text
Legacy Orders
├── Search → New
├── Details → New
├── Cancellation → Legacy
└── History → Legacy
```

Eventually:

```text
Legacy Orders
```

can be removed.

---

# 211. Feature Modules and Architecture Debt

Feature modules can still accumulate debt:

```text
Giant ViewModel
Huge Repository
Too many dependencies
Leaking DTOs
Platform checks
Global state
```

Modularization does not automatically create good architecture.

The internals still need discipline.

---

# 212. Feature Module Smells

Watch for:

```text
🚨 Feature has 30 dependencies
🚨 Feature exposes internal classes
🚨 Feature imports another feature's internals
🚨 Feature owns global state
🚨 Feature contains vendor SDK code everywhere
🚨 Feature directly accesses unrelated databases
🚨 Feature contains unrelated business capabilities
🚨 Feature module is larger than the application
```

These indicate scaling pressure.

---

# 213. Feature Module Smell: Giant ViewModel

Bad:

```text
OrderViewModel
├── network
├── database
├── analytics
├── navigation
├── payment
├── authentication
├── formatting
└── business rules
```

The ViewModel becomes an orchestration dump.

Prefer:

```text
ViewModel
   ↓
Use Cases
   ↓
Repositories
   ↓
Infrastructure
```

---

# 214. Feature Module Smell: Giant Repository

Bad:

```text
OrderRepository
├── API
├── database
├── payment
├── notification
├── analytics
└── navigation
```

A repository should primarily represent:

```text
Data access boundary
```

not the entire feature.

---

# 215. Feature Module Smell: Feature as a Utility Bucket

Bad:

```text
orders/
├── Order
├── Payment
├── User
├── Notification
└── RandomHelper
```

If unrelated concepts accumulate, the feature boundary is wrong.

---

# 216. Feature Module Smell: Platform Checks Everywhere

Bad:

```kotlin
if (Platform.isAndroid) {
    ...
} else {
    ...
}
```

throughout business code.

Prefer:

```text
Platform capability
```

or:

```text
expect / actual
```

at the appropriate boundary.

---

# 217. Feature Module Smell: Shared Global State

Bad:

```text
GlobalAppState
```

containing:

```text
orders
payments
profile
inventory
```

This creates hidden coupling.

Prefer feature-owned state.

---

# 218. Feature Module Smell: Direct SDK Dependency

Bad:

```text
Orders → Payment SDK
```

when Orders only needs:

```text
Payment authorization
```

Prefer:

```text
Orders
  ↓
PaymentGateway
  ↓
Payment Integration
```

---

# 219. Feature Module Smell: Cross-Feature Database Access

Bad:

```text
Orders → Payments Database
```

Better:

```text
Orders → Payment Contract
```

The owner of Payments controls its data.

---

# 220. Feature Module Smell: Public DTOs

Bad:

```kotlin
public data class OrderDto(...)
```

when consumers should only know:

```kotlin
Order
```

DTOs are transport representations.

Keep them internal where possible.

---

# 221. Feature Module Smell: Feature-to-Feature Cycles

Bad:

```text
Orders → Payments
Payments → Orders
```

Fix the business relationship.

Use:

```text
Contract
Event
Shared stable capability
Orchestration feature
```

where appropriate.

---

# 222. Feature Module Smell: Everything in CommonMain

`commonMain` should not become:

```text
A dumping ground for all shared code.
```

Platform-specific code should remain isolated.

---

# 223. Feature Module Smell: No Tests

A feature module without tests becomes risky as its ownership grows.

At minimum, test:

```text
Business rules
Use cases
Repository behavior
State transitions
```

according to feature complexity.

---

# 224. Feature Module Smell: No README

A module that is widely consumed but undocumented increases onboarding and integration cost.

A small README can solve much of this.

---

# 225. Feature Module Smell: No Owner

A shared feature without ownership becomes difficult to evolve.

Define:

```text
Owner
Reviewers
Support
```

---

# 226. Feature Module Smell: No Public API Discipline

If every class is public:

```text
Everything becomes a contract.
```

Use:

```text
internal
```

and focused public APIs.

---

# 227. Feature Module Smell: Feature Too Large

If:

```text
features/orders
```

contains:

```text
Orders
Payments
Inventory
Reporting
Notifications
```

then the feature is probably not one feature anymore.

Split based on actual business boundaries.

---

# 228. Feature Module Smell: Feature Too Small

If:

```text
OrderDetails
```

contains:

```text
One screen
One class
One test
```

a separate module may not provide enough value.

A package may be sufficient.

---

# 229. Feature Module Smell: Abstraction for Abstraction's Sake

Do not create:

```text
IOrderRepository
IOrderService
IOrderManager
IOrderProvider
IOrderCoordinator
```

unless they represent meaningful boundaries.

Interfaces should provide a reason.

---

# 230. Feature Module Smell: Generic Everything

Avoid:

```text
BaseFeature
BaseRepository
BaseViewModel
BaseUseCase
BaseManager
```

when they add little value.

Feature modules should model real business capabilities.

---

# 231. Feature Module Smell: Copy-Paste Architecture

Do not blindly duplicate a large template for every feature:

```text
presentation/
domain/
data/
repository/
mapper/
service/
manager/
factory/
```

If a feature does not need a layer, do not create it merely for symmetry.

---

# 232. Feature Module Structure Should Reflect Need

For a simple feature:

```text
features/profile/
├── Profile.kt
└── ProfileRepository.kt
```

may be enough.

For a complex feature:

```text
features/orders/
├── presentation/
├── domain/
├── data/
└── platform/
```

may be appropriate.

Architecture should follow complexity.

# 233. Feature Modules and Evolution

A feature can evolve:

```text

   ↓

   ↓

   ↓
Shared Feature Library
```

without changing its business identity.

This is an important evolutionary architecture pattern.

# 240. Feature Modules and Source Set Dependencies

A feature can depend on shared code in:

```text

```

while platform implementations use:

```text

```

The dependency graph should remain explicit.

# 241. Feature Modules and `expect` / `actual`

Example:

```kotlin
// commonMain

expect class OrderPlatformInfo {
    fun deviceIdentifier(): String
}
```

Android:

```kotlin
// androidMain

actual class OrderPlatformInfo {

    }
```

```kotlin

    }
```

Otherwise prefer a reusable platform capability.

# 242. Feature Modules and Capability Extraction

```text
DeviceIdentifier
```

do not duplicate it:

```text
Orders → DeviceIdentifier
Payments → DeviceIdentifier
Profile → DeviceIdentifier
```

Instead extract:

```text
platform/device
```

and let features consume the capability.

# 243. Feature Modules and the "First Consumer" Trap

A common mistake:

```text

        ↓
Put SecureStorage inside Orders
```

Later:

```text
Payments needs SecureStorage
```

Now ownership becomes awkward.

Instead ask:

```text
Who owns SecureStorage?
```

If it is cross-cutting platform infrastructure:

```text
platform/secure-storage
```

is a better boundary.

---

# 244. Feature Modules and Shared Capability Extraction

The evolution can be:

```text
Orders
   │
   └── internal storage

        ↓

Payments also needs storage

        ↓

Extract

platform/secure-storage
```

Extraction should follow real reuse, not speculation.

---

# 245. Feature Modules and Premature Shared Modules

Do not create:

```text
core/order-utils
```

because you think another feature might need it someday.

Create shared modules when:

```text
Reuse is real
+
Ownership is clear
+
Boundary is stable
```

```text

```

Create modules when the benefit exceeds the cost.

# 247. Feature Modules and Module Boundaries

A strong feature boundary provides:

```text

Test isolation
Ownership isolation
API isolation
```

Not every feature needs all five equally.

But the more benefits a boundary provides, the more valuable the module becomes.

---

# 248. Feature Modules and Change Isolation

changes.

```text
       ▼

       ▼
```

# 250. Feature Modules and Local Reasoning

```text

```

```text

```

and then reason mostly within that boundary.

Later:

# 255. Feature Modules and Selective Platform Support

# 285. Feature Modules and Extraction

```text
      ↓

      ↓

      ↓

      ↓

      ↓
```

# 286. Feature Modules and Duplication During Migration

```text
+
```

# 290. Feature Modules and Contract Testing

# 291. Feature Modules and Platform Implementations

with platform-specific behavior.

# 293. Feature Modules and Platform Abstraction

# 305. Feature Modules and Global Singletons

```text
+
```

# 306. Feature Modules and State Ownership

For example:

```text

```

may own cached order data.


should generally remain presentation-owned.

Avoid mixing:


without a reason.

# 307. Feature Modules and Cache Ownership

For example:

```text
   ↓

   ↓

```

The cache policy belongs to the data capability.

A global cache should not automatically know every feature's data.

# 308. Feature Modules and Offline Data

A feature may define:

```text
Sync policy
```

# 309. Feature Modules and Data Synchronization

```text
 ├── RemoteOrderDataSource
 ├── LocalOrderDataSource
 ├── OrderRepository
 └── OrderSync
```

# 310. Feature Modules and Conflict Resolution


# 311. Feature Modules and Generic Infrastructure

# 343. Feature Module Golden Rules

Remember these rules:

```text
1. A feature represents a business capability.
2. A feature is larger than a screen.
3. A feature is larger than a single use case.
4. A feature owns its business rules.
5. A feature should expose a small public API.
6. Feature internals should remain internal.
7. Feature-to-feature dependencies should be intentional.
8. Core should not depend on features.
9. Platform APIs should remain behind boundaries.
10. Vendor SDKs should remain behind integrations.
11. Shared code should be valuable, not merely reusable.
12. Feature modules should support local reasoning.
13. Module count is not the goal.
14. Ownership should be explicit.
15. Architecture should evolve with complexity.
```

---

# 344. Final Takeaways

Feature modules are where project structure begins to become real architecture.

They provide a boundary around:

```text
Business Capability
+
Ownership
+
Dependencies
+
Tests
+
Change
```

A good feature module lets a developer think:

```text
"I am working on Orders."
```

instead of:

```text
"I am working somewhere inside shared."
```

The difference becomes enormous as the application grows.

The strongest feature-module architecture looks like:

```text
             APPLICATION
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     Orders    Payments   Profile
        │         │         │
        └─────────┼─────────┘
                  ▼
                 Core
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     Network   Database  Security
                  │
                  ▼
              Platform
```

Inside each feature:

```text
              FEATURE
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
  Presentation   Domain     Data
       │           │          │
       └───────────┼──────────┘
                   ▼
              Source Sets
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
     commonMain AndroidMain iOSMain
```

And the most important boundary remains:

```text
Feature
   │
   ▼
Public Capability
   │
   ▼
Hidden Implementation
```

> [!TIP]
> **A feature module should make the feature easy to find, easy to own, easy to test, and difficult to accidentally couple to unrelated implementation details.**

The goal is not to create the largest number of modules.

The goal is to create **meaningful boundaries that allow the product, teams, and codebase to evolve independently**.
