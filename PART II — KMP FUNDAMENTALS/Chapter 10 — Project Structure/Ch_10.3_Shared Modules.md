# Chapter 10 — Project Structure

## Part 3 — Shared Modules

Shared modules are where many KMP architectures become either highly reusable or highly coupled.

The word **shared** sounds harmless:

```text
shared/
```

But a shared module can quickly become the place where everything ends up:

```text
Network
Database
Models
Utilities
Business Rules
UI
Authentication
Analytics
Logging
Random Helpers
```

Eventually:

```text
shared/
```

becomes:

```text
the entire application
```

That is not modular architecture.

A good shared module answers a much more precise question:

> **What capability is genuinely common, who owns it, and why should multiple parts of the system depend on it?**

---

# 1. What Is a Shared Module?

A shared module contains code intentionally reused by multiple consumers.

For example:

```text
core/network
core/security
core/database
core/observability
```

or:

```text
shared/design-system
shared/testing
shared/domain
```

depending on the architecture.

The important distinction is:

```text
Shared
≠
Everything reusable
```

Instead:

```text
Shared
=
Stable capability with meaningful common ownership
```

---

# 2. The Shared Module Mental Model

Think of a shared module as infrastructure or a capability that multiple features consume.

```text
             APPLICATION
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    Orders     Payments    Profile
       │          │          │
       └──────────┼──────────┘
                  ▼
               Shared
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    Network    Security   Database
```

The shared module should support the features.

It should not become the owner of feature-specific business logic.

---

# 3. Why Shared Modules Exist

A shared module can provide:

```text
Reuse
Consistency
Infrastructure
Cross-cutting capabilities
Common contracts
Testing utilities
Build conventions
Design system components
```

For example:

```text
Multiple features
      │
      ▼
Network Client
```

Instead of each feature creating:

```text
Own HTTP client
Own timeout policy
Own serialization setup
Own interceptors
```

the infrastructure can be centralized.

---

# 4. Shared Modules Are Architectural Boundaries

A shared module creates a boundary:

```text
Feature
   ↓
Shared Capability
```

The feature should know:

```text
What the capability does
```

without necessarily knowing:

```text
How it is implemented
```

---

# 5. Shared Does Not Mean Global

This distinction is critical.

```text
Shared
   ↓
Multiple consumers intentionally depend on it
```

while:

```text
Global
   ↓
Everything can access it
```

A shared module should still have:

```text
Ownership
API
Dependencies
Purpose
Consumers
```

---

# 6. The Shared Module Test

Before creating a shared module, ask:

```text
Who consumes it?
Why do they consume it?
Do they need the same behavior?
Who owns the capability?
Can the API remain stable?
```

If the answers are unclear:

```text
Do not create the shared module yet.
```

---

# 7. Reuse Is Not Enough

Suppose two features both have:

```kotlin
fun formatDate(date: Date): String
```

That does not automatically mean:

```text
core/date-utils
```

should be created.

The behavior might be:

```text
Different
Context-specific
Likely to evolve independently
```

Shared code should have:

```text
Shared meaning
```

not just:

```text
Similar implementation
```

---

# 8. Shared Meaning vs Shared Code

This is one of the most important architectural ideas.

Two pieces of code can look identical:

```text
Code similarity
```

without representing the same business concept.

Prefer sharing when:

```text
Meaning is shared
+
Ownership is clear
+
Behavior is expected to remain aligned
```

---

# 9. Example: Money

Suppose:

```text
Orders
Payments
Checkout
```

all use:

```kotlin
Money
```

If all three features share the same monetary semantics, a shared domain value object may be appropriate.

```kotlin
data class Money(
    val amount: BigDecimal,
    val currency: Currency
)
```

The decision depends on the business model.

---

# 10. Example: Customer

Suppose:

```text
Orders
Payments
Profile
```

all have:

```text
Customer
```

Do not immediately create:

```text
shared/Customer
```

Ask whether:

```text
OrderCustomer
PaymentCustomer
ProfileCustomer
```

actually represent different contexts.

They may.

---

# 11. Shared Modules and Bounded Contexts

A shared module can accidentally destroy boundaries.

For example:

```text
shared/models/
└── Customer.kt
```

Now:

```text
Orders
Payments
Profile
```

all depend on one global Customer model.

Over time, every context becomes coupled to:

```text
Customer
```

The model begins evolving according to multiple teams.

This is a warning sign.

---

# 12. Shared Modules and Context-Specific Models

Prefer:

```text
Orders
└── OrderCustomer

Payments
└── BillingCustomer

Profile
└── CustomerProfile
```

when the concepts have different meanings.

A small amount of duplication can be healthier than forced coupling.

---

# 13. Shared Module Categories

A KMP repository may contain several types of shared modules:

```text
Core Infrastructure
Platform Capabilities
Design System
Shared Domain
Contracts
Testing
Utilities
Integrations
```

Each category should have a clear purpose.

---

# 14. Example Shared Module Tree

```text
shared/
├── core/
│   ├── network/
│   ├── database/
│   ├── security/
│   └── observability/
│
├── domain/
│   ├── money/
│   └── identity/
│
├── design-system/
│
├── testing/
│
└── contracts/
```

The exact structure depends on the project.

The key is semantic ownership.

---

# 15. Core Infrastructure

Core infrastructure usually contains mechanisms used across many features.

Examples:

```text
Network client
Serialization
Database infrastructure
Logging
Analytics infrastructure
Configuration
Feature flags
```

These modules should avoid feature-specific business behavior.

---

# 16. `core:network`

A typical module:

```text
core/network
├── HttpClientFactory
├── NetworkConfig
├── Interceptor
├── NetworkError
└── SerializationConfig
```

Features can consume it.

```text
Orders ──────┐
Payments ────┼──→ core:network
Profile ─────┘
```

---

# 17. What `core:network` Should Not Contain

Avoid:

```text
OrderApi
PaymentApi
ProfileApi
OrderDto
PaymentDto
```

Those belong to their feature boundaries.

Instead:

```text
core:network
```

provides the mechanism.

Features define their own APIs.

---

# 18. Shared Mechanism vs Feature Behavior

This distinction is fundamental.

```text
HTTP Client
```

is a mechanism.

```text
CreateOrder
```

is business behavior.

Therefore:

```text
HTTP Client → Shared
CreateOrder → Orders
```

---

# 19. `core:database`

A shared database infrastructure module may provide:

```text
Database initialization
Driver configuration
Transactions
Migration infrastructure
Database factory
```

But feature-specific entities should remain owned by features when practical.

---

# 20. Database Ownership

Avoid:

```text
core:database
├── OrderEntity
├── PaymentEntity
├── ProfileEntity
└── InventoryEntity
```

if Core is intended to be infrastructure.

Prefer:

```text
features/orders
└── OrderEntity

features/payments
└── PaymentEntity

features/profile
└── ProfileEntity
```

while:

```text
core:database
```

provides the underlying database capability.

---

# 21. Shared Database Architecture

```text
Orders ───────┐
              │
Payments ─────┼──→ Database Infrastructure
              │
Profile ──────┘
```

The shared module provides:

```text
How to access the database
```

The feature owns:

```text
What data it stores
```

---

# 22. Shared Security Module

Security can be shared when it provides infrastructure:

```text
SecureStorage
Encryption
Certificate validation
Credential protection
Security configuration
```

Features consume security capabilities.

---

# 23. Security Capability

For example:

```kotlin
interface SecureStorage {

    suspend fun put(
        key: String,
        value: String
    )

    suspend fun get(
        key: String
    ): String?
}
```

Android and iOS implementations can differ.

The contract remains stable.

---

# 24. KMP Security Architecture

```text
                    Feature
                       │
                       ▼
                SecureStorage
                       ▲
                       │
            ┌──────────┴──────────┐
            │                     │
         Android                 iOS
            │                     │
      Android Keystore      Keychain
```

This is a good use of KMP abstraction.

---

# 25. Shared Module and `expect / actual`

Sometimes platform APIs differ enough to use:

```kotlin
expect
actual
```

For example:

```kotlin
// commonMain

expect class SecureStorage {
    suspend fun put(
        key: String,
        value: String
    )

    suspend fun get(
        key: String
    ): String?
}
```

Android:

```kotlin
// androidMain

actual class SecureStorage {
    actual suspend fun put(
        key: String,
        value: String
    ) {
        // Android implementation
    }

    actual suspend fun get(
        key: String
    ): String? {
        // Android implementation
        return null
    }
}
```

iOS provides its own implementation.

---

# 26. Interface vs `expect / actual`

A shared capability can use:

```text
Interface + dependency injection
```

or:

```text
expect / actual
```

Use an interface when:

```text
You want substitution
Testing
Multiple implementations
Explicit dependency injection
```

Use `expect / actual` when:

```text
The API is fundamentally platform-specific
```

The decision should be deliberate.

---

# 27. Shared Observability

Observability infrastructure can be shared:

```text
Logger
Analytics
Tracing
Metrics
Crash reporting abstraction
```

For example:

```kotlin
interface Logger {
    fun debug(message: String)
    fun info(message: String)
    fun error(
        message: String,
        throwable: Throwable? = null
    )
}
```

Features depend on the abstraction.

---

# 28. Shared Analytics

Avoid putting feature events directly into the analytics infrastructure.

Bad:

```text
core:analytics
└── OrderCompleted
└── PaymentFailed
└── ProfileUpdated
```

Better:

```text
Orders
└── OrderCompleted

Payments
└── PaymentFailed

Profile
└── ProfileUpdated
```

The shared analytics module transports the events.

---

# 29. Shared Analytics Architecture

```text
Orders
   │
   ▼
OrderCompleted
   │
   ▼
Analytics Contract
   │
   ▼
Analytics Infrastructure
   │
   ▼
Vendor Adapter
```

The shared module owns:

```text
Delivery mechanism
```

not:

```text
Business event meaning
```

---

# 30. Shared Logging

Logging is usually infrastructure.

A feature can write:

```text
"Order cancellation failed"
```

through:

```kotlin
logger.error(...)
```

The logger decides:

```text
Console
File
Remote system
Vendor
```

---

# 31. Shared Configuration

Configuration can be shared:

```text
Environment
API endpoint
Feature flags
Build information
```

But avoid a giant:

```kotlin
GlobalConfig
```

containing every application's setting.

Prefer focused configuration contracts.

---

# 32. Configuration as Capability

For example:

```kotlin
data class NetworkConfig(
    val baseUrl: String,
    val timeoutMillis: Long
)
```

Then:

```text
Network
```

receives only the configuration it needs.

---

# 33. Shared Feature Flags

Feature flag infrastructure can be shared:

```kotlin
interface FeatureFlags {
    fun isEnabled(
        flag: FeatureFlag
    ): Boolean
}
```

Feature-specific flags remain owned by the feature.

For example:

```kotlin
enum class OrdersFlag {
    NewCancellationFlow
}
```

---

# 34. Shared Design System

A design system is another common shared module.

It may contain:

```text
Colors
Typography
Buttons
Cards
Text fields
Spacing
Icons
Theme
Accessibility primitives
```

For Compose Multiplatform:

```text
shared/design-system
```

can provide common UI components.

---

# 35. Design System vs Feature UI

Shared:

```text
PrimaryButton
LoadingIndicator
AppTextField
AppCard
```

Feature-specific:

```text
OrderSummary
PaymentHistory
InventoryCard
```

The design system should not become a business component repository.

---

# 36. Shared Design System Architecture

```text
Orders ───────┐
Payments ────┼──→ Design System
Profile ─────┘
```

The Design System knows:

```text
How UI should look
```

The feature knows:

```text
What the UI means
```

---

# 37. Shared Testing Module

A testing module can provide:

```text
Coroutine test utilities
Fake clock
Test dispatchers
Flow test helpers
Common assertions
Fixture builders
```

Example:

```text
shared/testing
```

Features consume it only from test source sets.

---

# 38. Test Dependencies Should Stay Test-Only

Prefer:

```kotlin
commonTest {
    implementation(project(":shared:testing"))
}
```

rather than exposing testing utilities to production code.

This keeps production dependency graphs clean.

---

# 39. Shared Domain Module

A shared domain module is the most dangerous category because it can become:

```text
Global business model
```

Use it carefully.

Good candidates:

```text
Money
Currency
CountryCode
Locale
Time abstraction
```

when they genuinely have common semantics.

---

# 40. Shared Domain vs Feature Domain

Example:

```text
shared/domain
└── Money

features/orders
└── Order

features/payments
└── Payment
```

`Money` may be shared.

`Order` and `Payment` should remain feature-owned unless they truly form a shared business context.

---

# 41. Shared Models: The Global Model Trap

Bad:

```text
shared/models/
├── User
├── Order
├── Payment
├── Product
├── Inventory
├── Cart
└── EverythingElse
```

This looks organized.

Architecturally, it may be highly coupled.

---

# 42. Why Global Models Become Dangerous

If:

```text
Order
```

is shared everywhere:

```text
Orders
Payments
Analytics
Reporting
Profile
```

then every change to `Order` becomes potentially cross-cutting.

The model becomes a coupling hub.

---

# 43. Shared Model Decision

Before moving a model to shared, ask:

```text
Is the concept truly shared?
Does it mean the same thing everywhere?
Is ownership clear?
Will all consumers evolve together?
Is sharing cheaper than separate models?
```

If not:

```text
Keep it inside the feature.
```

---

# 44. Shared Contracts

Contracts can be useful when multiple consumers need a stable capability.

For example:

```text
contracts/payment
```

might contain:

```kotlin
interface PaymentGateway {
    suspend fun authorize(
        request: PaymentRequest
    ): PaymentResult
}
```

The contract should remain small.

---

# 45. Shared Contract vs Shared Implementation

A contract:

```text
Defines capability
```

An implementation:

```text
Provides capability
```

Keep the distinction clear.

```text
Payment Contract
       ▲
       │
Payment Implementation
```

---

# 46. Shared Modules and Dependency Inversion

A useful architecture:

```text
Feature
   ↓
Contract
   ▲
   │
Implementation
```

The feature depends on the stable abstraction.

The implementation can change.

---

# 47. Shared Modules and Dependency Direction

A healthy graph:

```text
Application
    │
    ├── Features
    │      │
    │      ▼
    │    Shared
    │
    └── Integrations
```

Avoid:

```text
Shared
   ↓
Features
```

when Shared is intended to be foundational.

---

# 48. Shared Module Cycles

Bad:

```text
Orders
  ↓
Shared
  ↓
Payments
  ↓
Orders
```

Shared modules should not become a hidden path between feature modules.

---

# 49. The Shared Module Cycle Trap

A common mistake:

```text
Orders needs Payments
Payments needs Orders
```

Developer creates:

```text
shared/business
```

and moves code there.

Now:

```text
Orders → Shared
Payments → Shared
```

The cycle appears to disappear.

But the shared module may now contain business logic owned by neither feature.

The architectural problem has been hidden, not solved.

---

# 50. Shared Module Ownership

Every shared module should answer:

```text
Who owns this?
```

Possible owners:

```text
Platform Team
Foundation Team
Design System Team
Security Team
Domain Team
Feature Team
```

If nobody owns it:

```text
Shared module
```

will eventually become technical debt.

---

# 51. Shared Module README

A shared module should document:

```markdown
# Core Network

## Purpose

Provides common HTTP client infrastructure.

## Consumers

- Orders
- Payments
- Profile

## Does Not Own

- Feature APIs
- Feature DTOs
- Business rules

## Owner

Platform Team
```

This prevents accidental expansion.

---

# 52. Shared Module API

The public API should be small.

For:

```text
core:network
```

consumers might see:

```text
HttpClientFactory
NetworkConfig
NetworkError
```

They should not see every implementation detail.

---

# 53. Shared Module Internal Implementation

For example:

```kotlin
internal class DefaultHttpClientFactory(
    private val config: NetworkConfig
)
```

The implementation can remain internal.

This allows refactoring without affecting consumers.

---

# 54. Shared Module and `internal`

Kotlin's:

```kotlin
internal
```

is extremely useful for shared modules.

Use it to protect:

```text
Implementation classes
Helpers
Adapters
Factories
Internal models
```

Expose only what consumers require.

---

# 55. Shared Module and Gradle `api`

As with feature modules:

```kotlin
api(...)
```

should be used intentionally.

If a shared module's dependency is not part of its public API:

```kotlin
implementation(...)
```

is usually better.

---

# 56. Shared Module Dependency Leakage

Bad:

```text
core:network
api → Retrofit
```

when consumers should not know Retrofit.

Better:

```text
core:network
implementation → Retrofit
```

This protects the module boundary.

---

# 57. Shared Modules and Vendor SDKs

A shared analytics module might internally use:

```text
Firebase
```

but consumers should depend on:

```text
Analytics
```

not:

```text
FirebaseAnalytics
```

This makes vendor replacement possible.

---

# 58. Shared Vendor Adapter

Architecture:

```text
Feature
   ↓
Analytics
   ↓
Firebase Adapter
   ↓
Firebase SDK
```

The vendor remains behind the integration boundary.

---

# 59. Shared Module and Replaceability

Good shared infrastructure makes replacement easier:

```text
Database A
    ↓
Database Contract
    ↓
Database B
```

or:

```text
Analytics A
    ↓
Analytics Abstraction
    ↓
Analytics B
```

The feature should not need to know the vendor.

---

# 60. Shared Module and Platform Replacement

The same principle applies to platform APIs:

```text
SecureStorage
```

can use:

```text
Android Keystore
iOS Keychain
```

without changing feature logic.

---

# 61. Shared Modules and KMP Source Sets

A typical shared KMP module:

```text
core/security/
├── src/
│   ├── commonMain/
│   ├── commonTest/
│   ├── androidMain/
│   └── iosMain/
└── build.gradle.kts
```

Shared API:

```text
commonMain
```

Platform implementations:

```text
androidMain
iosMain
```

---

# 62. Shared Module Source Set Example

```kotlin
kotlin {
    androidTarget()

    iosX64()
    iosArm64()
    iosSimulatorArm64()

    sourceSets {
        commonMain.dependencies {
            implementation(project(":shared:domain"))
        }

        commonTest.dependencies {
            implementation(kotlin("test"))
        }
    }
}
```

The exact setup depends on the KMP version and project conventions.

---

# 63. Shared Module with Native Implementations

Example:

```text
shared/security
│
├── commonMain
│   └── SecureStorage.kt
│
├── androidMain
│   └── AndroidSecureStorage.kt
│
└── iosMain
    └── IosSecureStorage.kt
```

The abstraction remains shared.

The mechanism remains platform-specific.

---

# 64. Shared Module with Multiple Platforms

As a project grows:

```text
commonMain
androidMain
iosMain
desktopMain
wasmJsMain
```

Not every shared module must support every target.

Support only what the capability requires.

---

# 65. Shared Module and Platform Explosion

A common mistake is creating:

```text
expect/actual
```

for every small utility.

This can lead to:

```text
commonMain
androidMain
iosMain
desktopMain
wasmMain
```

with unnecessary duplication.

Only introduce platform-specific source sets when the platform behavior is real.

---

# 66. Shared Module and `commonMain`

`commonMain` should contain the most reusable part of the module.

Examples:

```text
Interfaces
Domain abstractions
Business-neutral mechanisms
Serialization models
Shared utilities
```

when genuinely common.

---

# 67. Shared Module and Platform Leakage

Bad:

```kotlin
class NetworkClient(
    private val context: Context
)
```

inside:

```text
commonMain
```

This indicates Android-specific assumptions have leaked into shared code.

Use:

```text
Platform capability
```

or:

```text
expect / actual
```

as appropriate.

---

# 68. Shared Module and Platform-Neutral APIs

Prefer:

```kotlin
interface NetworkClient {
    suspend fun execute(
        request: NetworkRequest
    ): NetworkResponse
}
```

instead of:

```kotlin
interface NetworkClient {
    fun execute(
        request: RetrofitRequest
    ): Response<*>
}
```

The first is more portable.

---

# 69. Shared Module and Coroutines

Shared modules commonly expose:

```kotlin
suspend
Flow
StateFlow
```

These are good KMP-compatible abstractions when their semantics fit the capability.

---

# 70. Shared Module and Dispatchers

Avoid hardcoding platform dispatchers throughout shared code:

```kotlin
Dispatchers.IO
```

when the architecture needs platform-specific scheduling.

A dispatcher provider can be supplied:

```kotlin
interface AppDispatchers {
    val io: CoroutineDispatcher
    val default: CoroutineDispatcher
}
```

Use only if this abstraction provides real value.

---

# 71. Shared Module and Time

Time is another capability that can be shared carefully.

Instead of:

```kotlin
Clock.System.now()
```

everywhere when deterministic testing is needed, consider:

```kotlin
interface ClockProvider {
    fun now(): Instant
}
```

Tests can provide:

```text
FakeClock
```

The abstraction should exist because testing or portability requires it.

---

# 72. Shared Module and UUID

Likewise:

```kotlin
interface IdGenerator {
    fun generate(): String
}
```

can be useful if:

```text
Randomness
Determinism
Testing
Platform behavior
```

matter.

Do not abstract every standard-library function.

---

# 73. Shared Utilities Module

This is one of the most dangerous modules:

```text
core:utils
```

because everything can appear to belong there.

Examples of problematic growth:

```text
StringUtils
DateUtils
OrderUtils
PaymentUtils
UIUtils
NetworkUtils
RandomUtils
```

It becomes a dependency magnet.

---

# 74. The Utility Module Rule

Before adding something to:

```text
utils
```

ask:

```text
What capability does this represent?
Who owns it?
Is the name semantic?
Can it live closer to its consumer?
```

Often the answer is:

```text
Keep it inside the feature.
```

---

# 75. Utility Extraction Example

Instead of:

```text
core:utils
└── calculateOrderDiscount()
```

prefer:

```text
features/orders/domain
└── OrderDiscountPolicy
```

because the behavior belongs to Orders.

---

# 76. Shared Date Formatting

A generic function:

```kotlin
fun formatIsoDate(...)
```

might be shared.

But:

```kotlin
fun formatOrderDeliveryDate(...)
```

belongs to Orders.

The difference is semantic ownership.

---

# 77. Shared Validation

Generic:

```text
Email syntax validation
```

may be shared.

Business-specific:

```text
Can this user cancel this order?
```

belongs to Orders.

Do not move business rules into generic validators.

---

# 78. Shared Serialization

Serialization mechanisms can be shared:

```text
Json
Json configuration
Serializer factories
```

But DTOs should remain feature-owned.

```text
core:serialization
```

provides the mechanism.

```text
features/orders
```

provides:

```text
OrderDto
```

---

# 79. Shared Networking

Network infrastructure can provide:

```text
HttpClient
Headers
Interceptors
Timeouts
Serialization
Retry infrastructure
```

Feature modules provide:

```text
OrderApi
PaymentApi
ProfileApi
```

---

# 80. Shared Authentication Infrastructure

Authentication infrastructure can provide:

```text
Token storage
Token refresh
Session state
Credential handling
```

But feature-specific authorization rules remain with the feature.

For example:

```text
Can cancel order?
```

belongs to Orders.

---

# 81. Authentication vs Authorization

This distinction is important.

```text
Authentication
→ Who are you?

Authorization
→ What can you do?
```

Authentication may be shared.

Authorization often contains feature-specific business rules.

---

# 82. Shared Permission Capability

A shared capability might be:

```kotlin
interface CurrentUser {
    val id: UserId
    val roles: Set<Role>
}
```

Orders can then evaluate:

```text
Can current user cancel this order?
```

using its own business rules.

---

# 83. Shared Session State

A session may be application-wide:

```text
Authenticated
Unauthenticated
Expired
```

The session infrastructure can be shared.

But feature state should remain feature-owned.

---

# 84. Shared Modules and Global State

Be careful with:

```text
GlobalSession
GlobalAppState
GlobalRepository
GlobalManager
```

Shared infrastructure should not automatically mean shared mutable state.

Prefer explicit state ownership.

---

# 85. Shared Modules and Singleton Scope

A shared module may expose a singleton:

```text
HttpClient
Database
Logger
```

when the lifecycle justifies it.

But:

```text
Singleton
```

is an implementation/lifecycle decision.

It is not synonymous with:

```text
Shared architecture
```

---

# 86. Shared Modules and Dependency Injection

The composition root can provide shared dependencies:

```text
Application
   │
   ├── HttpClient
   ├── Database
   ├── Logger
   └── SecureStorage
```

Features consume only what they require.

---

# 87. Shared Module Dependency Graph

A healthy example:

```text
                    Application
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Orders         Payments        Profile
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                       Core
            ┌────────────┼────────────┐
            ▼            ▼            ▼
         Network      Security     Database
```

The arrows flow toward shared capabilities.

---

# 88. Shared Module Dependency Direction

Avoid:

```text
core:network
     ↓
features:orders
```

because Core now knows about a feature.

Instead:

```text
features:orders
     ↓
core:network
```

Core remains reusable.

---

# 89. Shared Module and Feature Independence

If:

```text
Orders
```

can compile and test with:

```text
FakeNetworkClient
```

then the dependency is healthy.

If Orders requires:

```text
entire application
```

to test, the boundary is too weak.

---

# 90. Shared Module and Testability

Shared modules should themselves be testable.

For example:

```text
core:network
```

tests:

```text
Timeout behavior
Retry behavior
Serialization
Header handling
Error mapping
```

Feature tests do not need to repeat all infrastructure tests.

---

# 91. Shared Module Contract Tests

A shared capability can define contract tests:

```text
SecureStorage Contract
       │
 ┌─────┴─────┐
 ▼           ▼
Android     iOS
```

Both implementations should satisfy the same expected behavior.

---

# 92. Shared Module and Fake Implementations

A capability can have:

```text
Production
Fake
Test
```

implementations.

For example:

```text
SecureStorage
├── AndroidSecureStorage
├── IosSecureStorage
└── FakeSecureStorage
```

This is valuable for deterministic testing.

---

# 93. Shared Module and Integration Boundaries

A shared module may integrate with:

```text
Firebase
Stripe
Sentry
Maps
Vendor SDK
```

but the vendor should remain behind the module boundary.

---

# 94. Shared Module and Vendor Lock-In

Without an abstraction:

```text
Orders
Payments
Profile
   ↓
Firebase
```

Replacing Firebase becomes expensive.

With:

```text
Features
   ↓
Analytics
   ↓
Firebase Adapter
```

the vendor is isolated.

---

# 95. Shared Module and External SDKs

The same pattern applies to:

```text
Maps
Payments
Analytics
Crash reporting
Push notifications
Identity
```

The shared module should expose:

```text
Application capability
```

rather than:

```text
Vendor API
```

---

# 96. Shared Modules and Design System Ownership

A design system should have its own ownership:

```text
Design System Team
```

Features consume:

```text
AppButton
AppCard
AppTextField
```

Features should not modify design-system internals casually.

---

# 97. Shared Modules and UI Consistency

The design system provides:

```text
Typography
Colors
Spacing
Components
Accessibility
Motion
```

This gives feature teams consistency without sharing business logic.

---

# 98. Shared Modules and UI Coupling

Avoid putting:

```text
OrderScreen
PaymentScreen
ProfileScreen
```

inside the design system.

Those are feature-owned.

---

# 99. Shared Modules and Navigation

Navigation infrastructure can be shared:

```text
Navigation abstraction
Route parser
Deep link infrastructure
```

but feature destinations should remain feature-owned.

---

# 100. Shared Navigation Capability

For example:

```kotlin
interface Navigator {
    fun navigate(
        destination: Destination
    )
}
```

The platform/application implements navigation.

Features emit semantic destinations.

---

# 101. Shared Modules and Application Composition

Shared modules should not own the application composition root.

The application assembles:

```text
Features
Shared Infrastructure
Platform Implementations
Integrations
```

---

# 102. Shared Module and Composition Root

```text
                Application
                     │
      ┌──────────────┼──────────────┐
      ▼              ▼              ▼
   Features       Shared        Integrations
                     │
                     ▼
                 Platform
```

The composition root connects everything.

---

# 103. Shared Modules and Circular Dependency Prevention

A good layering model:

```text
Feature
   ↓
Shared Contract
   ↓
Shared Infrastructure
   ↓
Platform
```

Do not allow:

```text
Platform
   ↓
Feature
```

unless the architecture intentionally models that relationship.

---

# 104. Shared Module and Platform Adapter

Example:

```text
shared:secure-storage
        │
        ▼
platform:android-secure-storage
platform:ios-secure-storage
```

The platform adapter can depend on shared contracts.

---

# 105. Shared Modules and KMP Hierarchical Source Sets

For larger KMP projects, intermediate source sets can be useful.

For example:

```text
commonMain
    │
    ├── appleMain
    │      ├── iosMain
    │      └── macosMain
    │
    └── androidMain
```

This allows common Apple-specific behavior without duplicating it.

Use hierarchy based on actual platform sharing.

---

# 106. Shared Module and Source Set Ownership

A source set should represent:

```text
Actual shared behavior
```

not:

```text
Convenient file placement
```

If Apple platforms truly share implementation, `appleMain` may be appropriate.

---

# 107. Shared Modules and Build Performance

Shared modules can improve build organization.

But a huge shared module can become a build bottleneck.

For example:

```text
shared/
   5000 files
```

means a change in one utility can affect many consumers.

---

# 108. The Giant Shared Module Problem

Bad:

```text
:shared
├── Network
├── Database
├── Orders
├── Payments
├── Profile
├── Analytics
├── UI
├── Authentication
└── 3000 more files
```

This is effectively:

```text
Monolith
```

inside a KMP project.

---

# 109. Shared Modules Should Be Cohesive

Prefer:

```text
core:network
core:database
core:security
design-system
testing
```

over:

```text
shared:everything
```

Each module should have a clear reason to exist.

---

# 110. Shared Module Size

There is no universal maximum size.

But watch for:

```text
Too many consumers
Too many responsibilities
Too many dependencies
Too many public APIs
Long build times
Frequent unrelated changes
```

These are stronger signals than file count.

---

# 111. Shared Module Change Frequency

Suppose:

```text
core:network
```

changes every day because many unrelated teams add feature APIs.

That indicates feature-specific code has leaked into the shared module.

The shared module should contain stable infrastructure.

---

# 112. Shared Module Stability

A healthy shared module tends to be:

```text
Stable
Well-tested
Widely reusable
Narrowly defined
Clearly owned
```

This does not mean it never changes.

It means changes are intentional.

---

# 113. Shared Module API Stability

The more consumers a shared module has:

```text
More consumers
    ↓
Higher compatibility cost
```

Therefore:

```text
Public API
```

should remain small.

---

# 114. Shared Module and Fan-In

If:

```text
20 features
```

depend on:

```text
core:network
```

that is normal.

If:

```text
20 features
```

depend on:

```text
shared:customer
```

investigate whether that model is truly shared.

---

# 115. Shared Module and Fan-Out

A shared module with:

```text
20 dependencies
```

may be too broad.

For example:

```text
shared:common
```

depending on:

```text
Network
Database
Security
Payments
Profile
Orders
```

is a strong architectural warning.

---

# 116. Shared Module and Stable Dependencies

A shared module should avoid depending on unstable feature modules.

Prefer:

```text
Feature → Shared
```

not:

```text
Shared → Feature
```

This keeps the dependency graph directional.

---

# 117. Shared Module and Business Logic

A shared module can contain business logic only when:

```text
The business concept is genuinely shared
+
The ownership is clear
+
The semantics are the same
```

For example:

```text
Money
Currency
```

may qualify.

But:

```text
CalculateOrderDiscount
```

belongs to Orders.

---

# 118. Shared Domain Example

```text
shared/domain
├── Money.kt
├── Currency.kt
└── CountryCode.kt
```

Potentially:

```text
features/orders/domain
├── Order.kt
└── OrderDiscountPolicy.kt
```

The boundary reflects business ownership.

---

# 119. Shared Module and Domain Language

Shared domain types should be:

```text
Stable
Well understood
Widely applicable
```

Do not move ambiguous concepts into shared simply because multiple features currently use them.

---

# 120. Shared Module and Semantic Coupling

Two features can share a type and become coupled semantically.

For example:

```text
shared/User
```

may force:

```text
Payments
Profile
Orders
```

to evolve around the same model.

Sometimes the better architecture is:

```text
Separate models
+
Explicit mapping
```

---

# 121. Shared Module and Mapping

Example:

```text
Shared Identity
       ↓
Orders
       ↓
OrderCustomer
```

The mapping is explicit.

This makes context boundaries visible.

---

# 122. Shared Module and Duplication

Architects often fear duplication too much.

Remember:

```text
Duplication
```

can be cheaper than:

```text
Coupling
```

especially when two models are likely to evolve differently.

---

# 123. Shared Module Decision Matrix

| Question | If Yes | If No |
|---|---|---|
| Multiple consumers? | Continue | Keep local |
| Same meaning? | Continue | Keep separate |
| Same ownership? | Continue | Define ownership |
| Stable contract? | Continue | Avoid premature sharing |
| Cross-cutting capability? | Shared may fit | Feature may own it |
| Platform-specific mechanism? | Platform/shared capability | Keep common |
| Business-specific? | Feature likely owns it | Shared may fit |

---

# 124. Shared Module Creation Checklist

Before creating:

```text
[ ] At least two real consumers
[ ] Same semantic meaning
[ ] Clear owner
[ ] Stable API
[ ] Clear dependency direction
[ ] No feature-specific business rules
[ ] No unnecessary platform leakage
[ ] Test strategy exists
[ ] Module name communicates purpose
[ ] Extraction has measurable value
```

---

# 125. Shared Module Extraction Checklist

When extracting existing code:

```text
1. Identify consumers
2. Identify ownership
3. Identify public API
4. Separate feature-specific code
5. Extract capability
6. Add tests
7. Migrate consumers
8. Remove old implementation
9. Update documentation
10. Add architecture rule if useful
```

# 126. Shared Module Naming

Prefer:

```text

core:database
core:observability
design-system
testing
```

Avoid:

```text
common
misc

shared-stuff
base
general
```

Names should explain responsibility.

---

# 127. Why `common` Is Often a Bad Name

Consider:

```text
common/
```

A developer asks:

> What belongs here?

Possible answers become:

```text
Anything used twice.
```

That is not an architectural rule.

Prefer semantic names.

---

# 128. Why `utils` Is Often a Bad Name

```text
utils/
```

has no natural ownership.

Therefore everything can be added.

A better question is:

```text
What capability does this code represent?
```

Then name the module after the capability.

---

# 129. Shared Module and Naming as Architecture

Compare:

```text
shared:utils
```

with:

```text
core:security
```

The second communicates:

```text
Purpose
Ownership area
Expected contents
```

Naming is part of architecture.

# 130. Shared Module and Documentation

A shared module should document:

```text
Purpose

Owner
Public API
Non-goals
Dependencies
Platform support
Testing
```

The `Non-goals` section is especially valuable.

# 131. Shared Module Non-Goals

Example:

```markdown

- Feature API definitions
- Business-specific models
- UI screens
- Vendor-specific application logic
```

This prevents future architectural drift.

# 132. Shared Module ADR

For important shared modules, an ADR can explain:

```text

Why it is shared
Why ownership is defined this way
Why alternatives were rejected
```

This protects architectural intent.

---

# 133. Shared Module and Architecture Governance

As organizations grow, shared modules become strategic infrastructure.

Changes may require:

```text
Review
Compatibility analysis
Migration plan
Consumer communication
```

especially for widely used modules.

---

# 134. Shared Module Versioning

Internal repositories may not require independent versioning.

But published shared libraries often need:

```text
Semantic versioning
Compatibility policy
Deprecation policy
Release notes
```

The more consumers, the more important version discipline becomes.

---

# 135. Shared Module and Breaking Changes

A breaking change:

```text
Old API
   ↓
Removed
```

can affect every consumer.

Prefer:

```text
Add new API
   ↓
Deprecate old API
   ↓
Migrate consumers
   ↓
Remove old API
```

when practical.

---

# 136. Shared Module and Compatibility Layers

An adapter can preserve consumers:

```text
Old API
   ↓
Compatibility Adapter
   ↓
New API
```

This can reduce migration risk.

---

# 137. Shared Module and Strangler Migration

A shared module can replace legacy infrastructure gradually:

```text
Legacy Network
       ↓
Network Abstraction
       ↓
New Network
```

Consumers migrate without changing business logic.

---

# 138. Shared Module and Platform Migration

The same strategy can support:

```text
Room → SQLDelight
Retrofit → Ktor
Vendor A → Vendor B
Android-only storage → KMP storage
```

when the abstraction boundary is meaningful.

---

# 139. Shared Module and Abstraction Cost

Abstraction is not free.

It adds:

```text
Types
Interfaces
Adapters
Indirection
Documentation
```

Create abstractions when they solve:

```text
Change
Testing
Portability
Ownership
Vendor isolation
```

not merely because interfaces look architectural.

---

# 140. Shared Module and Over-Abstraction

Bad:

```text
HttpClientProvider
HttpClientFactory
HttpClientManager
HttpClientService
IHttpClient
```

when all simply wrap one implementation.

Good architecture is not measured by interface count.

---

# 141. Shared Module and YAGNI

Do not build:

```text
future-proof shared abstraction
```

for hypothetical requirements.

Extract when:

```text
Actual reuse
+
Actual boundary
```

exists.

---

# 142. Shared Module and KMP Reuse

KMP makes sharing technically easier.

That does not mean everything should be shared.

The decision should be:

```text
Should this behavior be shared?
```

not merely:

```text
Can Kotlin share this?
```

---

# 143. KMP Sharing Spectrum

Think of sharing as a spectrum:

```text
No sharing
   │
   ▼
Shared utility
   │
   ▼
Shared capability
   │
   ▼
Shared domain logic
   │
   ▼
Shared presentation
   │
   ▼
Fully shared feature
```

Choose the appropriate level.

---

# 144. KMP Shared Logic First

Often the highest-value sharing is:

```text
Business logic
Repositories
Validation
State machines
Data transformations
```

before:

```text
Entire UI
```

This is especially useful when Android and iOS UX differs.

---

# 145. Shared Module and Native UI

Architecture:

```text
           Feature
              │
      ┌───────┴────────┐
      ▼                ▼
 Shared Logic       Native UI
      │             ┌────┴────┐
      │             ▼         ▼
      │          Android     iOS
      │
      ▼
    Domain
```

Shared modules support the common logic.

---

# 146. Shared Module and Shared UI

Alternatively:

```text
Feature
   │
   ▼
Shared UI
   │
 ┌─┴───────────┐
 ▼             ▼
Android       iOS
```

Again, the business boundary remains the feature.

---

# 147. Shared Module and Compose Multiplatform

A design system is a particularly natural shared UI module:

```text
shared/design-system
```

It can provide:

```text
Theme
Components
Typography
Spacing
Accessibility
```

Features compose those primitives into business UI.

---

# 148. Shared Module and UI Ownership

For example:

```text
Design System
└── AppButton

Orders
└── CancelOrderButton
```

The first owns:

```text
visual behavior
```

The second owns:

```text
business meaning
```

---

# 149. Shared Module and Accessibility

Accessibility primitives can be shared:

```text
Semantics
Content descriptions
Focus behavior
Touch target rules
```

Feature-specific labels and meaning remain feature-owned.

---

# 150. Shared Module and Localization Infrastructure

Shared localization infrastructure can provide:

```text
Resource loading
Locale handling
Formatting
```

Feature modules provide:

```text
Order-specific strings
Payment-specific strings
```

when resource ownership supports that structure.

---

# 151. Shared Module and Formatting

Generic formatting:

```text
Currency formatting
Date formatting
Number formatting
```

may be shared.

Business-specific formatting:

```text
OrderStatusFormatter
PaymentStatusFormatter
```

belongs to the feature.

---

# 152. Shared Module and Localization Context

Avoid a global:

```text
StringUtils
```

that contains:

```text
formatOrderStatus()
formatPaymentStatus()
formatProfileName()
```

Those behaviors belong to their contexts.

---

# 153. Shared Module and Error Infrastructure

A shared error mechanism can define:

```text
AppError
NetworkError
StorageError
```

But features should map infrastructure errors into:

```text
OrderError
PaymentError
ProfileError
```

when semantics differ.

---

# 154. Shared Module and Error Leakage

Bad:

```text
Orders UI
   ↓
HttpException
```

Better:

```text
Orders UI
   ↓
OrderError
```

The shared infrastructure error is translated at the feature boundary.

---

# 155. Shared Module and Retry Infrastructure

Generic retry infrastructure may be shared:

```text
RetryPolicy
Backoff
Timeout
```

but business operations decide whether retry is safe.

For example:

```text
GET order
```

may be retryable.

```text
Submit payment
```

may require idempotency before retry.

---

# 156. Shared Module and Networking Policy

Shared network infrastructure can provide:

```text
Timeout
Headers
Serialization
Authentication
Logging
Retry mechanism
```

But the feature can still define:

```text
Request-specific semantics
```

---

# 157. Shared Module and Authentication Tokens

A shared authentication module may provide:

```text
TokenProvider
TokenRefresh
SecureStorage
```

Features consume authenticated networking without handling raw credentials.

---

# 158. Shared Module and Authorization

Authorization should remain closer to business ownership:

```text
Orders
→ Can user cancel?

Payments
→ Can user refund?

Inventory
→ Can user adjust stock?
```

Shared infrastructure can provide identity and claims.

---

# 159. Shared Module and Feature Flags

A shared flag engine provides:

```text
Evaluation
Remote config
Caching
Persistence
```

Feature owns:

```text
Meaning of its flag
```

---

# 160. Shared Module and Remote Configuration

Remote configuration is infrastructure.

For example:

```text
core:config
```

can retrieve:

```text
Configuration values
```

but:

```text
Order max cancellation time
```

should be interpreted by Orders.

---

# 161. Shared Module and Policy Ownership

A shared module should avoid interpreting feature-specific policy.

Example:

```text
Network timeout
```

→ shared infrastructure.

```text
Order cancellation timeout
```

→ Orders.

---

# 162. Shared Module and Business Policy

Policies are often where shared modules become dangerous.

If:

```text
core:policy
```

contains:

```text
PaymentPolicy
OrderPolicy
InventoryPolicy
```

it has become a business logic dumping ground.

Keep policies near their owners.

---

# 163. Shared Module and Dependency Injection Frameworks

Hilt, Koin, Dagger, or another DI system may be used.

But the shared module should not necessarily expose the entire DI container.

Prefer:

```text
Explicit contracts
+
Composition
```

over global service lookup.

---

# 164. Shared Module and Service Locator

Avoid:

```kotlin
ServiceLocator.get<PaymentGateway>()
```

inside shared business logic.

This hides dependencies.

Constructor injection is usually easier to reason about.

---

# 165. Shared Module and Build Logic

Build logic is another form of sharing.

For example:

```text
build-logic
├── kmp-library
├── android-library
├── compose-library
└── testing
```

This shares:

```text
Build configuration
```

rather than application runtime code.

---

# 166. Build Logic Is Not Runtime Shared Code

Keep the distinction:

```text
build-logic
→ How modules are built

runtime modules
→ How applications behave
```

Do not mix them conceptually.

---

# 167. Shared Module and Version Catalog

A version catalog can centralize:

```text
Library versions
Plugin versions
Dependency aliases
```

For example:

```toml
[libraries]
ktor-client = { ... }
kotlin-test = { ... }
```

This is build-level sharing.

It does not create runtime coupling.

---

# 168. Shared Modules and Dependency Management

A shared module should avoid pulling in large dependency trees unnecessarily.

For example:

```text
core:logging
```

should not depend on:

```text
database
network
payments
```

unless genuinely required.

---

# 169. Shared Module and Minimal Dependencies

A useful principle:

> **A shared module should be easier to consume than the capability it replaces.**

If using:

```text
core:network
```

requires 15 unrelated dependencies, the abstraction may be too broad.

---

# 170. Shared Module and Dependency Weight

Shared modules have amplified impact.

If:

```text
20 features
```

depend on:

```text
core:large-module
```

then its dependency weight affects many consumers.

Keep shared modules lean.

---

# 171. Shared Module and API Surface

Measure conceptually:

```text
Internal implementation
████████████████████████

Public API
████
```

The goal is not literally a tiny API in every case.

The goal is:

```text
Public surface << Implementation surface
```

when encapsulation is appropriate.

---

# 172. Shared Module and Encapsulation

A shared module should behave like a service boundary:

```text
Consumer
   │
   ▼
Public Capability
   │
   ▼
Hidden Implementation
```

This allows implementation evolution.

---

# 173. Shared Module and Testing Boundaries

Tests should validate:

```text
Public behavior
```

rather than:

```text
Every private implementation detail
```

This makes refactoring safer.

---

# 174. Shared Module and Contract Tests

For example:

```text
SecureStorageContractTest
```

can be applied to:

```text
AndroidSecureStorage
IosSecureStorage
FakeSecureStorage
```

This verifies consistent behavior across implementations.

---

# 175. Shared Module and Platform Consistency

A KMP shared capability should have:

```text
Same semantic contract
```

across platforms.

The implementation can differ.

For example:

```text
Android → Keystore
iOS → Keychain
```

but:

```text
put/get semantics
```

should remain consistent.

---

# 176. Shared Module and Platform Differences

Do not pretend platforms are identical.

For example:

```text
Background execution
Permissions
Biometrics
File systems
Push notifications
```

may differ significantly.

The abstraction should expose:

```text
Common semantic behavior
```

and allow platform-specific differences where necessary.

---

# 177. Shared Module and Capability Design

A good capability interface is:

```text
Small
Meaningful
Stable
Testable
Platform-neutral
```

Example:

```kotlin
interface BiometricAuthenticator {
    suspend fun authenticate(
        reason: String
    ): AuthenticationResult
}
```

---

# 178. Shared Module and Capability Granularity

Avoid:

```kotlin
interface PlatformServices {
    fun camera()
    fun location()
    fun bluetooth()
    fun biometrics()
    fun notifications()
    fun storage()
}
```

This creates a giant platform abstraction.

Prefer focused capabilities.

---

# 179. Shared Module and Interface Segregation

Better:

```text
SecureStorage
BiometricAuthenticator
LocationProvider
PushNotificationSender
```

Consumers depend only on what they need.

---

# 180. Shared Module and Capability Ownership

A capability should have an owner.

For example:

```text
SecureStorage → Security/Platform Team
Analytics → Observability Team
Design System → Design System Team
Network → Platform Team
```

Ownership prevents uncontrolled growth.

---

# 181. Shared Module and Team Boundaries

Shared modules often become:

```text
Platform Team responsibility
```

because many feature teams depend on them.

This means platform teams should prioritize:

```text
Backward compatibility
Documentation
Migration support
Reliability
```

# 182. Shared Module and Consumer Support

```text

```

may need migration.

```text

Migration guide
Deprecation period
Examples
```

for important changes.

# 185. Shared Module and "Do Not Add"

An especially useful README section:

```markdown
## Do Not Add

Do not add:

- Feature-specific models
- Feature-specific business rules
- Screen implementations
- Vendor-specific consumer logic
- Unrelated utilities
```

This protects the module.

---

# 186. Shared Module and Architecture Drift

Without explicit boundaries:

```text
Day 1
Shared = Network

Day 100
Shared = Network + Models

Day 300
Shared = Network + Models + Business Logic

Day 600
Shared = Entire Application
```

Architecture drift happens gradually.

Regular reviews prevent it.

---

# 187. Shared Module and Review Questions

When reviewing a new shared module change, ask:

```text
Why is this shared?
Who owns it?
Who consumes it?
Could it remain feature-local?
Does it introduce business coupling?
Does it expose vendor/platform details?
Does it increase dependency weight?
```

---

# 188. Shared Module and Architecture Smells

Warning signs:

```text
🚨 `shared:common`
🚨 `shared:utils`
🚨 Global models
🚨 Global state
🚨 Feature business rules in Core
🚨 Feature APIs in Network
🚨 Vendor SDK exposed publicly
🚨 Shared module depends on features
🚨 Every feature depends on everything
```

---

# 189. Shared Module Smell: `common`

```text
common/
```

usually means:

```text
No ownership boundary.
```

Replace it with semantic modules:

```text
network
security
database
observability
design-system
```

---

# 190. Shared Module Smell: `utils`

If:

```text
utils/
```

contains unrelated functions, split by responsibility.

For example:

```text
DateFormatter
```

might belong to:

```text
core:localization
```

while:

```text
OrderFormatter
```

belongs to:

```text
orders
```

---

# 191. Shared Module Smell: Global Models

If every feature imports:

```text
shared:models
```

review whether the models represent:

```text
Actual shared concepts
```

or merely:

```text
Convenient DTO reuse
```

---

# 192. Shared Module Smell: Core Business Logic

If:

```text
core
```

contains:

```text
calculateOrderDiscount()
```

then Core is no longer infrastructure.

Move it to:

```text
Orders
```

unless the rule genuinely belongs to a shared domain.

---

# 193. Shared Module Smell: Feature Imports Vendor SDK

If:

```text
Orders
```

imports:

```text
Stripe SDK
```

directly, vendor coupling exists.

Introduce:

```text
PaymentGateway
```

and isolate the vendor.

---

# 194. Shared Module Smell: Shared Module Imports Features

If:

```text
core:network
```

imports:

```text
features:orders
```

the dependency direction is broken.

Reverse the dependency or redesign the boundary.

---

# 195. Shared Module Smell: Giant Shared Module

If:

```text
shared
```

contains:

```text
Network
Database
Security
UI
Business Logic
Features
```

split it according to actual capabilities and ownership.

---

# 196. Shared Module Smell: Premature Abstraction

If only one feature uses:

```text
CapabilityX
```

there may be no reason to create:

```text
shared:capability-x
```

yet.

Wait for real reuse unless there is another strong boundary reason.

---

# 197. Shared Module Smell: Accidental Reuse

Code should not become shared just because:

```text
"Someone else might need it."
```

This creates premature coupling.

Share based on:

```text
Actual requirement
+
Stable semantics
```

---

# 198. Shared Module Smell: Copy-Paste Instead of Boundary

Sometimes teams duplicate a small utility because sharing it would create excessive coupling.

That can be correct.

The goal is not:

```text
Zero duplication
```

The goal is:

```text
Healthy coupling
```

---

# 199. Shared Module and the Duplication vs Coupling Trade-off

Think:

```text
Small duplication
       │
       ▼
Independent evolution

Shared abstraction
       │
       ▼
Synchronized evolution
```

Choose based on expected change.

# 200. Shared Module and Stable Abstractions

A good shared abstraction reduces synchronized change:

```text
Consumer A
Consumer B
Consumer C
      │
      ▼
Stable Contract
      │
      ▼
Changing Implementation
```

That is the real value of abstraction.

# 201. Shared Module and Architecture Evolution

A shared module can start simple:

```text
core:network
```

and later split:

```text
core:network
core:serialization
core:auth
```

when independent ownership or build boundaries become useful.

Do not split preemptively.

# 202. Shared Module and Modularization Level

There are multiple levels:

```text
Package
   ↓
Gradle Module
   ↓
Library
   ↓
Published Artifact
```

Not every shared capability needs to become a published library.

Choose the smallest useful boundary.

# 203. Shared Module and Package vs Module

Use a package when:

```text
Same ownership
Same lifecycle
Same build boundary
```

Use a Gradle module when:

```text
Independent dependency boundary
Build isolation
Ownership boundary
Reuse
API encapsulation
```

provide meaningful value.


# 263. Shared Module Decision Example

Requirement:

> Every feature needs an `AppViewModel`.

Analysis:


| Area | Owns | Should Avoid |
|---|---|---|

| Core Database | DB infrastructure | Feature business rules |
| Core Security | Security capabilities | Feature authorization rules |
| Observability | Logging/analytics mechanism | Business events |
| Design System | UI primitives | Business screens |
| Testing | Test infrastructure | Production logic |
| Contracts | Stable capabilities | Implementations |
| Platform | Native mechanisms | Business rules |
| Features | Business capabilities | Generic infrastructure |

# 278. Shared Module Golden Rules

Remember:

```text
1. Shared does not mean global.
2. Share meaning, not just code.
3. Shared modules need owners.
4. Shared modules need narrow APIs.
5. Feature-specific business logic stays in features.
6. Core should not depend on features.
7. Vendor SDKs should remain behind boundaries.
8. Platform mechanisms should remain isolated.
9. Avoid giant `common` and `utils` modules.
10. Duplication can be cheaper than coupling.
11. KMP makes sharing possible; architecture decides what to share.
12. Extract shared modules because of real value, not because code can be reused.
13. Use `internal` to protect implementation details.
14. Use `api` vs `implementation` deliberately.
15. Prefer capability-based abstractions.
16. Keep shared modules cohesive.
17. Treat widely consumed shared APIs as contracts.
18. Test shared capabilities independently.
19. Keep business ownership explicit.
20. Optimize for controlled change, not maximum reuse.
```

---

# 279. Shared Module Checklist

Before approving a shared module:

```text
[ ] Is there more than one real consumer?
[ ] Do consumers need the same semantics?
[ ] Is ownership clear?
[ ] Is the module cohesive?
[ ] Is the public API small?
[ ] Are implementation details hidden?
[ ] Are dependencies directional?
[ ] Does it avoid feature-specific business logic?
[ ] Does it avoid unnecessary platform leakage?
[ ] Is KMP sharing actually useful?
[ ] Are tests available?
[ ] Is documentation available?
[ ] Are non-goals documented?
[ ] Does it improve change isolation?
[ ] Does it justify a Gradle module?
```

# 284. The Most Important KMP Lesson

KMP gives you the ability to share:

```text
Code
Business Logic
State
Infrastructure
UI
```

But architecture asks a different question:

> **What should be shared?**

That decision must come from:

```text
Business meaning
Ownership
Change frequency
Platform differences
Dependency direction
Testing needs
Team boundaries
```

not from technical convenience alone.

---

# 285. Final Takeaways

A shared module should be treated as a **stable architectural capability**, not as a storage box for reusable code.

Good:

```text
core:network
core:security
core:database
core:observability
design-system
testing
```

Potentially good:

```text
shared:domain
contracts:payment
```

when ownership and semantics are clear.

Dangerous:

```text
shared:models
shared:utils
shared:common
shared:everything
```

because these names rarely communicate boundaries.

The strongest shared-module architecture follows:

```text
                 BUSINESS FEATURES
                         │
                         ▼
               SHARED CAPABILITIES
                         │
                         ▼
                  INFRASTRUCTURE
                         │
                         ▼
                    PLATFORM
                         │
                         ▼
                     VENDORS
```

And the most important principle is:

> [!IMPORTANT]
> **Share capabilities, not implementation details. Share stable meaning, not accidental code similarity.**

A mature KMP architecture does not attempt to maximize shared code.

It attempts to maximize:

```text
Useful sharing
+
Low coupling
+
Clear ownership
+
Stable boundaries
+
Controlled change
```

That is what makes shared modules valuable as the KMP project grows.
