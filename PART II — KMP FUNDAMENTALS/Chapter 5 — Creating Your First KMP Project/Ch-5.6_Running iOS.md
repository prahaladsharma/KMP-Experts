# Chapter 5 — Creating Your First KMP Project

## Part 6 — Running iOS

> **Running the iOS target is where a KMP project proves that shared Kotlin can cross the Android boundary and become part of a native Apple application.**

The Android application is already running.

Now we move to the second platform:

```text
iOS
```

For an Android developer, this is where the workflow becomes unfamiliar.

The project still contains:

```text
Kotlin
Gradle
Shared Module
commonMain
```

But the final application is an Apple application built with Apple's toolchain.

The basic relationship is:

```text
                 KMP Shared Module
                         │
                         ▼
                    Kotlin/Native
                         │
                         ▼
                 Native Framework
                         │
                         ▼
                       Xcode
                         │
                         ▼
                    iOS Application
```

The goal of this part is to understand that flow and successfully run the iOS target.

---

# 1. What Are We Trying to Prove?

The first iOS run should prove:

```text
✓ iOS tooling is available
✓ Shared KMP code can compile for iOS
✓ Native output can be produced
✓ Xcode can consume the shared output
✓ iOS application can launch
✓ Shared Kotlin code can execute from the iOS application
```

The complete flow is:

```text
commonMain
    │
    ▼
KMP Shared Module
    │
    ▼
Kotlin/Native
    │
    ▼
Native Output
    │
    ▼
Xcode
    │
    ▼
iOS Application
    │
    ▼
Simulator / Device
```

---

# 2. iOS Is Still a Native Apple Application

This is the first concept to understand.

KMP does not turn the iOS application into an Android-style application.

The iOS application remains an Apple application.

It can use:

```text
Swift
SwiftUI
UIKit
Xcode
Apple SDKs
Apple signing
Apple resources
```

KMP contributes:

```text
Shared Kotlin Code
```

The architecture is therefore:

```text
              iOS Application
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
      Native UI             Shared KMP
          │                     │
          └──────────┬──────────┘
                     ▼
                  Runtime
```

---

# 3. The Apple Development Environment

To build and run the iOS target, you need an Apple development environment.

For the normal iOS development workflow this means:

```text
macOS
+
Xcode
+
Apple SDKs
```

The exact supported Xcode and Kotlin versions change over time.

For a real project, always verify the versions supported by your current Kotlin Multiplatform and Apple tooling.

# 4. Why macOS Matters

Android development can be performed on many operating systems.

iOS development has Apple's platform requirements.

Conceptually:

```text

   │

   ├── macOS
   └── Linux
```

while:

```text
iOS Development
       │
       ▼
     macOS
       │
       ▼
     Xcode
```

This is not something KMP removes.

It is part of the Apple platform development model.

```text

```

---

# 7. KMP vs Xcode

A useful distinction is:

| KMP | Xcode |
|---|---|
| Shared Kotlin code | iOS application |
| Kotlin/Native compilation | Apple application build |
| Common business logic | Swift / SwiftUI / UIKit |
| Multiplatform source sets | Apple resources |
| Shared dependencies | Apple frameworks |
| Native Kotlin output | Signing and packaging |

They work together.

One does not replace the other.

Let's use the same simple shared class:



```text

       │
       ▼

       │
       ▼
```

The shared Kotlin code is compiled for the iOS target and exposed through the generated native integration.

# 22. This Is the KMP Value Proposition

The goal is not:

```text
One UI everywhere
```

The goal is:

```text
Share what should be shared.
Keep what should remain native.
```

For example:

```text
Shared:
✓ Business rules
✓ Validation
✓ Domain models
✓ Networking
✓ Repository logic

Android:
✓ Android UI
✓ Android permissions
✓ Android-specific services

iOS:
✓ SwiftUI/UIKit
✓ Apple-specific integrations
✓ iOS-specific services
```

# 28. Simulator Architecture

The simulator target must match the development environment.

On modern Apple Silicon Macs, simulator targets commonly use:

```text
arm64
```

while older Intel-based environments use different simulator architecture requirements.

The project tooling normally handles the appropriate target configuration when configured correctly.

The important idea is:

```text
Machine Architecture
        +
Simulator Architecture
        +
KMP Target
```

must be compatible.

# 33. A Platform-Specific API

# 34. Shared Code Does Not Mean Shared Platform APIs

This distinction is critical.

You can share:

```text
Behavior
```

without sharing:

```text
Platform Implementation
```

For example:

```text
SecureStorage
```

can be a shared abstraction.

But:

```text
Keychain
```

is an Apple implementation detail.

Similarly:

```text
Encrypted Storage
```

could be shared conceptually while the actual implementation remains platform-specific.

This is the moment when the KMP value becomes tangible.

Before KMP:

```text

      +
iOS Logic
```

Potentially:

```text

```

With KMP:

```text
                 Shared Logic
                 /          \
                ▼            ▼
            Android         iOS
```

One change in:

```text

```

That is the productivity opportunity KMP creates.

# 48. But One Change Can Also Break Both

This is the other side of the equation.

If:

```text

```

contains critical business logic, a change there can affect:

```text

+
iOS
```

Therefore shared code increases reuse **and** increases the blast radius of changes.

This is why:

```text

Architecture
```

A shared module is not merely:



That means teams should treat shared code as a carefully owned contract.

For example:

```text

Authentication rules
Order state

Validation
```

can affect both applications.

# 52. Common Beginner Mistakes

### Mistake 1 — Thinking KMP Replaces Xcode

It doesn't.

Xcode remains part of the iOS application workflow.

---

### Mistake 2 — Treating iOS as an Android Target With a Different UI

The platform has different:

```text
APIs
Runtime behavior
Tooling
Packaging
Lifecycle
```

Respect those differences.

---

### Mistake 3 — Sharing Platform APIs

Don't put:

```text
UIKit
UIApplication
Android Context
```

into common business logic.

---

### Mistake 4 — Testing Only Android

A KMP project is not validated by an Android-only run.

Validate iOS early.

---

### Mistake 5 — Assuming Every Kotlin API Has the Same Swift API

Kotlin/Native interoperability has rules.

Design shared APIs with Swift consumption in mind.

---

### Mistake 6 — Maximizing Shared Code

More shared code does not automatically mean better architecture.

Share where the behavior should actually be shared.

# Chapter Takeaways

> [!TIP]
> **Running iOS is not about making an iPhone behave like Android. It is about compiling shared Kotlin into native iOS-compatible output and integrating it into a real Apple application.**

Remember:

1. iOS remains a native Apple application.
2. Xcode remains an important part of the iOS development workflow.
3. KMP does not replace Apple's SDKs, signing, or application packaging.
4. The shared KMP module is compiled for the iOS target using Kotlin/Native.
5. The resulting native output is integrated into the iOS application.
6. Simulator and physical-device builds can require different target configurations.
7. `commonMain` contains code intended to be shared across platforms.
8. `iosMain` contains iOS-specific shared-module implementation.
9. Swift and SwiftUI can consume appropriately exposed KMP APIs.
10. Shared Kotlin code should be designed carefully when exposed to Swift.
11. Android success does not prove iOS success.
12. iOS should be validated early when it is a product target.
13. Platform APIs should remain behind platform boundaries.
14. Native integrations such as Keychain or Apple-specific services can remain iOS-specific.
15. Shared code should be measured by responsibility, not by percentage.
16. A shared change can affect both Android and iOS.
17. Shared behavior should therefore have strong tests.
18. Native platform tests remain necessary for platform-specific behavior.
19. The first iOS run establishes a real Apple runtime baseline.
20. Android + iOS running the same shared behavior is the first genuine multiplatform milestone.
