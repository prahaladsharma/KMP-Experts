## 1. Why Mapping Matters

A production application rarely has only one representation of a piece of data.

A backend may return a JSON object with fields designed around its API contract. A local database may store the same information in a structure optimized for queries. The application domain may need a model that expresses business meaning. The UI may need a presentation model tailored to one screen.

These models may contain similar values, but they do not necessarily have the same responsibilities.

Consider a product returned by an API:

```json
{
  "product_id": "P-1001",
  "display_name": "Wireless Scanner",
  "price_minor": 129900,
  "is_available": true
}
```

The API representation is optimized for communication. The domain model should express the application's concept of a product. The database entity should fit persistence requirements.

If the UI directly consumes the API DTO, a backend field rename can ripple through ViewModels and screens. If the database entity is also used as the domain model, a schema migration can become an application-wide refactoring.

A mapper creates an explicit translation between these representations.

```text
Backend JSON
     |
     v
 ProductDto
     |
     | DTO -> Domain mapper
     v
   Product
     |
     | Domain -> UI mapper
     v
 ProductUiModel
```

For persistence, another mapping path may exist:

```text
ProductDto
    |
    | DTO -> Entity
    v
ProductEntity
    |
    | Entity -> Domain
    v
  Product
```

The mapper makes the transformation visible, testable, and independent of the source model's structure.

### 1.1 Mapping protects boundaries

Without mapping, external models can become internal dependencies:

```kotlin
class ProductViewModel(
    private val repository: ProductRepository,
) {
    fun displayName(product: ProductDto): String {
        return product.display_name
    }
}
```

The ViewModel now knows the API's naming convention.

A cleaner boundary returns a domain model:

```kotlin
class ProductViewModel(
    private val repository: ProductRepository,
) {
    fun displayName(product: Product): String {
        return product.name
    }
}
```

The benefit is not merely cleaner property names. The application can evolve its internal model without requiring the backend or database schema to evolve at the same time.

## 2. What Is a Mapper?

A mapper is a function or component that converts one representation of data into another.

Examples:

- `ProductDto` to `Product`.
- `ProductEntity` to `Product`.
- `Product` to `ProductEntity`.
- `Product` to `ProductRequestDto`.
- `Product` to `ProductUiModel`.

A mapper should normally be deterministic: the same input produces the same output, assuming the transformation does not intentionally depend on an external value such as the current time or locale.

A simple mapper:

```kotlin
fun ProductDto.toDomain(): Product {
    return Product(
        id = product_id,
        name = display_name,
        isAvailable = is_available,
    )
}
```

### 2.1 Mapping is not serialization

These operations solve different problems.

| Mapping | Serialization |
|---|---|
| Converts one application representation into another | Converts an object into a wire or storage format |
| Example: DTO to domain model | Example: Kotlin object to JSON |
| Expresses application-level translation | Expresses encoding and decoding rules |
| Often implemented with Kotlin functions | Often implemented with serialization libraries |

A serialization library may create a `ProductDto` from JSON. A mapper then converts that DTO into a `Product` domain model.

```text
JSON
  |
  | Deserialization
  v
ProductDto
  |
  | Mapping
  v
Product
```

### 2.2 Mapping is not validation

Mapping may perform simple normalization or reject structurally unusable data, but it should not silently become the entire business validation layer.

For example:

- Converting a backend field into a domain property is mapping.
- Parsing a date string into `Instant` is mapping or parsing.
- Checking whether a user is eligible to place an order is business validation.
- Deciding whether a stock quantity is sufficient for a requested order is domain policy.

Keep these responsibilities explicit.

## 3. The Models a Mapper Connects

A well-structured application may have several models representing the same concept.

| Model | Responsibility | Example |
|---|---|---|
| DTO | Represents the API contract | `ProductDto` |
| Entity | Represents persisted data | `ProductEntity` |
| Domain model | Represents application meaning | `Product` |
| UI model | Represents screen presentation | `ProductUiModel` |
| Request model | Represents an outgoing API payload | `UpdateProductRequest` |

### 3.1 DTO

A Data Transfer Object reflects the remote API's structure.

```kotlin
@Serializable
data class ProductDto(
    @SerialName("product_id")
    val productId: String,
    @SerialName("display_name")
    val displayName: String,
    @SerialName("price_minor")
    val priceMinor: Long,
    @SerialName("is_available")
    val isAvailable: Boolean,
)
```

It may contain serialization annotations, backend-specific field names, and nullable fields dictated by the API.

### 3.2 Entity

An entity reflects the persistence structure.

```kotlin
data class ProductEntity(
    val id: String,
    val name: String,
    val priceMinor: Long,
    val available: Boolean,
    val lastSyncedAtMillis: Long?,
)
```

The entity may include local-only fields such as synchronization timestamps, pending changes, or database keys.

### 3.3 Domain model

A domain model represents the concept used by application logic.

```kotlin
data class Product(
    val id: ProductId,
    val name: String,
    val price: Money,
    val availability: Availability,
)

@JvmInline
value class ProductId(val value: String)

data class Money(
    val minorUnits: Long,
)

enum class Availability {
    AVAILABLE,
    UNAVAILABLE,
}
```

The domain model does not need to mirror the API or database.

### 3.4 UI model

A UI model can contain values formatted for a specific screen.

```kotlin
data class ProductUiModel(
    val id: String,
    val title: String,
    val formattedPrice: String,
    val availabilityLabel: String,
    val canAddToCart: Boolean,
)
```

The UI model may depend on locale, currency formatting, or design decisions. Those concerns usually belong in a presentation mapper or formatter rather than in a shared domain mapper.

### 3.5 Do not create every model automatically

Separate models are useful when they have different reasons to change.

If a small feature has no persistence layer and no meaningful difference between the API and application model, a DTO-to-domain layer may be unnecessary. Avoid creating four nearly identical classes simply to satisfy a folder convention.

The purpose of mapping is to protect real boundaries—not to increase file count.

## 4. Where Should Mapping Happen?

Mapping should happen at the boundary where one representation is converted into another.

A common arrangement:

```text
                  Presentation
                      |
                      v
                 Domain Model
                      ^
                      |
              Repository Contract
                      ^
                      |
               Data Repository
                 /         \
                v           v
             Remote       Local
             Source       Source
                |           |
                v           v
              DTO        Entity
                \           /
                 \         /
                  Mappers
```

### 4.1 DTO to domain

Usually performed in the data layer, close to the remote data source or repository.

```kotlin
val product: Product = dto.toDomain()
```

### 4.2 Entity to domain

Usually performed when local data is exposed to the application.

```kotlin
val product: Product = entity.toDomain()
```

### 4.3 Domain to entity

Usually performed before saving application data to local persistence.

```kotlin
val entity: ProductEntity = product.toEntity()
```

### 4.4 Domain to request DTO

Usually performed before sending a command to a backend.

```kotlin
val request: UpdateProductRequest = product.toUpdateRequest()
```

### 4.5 Domain to UI model

Usually performed in the presentation layer, often in a ViewModel, presenter, or dedicated UI mapper.

```kotlin
val uiModel: ProductUiModel = product.toUiModel()
```

Do not put screen-specific labels and localized strings into a shared repository mapper. That couples data access to presentation requirements.

## 5. Extension Functions as Mappers

For many Kotlin projects, extension functions are a simple and readable mapping technique.

### 5.1 Basic extension mapper

```kotlin
fun ProductDto.toDomain(): Product {
    return Product(
        id = ProductId(productId),
        name = displayName,
        price = Money(priceMinor),
        availability = if (isAvailable) {
            Availability.AVAILABLE
        } else {
            Availability.UNAVAILABLE
        },
    )
}
```

Usage:

```kotlin
val domainProduct = productDto.toDomain()
```

Benefits:

- Concise and discoverable.
- No mapper object is required for simple conversions.
- Easy to unit test.
- Works naturally in common Kotlin code.
- Keeps transformation close to the source model.

### 5.2 Reverse mapping

```kotlin
fun Product.toEntity(): ProductEntity {
    return ProductEntity(
        id = id.value,
        name = name,
        priceMinor = price.minorUnits,
        available = availability == Availability.AVAILABLE,
        lastSyncedAtMillis = null,
    )
}
```

### 5.3 Keep extension functions focused

Avoid one extension function that performs unrelated tasks:

```kotlin
// Avoid combining mapping, network access, storage, and business workflows.
suspend fun ProductDto.toProductAndSave(
    database: ProductDatabase,
    api: ProductApi,
): Product {
    // Too many responsibilities for a mapper.
}
```

A mapper should transform values. It should not secretly make network calls, read databases, or mutate application state.

### 5.4 Avoid ambiguous extension names

Prefer names that make the target representation clear:

- `toDomain()`
- `toEntity()`
- `toDto()`
- `toRequest()`
- `toUiModel()`

When several modules define similarly named types, use explicit imports or dedicated mapper objects to avoid ambiguity.

## 6. DTO to Domain Mapping

The most common mapping path is from an API DTO into a domain model.

### 6.1 Different names

Backend naming may use snake case while Kotlin uses camel case.

```kotlin
@Serializable
data class UserDto(
    @SerialName("user_id")
    val userId: String,
    @SerialName("full_name")
    val fullName: String,
    @SerialName("email_address")
    val emailAddress: String,
)

data class User(
    val id: String,
    val name: String,
    val email: EmailAddress,
)

@JvmInline
value class EmailAddress(val value: String)

fun UserDto.toDomain(): User {
    return User(
        id = userId,
        name = fullName,
        email = EmailAddress(emailAddress),
    )
}
```

The domain model uses names that make sense inside the application.

### 6.2 Combining fields

The API may split information across several fields while the domain model groups it into a value object.

```kotlin
@Serializable
data class AddressDto(
    val street: String?,
    val city: String?,
    val postalCode: String?,
)

data class Address(
    val street: String,
    val city: String,
    val postalCode: String?,
)

fun AddressDto.toDomain(): Address {
    return Address(
        street = street.orEmpty(),
        city = city.orEmpty(),
        postalCode = postalCode,
    )
}
```

This example assumes an empty street or city is an acceptable domain representation. If those fields are required, use a validation result rather than silently replacing missing values.

### 6.3 Splitting one API field into domain values

A backend may return a combined display name:

```kotlin
data class CustomerDto(
    val displayName: String,
)
```

The domain may require separate values:

```kotlin
data class Customer(
    val firstName: String,
    val lastName: String,
)
```

Do not split names using a simplistic whitespace rule unless the product requirements support it. Names have cultural and formatting variations. Sometimes the domain should retain a single display name instead.

Mapping decisions should be driven by the meaning and guarantees of the data, not by assumptions about strings.

## 7. Entity to Domain Mapping

Local entities often contain fields that the domain does not need.

```kotlin
data class CartItemEntity(
    val rowId: Long,
    val productId: String,
    val productName: String,
    val quantity: Int,
    val syncStatus: String,
    val updatedAtMillis: Long,
)

data class CartItem(
    val productId: ProductId,
    val productName: String,
    val quantity: Int,
)
```

Mapper:

```kotlin
fun CartItemEntity.toDomain(): CartItem {
    return CartItem(
        productId = ProductId(productId),
        productName = productName,
        quantity = quantity,
    )
}
```

The database row identifier and sync metadata remain persistence concerns.

### 7.1 Entity fields that matter to the domain

Sometimes a persistence field carries meaningful application state. For example, a pending operation may need to be visible to the UI.

Do not discard it automatically. Decide whether it belongs in the domain model, a synchronization status model, or a presentation-specific model.

```kotlin
enum class SyncState {
    SYNCED,
    PENDING,
    FAILED,
}
```

Mapping a database string to this enum is preferable to allowing arbitrary storage strings to spread through the application.

### 7.2 Database schema changes should remain local

If a database changes from one column to two columns, only the entity and its mapper should need adjustment when the domain concept remains unchanged.

That is one of the practical benefits of a mapping boundary.

## 8. Domain to DTO and Entity Mapping

Mapping is not always one-way. Applications often need to convert domain values into request payloads or persistence models.

### 8.1 Domain to request DTO

```kotlin
@Serializable
data class UpdateProductRequest(
    @SerialName("display_name")
    val displayName: String,
    @SerialName("price_minor")
    val priceMinor: Long,
)

fun Product.toUpdateRequest(): UpdateProductRequest {
    return UpdateProductRequest(
        displayName = name,
        priceMinor = price.minorUnits,
    )
}
```

Do not send domain-only values to the backend unless the API contract expects them.

### 8.2 Domain to entity

```kotlin
fun Product.toEntity(): ProductEntity {
    return ProductEntity(
        id = id.value,
        name = name,
        priceMinor = price.minorUnits,
        available = availability == Availability.AVAILABLE,
        lastSyncedAtMillis = null,
    )
}
```

### 8.3 Why request DTOs may differ from response DTOs

An API may return server-generated fields such as:

- Database identifier.
- Creation timestamp.
- Server-calculated price.
- Permissions.
- Audit metadata.

Those values should not necessarily appear in a create request.

Separate request and response models when their contracts differ. Reusing one DTO for every operation can lead to sending fields the backend should own.

### 8.4 Partial updates

A PATCH request may distinguish between:

- Field not provided: leave unchanged.
- Field provided as `null`: clear the value.
- Field provided with a value: update it.

A nullable property alone may not represent all three states. Use an explicit update-field wrapper or request representation when the API contract requires this distinction.

```kotlin
sealed interface FieldUpdate<out T> {
    data object Unchanged : FieldUpdate<Nothing>
    data object Clear : FieldUpdate<Nothing>
    data class Set<T>(val value: T) : FieldUpdate<T>
}
```

This is an application-defined type. Its serializer must encode the backend's exact PATCH semantics.

## 9. Nested Objects and Collections

Real API responses are rarely flat. A mapper should translate nested models recursively and keep each transformation focused.

### 9.1 Nested DTOs

```kotlin
@Serializable
data class OrderDto(
    val orderId: String,
    val customer: CustomerDto,
    val items: List<OrderItemDto>,
)

@Serializable
data class CustomerDto(
    val customerId: String,
    val name: String,
)

@Serializable
data class OrderItemDto(
    val productId: String,
    val quantity: Int,
)
```

Domain models:

```kotlin
data class Order(
    val id: String,
    val customer: Customer,
    val items: List<OrderItem>,
)

data class Customer(
    val id: String,
    val name: String,
)

data class OrderItem(
    val productId: String,
    val quantity: Int,
)
```

Mappers:

```kotlin
fun CustomerDto.toDomain() = Customer(
    id = customerId,
    name = name,
)

fun OrderItemDto.toDomain() = OrderItem(
    productId = productId,
    quantity = quantity,
)

fun OrderDto.toDomain() = Order(
    id = orderId,
    customer = customer.toDomain(),
    items = items.map(OrderItemDto::toDomain),
)
```

The parent mapper delegates nested transformations to the relevant child mappers.

### 9.2 Collections

Kotlin's `map` is often all that is needed:

```kotlin
fun List<ProductDto>.toDomain(): List<Product> {
    return map(ProductDto::toDomain)
}
```

For a single object:

```kotlin
val product = dto.toDomain()
```

For a list:

```kotlin
val products = response.products.map(ProductDto::toDomain)
```

### 9.3 Preserve ordering unless the contract says otherwise

Do not sort or deduplicate a collection during mapping unless that is part of the defined transformation.

If the backend returns a ranked list, changing its order can change product behavior. If duplicates are invalid, validate or normalize them explicitly rather than silently hiding them.

### 9.4 Large collections

For very large datasets, consider where mapping occurs and whether the application should process pages or database streams rather than materializing everything at once.

Mapping itself is usually inexpensive, but allocating multiple complete copies of a large collection can increase memory pressure.

## 10. Nullability, Defaults, and Missing Fields

Nullability is one of the most important mapping concerns because external data may be incomplete, inconsistent, or versioned independently of the application.

### 10.1 Nullable DTO field

```kotlin
@Serializable
data class ProfileDto(
    val id: String,
    val nickname: String?,
)
```

Domain model:

```kotlin
data class Profile(
    val id: String,
    val nickname: String,
)
```

Mapper:

```kotlin
fun ProfileDto.toDomain(): Profile {
    return Profile(
        id = id,
        nickname = nickname.orEmpty(),
    )
}
```

This is correct only if an empty nickname is a valid application meaning. If the distinction between unknown and empty matters, preserve nullability.

### 10.2 Missing and explicit null are not always the same

A JSON field may be:

```json
{}
```

or:

```json
{ "nickname": null }
```

Depending on the serializer configuration and DTO declaration, a missing field may use a default, fail decoding, or be treated differently from explicit `null`.

The mapper receives the deserialized model, not the original JSON syntax. If the application needs to distinguish missing from explicit null, the DTO must preserve that distinction during deserialization.

### 10.3 Defaults should be intentional

```kotlin
@Serializable
data class ProductDto(
    val id: String,
    val tags: List<String> = emptyList(),
)
```

A default empty list can be useful when the API omits `tags` and the application considers that equivalent to no tags.

Do not use defaults to conceal a broken API contract. A missing required identifier should not silently become an empty string.

### 10.4 Required field validation

If an API field is optional but the domain requires it, make the conversion explicit:

```kotlin
sealed interface MappingResult<out T> {
    data class Success<T>(val value: T) : MappingResult<T>
    data class Failure(val reason: MappingFailure) : MappingResult<Nothing>
}

sealed interface MappingFailure {
    data object MissingProductId : MappingFailure
    data object InvalidPrice : MappingFailure
}
```

A mapper can return a `MappingResult<Product>` instead of pretending every input is valid.

## 11. Enum and Unknown-Value Mapping

Backend enums evolve independently of mobile releases. A server may introduce a new value before every installed client has been updated.

### 11.1 Direct enum mapping

```kotlin
enum class ProductStatus {
    ACTIVE,
    INACTIVE,
}

fun ProductStatusDto.toDomain(): ProductStatus {
    return when (this) {
        ProductStatusDto.ACTIVE -> ProductStatus.ACTIVE
        ProductStatusDto.INACTIVE -> ProductStatus.INACTIVE
    }
}
```

Direct mapping is safe only when the input type can represent every value that may arrive.

### 11.2 Unknown values

If the backend sends a string, a strict `enumValueOf()` can throw for a future value.

```kotlin
enum class ProductStatus {
    ACTIVE,
    INACTIVE,
    UNKNOWN,
}

fun String.toProductStatus(): ProductStatus {
    return when (uppercase()) {
        "ACTIVE" -> ProductStatus.ACTIVE
        "INACTIVE" -> ProductStatus.INACTIVE
        else -> ProductStatus.UNKNOWN
    }
}
```

The fallback is a product decision. Some unknown values should be preserved as raw strings rather than collapsed into `UNKNOWN`.

```kotlin
sealed interface RemoteStatus {
    data object Active : RemoteStatus
    data object Inactive : RemoteStatus
    data class Unsupported(val rawValue: String) : RemoteStatus
}
```

This allows the application to retain diagnostic information and decide how to display or handle future values.

### 11.3 Do not confuse unknown with invalid

An unknown status may be a valid future backend value. An empty or malformed status may indicate corrupt data. Decide whether both can use the same fallback.

## 12. Dates, Money, and Value Objects

Primitive values often carry more meaning than their Kotlin type suggests. Mapping is a good place to convert raw values into domain-specific types.

### 12.1 Date and time

A backend may return an ISO-8601 timestamp:

```kotlin
@Serializable
data class ShipmentDto(
    val shipmentId: String,
    val expectedDeliveryAt: String,
)
```

A domain model may use `kotlinx.datetime.Instant`:

```kotlin
data class Shipment(
    val id: String,
    val expectedDeliveryAt: Instant,
)
```

Mapper:

```kotlin
fun ShipmentDto.toDomain(): Shipment {
    return Shipment(
        id = shipmentId,
        expectedDeliveryAt = Instant.parse(expectedDeliveryAt),
    )
}
```

Parsing can fail if the backend sends malformed or unexpected input. If the payload is not guaranteed, use a safe parsing result and represent invalid data explicitly.

Use the correct semantic type:

- `Instant` for a point on the global timeline.
- `LocalDate` for a calendar date without a time zone.
- `LocalDateTime` for a local date and time without an offset.
- `TimeZone` when interpreting local time in a particular region.

Do not treat all date strings as interchangeable.

### 12.2 Money

Avoid using `Double` for financial amounts.

A backend may send an amount in minor units:

```kotlin
data class PriceDto(
    val amountMinor: Long,
    val currencyCode: String,
)
```

Domain model:

```kotlin
data class Money(
    val amountMinor: Long,
    val currency: CurrencyCode,
)

@JvmInline
value class CurrencyCode(val value: String)
```

Mapper:

```kotlin
fun PriceDto.toDomain(): Money {
    return Money(
        amountMinor = amountMinor,
        currency = CurrencyCode(currencyCode),
    )
}
```

Do not assume every currency has two decimal places. Currency precision and rounding rules should be handled by a well-defined money abstraction or formatting component.

### 12.3 Identifiers

Use value classes when they improve type safety:

```kotlin
@JvmInline
value class OrderId(val value: String)

@JvmInline
value class CustomerId(val value: String)
```

A mapper can convert raw strings into the appropriate identifiers. This reduces accidental interchange of IDs that happen to share the same primitive type.

### 12.4 Units and measurements

If a backend returns a distance in meters but the domain uses a typed measurement, convert it explicitly.

```kotlin
data class Distance(
    val meters: Double,
)

fun Double.toDistance(): Distance = Distance(meters = this)
```

Avoid embedding unit assumptions in property names or UI formatting. A typed domain value makes the unit explicit.

## 13. Mapping Polymorphic API Models

Some APIs return different object shapes depending on a discriminator or event type.

### 13.1 Transport model

```kotlin
@Serializable
sealed interface PaymentDto {
    @Serializable
    @SerialName("card")
    data class Card(
        val lastFourDigits: String,
    ) : PaymentDto

    @Serializable
    @SerialName("wallet")
    data class Wallet(
        val provider: String,
    ) : PaymentDto
}
```

### 13.2 Domain model

```kotlin
sealed interface PaymentMethod {
    data class Card(
        val maskedNumber: String,
    ) : PaymentMethod

    data class DigitalWallet(
        val providerName: String,
    ) : PaymentMethod
}
```

### 13.3 Mapper

```kotlin
fun PaymentDto.toDomain(): PaymentMethod {
    return when (this) {
        is PaymentDto.Card -> PaymentMethod.Card(
            maskedNumber = "•••• $lastFourDigits",
        )

        is PaymentDto.Wallet -> PaymentMethod.DigitalWallet(
            providerName = provider,
        )
    }
}
```

The mapper translates transport-specific variants into domain concepts.

### 13.4 Unknown subtype strategy

If the serializer cannot decode an unknown subtype, mapping never receives it. Forward compatibility must therefore be addressed at the serialization boundary as well as the mapper boundary.

Possible approaches include:

- A custom serializer that preserves unknown payloads.
- A raw JSON fallback model.
- A stable envelope with a known type field and opaque payload.
- An API contract that guarantees a safe fallback variant.

The mapper should not claim to handle unknown variants unless the deserialization layer can actually represent them.

## 14. Mapping and Validation

A mapper may need to deal with data that is syntactically valid but unsuitable for the domain.

Consider an API response:

```kotlin
data class InventoryDto(
    val sku: String,
    val quantity: Int,
)
```

The domain may require a non-negative quantity:

```kotlin
data class Inventory(
    val sku: String,
    val quantity: Int,
)
```

A direct mapper would allow invalid values through:

```kotlin
fun InventoryDto.toDomain() = Inventory(
    sku = sku,
    quantity = quantity,
)
```

If negative quantities are invalid according to the application's data contract, use explicit validation:

```kotlin
sealed interface InventoryMappingResult {
    data class Success(val inventory: Inventory) : InventoryMappingResult
    data class InvalidQuantity(val received: Int) : InventoryMappingResult
}

fun InventoryDto.toDomainResult(): InventoryMappingResult {
    return if (quantity < 0) {
        InventoryMappingResult.InvalidQuantity(quantity)
    } else {
        InventoryMappingResult.Success(
            Inventory(
                sku = sku,
                quantity = quantity,
            ),
        )
    }
}
```

### 14.1 Mapping failure vs. business rejection

Keep the distinction clear:

| Situation | Better responsibility |
|---|---|
| Required API field cannot be parsed | Parsing / mapping boundary |
| Database value has an invalid representation | Persistence mapping boundary |
| User is not allowed to update a product | Domain authorization rule |
| Requested quantity exceeds available stock | Domain or application rule |
| UI cannot format an unsupported locale | Presentation formatting |
| API sends an unknown enum string | Deserialization / mapping policy |

### 14.2 Avoid silently repairing important data

Examples of risky silent transformations:

- Negative money converted to zero.
- Invalid dates replaced with the current date.
- Missing identifiers replaced with empty strings.
- Unknown payment types treated as cash.
- Invalid quantities clamped without recording the issue.

Normalization is valid when it is part of a documented contract. Otherwise, surface the problem so the application can respond correctly.

## 15. Mapper Design in Kotlin Multiplatform

KMP benefits from mapping boundaries because shared application models should not depend on platform-specific API or persistence representations.

### 15.1 Shared domain model and mapper

```text
shared/
└── src/
    └── commonMain/
        └── kotlin/
            └── product/
                ├── domain/
                │   └── Product.kt
                └── data/
                    ├── remote/
                    │   └── ProductDto.kt
                    ├── local/
                    │   └── ProductEntity.kt
                    └── mapper/
                        └── ProductMapper.kt
```

A shared mapper:

```kotlin
// commonMain
fun ProductDto.toDomain(): Product {
    return Product(
        id = ProductId(productId),
        name = displayName,
        price = Money(priceMinor),
        availability = if (isAvailable) {
            Availability.AVAILABLE
        } else {
            Availability.UNAVAILABLE
        },
    )
}
```

This mapper can be shared when the DTO, domain model, and required libraries are compatible with all configured targets.

### 15.2 Platform-specific models

A platform-specific SDK may return a type that cannot be used in `commonMain`.

Convert that type at the platform boundary into a shared representation:

```text
Android SDK model ──> Android adapter ──> common model
Apple SDK model   ──> iOS adapter     ──> common model
```

Do not force Android or Apple framework classes into common source sets merely to reuse a mapper.

### 15.3 Avoid platform formatting in shared data mappers

Currency symbols, localized dates, pluralization, and UI labels may differ by locale and platform presentation rules.

A shared domain mapper should normally create typed values. Formatting should happen through a presentation formatter or an explicitly shared localization abstraction.

### 15.4 Source-set placement

| Mapper type | Typical source set |
|---|---|
| DTO to domain | `commonMain`, if DTO is shared |
| Entity to domain | `commonMain`, if persistence model is shared |
| Domain to entity | `commonMain`, if persistence model is shared |
| Platform SDK to shared model | `androidMain` or `iosMain` |
| Domain to Compose UI model | Android presentation module |
| Domain to SwiftUI presentation value | iOS presentation layer |
| Common mapper tests | `commonTest` |

The location follows the types involved. A mapper belongs where all of its input and output types can legally be referenced.

## 16. Manual Mapping vs. Mapping Libraries

Kotlin provides enough language features to implement most mappings manually. Libraries can help when a project has many repetitive transformations.

### 16.1 Manual mapping

```kotlin
fun UserDto.toDomain(): User {
    return User(
        id = id,
        name = fullName,
        email = EmailAddress(email),
    )
}
```

Advantages:

- Explicit behavior.
- Easy debugging.
- No mapping framework dependency.
- Simple KMP compatibility.
- Straightforward unit tests.

Trade-offs:

- Repetitive for large model graphs.
- New properties must be considered manually.
- Large projects may accumulate many mapping functions.

### 16.2 Mapping libraries

A mapping library may generate or reduce repetitive conversion code. Before adopting one, evaluate:

- KMP target support.
- Kotlin compiler and plugin compatibility.
- Generated-code readability.
- Handling of nullability and defaults.
- Support for nested and polymorphic models.
- Compile-time diagnostics.
- Build performance.
- Ease of debugging.
- Maintenance and release activity.

Do not select a mapper library only because it reduces lines of code. The transformation rules must remain understandable.

### 16.3 Manual mapping is not inherently inferior

For important domain boundaries, explicit mapping often communicates business meaning more clearly than a generic property copier.

For example, converting a raw backend status into a domain state may require a deliberate fallback. A generated mapper cannot infer that policy safely without configuration.

### 16.4 A balanced approach

A practical approach is:

- Use extension functions for small, direct transformations.
- Use mapper classes when dependencies or configuration are required.
- Use generated mapping only when repetitive mapping is a genuine maintenance problem.
- Keep important normalization and validation rules explicit.

## 17. Testing Mappers

Mapper tests should be fast, deterministic, and independent of networking or database infrastructure.

### 17.1 Test a DTO mapper

```kotlin
class ProductMapperTest {

    @Test
    fun `maps product dto to domain`() {
        val dto = ProductDto(
            productId = "P-1001",
            displayName = "Wireless Scanner",
            priceMinor = 129900,
            isAvailable = true,
        )

        val result = dto.toDomain()

        assertEquals("P-1001", result.id.value)
        assertEquals("Wireless Scanner", result.name)
        assertEquals(129900L, result.price.minorUnits)
        assertEquals(Availability.AVAILABLE, result.availability)
    }
}
```

### 17.2 Test nullable values

```kotlin
@Test
fun `maps missing optional nickname according to domain contract`() {
    val dto = ProfileDto(
        id = "u-1",
        nickname = null,
    )

    val result = dto.toDomain()

    assertEquals("", result.nickname)
}
```

This test is appropriate only if the chosen domain contract intentionally converts a missing nickname to an empty string.

### 17.3 Test unknown enum values

```kotlin
@Test
fun `maps unsupported status to unknown`() {
    val result = "PAUSED_BY_NEW_BACKEND_RULE".toProductStatus()

    assertEquals(ProductStatus.UNKNOWN, result)
}
```

### 17.4 Test invalid input

If mapping returns a result type, test both valid and invalid paths.

```kotlin
@Test
fun `rejects negative inventory quantity`() {
    val dto = InventoryDto(
        sku = "SKU-1",
        quantity = -5,
    )

    val result = dto.toDomainResult()

    assertEquals(
        InventoryMappingResult.InvalidQuantity(-5),
        result,
    )
}
```

### 17.5 Test nested mapping

Test nested mappers independently and then test that the parent mapper composes them correctly.

### 17.6 What should not be in a mapper unit test?

A mapper test should not need:

- A real HTTP server.
- A database connection.
- Dependency injection startup.
- A Compose UI test environment.
- A platform device.

If a mapper requires all of these, it is probably doing more than mapping.

### 17.7 Common test source sets

For shared KMP mapping logic, place tests in `commonTest` when the models and test framework are supported there. Platform adapter mappers should be tested in their corresponding platform test source sets.

## 18. Performance and Maintainability

Mapping usually involves object allocation and collection transformation. For typical application payloads, this cost is small compared with network and database work. Large or frequent transformations still deserve attention.

### 18.1 Avoid repeated mapping

If the same large collection is mapped several times in one pipeline, consider whether the repository can map once and expose the resulting stream.

```kotlin
val products: Flow<List<Product>> =
    local.observeProducts()
        .map { entities -> entities.map(ProductEntity::toDomain) }
```

Avoid mapping the same values independently in multiple consumers when a shared repository stream is appropriate.

### 18.2 Avoid unnecessary intermediate collections

For large datasets, repeated `map`, `filter`, and `toList` operations can allocate intermediate collections. Combine transformations when it improves efficiency without harming readability.

### 18.3 Do not optimize prematurely

A straightforward mapper is usually easier to maintain than a clever generic reflection-based conversion system.

Measure allocation and CPU cost before introducing caching or code-generation complexity.

### 18.4 Keep mapping functions deterministic

A mapper that reads the current time, accesses a global locale, or queries a database is harder to test.

If a transformation needs an external value, pass it explicitly:

```kotlin
fun SubscriptionDto.toDomain(
    receivedAt: Instant,
): Subscription {
    return Subscription(
        id = id,
        status = status.toDomain(),
        receivedAt = receivedAt,
    )
}
```

This makes the dependency visible and the test deterministic.

### 18.5 Avoid mutable output models

Prefer immutable domain values where possible. A mapper should not return a shared mutable object that can be changed unexpectedly by several consumers.

## 19. Common Mapping Mistakes

### Mistake 1: Using DTOs throughout the application

```kotlin
class ProductViewModel(
    private val repository: ProductRepository,
) {
    fun title(dto: ProductDto) = dto.displayName
}
```

**Problem:** the presentation layer is coupled to the API contract.

**Better:** map to a domain model at the data boundary.

### Mistake 2: Returning entities from repositories

```kotlin
interface ProductRepository {
    fun observeProducts(): Flow<List<ProductEntity>>
}
```

**Problem:** consumers now depend on database schema and persistence details.

**Better:** expose domain models unless the entity is intentionally the application model in a very small design.

### Mistake 3: One mapper handles everything

A `ProductMapper` that parses JSON, queries the database, validates stock, formats currency, and creates UI state has too many responsibilities.

**Better:** separate transport mapping, persistence mapping, domain rules, and presentation formatting.

### Mistake 4: Silent fallback values

Converting every missing string to `""` and every invalid number to `0` can hide corrupt data.

**Better:** preserve nullability or return an explicit mapping failure when the distinction matters.

### Mistake 5: Assuming backend enums never change

Strict enum conversion can break an older mobile app when a backend adds a new value.

**Better:** design unknown-value behavior at the deserialization and mapping boundaries.

### Mistake 6: Mapping UI strings in common data code

A shared mapper that returns `"Available"` or a formatted currency string couples data to locale and presentation.

**Better:** map to typed domain values and format in the presentation layer.

### Mistake 7: Generic reflection-based mappers everywhere

Reflection can hide transformations, make errors harder to locate, and create target or performance constraints.

**Better:** prefer explicit mapping unless a well-supported generator provides clear value.

### Mistake 8: Mapping with side effects

A mapper should not save records, trigger requests, or mutate global state.

**Better:** keep mapping pure and let repositories or dedicated components coordinate side effects.

### Mistake 9: Assuming serialization handles domain mapping

`@SerialName` and serializer configuration map JSON fields to DTO properties. They do not automatically create a well-designed domain model.

**Better:** keep deserialization and application mapping as separate, intentional steps.

### Mistake 10: Ignoring reverse mapping

A feature may correctly map responses into domain models but send domain-only fields or omit required request fields when updating data.

**Better:** define request mapping separately and test the outgoing payload contract.

## 20. Production Mapper Checklist

### Model boundaries

- [ ] DTOs represent remote contracts.
- [ ] Entities represent persistence needs.
- [ ] Domain models represent application meaning.
- [ ] UI models remain presentation-specific.
- [ ] Separate models exist for a clear reason.

### Transformation quality

- [ ] Mapping functions have one responsibility.
- [ ] Field renaming and type conversion are explicit.
- [ ] Nested objects use focused child mappers.
- [ ] Collection ordering is preserved where required.
- [ ] Unknown enum values have a defined policy.
- [ ] Date, money, ID, and measurement types preserve their semantics.
- [ ] Reverse mappings use request-specific models where appropriate.

### Nullability and validation

- [ ] Missing and explicit-null semantics are understood.
- [ ] Defaults reflect the API contract.
- [ ] Required fields are not silently replaced with empty values.
- [ ] Invalid values are handled explicitly.
- [ ] Business rules are not hidden inside generic mappers.

### Kotlin Multiplatform

- [ ] Shared mappers reference only types supported in `commonMain`.
- [ ] Platform SDK models are converted at platform boundaries.
- [ ] UI formatting is kept out of shared data mappers.
- [ ] Common mapping logic is tested in `commonTest` where possible.

### Maintainability

- [ ] Mapping functions are deterministic where practical.
- [ ] Side effects are kept outside mappers.
- [ ] Tests cover normal, nullable, unknown, and invalid values.
- [ ] Mapping performance is measured before optimization.
- [ ] Generated mapping tools are compatible with project targets and compiler versions.

## 21. Key Takeaways

Mapping is one of the most important boundaries in a maintainable data layer.

Remember these principles:

1. **A mapper translates representations.** It is not a network client, database coordinator, or business workflow.
2. **DTOs, entities, domain models, and UI models have different responsibilities.** Keep them separate when their reasons to change differ.
3. **Map at boundaries.** Convert transport and persistence data before exposing it to application consumers.
4. **Extension functions are often enough.** Keep transformations explicit and focused.
5. **Nullability and defaults are contract decisions.** Do not hide missing or invalid data behind arbitrary fallback values.
6. **Unknown backend values need a strategy.** Mobile clients must tolerate compatible API evolution.
7. **Typed values improve domain safety.** Dates, money, identifiers, and measurements should preserve their meaning.
8. **KMP favors portable mapping.** Share transformations when their input and output types are truly multiplatform.
9. **Keep presentation formatting separate.** Domain mapping should not depend on Compose, SwiftUI, or a device locale.
10. **Test mapping independently.** Pure mapper tests should be fast and deterministic.

A good mapper creates a small but powerful guarantee:

> External data can change its shape without forcing the entire application to change with it.
