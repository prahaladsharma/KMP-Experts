## 1. Why Enum Serialization Matters

Applications use finite states everywhere:

- Order status.
- Payment status.
- User role.
- Shipment state.
- Authentication method.
- Notification type.
- Warehouse task status.
- Feature or workflow state.

Kotlin represents these values naturally with `enum class`.

```kotlin
enum class OrderStatus {
    CREATED,
    PROCESSING,
    SHIPPED,
    DELIVERED
}
```

A backend may represent the same values as strings:

```json
{
  "order_id": "ORD-1001",
  "status": "PROCESSING"
}
```

The serializer must translate between the JSON representation and the Kotlin enum entry.

That sounds simple, but enum values are a common source of production failures. A backend may rename a value, add a new state, change casing, or use short codes instead of readable names.

A mobile application may also remain installed for months. It can receive a value that did not exist when the application was built.

The important question is not only:

**How do we serialize an enum?**

It is also:

**What should the application do when the API sends an enum value it does not recognize?**

This chapter explores both sides: the mechanics of enum serialization and the compatibility decisions needed for production systems.

## 2. Kotlin Enums and Their Serialized Representation

A Kotlin enum is a fixed set of named constants.

```kotlin
enum class PaymentStatus {
    PENDING,
    AUTHORIZED,
    DECLINED,
    REFUNDED
}
```

Each entry has:

- A name, such as `AUTHORIZED`.
- An ordinal, which is its position in the declaration.
- A stable identity within that compiled enum type.

The ordinal is not a good API contract. Reordering enum entries changes their ordinals.

For example:

```kotlin
enum class PaymentStatus {
    PENDING,      // ordinal 0
    AUTHORIZED,   // ordinal 1
    DECLINED      // ordinal 2
}
```

If someone inserts a new entry before `AUTHORIZED`, its ordinal changes.

External APIs should generally use explicit string values or documented numeric codes—not Kotlin enum ordinals.

### A useful distinction

| Representation | Example | Recommendation |
|---|---|---|
| Enum name | `"AUTHORIZED"` | Good when contract matches |
| Explicit API string | `"authorized"` | Good with `@SerialName` |
| Backend code | `"A"` | Use explicit mapping |
| Enum ordinal | `1` | Avoid as an API contract |
| Display label | `"Payment approved"` | Keep separate from wire value |

An enum's display text, internal name, and serialized API value are three different concepts. Do not treat them as interchangeable.

## 3. Default Enum Serialization

Kotlin Serialization generates an enum serializer for an `@Serializable` enum.

```kotlin
import kotlinx.serialization.Serializable

@Serializable
enum class OrderStatus {
    CREATED,
    PROCESSING,
    SHIPPED,
    DELIVERED
}
```

A DTO can use it directly:

```kotlin
@Serializable
data class OrderResponseDto(
    val orderId: String,
    val status: OrderStatus
)
```

Example:

```kotlin
val json = Json

val order = OrderResponseDto(
    orderId = "ORD-1001",
    status = OrderStatus.PROCESSING
)

val encoded = json.encodeToString(order)
```

The JSON output is:

```json
{
  "orderId": "ORD-1001",
  "status": "PROCESSING"
}
```

The default enum serializer uses the enum entry's serialized name. Unless configured otherwise, this is the entry name.

### Decoding

```kotlin
val payload = """
    {
      "orderId": "ORD-1001",
      "status": "PROCESSING"
    }
""".trimIndent()

val decoded = json.decodeFromString<OrderResponseDto>(payload)
```

The result contains:

```kotlin
decoded.status == OrderStatus.PROCESSING
```

### Unknown values

By default, an unknown enum value is a serialization error.

```json
{
  "orderId": "ORD-1001",
  "status": "OUT_FOR_DELIVERY"
}
```

If `OUT_FOR_DELIVERY` is not declared in `OrderStatus`, decoding fails unless a compatibility mechanism is deliberately configured.

That behavior is often desirable: silently interpreting an unknown state as a different known state can be dangerous.

## 4. Renaming Enum Entries with `@SerialName`

The API may use a value that differs from the Kotlin enum entry name.

For example, Kotlin prefers uppercase names:

```kotlin
enum class AccountStatus {
    ACTIVE,
    SUSPENDED,
    CLOSED
}
```

The API may send lowercase strings:

```json
{
  "status": "active"
}
```

Use `@SerialName` to define the serialized value:

```kotlin
@Serializable
enum class AccountStatus {
    @SerialName("active")
    ACTIVE,

    @SerialName("suspended")
    SUSPENDED,

    @SerialName("closed")
    CLOSED
}
```

Now serialization produces the API representation:

```kotlin
val encoded = json.encodeToString(AccountStatus.ACTIVE)
// "active"
```

And decoding accepts that exact serialized name:

```kotlin
val decoded = json.decodeFromString<AccountStatus>("\"suspended\"")
// AccountStatus.SUSPENDED
```

### Use `@SerialName` as contract documentation

A good enum declaration makes the API contract visible:

```kotlin
@Serializable
enum class ShipmentStatus {
    @SerialName("pending")
    PENDING,

    @SerialName("in_transit")
    IN_TRANSIT,

    @SerialName("delivered")
    DELIVERED
}
```

This is preferable to scattering string conversions across repositories and ViewModels.

### Class-level serialized names versus enum entry names

`@SerialName` can be used on serializable classes and enum entries. For enum APIs, place it on the enum entry whose wire representation differs from its Kotlin name.

Do not assume that a class-level name changes every enum entry's serialized value.

## 5. Case Sensitivity and Naming Conventions

Enum serialized names are exact values. These are different strings:

```text
PROCESSING
processing
Processing
in_progress
IN_PROGRESS
```

If the API contract says `"in_progress"`, the safest DTO mapping is:

```kotlin
@Serializable
enum class TaskStatus {
    @SerialName("pending")
    PENDING,

    @SerialName("in_progress")
    IN_PROGRESS,

    @SerialName("completed")
    COMPLETED
}
```

Do not depend on incidental casing behavior.

### Should we normalize case before decoding?

Sometimes a backend has inconsistent casing. One solution is to normalize the JSON value before enum decoding, but this should be a deliberate compatibility rule—not a hidden assumption.

For example, a custom serializer could read a string and normalize it. However, normalization can be unsafe when values are case-sensitive identifiers or when two values differ only by case.

Prefer fixing inconsistent API contracts at the backend. If a client-side workaround is required, document it and test the accepted variants.

### Global naming strategies

JSON naming strategies can transform property names, such as `createdAt` to `created_at`. They do not automatically mean every enum wire value should be lowercased or converted to snake_case.

Treat property naming and enum value naming as separate concerns.

## 6. Unknown Enum Values and Forward Compatibility

This is one of the most important topics in mobile API design.

Imagine version 1 of an application knows:

```kotlin
@Serializable
enum class DeliveryStatus {
    PENDING,
    PACKED,
    SHIPPED,
    DELIVERED
}
```

Later, the backend introduces:

```json
{
  "status": "OUT_FOR_DELIVERY"
}
```

An older application does not know this entry.

There are several strategies.

### Strategy A: Fail explicitly

Keep the enum strict.

```kotlin
@Serializable
enum class DeliveryStatus {
    PENDING,
    PACKED,
    SHIPPED,
    DELIVERED
}
```

Advantages:

- Contract mismatches are visible.
- Unknown states cannot accidentally be treated as valid known states.
- Critical workflows fail rather than guessing.

Disadvantages:

- A new backend enum can break older clients.
- A list response containing one unknown value may fail to decode as a whole.

Use strict decoding when an unknown state makes the operation unsafe or impossible.

### Strategy B: Add an `UNKNOWN` entry with a custom mapping

A plain enum entry named `UNKNOWN` does not automatically become a catch-all for unknown strings.

This declaration:

```kotlin
@Serializable
enum class DeliveryStatus {
    PENDING,
    SHIPPED,
    DELIVERED,
    UNKNOWN
}
```

still does not mean `"OUT_FOR_DELIVERY"` maps to `UNKNOWN` by default.

You need a custom mapping strategy.

### Strategy C: Keep the raw API value as a string

```kotlin
@Serializable
data class DeliveryResponseDto(
    val status: String
)
```

Then map it:

```kotlin
enum class DeliveryStatus {
    PENDING,
    SHIPPED,
    DELIVERED,
    UNKNOWN
}

fun String.toDeliveryStatus(): DeliveryStatus =
    when (this) {
        "PENDING" -> DeliveryStatus.PENDING
        "SHIPPED" -> DeliveryStatus.SHIPPED
        "DELIVERED" -> DeliveryStatus.DELIVERED
        else -> DeliveryStatus.UNKNOWN
    }
```

This is often a good choice when the application needs to tolerate new backend values while keeping domain logic finite and explicit.

The raw string can also be retained for diagnostics or future handling, subject to safe logging rules.

### Strategy D: Use `coerceInputValues`

Kotlin Serialization's JSON configuration provides `coerceInputValues`.

```kotlin
val json = Json {
    coerceInputValues = true
}
```

For an enum property, an unknown enum value can be treated as an invalid input and, when the property is optional or nullable under the relevant rules, the decoder can use its default or null value.

Example:

```kotlin
@Serializable
enum class TaskStatus {
    PENDING,
    COMPLETED
}

@Serializable
data class TaskDto(
    val id: String,
    val status: TaskStatus = TaskStatus.PENDING
)
```

With coercion enabled, an unknown enum value for `status` can be treated as missing and the default used.

**Important:** this does not create an `UNKNOWN` enum value and does not preserve the original unknown string. It also does not make every malformed value safe. Understand the exact behavior for the field's nullability/default configuration and test it with the serialization version in use.

### Choosing a strategy

| Requirement | Suitable approach |
|---|---|
| Unknown state must stop processing | Strict enum |
| Unknown state should become a safe domain fallback | Raw string DTO + mapper |
| Unknown value should use a field default | `coerceInputValues`, with careful tests |
| Unknown value must be preserved | Raw string or custom representation |
| API contract is stable and controlled | `@SerialName` enum |

Avoid silently mapping a new state to an existing state such as `DELIVERED`. That can create incorrect business behavior.

## 7. `coerceInputValues` and `explicitNulls`

JSON configuration can influence how enum values and nullable properties are decoded.

### `coerceInputValues`

```kotlin
val json = Json {
    coerceInputValues = true
}
```

This setting can coerce certain invalid input values, including unknown enum values, into missing values when the property can be filled by a default or nullable behavior.

It is not a universal “ignore bad data” switch.

Test the exact contract:

- Unknown enum on a required non-null property without a default.
- Unknown enum on a property with a default.
- Unknown enum on a nullable property.
- Explicit `null`.
- Missing property.

### `explicitNulls`

```kotlin
val json = Json {
    explicitNulls = false
}
```

This setting affects how nullable properties with null values are represented and handled in JSON. It is not an enum fallback mechanism.

For example, enum values are non-null by default unless the property is declared nullable:

```kotlin
@Serializable
data class UserDto(
    val status: AccountStatus?
)
```

Do not disable explicit nulls merely to solve an unknown enum problem. These settings solve different serialization concerns.

### Configuration should be intentional

```kotlin
val apiJson = Json {
    ignoreUnknownKeys = true
    coerceInputValues = false
    explicitNulls = true
}
```

The values above are illustrative. Choose settings based on the API contract, compatibility needs, and tests—not by copying a generic configuration.

## 8. Enum Values That Use Backend Codes

Some APIs do not use readable enum strings. They use compact codes.

Example:

| Backend code | Meaning |
|---|---|
| `N` | New |
| `P` | Processing |
| `C` | Completed |
| `X` | Cancelled |

A Kotlin enum can remain expressive:

```kotlin
enum class JobStatus {
    NEW,
    PROCESSING,
    COMPLETED,
    CANCELLED
}
```

A custom serializer maps codes to enum entries.

```kotlin
object JobStatusSerializer : KSerializer<JobStatus> {

    override val descriptor: SerialDescriptor =
        PrimitiveSerialDescriptor(
            "JobStatus",
            PrimitiveKind.STRING
        )

    override fun serialize(
        encoder: Encoder,
        value: JobStatus
    ) {
        val code = when (value) {
            JobStatus.NEW -> "N"
            JobStatus.PROCESSING -> "P"
            JobStatus.COMPLETED -> "C"
            JobStatus.CANCELLED -> "X"
        }

        encoder.encodeString(code)
    }

    override fun deserialize(decoder: Decoder): JobStatus =
        when (val code = decoder.decodeString()) {
            "N" -> JobStatus.NEW
            "P" -> JobStatus.PROCESSING
            "C" -> JobStatus.COMPLETED
            "X" -> JobStatus.CANCELLED
            else -> throw SerializationException(
                "Unknown job status code"
            )
        }
}
```

Use it on a DTO property:

```kotlin
@Serializable
data class JobDto(
    val id: String,

    @Serializable(with = JobStatusSerializer::class)
    val status: JobStatus
)
```

### Why not use ordinal values?

Never implement code mapping using:

```kotlin
value.ordinal
```

The order of enum declarations is an implementation detail. A developer may reorder entries or insert a new one, changing ordinal values and potentially corrupting the API contract.

Use explicit `when` mappings or explicit stable codes.

### Unknown code policy

The example throws for an unknown code. If the API may introduce new codes and the client must remain tolerant, consider storing the raw code in the DTO and mapping it into a domain fallback.

## 9. Custom Enum Serializers

A custom serializer is useful when the enum's wire representation is not its serialized name.

The general structure is:

```kotlin
object StatusSerializer : KSerializer<Status> {

    override val descriptor: SerialDescriptor =
        PrimitiveSerialDescriptor(
            "Status",
            PrimitiveKind.STRING
        )

    override fun serialize(
        encoder: Encoder,
        value: Status
    ) {
        // Kotlin enum -> API value
    }

    override fun deserialize(decoder: Decoder): Status {
        // API value -> Kotlin enum
    }
}
```

### Reusable mapping pattern

For a small enum, a `when` expression is easy to read. For a larger enum, you can keep the code mapping close to the enum declaration.

```kotlin
enum class Priority(val apiCode: String) {
    LOW("L"),
    NORMAL("N"),
    HIGH("H"),
    CRITICAL("C");

    companion object {
        fun fromApiCode(code: String): Priority? =
            entries.firstOrNull { it.apiCode == code }
    }
}
```

Serializer:

```kotlin
object PrioritySerializer : KSerializer<Priority> {

    override val descriptor: SerialDescriptor =
        PrimitiveSerialDescriptor(
            "Priority",
            PrimitiveKind.STRING
        )

    override fun serialize(
        encoder: Encoder,
        value: Priority
    ) {
        encoder.encodeString(value.apiCode)
    }

    override fun deserialize(decoder: Decoder): Priority {
        val code = decoder.decodeString()

        return Priority.fromApiCode(code)
            ?: throw SerializationException(
                "Unknown priority code"
            )
    }
}
```

`entries` is available in modern Kotlin versions. If a project targets an older Kotlin version, use the enum entries API supported by that version.

### Avoid duplicate mapping tables

Do not maintain one mapping in the serializer, another in the repository, and another in the UI. Keep the API mapping in one well-defined place.

## 10. When a String Is Better Than an Enum DTO

An enum is appropriate when the set of values is finite and the application understands the meaning of every value it needs to process.

But an API field may be an open-ended code rather than a closed set.

For example:

```json
{
  "workflow_state": "WAITING_FOR_EXTERNAL_APPROVAL"
}
```

If the backend frequently introduces new states, decoding directly into a strict enum can make old clients fragile.

Use a string in the DTO:

```kotlin
@Serializable
data class WorkflowResponseDto(
    @SerialName("workflow_state")
    val workflowState: String
)
```

Then create a domain mapping:

```kotlin
enum class WorkflowState {
    DRAFT,
    WAITING_FOR_APPROVAL,
    APPROVED,
    REJECTED,
    UNKNOWN
}

fun String.toWorkflowState(): WorkflowState =
    when (this) {
        "DRAFT" -> WorkflowState.DRAFT
        "WAITING_FOR_APPROVAL",
        "WAITING_FOR_EXTERNAL_APPROVAL" ->
            WorkflowState.WAITING_FOR_APPROVAL
        "APPROVED" -> WorkflowState.APPROVED
        "REJECTED" -> WorkflowState.REJECTED
        else -> WorkflowState.UNKNOWN
    }
```

### Keep the raw value when it matters

A richer domain representation can preserve both the recognized state and original code:

```kotlin
data class WorkflowStatus(
    val state: WorkflowState,
    val rawValue: String
)
```

This can help diagnostics, analytics, and gradual rollout handling. Be careful not to expose raw backend codes as user-facing labels.

### A practical decision rule

Use an enum directly in the DTO when the API contract is closed, controlled, and compatible with strict decoding.

Use a string DTO field when the backend value set is open, evolves independently, or must be preserved even when the client does not recognize it.

## 11. Enum Mapping: DTO to Domain

A DTO enum and a domain enum do not have to be the same type.

The API may use:

```kotlin
@Serializable
enum class ApiPaymentStatus {
    @SerialName("P")
    PENDING,

    @SerialName("A")
    APPROVED,

    @SerialName("D")
    DECLINED
}
```

The domain may use:

```kotlin
enum class PaymentStatus {
    WAITING_FOR_PAYMENT,
    APPROVED,
    DECLINED,
    UNKNOWN
}
```

Mapper:

```kotlin
fun ApiPaymentStatus.toDomain(): PaymentStatus =
    when (this) {
        ApiPaymentStatus.PENDING ->
            PaymentStatus.WAITING_FOR_PAYMENT

        ApiPaymentStatus.APPROVED ->
            PaymentStatus.APPROVED

        ApiPaymentStatus.DECLINED ->
            PaymentStatus.DECLINED
    }
```

### Why separate them?

- API names can change without changing domain language.
- Domain states can combine multiple backend states.
- Domain models can include `UNKNOWN` even if the API enum is strict.
- Business rules remain independent of the wire format.
- Backend-specific codes do not leak into presentation logic.

### Mapping a raw string DTO

If the DTO preserves a string:

```kotlin
fun PaymentResponseDto.toDomain(): Payment =
    Payment(
        id = PaymentId(id),
        status = status.toPaymentStatus()
    )
```

Keep unknown handling explicit in the mapper.

Do not place UI labels such as `"Payment successful"` inside the enum serializer. Presentation should map domain states to localized resources.

## 12. Enum Serialization in Requests

Enum serialization matters for outgoing requests too.

Suppose the API expects:

```json
{
  "action": "CANCEL"
}
```

Request DTO:

```kotlin
@Serializable
enum class OrderAction {
    @SerialName("CONFIRM")
    CONFIRM,

    @SerialName("CANCEL")
    CANCEL
}

@Serializable
data class UpdateOrderRequestDto(
    val action: OrderAction
)
```

Encoding:

```kotlin
val request = UpdateOrderRequestDto(
    action = OrderAction.CANCEL
)

val body = Json.encodeToString(request)
```

Output:

```json
{
  "action": "CANCEL"
}
```

### Do not send display labels

A UI might show:

```text
Cancel order
```

The API expects:

```text
CANCEL
```

These are different responsibilities.

The presentation layer owns the localized display label. The request DTO owns the API representation.

### Request compatibility

For outgoing values, be especially careful with fallback behavior. Never serialize an unknown domain state as a valid but unrelated API action.

If the domain supports a state that the endpoint cannot accept, validate that before building the request DTO.

## 13. Enums in Nested and Polymorphic Models

Enums commonly appear inside nested response structures.

```kotlin
@Serializable
data class OrderResponseDto(
    val id: String,
    val customer: CustomerDto,
    val items: List<OrderItemDto>
)

@Serializable
data class CustomerDto(
    val name: String,
    val type: CustomerType
)

@Serializable
enum class CustomerType {
    @SerialName("individual")
    INDIVIDUAL,

    @SerialName("business")
    BUSINESS
}

@Serializable
data class OrderItemDto(
    val sku: String,
    val status: ItemStatus
)

@Serializable
enum class ItemStatus {
    @SerialName("allocated")
    ALLOCATED,

    @SerialName("picked")
    PICKED,

    @SerialName("packed")
    PACKED
}
```

Generated serializers handle nested enum values automatically when all involved types are serializable.

### Enum discriminator versus polymorphic discriminator

Do not confuse a normal enum property with a polymorphic discriminator.

An enum field:

```json
{
  "status": "PROCESSING"
}
```

represents one value from a fixed set.

A polymorphic discriminator:

```json
{
  "type": "card",
  "lastFourDigits": "1234"
}
```

selects a subtype with a potentially different object structure.

They can appear together, but they solve different problems.

## 14. Enum Evolution and API Compatibility

Enums are often treated as harmless constants, but they are part of the API contract.

Consider a backend deployment that adds:

```text
RETURNED
```

Older mobile applications may not know that value.

### Safe evolution practices

1. Prefer adding new values without changing existing meanings.
2. Do not reuse an old code for a new meaning.
3. Do not expose enum ordinals as wire values.
4. Document whether clients must tolerate unknown values.
5. Test older-client behavior against newly introduced values.
6. Keep unknown-state handling safe for business-critical operations.
7. Coordinate releases when a new state changes workflow behavior.

### Versioning strategy

If an endpoint has a tightly controlled set of values, strict enums may be appropriate.

If the backend evolves independently and clients must remain compatible, use a raw string DTO or a deliberately tolerant custom serializer.

### Unknown does not mean safe

An unknown state should not automatically allow an operation.

For example, if a payment status is unknown, the client should not assume payment is complete. A safe fallback is often to disable actions or present a generic state until the application can refresh or understand the value.

## 15. Kotlin Multiplatform Considerations

Enum serialization works well in shared Kotlin code. A single common DTO can be decoded consistently on Android and iOS.

Example:

```text
shared/
└── src/
    ├── commonMain/
    │   └── kotlin/
    │       ├── data/
    │       │   └── dto/
    │       │       └── OrderResponseDto.kt
    │       └── domain/
    │           └── OrderStatus.kt
    ├── commonTest/
    │   └── kotlin/
    │       └── data/
    │           └── OrderStatusSerializationTest.kt
    ├── androidMain/
    └── iosMain/
```

Shared enum:

```kotlin
@Serializable
enum class OrderStatusDto {
    @SerialName("created")
    CREATED,

    @SerialName("processing")
    PROCESSING,

    @SerialName("shipped")
    SHIPPED,

    @SerialName("delivered")
    DELIVERED
}
```

### KMP best practices

- Keep shared enums free from Android and iOS framework dependencies.
- Put API-specific serialized names in the data layer when appropriate.
- Keep UI labels in platform presentation resources.
- Test enum decoding in `commonTest`.
- Avoid relying on enum ordinal values across platform boundaries.
- Use common-compatible custom serializers when backend codes require mapping.

### Shared domain enum or shared DTO enum?

They may be shared, but they do not have to be the same type.

If the API contract and domain language are stable and identical, reusing one enum may be a reasonable simplification.

If the API has legacy codes, backend-specific naming, or frequent changes, keep a separate DTO representation and map it into a domain enum.

The important part is to make the dependency intentional.

## 16. Testing Enum Serialization

Enum tests should verify the actual wire representation, not just Kotlin enum equality.

### 16.1 Test encoding

```kotlin
@Test
fun orderStatus_encodesUsingSerialName() {
    val result = Json.encodeToString(
        OrderStatusDto.SHIPPED
    )

    assertEquals("\"shipped\"", result)
}
```

Corrected example using the declared enum entry:

```kotlin
@Test
fun orderStatus_encodesUsingSerialName() {
    val result = Json.encodeToString(
        OrderStatusDto.SHIPPED
    )

    assertEquals("\"shipped\"", result)
}
```

### 16.2 Test decoding

```kotlin
@Test
fun orderStatus_decodesUsingSerialName() {
```

## 17. Common Enum Serialization Mistakes

| Mistake | Why it is problematic | Better approach |
|---|---|---|
| Using `ordinal` as API value | Reordering entries changes the number | Use explicit strings or codes |
| Assuming `UNKNOWN` is automatic | Unknown input still fails by default | Use a custom mapping or raw string DTO |
| Ignoring casing differences | Serialized names are exact | Match contract with `@SerialName` |
| Using display labels as API values | Labels can be localized or changed | Keep display and wire values separate |
| Mapping unknown to a known state | Can cause incorrect workflow behavior | Use an explicit fallback |
| Applying `coerceInputValues` blindly | May replace invalid input with defaults | Test exact field behavior |
| Using a strict enum for an open-ended code | New backend values can break older clients | Preserve raw string when needed |
| Duplicating code mapping | Different layers can disagree | Centralize mapping |
| Putting UI text in serializers | Couples data layer to presentation | Map domain state to localized text |
| Treating enum and polymorphic types as identical | They represent different structures | Use the appropriate serialization mechanism |

## 18. Production Checklist

### Contract
- [ ] Every enum entry matches a documented API value.
- [ ] `@SerialName` is used for values that differ from Kotlin names.
- [ ] Casing and spelling are verified against real payloads.
- [ ] Backend codes are mapped explicitly.
- [ ] Enum ordinals are not used as external identifiers.

### Compatibility
- [ ] Unknown-value behavior is documented.
- [ ] Strict versus tolerant decoding is a conscious decision.
- [ ] `coerceInputValues` is used only with tested semantics.
- [ ] Unknown states do not accidentally enable unsafe operations.
- [ ] New backend enum values are covered by compatibility tests.

### Architecture
- [ ] API-specific enums are kept at the data boundary when appropriate.
- [ ] DTO-to-domain mapping is explicit.
- [ ] UI labels are not embedded in serializers.
- [ ] Request values are validated before serialization.
- [ ] Mapping logic is not duplicated across layers.

### Kotlin Multiplatform
- [ ] Shared enums use common-compatible Kotlin types.
- [ ] Common serialization behavior is tested in `commonTest`.
- [ ] Platform-specific presentation labels remain platform concerns.
- [ ] Android and iOS consume the same documented wire values.

## 19. Final Thoughts

Enums make application states readable and type-safe. Serialization makes those states transferable. The challenge is keeping the two representations aligned without making the application fragile when an API evolves.

For stable contracts, `@Serializable` and `@SerialName` are usually all that is needed. For backend codes or unusual representations, a custom serializer provides an explicit mapping. For open-ended values, a raw string DTO followed by a domain mapper can provide better forward compatibility.

The most important decision is how the application responds to a value it does not recognize. That behavior should be safe, documented, and tested—not left to chance.

In Kotlin Multiplatform, shared enum serialization gives Android and iOS one consistent interpretation of the API contract. Keep wire values explicit, domain meaning separate, and unknown states under control.
