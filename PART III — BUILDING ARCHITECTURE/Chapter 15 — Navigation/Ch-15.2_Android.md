## 1. Android Navigation in a KMP Application

Android navigation connects user actions to the screens displayed by the application. In a Kotlin Multiplatform project, the Android implementation belongs to the Android UI layer when the app uses native Android navigation APIs.

A KMP codebase may share domain logic, repositories, use cases, and even Compose UI. That does **not** mean Android-specific navigation types should automatically be moved into `commonMain`.

For an Android application using Jetpack Compose, AndroidX Navigation Compose is a standard option. It provides a navigation controller, a navigation graph, destination rendering, argument handling, and integration with Android lifecycle and saved state.

A typical flow looks like this:

```text
User action
    │
    ▼
Composable emits intent
    │
    ▼
Navigation layer receives route
    │
    ▼
NavController updates back stack
    │
    ▼
NavHost renders destination
    │
    ▼
Destination obtains screen state
```

Keep navigation responsibilities clear:

- **Composable screen:** renders UI and reports user actions.
- **Navigation host:** declares which destinations can be shown.
- **NavController:** performs navigation operations and manages the back stack.
- **ViewModel:** owns screen state and business-facing UI logic.
- **Shared domain layer:** supplies business rules and data, without depending on Android navigation classes.

## 2. Choose the Right Navigation Approach

Android navigation depends on the UI technology and the architecture of the app.

| Application style | Common approach | Notes |
|---|---|---|
| Jetpack Compose UI | Navigation Compose | Declarative destination rendering |
| Traditional Views | Navigation component with fragments or views | Fits view-based Android apps |
| Compose Multiplatform shared UI | A multiplatform navigation library or an appropriate shared navigation abstraction | Verify target support and lifecycle behavior |
| Shared KMP logic with native Android and iOS UI | Android navigation on Android, native navigation on iOS | Share domain decisions, not platform UI classes |

This chapter uses **Jetpack Compose with AndroidX Navigation Compose**. The code is intended for an Android source set and is not a `commonMain` implementation.

### Type-safe routes

Modern Navigation Compose versions support type-safe routes using Kotlin serialization. The examples below use that approach. Confirm the APIs against the Navigation version selected by your project; older versions may use string routes instead.

## 3. Add Navigation Compose

In an Android module, add the Navigation Compose dependency and Kotlin serialization support using versions compatible with the project's Kotlin and Android Gradle Plugin setup.

Example using a version catalog:

```toml
# gradle/libs.versions.toml

[versions]
navigation = "2.9.0"
kotlinxSerialization = "1.8.1"

[libraries]
androidx-navigation-compose = {
    module = "androidx.navigation:navigation-compose",
    version.ref = "navigation"
}
kotlinx-serialization-json = {
    module = "org.jetbrains.kotlinx:kotlinx-serialization-json",
    version.ref = "kotlinxSerialization"
}

[plugins]
kotlin-serialization = {
    id = "org.jetbrains.kotlin.plugin.serialization",
    version.ref = "kotlin"
}
```

> **Version note:** These are illustrative version-catalog entries, not a recommendation to override an existing project's versions blindly. Use mutually compatible versions and check the official Android documentation for the latest stable release.

Apply the serialization plugin and dependency in the Android app module:

```kotlin
plugins {
    alias(libs.plugins.kotlin.serialization)
}

dependencies {
    implementation(libs.androidx.navigation.compose)
    implementation(libs.kotlinx.serialization.json)
}
```

If the project already centralizes dependency versions, keep the version catalog consistent with the rest of the build. Do not add the serialization plugin a second time if it is already applied.

## 4. Model Destinations with Type-Safe Routes

Define destinations as serializable Kotlin types. This keeps route arguments explicit and avoids spreading raw route strings throughout the UI.

```kotlin
import kotlinx.serialization.Serializable

@Serializable
data object HomeRoute

@Serializable
data object CartRoute

@Serializable
data class ProductDetailsRoute(
    val productId: String
)

@Serializable
data object CheckoutRoute
```

These route classes identify destinations. They do not hold the full product, cart, or checkout state.

### Why pass an identifier?

Passing `productId` is generally more robust than placing an entire product object in navigation state:

- The details screen can load fresh data.
- Navigation arguments remain small.
- Restoration is easier to reason about.
- The route does not depend on serializing a complex domain model.
- The screen can represent loading, success, and error states independently.

Validate identifiers before using them to fetch protected or sensitive data. A route parameter is not proof that the user is authorized to access a resource.

## 5. Create the Navigation Host

A `NavHost` connects the navigation controller to the destination graph. Each destination maps a route type to composable content.

```kotlin
import androidx.compose.runtime.Composable
import androidx.navigation.NavHostController
import androidx.navigation.compose.NavHost
import androidx.navigation.compose.composable
import androidx.navigation.compose.rememberNavController

@Composable
fun AppNavigation(
    navController: NavHostController = rememberNavController()
) {
    NavHost(
        navController = navController,
        startDestination = HomeRoute
    ) {
        composable<HomeRoute> {
            HomeScreen(
                onOpenCart = {
                    navController.navigate(CartRoute)
                },
                onOpenProduct = { productId ->
                    navController.navigate(
                        ProductDetailsRoute(productId)
                    )
                }
            )
        }

        composable<CartRoute> {
            CartScreen(
                onCheckout = {
                    navController.navigate(CheckoutRoute)
                }
            )
        }

        composable<ProductDetailsRoute> { entry ->
            val route = entry.toRoute<ProductDetailsRoute>()

            ProductDetailsScreen(
                productId = route.productId,
                onBack = {
                    navController.popBackStack()
                }
            )
        }

        composable<CheckoutRoute> {
            CheckoutScreen(
                onBack = {
                    navController.popBackStack()
                }
            )
        }
    }
}
```

The example illustrates the structure. It assumes that `HomeScreen`, `CartScreen`, `ProductDetailsScreen`, and `CheckoutScreen` are defined elsewhere, and that the project uses a Navigation Compose release supporting typed routes and `toRoute<T>()`.

Add the required import for route decoding:

```kotlin
import androidx.navigation.toRoute
```

### Keep the host at the app or flow boundary

A small app may have one host. A larger app can split navigation into nested graphs or feature-level graph builders. Avoid putting the entire navigation graph inside a screen composable that is recreated as the user moves around the app.

## 6. Navigate Between Screens

A composable should usually receive callbacks rather than a `NavController`. This reduces coupling between reusable UI and the navigation framework.

```kotlin
@Composable
fun HomeScreen(
    onOpenCart: () -> Unit,
    onOpenProduct: (String) -> Unit
) {
    // Render home content.
    // Call onOpenCart() when the cart action is selected.
    // Call onOpenProduct(productId) when a product is selected.
}
```

The screen knows that the user wants to open a product, but it does not need to know how the application implements its navigation stack.

### Why not pass `NavController` everywhere?

Passing the controller through every composable can:

- Couple UI components to Navigation Compose.
- Make previews and isolated tests harder.
- Encourage navigation decisions to spread across the UI.
- Make it harder to change navigation behavior centrally.

Passing callbacks or typed navigation events is often simpler. A feature-level navigation interface can be useful when multiple screens need the same navigation capability.

## 7. Pass Arguments Safely

Typed routes allow required route parameters to be represented in Kotlin.

```kotlin
@Serializable
data class ProductDetailsRoute(
    val productId: String
)
```

Navigate to the destination:

```kotlin
navController.navigate(
    ProductDetailsRoute(productId = selectedProduct.id)
)
```

Read the argument in the destination:

```kotlin
composable<ProductDetailsRoute> { entry ->
    val route = entry.toRoute<ProductDetailsRoute>()

    ProductDetailsRouteContent(
        productId = route.productId
    )
}
```

`ProductDetailsRouteContent` here represents the screen content function you define in the application.

### Argument rules

1. Pass the smallest stable value needed to identify the destination.
2. Treat external route parameters as untrusted input.
3. Handle missing or invalid data in the screen state.
4. Avoid putting access tokens, passwords, or other secrets in routes or deep links.
5. Do not assume that a valid route grants authorization.
6. Use saved state or a data layer for information that is too large or unsuitable for navigation arguments.

## 8. Back Navigation and Stack Management

The back stack determines where Back takes the user. The default stack behavior is appropriate for many flows, but production applications need explicit decisions about authentication, checkout, tabs, and repeated navigation.

### Basic back navigation

```kotlin
val didPop = navController.popBackStack()
```

The result indicates whether a destination was popped. If the stack cannot pop, the app should allow the appropriate platform-level behavior rather than assuming a previous screen exists.

In screen callbacks, it is often enough to invoke `popBackStack()` from the navigation layer. Do not implement a separate fake Back stack inside each screen.

### Avoid duplicate destinations when appropriate

For a top-level destination, repeated taps may create unwanted duplicates. A common pattern is:

```kotlin
navController.navigate(HomeRoute) {
    launchSingleTop = true
}
```

`launchSingleTop` avoids adding another copy when the target is already at the top of the stack. It does not, by itself, implement every bottom-navigation requirement.

### Pop to a known destination

When a flow completes, the app may need to return to an existing destination and remove intermediate entries.

```kotlin
navController.navigate(HomeRoute) {
    popUpTo<HomeRoute> {
        inclusive = false
    }
    launchSingleTop = true
}
```

Use this only when the graph and intended history match the example. For a login flow, checkout, or nested graph, verify the exact destination to pop to and whether it should remain in the stack.

### Back behavior is product behavior

Test cases should include:

- Back from a details screen.
- Back at the root destination.
- Back while a dialog or bottom sheet is visible.
- Back after authentication succeeds.
- Back after checkout completes.
- Back after opening a deep link.
- Back after switching tabs.

## 9. Nested Graphs and Authentication Flows

Nested graphs group related destinations and keep feature flows easier to manage. For example, authentication might contain Welcome, Sign In, and Reset Password destinations.

A nested graph is useful when the destinations form one coherent flow and share navigation rules.

Conceptually:

```text
App Graph
├── Main Graph
│   ├── Home
│   ├── Product Details
│   └── Cart
└── Authentication Graph
    ├── Welcome
    ├── Sign In
    └── Reset Password
```

The exact graph-building API depends on the Navigation Compose version and whether the app uses typed routes.

### Authentication success

After a successful login, the application usually should not allow Back to return to the sign-in screen as if the user were still unauthenticated.

The flow should:

1. Confirm authentication through the authentication/data layer.
2. Update the signed-in application state.
3. Navigate to the appropriate authenticated destination.
4. Remove the authentication flow from the active back history when required.
5. Re-check access to protected resources independently of navigation.

Navigation is not an authorization boundary. Backend APIs and repositories must still enforce access rules.

## 10. Deep Links

A deep link lets an external source open a particular app destination. Examples include a product link in a message, a notification that opens an order, or a verified app link from a website.

A robust deep-link implementation needs to answer three questions:

- **Resolution:** Which destination corresponds to this URL?
- **Validation:** Are the incoming parameters well-formed and allowed?
- **History:** What should Back do after the destination opens?

For Android, deep links can be configured through navigation destinations and Android manifest intent filters. Verified Android App Links can associate a website domain with an app.

Illustrative URI:

```text
https://example.com/products/42
```

The app should resolve the product identifier, validate it, and load product details through the normal data layer. Do not trust the URL to establish a user's identity or permissions.

### Deep-link checklist

- Declare only the schemes and hosts the app intends to handle.
- Prefer HTTPS for web links and configure Android App Links verification when appropriate.
- Validate route arguments.
- Handle deleted, unavailable, or unauthorized resources.
- Define a sensible Back stack for external entry.
- Test links when the app is closed, already running, and in the background.

Deep-link declarations vary by graph style and Android manifest configuration. Follow the official documentation for the exact APIs used by the project.

## 11. State, Lifecycle, and Restoration

Navigation state and screen state are related, but they are not the same.

| State | Example | Typical owner |
|---|---|---|
| Navigation state | Current destination and back stack | Navigation component |
| Screen UI state | Loading indicator, selected filter, validation message | ViewModel or UI state holder |
| Domain state | Cart contents, authenticated user, product data | Domain/data layer |
| Temporary UI state | Expanded menu or a local animation | Compose state |
| Restorable user input | Draft form values that should survive recreation | Saved state or durable storage, as appropriate |

Do not put every screen value into navigation arguments. Navigation arguments should identify the destination and provide essential inputs; the screen's state holder should load and manage the rest.

### ViewModel scoping

Navigation destinations can provide lifecycle-aware `ViewModel` scoping. A destination-scoped ViewModel is usually appropriate for screen state. A graph-scoped ViewModel may be appropriate when multiple destinations in one flow intentionally share state.

Be explicit about ownership. A ViewModel scoped to a destination may be cleared when that destination leaves the back stack, while graph-scoped state can live longer. Verify the scope behavior of the selected Navigation version and setup.

### Restoration

Test how the app behaves after activity recreation and process death. The navigation library can restore supported navigation state, but app-specific state may still need to be persisted separately.

Never rely only on an in-memory route object to preserve important business data.

## 12. Navigation with ViewModels and UI Events

ViewModels should not depend directly on Android UI objects or retain a `NavController`. A clean boundary is for the ViewModel to expose screen state and user-facing events, while the UI or navigation layer performs the navigation.

One possible event model:

```kotlin
sealed interface ProductDetailsEvent {
    data object NavigateBack : ProductDetailsEvent
    data class OpenRelatedProduct(
        val productId: String
    ) : ProductDetailsEvent
}
```

A screen can report these events to its caller:

```kotlin
@Composable
fun ProductDetailsScreen(
    productId: String,
    onNavigateBack: () -> Unit,
    onOpenRelatedProduct: (String) -> Unit
) {
    // Observe state and render content.
    // Invoke callbacks in response to user actions.
}
```

The navigation host wires callbacks to navigation operations:

```kotlin
composable<ProductDetailsRoute> { entry ->
    val route = entry.toRoute<ProductDetailsRoute>()

    ProductDetailsScreen(
        productId = route.productId,
        onNavigateBack = {
            navController.popBackStack()
        },
        onOpenRelatedProduct = { relatedId ->
            navController.navigate(
                ProductDetailsRoute(relatedId)
            )
        }
    )
}
```

This design keeps the screen reusable and makes navigation behavior visible at the host boundary.

### One-time events need care

Navigation is often a one-time effect, while `StateFlow` represents state that may be replayed to new collectors. If navigation commands are modeled as state without careful consumption, a screen can navigate again after recreation or collection restarts.

Choose an event-delivery approach deliberately. Test it through lifecycle changes and avoid assuming that every event stream provides exactly-once delivery under all conditions.

## 13. Testing Navigation

Navigation should be tested as user-visible behavior and as stack policy—not only as a set of route declarations.

### What to test

| Test | Expected behavior |
|---|---|
| Tap a product on Home | Product Details appears with the correct ID |
| Press Back from details | The previous destination is restored |
| Open a repeated top-level destination | No unintended duplicate entry |
| Complete authentication | Protected destination opens and auth history is handled |
| Open a valid deep link | The intended destination is shown |
| Open an invalid deep link | The app handles it safely |
| Recreate the activity | Required navigation and screen state are restored |
| Press Back at the root | Platform-appropriate exit behavior occurs |

### UI test example

A Compose UI test can verify that tapping an item displays the expected destination. The exact test tags and setup depend on the app's screens.

```kotlin
@get:Rule
val composeRule = createComposeRule()

@Test
fun selectingProduct_opensProductDetails() {
    composeRule.setContent {
        AppNavigation()
    }

    composeRule
        .onNodeWithTag("product-42")
        .performClick()

    composeRule
        .onNodeWithText("Product details")
        .assertIsDisplayed()
}
```

This is illustrative: the app must expose a node tagged `product-42` and render the text `Product details`. Add the required Compose UI testing dependencies and imports for the project's test setup.

For deeper coverage, test navigation decisions independently from rendering where the architecture allows it, and use UI tests to verify the integrated experience.

## 14. Android Navigation in a KMP Architecture

A common architecture for shared business logic and Android-specific UI can look like this:

```text
:composeApp or :androidApp
└── Android UI
    ├── Navigation Compose
    ├── Navigation graph
    ├── Screens / Composables
    └── Android ViewModels
             │
             ▼
:shared
├── Domain models
├── Use cases
├── Repository interfaces
└── Shared business logic
             │
             ▼
Shared or platform-specific data implementations
```

This is one possible layout, not a mandatory module structure.

### What belongs where?

**Android source set (`androidMain` or Android app module):**

- `NavController`, `NavHost`, and AndroidX navigation graph declarations.
- Android-specific deep-link and intent integration.
- Android UI and lifecycle wiring.
- Android-only navigation adapters.

**Shared source set (`commonMain`):**

- Domain models and use cases.
- Business decisions such as whether a user is authenticated.
- Platform-neutral data contracts.
- Shared UI state and events, where useful.
- Route intent models only when they genuinely belong in the shared contract.

Do not place `androidx.navigation` classes in `commonMain`. If the project shares its UI using Compose Multiplatform, select a navigation library that explicitly supports the required targets and lifecycle behavior.

### Native iOS UI with shared KMP logic

If iOS uses SwiftUI or UIKit, keep its actual navigation in the iOS UI layer. Shared Kotlin can return authentication or workflow outcomes; Swift code can translate those outcomes into native navigation.

The goal is not to force Android and iOS to have identical navigation code. The goal is to share the right logic while preserving a coherent experience on each platform.

## 15. Common Mistakes

| Mistake | Why it hurts | Better approach |
|---|---|---|
| Putting AndroidX navigation classes in `commonMain` | Breaks common-source portability | Keep them in Android code |
| Passing `NavController` into every composable | Couples UI to the navigation framework | Prefer callbacks or a deliberate navigation interface |
| Using route strings everywhere | Makes route changes error-prone | Use typed routes where supported |
| Passing whole domain objects as arguments | Couples navigation to data representation | Pass stable IDs and load data |
| Keeping navigation policy in unrelated screens | Makes flow changes difficult | Define policy at a host or feature boundary |
| Ignoring the root Back behavior | Can cause confusing exits | Test root and nested back-stack behavior |
| Using `launchSingleTop` as a complete tab solution | It only covers one part of stack behavior | Define each tab's history and reselection policy |
| Treating deep links as trusted | Can expose invalid or unauthorized flows | Validate input and enforce authorization in the data/backend layers |
| Making ViewModels own `NavController` | Couples state holders to UI infrastructure | Emit state/events and navigate at the UI boundary |
| Assuming state is always restored | Important input may disappear | Test recreation and persist required data separately |
| Adding a custom navigation framework too early | Increases maintenance overhead | Use Navigation Compose until concrete requirements justify more |

## 16. Production Checklist

Use this checklist when reviewing Android navigation before release.

- [ ] Destinations and required arguments are clearly modeled.
- [ ] Navigation Compose and Kotlin serialization versions are compatible.
- [ ] Navigation APIs are kept out of `commonMain` unless a supported multiplatform abstraction is intentionally used.
- [ ] Screen composables do not needlessly depend on `NavController`.
- [ ] Back behavior is defined for root, nested, modal, and authentication flows.
- [ ] Repeated navigation does not create unwanted duplicate destinations.
- [ ] Deep links validate incoming arguments and handle missing resources.
- [ ] Protected resources enforce authorization independently of navigation.
- [ ] ViewModel and navigation-state ownership are explicit.
- [ ] Required UI state survives the lifecycle events the product supports.
- [ ] Navigation tests cover happy paths, invalid input, and Back behavior.
- [ ] Accessibility and platform conventions remain intact.
- [ ] Official documentation is checked when updating Navigation Compose.

## 17. Chapter Summary

Android navigation in a KMP project should be designed around a clear platform boundary.

With Jetpack Compose and Navigation Compose:

- Model destinations with typed routes when the selected library version supports them.
- Declare destinations in a `NavHost`.
- Use `NavController` to apply navigation actions and manage the back stack.
- Pass stable identifiers rather than large domain objects.
- Keep composables focused on UI and expose navigation callbacks.
- Treat deep links as external input and enforce access rules outside the navigation layer.
- Test Back behavior, stack policy, and lifecycle restoration.
- Keep Android-specific navigation in Android code when business logic is shared across platforms.

**The key principle:** share business rules where they create value, keep platform navigation at the correct boundary, and make every navigation transition intentional.
