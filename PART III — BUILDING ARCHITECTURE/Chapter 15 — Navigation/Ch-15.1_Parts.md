## 1. What Navigation Means in KMP

Navigation is the mechanism that moves a user between meaningful destinations in an application. A destination might be a login screen, product details, a dashboard, a settings page, or a multi-step checkout flow.

In a Kotlin Multiplatform project, navigation has an additional architectural dimension: **which parts of the navigation model should be shared, and which parts should remain platform-specific?**

Android and iOS have different application lifecycles, UI conventions, and integration points. A KMP app can share route definitions and navigation-related business decisions while keeping platform-specific behavior where it belongs. Alternatively, a project can use a shared UI and a multiplatform navigation library. The right boundary depends on the app's architecture and requirements.

Navigation is not simply a collection of screen-to-screen calls. A reliable navigation system needs to represent:

- **Destinations** — the places a user can visit.
- **Navigation state** — the current destination and the history needed to move backward.
- **Actions** — operations such as opening a destination, going back, or replacing a flow.
- **Arguments** — data required by a destination.
- **Transitions** — how the interface moves between destinations.
- **Platform integration** — lifecycle, system back behavior, deep links, and platform UI conventions.

These parts work together, but they do not all need to live in the same module.

## 2. The Main Parts of Navigation

A useful way to understand navigation is to break it into responsibilities.

| Part | Responsibility | Example |
|---|---|---|
| Route or destination | Identifies a screen or app location | `ProductDetails(productId)` |
| Navigation state | Records the current location and history | Home → Product Details |
| Back stack | Stores destinations that can be revisited | Home beneath Product Details |
| Navigation action | Expresses a requested movement | Open product details |
| Navigation controller / coordinator | Applies navigation actions and updates state | Push or pop a destination |
| Navigation host / container | Displays the destination selected by navigation state | Compose `NavHost` or a shared navigation container |
| Arguments | Supplies destination-specific data | Product ID |
| Deep-link handler | Maps an external URL or app link to a destination | `myapp://products/42` |
| Transition | Defines visual movement between destinations | Slide, fade, or platform-native transition |
| Platform adapter | Connects navigation to OS-specific behavior | Android back handling or an iOS navigation controller |

Terminology varies across frameworks. A library may combine the controller and host, or use a *router*, *navigator*, *stack*, or *coordinator* instead. Focus on the responsibility rather than the exact class name.

### A mental model

```text
User intent
    │
    ▼
Navigation action
    │
    ▼
Navigation state / back stack
    │
    ▼
Navigation host
    │
    ▼
Visible destination
```

The user taps a product. The application requests navigation to product details, updates the navigation state, and renders the corresponding destination.

## 3. Routes and Destinations

A **destination** is a place in the app. A **route** is the representation used to identify that place and, where necessary, carry the data required to display it.

For example:

- `Home`
- `Profile`
- `ProductDetails(productId = "42")`
- `Search(query = "headphones")`

Routes should express navigation intent clearly. They should not be tightly coupled to a particular composable, view controller, or UI implementation unless the chosen navigation framework specifically requires that representation.

### Prefer typed routes where possible

Typed routes make required arguments explicit and reduce errors caused by string-based navigation.

```kotlin
sealed interface AppRoute {
    data object Home : AppRoute
    data object Profile : AppRoute
    data class ProductDetails(
        val productId: String
    ) : AppRoute
}
```

This model distinguishes a static destination from one that needs an argument. The compiler can help identify missing or incorrectly typed values.

This is a **route model**, not a complete navigation implementation. A real application still needs a mechanism to store the current route, manage history, and render destinations.

### Route design guidelines

- Use stable identifiers rather than passing large domain objects between screens.
- Validate arguments when they originate outside the app, such as a deep link.
- Keep routes independent of UI classes when that makes the shared model easier to test.
- Avoid using display text as a route identifier.
- Decide how routes are serialized if they must survive process recreation or be restored from persistent state.

For example, pass a product ID to a details destination and load the product through the repository. This avoids coupling navigation history to a potentially stale in-memory object.

## 4. Navigation State and Back Stack

Navigation state describes where the user is and how the application got there.

A **back stack** is a common way to represent navigation history. When a user opens Product Details from Home, the stack might look like this:

```text
Top
┌─────────────────────┐
│ Product Details     │  ← Current destination
├─────────────────────┤
│ Home                │
└─────────────────────┘
Bottom
```

A back action removes the current destination and reveals the previous one, assuming the navigation policy allows that operation.

Not every navigation model is a simple stack. Bottom navigation, tabs, nested graphs, and multi-pane interfaces may preserve multiple navigation histories or use different state structures.

### State must have a clear owner

If multiple UI components independently modify navigation history, the app can end up with inconsistent back behavior. Prefer one well-defined navigation owner for each navigation flow.

That owner may be a navigation library's controller, a shared navigation state holder, or a platform coordinator. The important point is that the source of truth is explicit.

### State and lifecycle

Navigation state may need to survive events such as:

- Android activity or process recreation.
- iOS scene changes or restoration requirements.
- Configuration changes.
- Returning to a previously selected tab.
- Reopening a flow after authentication.

Do not assume that every in-memory navigation object automatically survives every lifecycle event. Confirm the restoration behavior of the chosen library and explicitly persist the state that the product requires.

## 5. Navigation Actions

Navigation actions describe what should happen to the current navigation state.

Common actions include:

| Action | Meaning | Typical use |
|---|---|---|
| Navigate / push | Add a destination to the current flow | Open details |
| Back / pop | Return to the previous destination | Close details |
| Replace | Replace the current destination | Move from splash to home |
| Reset / clear stack | Start a fresh navigation flow | Finish onboarding |
| Pop to destination | Return to an existing destination | Return to a checkout step |
| Open deep link | Resolve an external link into an app destination | Open a shared product |
| Select tab | Switch a top-level section | Move from Home to Profile |

Exact behavior depends on the navigation framework and its configuration. For example, opening the same destination repeatedly may create multiple stack entries unless the app intentionally prevents duplicates.

### Navigation should express intent

UI code is easier to maintain when it communicates the user's intention rather than manually manipulating implementation details across many screens.

For example, a product card can request `ProductDetails(productId)` without knowing whether the destination is shown by a shared Compose host, an Android navigation component, or an iOS coordinator.

This separation is particularly useful when the same business flow is used by multiple platform interfaces.

## 6. The Navigation Host or Coordinator

The navigation host or coordinator connects navigation state to the actual interface.

Its responsibilities commonly include:

1. Observing or owning navigation state.
2. Resolving the current destination.
3. Displaying the matching screen.
4. Applying transitions where supported.
5. Handling back actions and navigation boundaries.
6. Connecting nested flows or navigation graphs.

In Jetpack Compose Navigation, a `NavHost` associates a navigation graph with a controller and displays the active destination. In a shared-UI KMP app, a multiplatform navigation library may provide a similar host. In a native-UI architecture, an iOS coordinator or `UINavigationController` may handle presentation on iOS.

These approaches are alternatives, not interchangeable APIs. Choose the implementation that matches the app's UI and navigation architecture.

### Keep screen rendering separate from navigation policy

A screen should focus primarily on rendering state and emitting user events. Navigation policy should be handled by a well-defined layer rather than scattered across unrelated UI components.

For example, after a successful login, the authentication flow may request navigation to the dashboard and remove login destinations from the back history. That policy belongs to the flow or navigation owner—not to an arbitrary text field or button component.

## 7. Platform Integration

KMP does not require every part of navigation to be shared. The correct boundary depends on whether the app shares its UI, only its business logic, or a mixture of shared and native interfaces.

### Shared UI with Compose Multiplatform

A shared UI application can use a multiplatform navigation library to represent destinations and render screens across supported targets. Check the library's current target support, lifecycle integration, state restoration, and deep-link capabilities before adopting it.

### Shared logic with native UI

A project can share route-related domain decisions while using native navigation mechanisms:

- Android can use a navigation component or Compose navigation host.
- iOS can use SwiftUI navigation APIs, `UINavigationController`, or a coordinator pattern.

In this arrangement, shared Kotlin should expose platform-neutral intent or state. Platform code translates that intent into the navigation operations appropriate for its UI framework.

### A practical boundary

```text
             Shared Kotlin
     ┌──────────────────────────┐
     │ Route/domain intent      │
     │ Authentication outcome  │
     │ Navigation decisions    │
     └────────────┬─────────────┘
                  │
          Platform boundary
             ┌────┴────┐
             ▼         ▼
        Android UI   iOS UI
        Navigation   Navigation
```

This is a conceptual architecture, not a required module layout. If the UI itself is shared, the navigation host may also be shared.

## 8. A Typical Navigation Flow

Consider a shopping app where a user opens a product from the home screen.

1. **The user selects a product.** The product card emits a click event.
2. **The app identifies the destination.** It creates or requests a `ProductDetails` route with the product ID.
3. **The navigation owner processes the action.** It updates the active destination and history according to the app's rules.
4. **The host renders the destination.** The details screen receives the product ID.
5. **The screen loads its content.** A ViewModel or state holder obtains product information from the appropriate data layer.
6. **The user presses Back.** The navigation owner applies the platform's back behavior and returns to the previous destination.

The route should usually carry the minimum data needed to identify the destination. Product details themselves can be loaded through the repository, allowing the screen to refresh data and handle loading or error states independently.

## 9. Example: Modeling Routes in Shared Kotlin

The following example uses plain Kotlin to define a small route model. It has no dependency on Android classes, Swift types, or a particular navigation library.

```kotlin
sealed interface AppRoute {
    data object Home : AppRoute

    data object Cart : AppRoute

    data class ProductDetails(
        val productId: String
    ) : AppRoute

    data object Checkout : AppRoute
}
```

A UI event can describe the user's intent:

```kotlin
sealed interface HomeAction {
    data class OpenProduct(
        val productId: String
    ) : HomeAction

    data object OpenCart : HomeAction
}
```

A flow or UI layer can translate these events into navigation requests:

```kotlin
fun handleHomeAction(
    action: HomeAction,
    navigate: (AppRoute) -> Unit
) {
    when (action) {
        is HomeAction.OpenProduct -> {
            navigate(
                AppRoute.ProductDetails(action.productId)
            )
        }

        HomeAction.OpenCart -> {
            navigate(AppRoute.Cart)
        }
    }
}
```

This function does not maintain a back stack or render a screen. It demonstrates a useful boundary: the event handler expresses **where the user wants to go**, while the supplied navigation function determines how that request is carried out.

In production code, the navigation callback may be replaced with a typed navigator interface, a library-specific controller, or a platform adapter. Avoid introducing abstractions that simply duplicate the features of a navigation library without a concrete benefit.

## 10. Common Navigation Patterns

### Stack navigation

Destinations are pushed onto a stack and popped when the user goes back. Suitable for detail pages and linear flows.

### Bottom navigation or tabs

Top-level sections can maintain independent histories. Define whether switching tabs preserves each tab's stack and how reselection behaves.

### Nested navigation graphs

A larger flow can contain smaller flows, such as onboarding, authentication, and checkout. Encapsulation keeps each flow's destinations and transitions easier to reason about.

### Modal navigation

Dialogs, sheets, and full-screen modals represent temporary tasks. They may use a presentation model different from ordinary stack navigation.

### Deep-link navigation

An external URL or notification opens a specific destination. Deep-link handling must validate incoming values and determine the appropriate parent history so Back behaves sensibly.

### Authentication-gated navigation

A protected destination may require a signed-in user. Decide whether to preserve the requested destination while authentication occurs, and ensure logout clears or redirects protected navigation history as required.

## 11. Design Principles

Use these principles when building navigation for a maintainable KMP application:

- **Make route intent explicit.** Prefer typed destinations and clear action names.
- **Keep platform details at the boundary.** Share only what benefits from being shared.
- **Give navigation state a clear owner.** Avoid competing sources of truth.
- **Pass identifiers, not large objects.** Load screen data through the appropriate data layer.
- **Treat deep links as external input.** Validate parameters and handle unknown destinations.
- **Define Back behavior intentionally.** Include Android system Back, iOS navigation conventions, modals, and nested flows.
- **Plan restoration.** Verify which state survives recreation and how it is restored.
- **Test navigation policy.** Check stack changes, authentication gates, duplicate destinations, and deep-link resolution.
- **Respect platform UX.** Shared code should not force identical behavior where the platforms have different conventions.
- **Use a library deliberately.** Check current multiplatform support, maintenance, accessibility, and lifecycle behavior rather than selecting a library based only on its API style.

## 12. Common Mistakes

| Mistake | Why it causes problems | Better approach |
|---|---|---|
| Scattering navigation calls throughout UI code | Navigation rules become difficult to change | Centralize flow policy or use a clear navigator boundary |
| Using arbitrary strings for every route | Typos and missing arguments are easy to introduce | Use typed routes where practical |
| Passing entire domain objects between screens | Creates stale-data and serialization problems | Pass stable identifiers and reload data |
| Sharing Android-only navigation classes with common code | Breaks platform neutrality | Keep Android APIs in Android source sets |
| Assuming a shared UI is mandatory in KMP | Unnecessarily couples platform interfaces | Share UI only when it serves the product |
| Ignoring Back behavior | Users can return to invalid or unexpected screens | Define stack and platform behavior explicitly |
| Treating a deep link as trusted input | Can produce invalid states or expose protected flows | Validate and authorize before displaying content |
| Ignoring restoration | Navigation can reset unexpectedly after recreation | Test the chosen framework's restoration behavior |
| Building a custom framework without need | Adds maintenance burden | Start with the smallest abstraction that meets requirements |

## 13. Chapter Summary

Navigation is a system of related responsibilities—not just a call that opens another screen.

The key parts are:

- **Routes and destinations** identify where the user can go.
- **Navigation state and back stack** describe the current location and history.
- **Actions** express the movement the user or application requests.
- **A host or coordinator** connects navigation state to rendered screens.
- **Arguments and deep links** provide destination input.
- **Platform integration** handles lifecycle, Back behavior, and native conventions.

In KMP, the architectural decision is not simply whether navigation should be shared. It is **which navigation responsibilities benefit from sharing, and where platform-specific behavior should remain**.

With these parts understood, the next step is to see how they fit into a concrete navigation architecture and how a chosen library or platform implementation manages state and transitions.
