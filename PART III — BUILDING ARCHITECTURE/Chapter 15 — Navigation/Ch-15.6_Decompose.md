## 1. Why Decompose?

Kotlin Multiplatform (KMP) lets an application share domain logic, data access, and potentially presentation logic across Android, iOS, desktop, and other targets. Navigation is more complicated than choosing which composable to display: real applications must also manage component lifecycles, back behavior, saved state, nested flows, and platform integration.

**Decompose** is a Kotlin Multiplatform library for building component-oriented applications. It provides navigation primitives and lifecycle/state-management building blocks that can be used from shared Kotlin code, while allowing each platform to render the resulting component tree using its own UI framework.

Decompose is useful when you want to:

- Keep navigation and presentation state in common Kotlin code.
- Model screens as lifecycle-aware components.
- Represent navigation as typed configurations rather than scattered string routes.
- Support stacks, child components, tabs, and nested flows.
- Share presentation logic while using Compose Multiplatform or native SwiftUI/UIKit for rendering.
- Test navigation behavior without launching a full UI.

It is not the only valid KMP navigation approach. AndroidX Navigation, Voyager, and platform-native navigation can also be appropriate depending on the architecture. The important choice is to make navigation ownership explicit and consistent.

### Navigation is more than screen selection

A production navigation system typically coordinates several concerns:

| Concern | What it means |
|---|---|
| Navigation state | Which screens or flows are active |
| Component lifecycle | When a component is created, started, stopped, or destroyed |
| State preservation | What survives configuration changes or process recreation |
| Back handling | Which active component gets the first chance to handle Back |
| Arguments | How a destination receives the data it needs |
| Platform integration | How URLs, system Back, and native presentation work |
| UI rendering | How each platform displays a component |

Decompose gives you primitives for these concerns, but application-level policies—such as authorization, analytics, and error handling—still need to be designed.

## 2. The Core Mental Model

The central idea is to separate **navigation state**, **component behavior**, and **UI rendering**.

```text
┌───────────────────────────────────────────┐
│ Platform entry point                      │
│ Android Activity / iOS App or UIViewController │
└──────────────────────┬────────────────────┘
                       │
                       ▼
┌───────────────────────────────────────────┐
│ Root component                            │
│ Owns the top-level navigation model       │
└──────────────────────┬────────────────────┘
                       │
                       ▼
┌───────────────────────────────────────────┐
│ Child components                          │
│ Home · Search · Details · Checkout        │
│ Each owns focused presentation behavior   │
└──────────────────────┬────────────────────┘
                       │
                       ▼
┌───────────────────────────────────────────┐
│ Shared domain and data layers              │
│ Use cases · Repositories · APIs · Database│
└───────────────────────────────────────────┘
```

A component is not merely a UI function. It can own:

- A lifecycle.
- State and event handling.
- Child components.
- Navigation callbacks.
- A `CoroutineScope` or lifecycle-aware work.
- Dependencies needed for its feature.

A Compose function or SwiftUI view then renders that component. This separation makes navigation behavior easier to test and keeps platform-specific UI concerns out of the shared navigation model.

### The three responsibilities

1. **Configuration** describes a destination and the arguments needed to create it.
2. **Navigation model** manages active configurations and transitions.
3. **Component** implements the behavior and state for an active destination.

Keep configurations small and stable. A configuration should generally contain identifiers or serializable values, not repositories, view models, or entire domain objects.

## 3. Add Decompose to a KMP Project

Decompose is published as a set of Kotlin Multiplatform artifacts. The exact artifact coordinates and APIs can evolve, so check the current official setup documentation and release notes before selecting versions.

A typical version-catalog entry may look like this:

```toml
# gradle/libs.versions.toml
[versions]
decompose = "<current-compatible-version>"

[libraries]
decompose = { module = "com.arkivanov.decompose:decompose", version.ref = "decompose" }
decompose-compose = { module = "com.arkivanov.decompose:extensions-compose", version.ref = "decompose" }
```

Replace the placeholder with a real version compatible with your Kotlin and Compose Multiplatform setup. Do not copy a version blindly from an old tutorial.

In a shared module, dependencies commonly belong in `commonMain` when the artifact supports the required targets:

```kotlin
// shared/build.gradle.kts
kotlin {
    sourceSets {
        commonMain.dependencies {
            implementation(libs.decompose)
            implementation(libs.decompose.compose)
        }
    }
}
```

Some projects use newer Decompose Compose integration artifacts or a different dependency arrangement. Follow the documentation for the exact library version you adopt.

### Dependency rule

Do not add a library to `commonMain` unless it supports every target compiled by that source set. If an integration is Android-only, keep it in `androidMain`. The shared navigation model should not depend on `androidx.activity`, Android `Context`, or iOS framework types.

## 4. Define Navigation Configuration

For a simple application, the root navigation can use a stack of configurations.

A configuration identifies the destination and carries the minimum information needed to construct it. The following example illustrates the shape; adapt serialization and constructor details to the Decompose version in your project.

```kotlin
import kotlinx.serialization.Serializable

@Serializable
sealed interface RootConfig {

    @Serializable
    data object Home : RootConfig

    @Serializable
    data object Search : RootConfig

    @Serializable
    data class ProductDetails(
        val productId: String
    ) : RootConfig
}
```

If your chosen Decompose API requires a particular configuration interface or serialization strategy, implement that contract according to its official documentation. The architectural point remains the same: configurations should be immutable descriptions of destinations.

### Why typed configurations are preferable to string routes

Avoid this style:

```kotlin
// Fragile: strings can drift and arguments are untyped.
navigate("product-details/$productId")
```

Prefer a typed destination:

```kotlin
RootConfig.ProductDetails(productId = productId)
```

Typed configurations make destination variants visible to the compiler and help refactoring tools. They do not eliminate validation: a product ID can still be missing, malformed, or unauthorized.

### Keep configuration data minimal

Good configuration:

```kotlin
RootConfig.ProductDetails(productId = "sku-482")
```

Risky configuration:

```kotlin
// Avoid passing a large mutable model as navigation state.
RootConfig.ProductDetails(
    product = entireProductObject,
    repository = productRepository
)
```

Load the current product through a repository using its identifier. This avoids stale serialized data and keeps navigation state compact.

## 5. Build a Root Component

The root component owns the top-level navigation model and creates child components for the active destinations.

A typical Decompose stack uses concepts such as `StackNavigation`, `ChildStack`, and a stack navigator. Names and generic signatures can vary between releases; consult the API documentation for the version used by your project.

The following is an architectural sketch of the responsibilities:

```kotlin
class RootComponent(
    componentContext: ComponentContext,
    private val onOpenProduct: (String) -> Unit
) : ComponentContext by componentContext {

    // Own the navigation controller/model here.
    // Expose an observable child stack to the UI.
    // Create destination components from RootConfig values.

    fun openHome() {
        // Replace or navigate to the Home configuration.
    }

    fun openSearch() {
        // Push or activate the Search configuration.
    }

    fun openProductDetails(productId: String) {
        // Push ProductDetails(productId).
    }

    fun onBack() {
        // Delegate to the navigation model's back operation.
    }
}
```

This intentionally focuses on the component contract rather than presenting a version-specific constructor as universally compilable. In a real implementation, initialize the Decompose navigation model in the root constructor, expose its `ChildStack`, and supply a child factory that maps each configuration to a component.

### Root component responsibilities

- Define the application-level navigation graph.
- Create and own top-level child components.
- Expose state needed by the platform UI.
- Coordinate root-level back behavior.
- Accept external entry points such as deep links.
- Avoid implementing feature-specific business rules itself.

### Do not turn the root into a god object

A root component should not become the owner of every form field, API request, validation rule, and dialog in the application. Its primary job is to coordinate navigation and the lifecycle of top-level features. Delegate behavior to child components.

## 6. Create Child Components

A child component owns the behavior of one destination or feature flow. For example, a product details component can accept a product identifier and a callback for navigation.

```kotlin
interface ProductDetailsComponent {
    val productId: String

    fun onRetry()
    fun onBack()
}
```

A concrete implementation can receive its `ComponentContext`, repository, and navigation callbacks through constructor injection:

```kotlin
class DefaultProductDetailsComponent(
    componentContext: ComponentContext,
    override val productId: String,
    private val repository: ProductRepository,
    private val onBackRequested: () -> Unit
) : ProductDetailsComponent,
    ComponentContext by componentContext {

    override fun onRetry() {
        // Ask the feature state holder to reload product details.
    }

    override fun onBack() {
        onBackRequested()
    }
}
```

The `ProductRepository` and `ComponentContext` types represent application/library contracts that must exist in your project. Add imports and lifecycle-aware state management appropriate to your selected Decompose and coroutine versions.

### Why callbacks are useful

The child can request an action without knowing how the parent implements navigation. It does not need to depend directly on the root class.

```text
ProductDetailsComponent
        │
        │ onBackRequested()
        ▼
RootComponent
        │
        │ pops the active stack entry
        ▼
Previous child becomes active
```

This reduces coupling and makes child components easier to test in isolation.

### Avoid passing the root everywhere

Do not pass the entire root component into every child just to call `navigate()`. Prefer narrow callbacks or a clearly defined navigation contract. That prevents feature components from depending on unrelated root functionality.

## 7. Render Components in Compose Multiplatform

Decompose separates the navigation model from the UI. A Compose UI can observe the root's child stack and render the active child using the Decompose Compose integration.

The exact adapter and helper function depend on the library version, but the rendering structure is conceptually similar to this:

```kotlin
@Composable
fun RootContent(
    component: RootComponent
) {
    // Observe the root's child stack using the
    // Decompose Compose integration for your version.

    // Render the active child according to its configuration:
    // Home             -> HomeContent(...)
    // Search           -> SearchContent(...)
    // ProductDetails   -> ProductDetailsContent(...)
}
```

Use the official child-stack rendering API for your selected version rather than manually collecting internal state or inventing lifecycle behavior. The adapter should keep component lifecycle transitions aligned with which children are active.

A feature renderer can stay simple:

```kotlin
@Composable
fun ProductDetailsContent(
    component: ProductDetailsComponent
) {
    // Render loading, success, empty, and error states.
    // Forward user actions to the component.
}
```

### UI should render state, not own navigation policy

The UI can forward user intent:

```kotlin
Button(
    onClick = { component.onRetry() }
) {
    Text("Try again")
}
```

But it should not reconstruct navigation state independently. If the Compose UI owns one stack and the shared component owns another, Back behavior and restoration can become inconsistent.

### Compose Multiplatform and native iOS UI

Decompose does not require the same UI toolkit on every platform. A project can:

- Render shared components with Compose Multiplatform.
- Render the same component contracts from SwiftUI/UIKit.
- Share domain and navigation logic while keeping rendering native.

For native iOS rendering, expose a stable bridge from Kotlin to Swift. Avoid leaking internal Decompose implementation details across the bridge unless that is a deliberate integration choice.

## 8. Handle Back Navigation

Back navigation is a behavior contract, not just a button click.

A useful policy is:

1. Give the currently active feature a chance to handle Back if it owns a local state such as an expanded panel or an unsaved form.
2. If the feature does not consume Back, pop the current navigation stack when possible.
3. If the root stack cannot go back, let the platform apply its root-level behavior.

The exact integration differs by platform. Android system Back, iOS navigation gestures, desktop Escape, and browser Back should not be assumed to behave identically.

### A narrow back contract

```kotlin
interface BackHandler {
    /**
     * Returns true when this component consumed the Back action.
     */
    fun handleBack(): Boolean
}
```

This is an application-level example, not a replacement for Decompose's own back-handler facilities. Prefer the library's supported back dispatcher/handler integration when available.

### Example decision flow

```text
Back action received
        │
        ▼
Does the active feature consume Back?
        │
   ┌────┴────┐
  Yes        No
   │          │
   ▼          ▼
Stop      Can navigation pop?
               │
          ┌────┴────┐
         Yes        No
          │          │
          ▼          ▼
       Pop stack   Platform/root
                   default behavior
```

### Unsaved changes

For forms or checkout flows, define an explicit policy:

- Is Back allowed immediately?
- Should a confirmation dialog appear?
- Is draft state saved automatically?
- Can a deep link replace the current flow?

Do not scatter these decisions across composables. Keep the decision close to the feature that owns the state, and route the final navigation action through the parent or navigation model.

## 9. Pass Arguments Between Screens

Pass the smallest stable identifier required to load destination data.

```kotlin
root.openProductDetails(productId = "sku-482")
```

The child component receives the identifier:

```kotlin
class DefaultProductDetailsComponent(
    componentContext: ComponentContext,
    private val productId: String,
    private val repository: ProductRepository
) : ComponentContext by componentContext {

    // Load current data from the repository using productId.
}
```

### Validate at the boundary

Navigation arguments are not automatically trusted merely because they are typed.

For an incoming product ID, validate:

- The value is not blank.
- The format matches the backend contract.
- The product exists.
- The current user is authorized to view it.

A well-formed ID does not grant access. Authorization belongs in the appropriate domain/data layer, not solely in the navigation component.

### Use result callbacks for small return values

If a child flow needs to return a result—such as whether a filter was applied—use an explicit result callback or shared state contract. Avoid using a global mutable singleton as an implicit communication channel.

For complex results, prefer storing the selected value in a shared state holder or repository and return a stable identifier.

## 10. Preserve State and Restore Navigation

State restoration is a critical part of navigation design. Users expect to return to a meaningful screen after an app is recreated, but not every piece of state should be persisted.

Decompose provides state-saving/restoration mechanisms that integrate with its component and navigation models. The exact setup depends on the version and platform host.

### Distinguish three kinds of state

| State type | Examples | Recommended treatment |
|---|---|---|
| Navigation state | Current stack, active tab | Save through the supported navigation state mechanism |
| UI state | Search query, selected filter, expanded section | Save when it materially improves user continuity |
| Domain state | Cart, order, account data | Persist in the appropriate repository or backend |

Do not assume that saving the navigation stack also saves every child component's local state, coroutine, or loaded domain model.

### State restoration rules

- Keep navigation configurations serializable or compatible with the library's state-saving mechanism.
- Persist identifiers rather than large mutable objects.
- Re-load data that may have changed on the server.
- Handle deleted or inaccessible destinations gracefully.
- Keep restoration resilient to schema changes between app versions.
- Test process recreation on Android and app relaunch behavior on iOS separately.

### Example restoration scenario

1. The user opens a product details screen.
2. The navigation model stores the active configuration with the product identifier.
3. The operating system terminates the process.
4. The app recreates the root component using the supported saved-state integration.
5. The product details component is rebuilt.
6. The feature reloads current product data from the repository.

The goal is not to preserve an old in-memory object graph. It is to restore a meaningful destination and reconstruct the required state safely.

## 11. Deep Links and External Entry Points

A deep link starts the app at a destination selected by an external URL, notification, or another app. Decompose can represent the destination in its navigation model, while platform-specific code remains responsible for receiving and validating the incoming link.

For example:

```text
myapp://products/sku-482
```

A robust deep-link pipeline looks like this:

```text
Incoming URL
    │
    ▼
Platform link handler
    │
    ▼
Parse and validate URL
    │
    ▼
Resolve destination configuration
    │
    ▼
Apply navigation policy
    │
    ▼
Create/activate destination component
    │
    ▼
Load and authorize destination data
```

### Do not parse URLs in every screen

Centralize URL parsing and route resolution. A parser can convert an incoming URI into a typed intent:

```kotlin
sealed interface DeepLinkIntent {
    data class Product(val productId: String) : DeepLinkIntent
    data object Home : DeepLinkIntent
}
```

The actual URL parser is platform- or library-specific. Keep its output independent of Android `Intent` or iOS `NSUserActivity` types so that common navigation policy remains portable.

### Define a back-stack policy

Opening a product link raises a product decision: should the app replace the current stack, add a destination above the existing stack, or construct a canonical path such as Home → Product Details?

Choose a policy deliberately. A link opened from a cold start may need a different back stack from the same link opened while the user is already inside the app.

### Security checks

- Accept only supported schemes and hosts.
- Validate identifiers before creating destination state.
- Do not treat a deep link as proof of authorization.
- Avoid placing access tokens or sensitive data in URLs.
- Define fallback behavior for expired, malformed, or unsupported links.

## 12. Tabs and Nested Navigation

Many applications have independent navigation histories for sections such as Home, Search, Orders, and Profile. A single global stack can make tab behavior awkward if each tab is expected to retain its own history.

A component-oriented design can model each tab as a child component with its own navigation state.

```text
Root
└── Tab component
    ├── Home tab
    │   └── Home → Category → Product
    ├── Search tab
    │   └── Search → Results → Product
    └── Profile tab
        └── Profile → Settings
```

### Decide the expected tab behavior

Before implementing tabs, document the intended rules:

- Does switching tabs preserve each tab's back stack?
- Does tapping the selected tab return to its root?
- Does selecting a tab reset scroll position?
- Which stack handles Back?
- Can a deep link activate a non-selected tab?
- Does the application restore the previously selected tab?

### Keep navigation ownership local

A tab component should own the navigation history for its feature. The root should coordinate which tab is active, not duplicate every tab's internal stack.

This is especially useful when different teams own different feature areas: each team can maintain its own child component contract while the root integrates them.

## 13. Dependency Injection and Shared Business Logic

Decompose components are ordinary Kotlin objects, so constructor injection works well.

```kotlin
class DefaultRootComponent(
    componentContext: ComponentContext,
    private val productRepository: ProductRepository,
    private val sessionRepository: SessionRepository
) : ComponentContext by componentContext
```

A production implementation should pass only the dependencies each component needs. Use your project's DI framework—such as Koin, kotlin-inject, or a manually assembled component tree—without making the navigation layer depend on a specific platform container.

### Recommended dependency direction

```text
UI renderer
    │ calls
    ▼
Feature component
    │ uses
    ▼
Use cases / domain contracts
    │ implemented by
    ▼
Repositories and data sources
```

Navigation should not directly execute SQL, build HTTP requests, or contain business validation. Instead, a feature component invokes a use case or repository contract and exposes the resulting state to the UI.

### Authentication and protected destinations

Do not rely on hiding a screen to secure it. Before exposing protected data:

1. Resolve the current session.
2. Apply navigation policy for signed-out users.
3. Validate access in the domain/data layer.
4. Handle expired sessions during an active flow.
5. Return to a safe destination after sign-out.

If a user signs out while viewing a protected child, define whether the root resets the stack, displays a session-expired flow, or preserves a non-sensitive public destination.

## 14. Lifecycle-Aware Work

Decompose components can participate in lifecycle management. Use that lifecycle to align feature work with the component's active state, while keeping business operations resilient to cancellation and recreation.

### Examples of lifecycle-sensitive work

- Collecting a screen-specific flow.
- Registering a temporary listener.
- Starting a camera preview or location subscription.
- Cancelling UI-bound work when a component is destroyed.
- Suspending expensive rendering-related computation when inactive.

### Avoid launching everything in an unstructured scope

This is risky:

```kotlin
// Risky if this scope outlives the component or has no clear owner.
GlobalScope.launch {
    // Screen-specific request
}
```

Prefer a lifecycle-aware scope owned by the component or an explicit use-case scope. The exact API depends on the Decompose and coroutine versions in use.

### Lifecycle is not durable storage

A component being recreated does not mean its in-memory state has survived. Use saved state for navigation/UI continuity and repositories for durable business data.

Also distinguish cancellation from failure. If a component disappears while a request is running, cancellation may be expected; network errors, authorization failures, and invalid data need explicit handling.

## 15. Testing Navigation

The strongest reason to model navigation outside the UI is that its behavior can be tested directly.

### Unit-test the navigation contract

Test cases should cover:

- Initial destination.
- Navigating from Home to Search.
- Opening details with a valid identifier.
- Back returning to the expected previous destination.
- Root-level Back behavior.
- Tab stack preservation.
- Deep-link resolution.
- Authentication redirects.
- Restoration of a previously active destination.
- Invalid or inaccessible destination arguments.

### Example behavior test outline

```kotlin
class RootNavigationTest {

    @Test
    fun openingProductDetailsUsesRequestedProductId() {
        // Arrange a root component with test dependencies.
        // Act: open product details for "sku-482".
        // Assert: the active child represents ProductDetails("sku-482").
    }
}
```

This is an outline, not a complete runnable test: instantiate the component with the testing facilities and constructors provided by your chosen Decompose version.

### Test the UI separately

Use Compose Multiplatform or platform UI tests for:

- Whether the correct child content is rendered.
- Whether buttons invoke the expected component callbacks.
- Whether system Back is wired correctly.
- Whether dialogs and transitions behave correctly.
- Accessibility semantics and focus behavior.

Avoid making every navigation unit test a screenshot or end-to-end test. Most stack transitions can be verified much faster at the component/model level.

## 16. Common Mistakes

| Mistake | Why it causes problems | Better approach |
|---|---|---|
| Mixing UI state and navigation state | Recomposition can create confusing behavior | Keep the navigation model in the component layer |
| Using untyped route strings everywhere | Typos and argument parsing spread through the app | Use typed configurations |
| Passing full domain objects in configurations | State becomes large and stale | Pass stable identifiers |
| Putting all logic in the root | Root becomes difficult to change and test | Delegate to child components |
| Passing the root to every child | Features become tightly coupled | Use narrow callbacks or contracts |
| Ignoring restoration | Users can return to broken or empty destinations | Test recreation and relaunch explicitly |
| Treating a deep link as authorization | Protected data may be exposed | Validate access in the domain/data layer |
| Duplicating navigation state in Compose | Back stack and rendered UI can diverge | Keep one source of navigation truth |
| Using global coroutine scopes | Work may outlive its owner | Tie work to the correct lifecycle/scope |
| Assuming every platform has identical Back behavior | UX differs between Android, iOS, desktop, and web | Define and test platform-specific policies |
| Over-abstracting every navigation call | The graph becomes harder to follow | Abstract only stable boundaries |
| Copying API snippets across library versions | Constructor names and integrations may change | Verify against the installed version's documentation |

## 17. Production Checklist

Use this checklist during implementation and code review.

### Architecture
- [ ] Navigation ownership is explicit.
- [ ] Configurations are typed and contain minimal stable data.
- [ ] Feature behavior lives in child components or domain use cases.
- [ ] Components depend on narrow contracts rather than the entire root.
- [ ] Shared code does not depend on Android-only or iOS-only APIs.

### Lifecycle and state
- [ ] Component lifecycle is integrated with the platform host.
- [ ] Screen-specific work has a clear cancellation owner.
- [ ] Navigation restoration is configured and tested.
- [ ] Durable business state lives in repositories or the backend.
- [ ] Invalid restored destinations have a safe fallback.

### Navigation behavior
- [ ] Back behavior is defined for root, nested flows, and tabs.
- [ ] Unsaved forms have an explicit exit policy.
- [ ] Deep links resolve to typed intents/configurations.
- [ ] Cold-start and warm-start deep links have deliberate stack behavior.
- [ ] Authentication changes reset or redirect navigation safely.

### Quality
- [ ] Navigation transitions have unit tests.
- [ ] Platform Back and link entry points have integration tests.
- [ ] UI tests verify destination rendering and accessibility.
- [ ] Dependencies are compatible with every declared KMP target.
- [ ] Code examples and integrations match the exact library version in the build.

## 18. Summary

Decompose provides a component-oriented foundation for Kotlin Multiplatform navigation. Its value is not simply that it can move between screens. It helps teams organize navigation state, child component lifecycles, and presentation behavior around explicit component boundaries.

Keep these principles in mind:

1. Model destinations with typed configurations.
2. Let the root coordinate top-level navigation and let children own feature behavior.
3. Keep rendering separate from navigation policy.
4. Pass identifiers instead of large mutable objects.
5. Treat restoration, Back behavior, tabs, and deep links as explicit product requirements.
6. Use lifecycle-aware work and keep durable data outside in-memory components.
7. Test navigation behavior independently from the UI.
8. Verify library APIs against the version actually used by your project.

The strongest KMP architecture is not the one that forces every platform into an identical UI. It is the one that shares the right responsibilities while respecting each platform's lifecycle and user expectations.
