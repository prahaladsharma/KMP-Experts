# Chapter 10 — Project Structure

## Part 3 — Layers

In the previous parts, we established two ideas:

- A KMP project is made of clearly defined **parts**.
- Clean Architecture is primarily about **responsibility and dependency direction**.

The next step is understanding **layers**.

A layer is a boundary that groups code according to the kind of responsibility it owns.

A simple KMP application can be visualized as:

```text
┌───────────────────────────────────────────┐
│                Presentation               │
│       UI State / ViewModel / Events       │
└─────────────────────┬─────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│                  Domain                   │
│      Business Rules / Use Cases / Models  │
└─────────────────────┬─────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│                   Data                    │
│   Repository / Network / Database / DTO  │
└───────────────────────────────────────────┘
```

These layers are not merely folder names.

They answer a more important question:

> **What kind of decision is allowed to live here?**

That question becomes especially important in Kotlin Multiplatform because a shared module can contain code that is portable across platforms while still having very different responsibilities.

---

# 1. What Is a Layer?

A layer is a logical boundary around a particular type of responsibility.

For example:

| Layer | Main responsibility |
|---|---|
| Presentation | User-facing state and interaction |
| Domain | Business rules and application decisions |
| Data | Obtaining, storing, and transforming data |
| Platform | Operating-system-specific capabilities |
| Infrastructure | Technical implementation details |
| Application | Composition and startup |

A small KMP project does not necessarily need all of these as separate modules.

The important distinction is:

```text
Layer ≠ Module
```

A layer can exist inside one module:

```text
shared/
└── commonMain/
    ├── presentation/
    ├── domain/
    └── data/
```

Or layers can be separated into modules:

```text
presentation/
domain/
data/
core/
```

The architecture remains valid as long as the responsibilities and dependency direction are clear.

---

# 2. Why Layers Matter

Without layers, code tends to grow around technical convenience.

For example:

```text
OrderScreen
    │
    ├── API call
    ├── JSON parsing
    ├── validation
    ├── database query
    ├── business calculation
    ├── analytics
    └── navigation
```

Everything may work.

But the screen now knows too much.

A layered architecture changes the flow:

```text
UI
 │
 ▼
Presentation
 │
 ▼
Domain
 │
 ▼
Data
 │
 ├── Network
 └── Database
```

Each layer can concentrate on one kind of problem.

The result is easier to:

- understand
- test
- replace
- extend
- review
- share across platforms

---

# 3. The Classic Three Layers

For most KMP applications, three layers provide a strong starting point:

```text
             ┌─────────────────┐
             │  Presentation   │
             └────────┬────────┘
                      │
                      ▼
             ┌─────────────────┐
             │     Domain      │
             └────────┬────────┘
                      │
                      ▼
             ┌─────────────────┐
             │      Data       │
             └─────────────────┘
```

The responsibilities are intentionally different.

### Presentation

Answers:

> What should the user see and how should the UI react?

### Domain

Answers:

> What should the application do?

### Data

Answers:

> Where does the required data come from and how is it persisted?

This separation gives the project a useful vocabulary.

---

# 4. Presentation Layer

The presentation layer represents the state and interaction model exposed to the UI.

A common structure:

```text
presentation/
├── state/
├── event/
├── effect/
└── viewmodel/
```

For example:

```kotlin
data class OrderUiState(
    val isLoading: Boolean = false,
    val order: OrderUiModel? = null,
    val error: String? = null
)
```

The presentation layer can process user actions:

```kotlin
sealed interface OrderEvent {

    data object Load : OrderEvent

    data object Cancel : OrderEvent
}
```

The presentation component coordinates with the domain:

```kotlin
class OrderViewModel(
    private val getOrder: GetOrderUseCase,
    private val cancelOrder: CancelOrderUseCase
) {
    // Presentation state and event handling
}
```

The ViewModel does not need to know:

```text
How HTTP works
How the database works
How JSON is parsed
How Android stores credentials
How iOS stores credentials
```

Those responsibilities belong elsewhere.

---

# 5. Presentation Is Not the UI

This distinction is important in KMP.

The UI can be:

```text
Android
├── Jetpack Compose
└── Android Views

iOS
├── SwiftUI
└── UIKit
```

The presentation layer can contain shared application state:

```text
Shared Presentation
       │
       ├── UI State
       ├── Events
       ├── Reducers
       ├── ViewModels / Presenters
       └── Presentation mapping
```

The actual UI can remain platform-specific:

```text
              Shared Presentation
                      │
             ┌────────┴────────┐
             ▼                 ▼
        Android UI          iOS UI
        Compose             SwiftUI
```

This allows native UI technologies to consume the same application state without forcing the UI layer itself to be identical.

---

# 6. Domain Layer

The domain layer represents the business behavior of the application.

Typical contents:

```text
domain/
├── model/
├── usecase/
├── repository/
└── validation/
```

Example model:

```kotlin
data class Product(
    val id: String,
    val name: String,
    val price: Money
)
```

Example use case:

```kotlin
class CalculateDiscountUseCase {

    operator fun invoke(
        price: Money,
        customerType: CustomerType
    ): Money {
        return when (customerType) {
            CustomerType.Regular -> price
            CustomerType.Premium -> price * 0.90
        }
    }
}
```

This code describes a business rule.

It should not need:

```kotlin
Context
Activity
UIViewController
Retrofit
Room
SwiftUI
Compose
```

The domain layer should remain as independent as practical.

---

# 7. Domain Models vs UI Models

A domain model represents the application's business meaning.

A UI model represents what the presentation layer needs.

For example:

```kotlin
data class Order(
    val id: String,
    val status: OrderStatus,
    val total: Money
)
```

The UI may need:

```kotlin
data class OrderUiModel(
    val title: String,
    val statusText: String,
    val formattedTotal: String,
    val canCancel: Boolean
)
```

The mapping can happen at the presentation boundary:

```kotlin
fun Order.toUiModel(): OrderUiModel {
    return OrderUiModel(
        title = "Order #$id",
        statusText = status.name,
        formattedTotal = total.format(),
        canCancel = status == OrderStatus.Pending
    )
}
```

This prevents UI-specific formatting from leaking into the domain.

# 8. Data Layer

The data layer handles external data sources.

A typical structure:

```text
data/
├── repository/
├── remote/
├── local/
├── mapper/
└── model/
```

For example:

```text
Remote API
    │
    ▼
Remote Data Source
    │
    ▼
DTO
    │
    ▼
Mapper
    │
    ▼
Domain Model
```

Local storage can follow the same boundary:

```text
Database
    │
    ▼
Local Data Source
    │
    ▼
Entity
    │
    ▼
Mapper
    │
    ▼
Domain Model
```

The repository coordinates these sources.

---

# 9. Repository Layer

A repository is a boundary between application logic and data access.

The domain can define:

```kotlin
interface OrderRepository {

    suspend fun getOrder(
        id: String
    ): Order

    suspend fun cancelOrder(
        id: String
    )
}
```

The data layer implements it:

```kotlin
class OrderRepositoryImpl(
    private val remote: OrderRemoteDataSource,
    private val local: OrderLocalDataSource
) : OrderRepository {

    override suspend fun getOrder(
        id: String
    ): Order {
        val response = remote.getOrder(id)

        val order = response.toDomain()

        local.save(order)

        return order
    }

    override suspend fun cancelOrder(
        id: String
    ) {
        remote.cancelOrder(id)
        local.remove(id)
    }
}
```

The domain knows the contract.

The data layer knows the implementation.

```text
Domain
  │
  ▼
OrderRepository
  ▲
  │
Data
  │
  ├── Remote
  └── Local
```

---

# 10. Network Layer

The network layer belongs to the data/infrastructure side.

A possible structure:

```text
network/
├── api/
├── dto/
├── client/
└── mapper/
```

Example API contract:

```kotlin
interface OrderApi {

    suspend fun getOrder(
        id: String
    ): OrderDto
}
```

The network implementation might use a multiplatform-compatible HTTP client.

The important architectural boundary is:

```text
Domain
   │
   ▼
Repository
   │
   ▼
Network abstraction
   │
   ▼
HTTP implementation
```

The domain should not need to know which HTTP library is being used.

---

# 11. Database Layer

Persistence belongs to the data/infrastructure side.

For example:

```text
data/
└── local/
    ├── database/
    ├── entity/
    ├── dao/
    └── mapper/
```

The domain should not depend directly on a database entity.

For example:

```kotlin
data class OrderEntity(
    val id: String,
    val status: String,
    val totalCents: Long
)
```

The domain model can remain:

```kotlin
data class Order(
    val id: String,
    val status: OrderStatus,
    val total: Money
)
```

Mapping creates the boundary:

```kotlin
fun OrderEntity.toDomain(): Order {
    return Order(
        id = id,
        status = OrderStatus.valueOf(status),
        total = Money(totalCents)
    )
}
```

This allows the storage representation to evolve independently.

---

# 12. Platform Layer

KMP introduces another important boundary:

```text
Shared Layers
      │
      ▼
Platform Boundary
      │
 ┌────┴────┐
 ▼         ▼
Android    iOS
```

Some capabilities cannot or should not be implemented identically across platforms.

Examples:

- secure storage
- biometric authentication
- push notifications
- device information
- platform logging
- file system access
- permissions
- lifecycle integration

A shared contract can define the capability:

```kotlin
interface SecureStorage {

    suspend fun save(
        key: String,
        value: String
    )

    suspend fun read(
        key: String
    ): String?
}
```

Then:

```text
SecureStorage
     │
     ├── AndroidSecureStorage
     │
     └── IosSecureStorage
```

The shared layers depend on the contract rather than the platform implementation.

---

# 13. Application Layer

There is often another layer that is overlooked: the application or composition layer.

Its responsibility is to connect the pieces.

For example:

```text
Application
    │
    ├── Dependency Injection
    ├── Configuration
    ├── Environment
    ├── Startup
    └── Composition
```

It can construct:

```text
OrderApi
   ↓
OrderRemoteDataSource
   ↓
OrderRepositoryImpl
   ↓
GetOrderUseCase
   ↓
OrderViewModel
```

The composition root decides **which implementation is used**.

This is different from business logic.

# 14. The Complete Layered Flow

A realistic KMP request may look like:

```text
┌───────────────────────────────┐
│ Android Compose / iOS SwiftUI │
└───────────────┬───────────────┘
                │
                ▼
┌───────────────────────────────┐
│          Presentation         │
│ State / Event / ViewModel     │
└───────────────┬───────────────┘
                │
                ▼
┌───────────────────────────────┐
│            Domain             │
│ Use Case / Business Rules     │
└───────────────┬───────────────┘
                │
                ▼
┌───────────────────────────────┐
│             Data              │
│ Repository / Mapper / Cache   │
└───────────────┬───────────────┘
                │
          ┌─────┴─────┐
          ▼           ▼
       Network      Database
```

Platform services enter through defined boundaries:

```text
                    Shared Layers
                         │
                         ▼
                 Platform Contract
                    │           │
                    ▼           ▼
                 Android       iOS
```

# 15. Layer vs Source Set

This is one of the most important distinctions in KMP.

A source set answers:

> **For which targets is this code compiled?**

A layer answers:

> **What responsibility does this code have?**

These are different dimensions.

For example:

```text
commonMain
│
├── presentation
├── domain
└── data
```

and:

```text
androidMain
│
└── platform
```

The first describes both target compatibility and responsibility.

The second is primarily platform-specific implementation.

You can therefore have:

```text
commonMain/domain
commonMain/data
commonMain/presentation
```

and:

```text
androidMain/platform
iosMain/platform
```

The architecture works because these boundaries answer different questions.

---

# 16. Layer vs Module

Another important distinction:

```text
Module
    = Build and dependency boundary

Layer
    = Responsibility boundary
```

For example:

```text
shared module
├── presentation layer
├── domain layer
└── data layer
```

Or:

```text
domain module
data module
presentation module
```

Both are possible.

The second creates stronger Gradle-level enforcement.

The first is simpler.

Neither is universally correct.

---

# 17. When Layers Become Modules

A project may begin with:

```text
shared/
└── commonMain/
    ├── presentation/
    ├── domain/
    └── data/
```

As the codebase grows, it may become:

```text
shared/
domain/
data/
presentation/
```

or:

```text
core-domain/
core-data/
feature-orders/
feature-profile/
```

Why make this change?

Because a Gradle module can provide:

- dependency isolation
- compilation boundaries
- clearer ownership
- faster incremental builds
- reusable APIs
- stronger architectural enforcement

But there is a cost:

- more build configuration
- more dependency management
- more module navigation
- more Gradle complexity

Therefore:

> **Use module boundaries when the architectural benefit justifies the build complexity.**

---

# 18. Dependency Direction Between Layers

A simple dependency graph is:

```text
Presentation
     │
     ▼
   Domain
     ▲
     │
    Data
```

The key idea is that the domain defines important contracts.

For example:

```kotlin
interface ProductRepository {
    suspend fun getProduct(
        id: String
    ): Product
}
```

The data layer implements the contract.

```kotlin
class ProductRepositoryImpl(
    private val api: ProductApi
) : ProductRepository {
    // implementation
}
```

This is dependency inversion.

The concrete implementation depends on the abstraction.

---

# 19. Why Data Should Not Leak Upward

Suppose an API returns:

```kotlin
data class ProductDto(
    val product_id: String,
    val product_name: String,
    val price_in_cents: Long
)
```

If the presentation layer directly consumes `ProductDto`:

```text
UI
 │
 ▼
ProductDto
 │
 ▼
API
```

then the UI becomes coupled to the backend contract.

If the backend changes:

```text
product_name
    ↓
name
```

the UI may break.

A better flow is:

```text
API
 │
 ▼
ProductDto
 │
 ▼
Mapper
 │
 ▼
Product
 │
 ▼
Presentation Model
 │
 ▼
UI
```

Each layer owns its representation.

---

# 20. Why UI Models Should Not Become Domain Models

Consider:

```kotlin
data class ProductUiModel(
    val title: String,
    val subtitle: String,
    val priceText: String,
    val showDiscountBadge: Boolean
)
```

This is useful for presentation.

But putting this in the domain creates a problem:

```text
Domain
  │
  ▼
"showDiscountBadge"
```

The domain is now aware of a UI concept.

Instead:

```text
Domain
  │
  ▼
Product
  │
  ▼
Presentation Mapper
  │
  ▼
ProductUiModel
```

The domain describes business meaning.

The presentation describes how that meaning is displayed.

---

# 21. Mapping Between Layers

Mapping is often the explicit boundary between representations.

```text
DTO
 │
 ▼
toDomain()
 │
 ▼
Domain Model
 │
 ▼
toUiModel()
 │
 ▼
UI Model
```

Example:

```kotlin
fun ProductDto.toDomain(): Product {
    return Product(
        id = productId,
        name = productName,
        price = Money(priceInCents)
    )
}
```

Then:

```kotlin
fun Product.toUiModel(): ProductUiModel {
    return ProductUiModel(
        title = name,
        subtitle = id,
        priceText = price.format(),
        showDiscountBadge = price.isDiscounted
    )
}
```

Mapping may look like additional code.

It is.

But that code makes boundaries explicit.

---

# 22. Layers and Error Handling

Errors are another place where layers can become tightly coupled.

An API might return:

```text
HTTP 401
HTTP 403
HTTP 404
HTTP 500
```

The domain may not need to know HTTP semantics.

Instead, the data layer can translate infrastructure errors:

```kotlin
sealed interface DataError {
    data object Unauthorized : DataError
    data object NotFound : DataError
    data object Network : DataError
    data object Unknown : DataError
}
```

The domain can expose application-relevant outcomes.

For example:

```kotlin
sealed interface LoginResult {
    data object Success : LoginResult
    data object InvalidCredentials : LoginResult
    data object NetworkUnavailable : LoginResult
}
```

The translation can happen at the appropriate boundary.

This prevents infrastructure-specific concepts from leaking throughout the application.

---

# 23. Layers and State

KMP applications often use shared state management.

A useful flow is:

```text
Data
 │
 ▼
Domain Result
 │
 ▼
Presentation State
 │
 ▼
Platform UI
```

For example:

```kotlin
sealed interface OrderState {

    data object Loading : OrderState

    data class Success(
        val order: OrderUiModel
    ) : OrderState

    data class Error(
        val message: String
    ) : OrderState
}
```

The state belongs to presentation.

The domain should not need to know about UI states such as:

```text
Loading
ErrorDialogVisible
SnackbarVisible
ButtonEnabled
```

unless those states genuinely represent domain concepts.

---

# 24. Layers and MVI

MVI fits naturally into the presentation layer.

```text
              MVI
               │
       ┌───────┼───────┐
       ▼       ▼       ▼
     Event    State   Effect
               │
               ▼
           Use Case
               │
               ▼
            Domain
               │
               ▼
             Data
```

Example:

```kotlin
sealed interface OrderIntent {
    data object Load : OrderIntent
    data object Cancel : OrderIntent
}
```

The reducer or ViewModel translates intents into actions.

```text
User
 │
 ▼
Intent
 │
 ▼
Presentation
 │
 ▼
Use Case
 │
 ▼
Domain
 │
 ▼
Data
```

The MVI pattern controls presentation state.

The layers control responsibility and dependencies.

# 25. Layers and MVVM

The same architecture can be used with MVVM:

```text
View
 │
 ▼
ViewModel
 │
 ▼
Use Case
 │
 ▼
Repository
 │
 ▼
Data Source
```

The ViewModel should primarily coordinate:

```text
Input
 ↓
Use Case
 ↓
Result
 ↓
State
```

This prevents the ViewModel from becoming a second repository or a second domain layer.

# 26. Platform UI and Shared Layers

A common KMP architecture can keep UI native while sharing the underlying layers.

```text
               Android
                  │
           Compose UI
                  │
                  ▼
            Shared State
                  │
                  ▼
             Shared Domain
                  │
                  ▼
              Shared Data


                 iOS
                  │
              SwiftUI
                  │
                  ▼
            Shared State
                  │
                  ▼
             Shared Domain
                  │
                  ▼
              Shared Data
```

This architecture gives each platform freedom at the UI boundary while maximizing reuse where business behavior is naturally shared.

# 27. Layers and Platform-Specific UI

A platform UI may require platform-specific presentation code.

For example:

```text
shared/
└── commonMain/
    ├── domain/
    └── data/

androidApp/
└── presentation/

iosApp/
└── presentation/
```

This is perfectly valid.

KMP does not require shared presentation.

The correct boundary depends on the product.

The important principle is:

> **Share the logic that benefits from sharing; keep platform-specific concerns where they are clearer.**

---

# 28. Layers and `expect` / `actual`

Suppose the domain needs a clock.

A simple platform abstraction could be:

```kotlin
interface Clock {
    fun currentTimeMillis(): Long
}
```

Then platform implementations can be provided through dependency injection.

Alternatively:

```kotlin
expect fun currentTimeMillis(): Long
```

with:

```kotlin
actual fun currentTimeMillis(): Long {
    // Android implementation
}
```

and:

```kotlin
actual fun currentTimeMillis(): Long {
    // iOS implementation
}
```

Both approaches create a platform boundary.

The architectural question is:

```text
Is the platform capability part of a contract?
```

If yes, the implementation can remain outside the business layer.

---

# 29. Layers and Dependency Injection

Dependency Injection connects the layers.

For example:

```kotlin
class GetProductUseCase(
    private val repository: ProductRepository
)
```

The use case receives the dependency.

It does not create it.

The composition layer creates:

```text
ProductApi
     ↓
ProductRemoteDataSource
     ↓
ProductRepositoryImpl
     ↓
GetProductUseCase
     ↓
ProductViewModel
```

This creates a clean object graph.

A dependency injection framework can automate this, but the architecture should exist independently of the framework.

---

# 30. The Dependency Injection Framework Is Not the Architecture

It is easy to confuse:

```text
Hilt
Koin
Dagger
Manual DI
```

with architecture.

They are not architecture.

They are tools for constructing dependencies.

The architecture is:

```text
Presentation
     ↓
Domain
     ↓
Data
```

Dependency injection helps implement the connections.

```text
Architecture
      +
Dependency Injection
      =
Constructed Object Graph
```

If the DI framework is removed, the architectural boundaries should still make sense.

Each layer can be tested according to its responsibility.

### Presentation tests

Test:

```text

State
Reducers
ViewModel behavior
```

### Domain tests

Test:

```text
Business rules
Use cases
Validation
Calculations
State transitions
```

### Data tests

Test:

```text

Mapping
Remote data handling

Caching
```

This produces a test structure that mirrors the architecture.

```text
                    Tests
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
  Presentation      Domain        Data
```

# 32. Layer-Specific Tests

For example, a domain test:

```kotlin
@Test
fun premium_customer_receives_discount() {

    val useCase = CalculateDiscountUseCase()

    val result = useCase(
        price = Money(1000),
        customerType = CustomerType.Premium
    )

    assertEquals(
        Money(900),
        result
    )
}
```

No platform is involved.

A repository test may use a fake data source:

```kotlin
class FakeOrderApi : OrderApi {

    override suspend fun getOrder(
        id: String
    ): OrderDto {
        return OrderDto(
            id = id,
            status = "PENDING"
        )
    }
}
```

The test verifies the data boundary rather than UI behavior.

# 33. Layer Boundaries and Compilation

When layers become separate Gradle modules, the build system can enforce architectural boundaries.

For example:

```text
:app
  ↓
:feature-orders
  ↓
:domain
```

If `domain` does not depend on `androidApp`, Gradle makes that boundary explicit.

This is stronger than a folder convention.

A folder can be ignored.

A module dependency can be enforced by the build system.

This is one reason modularization becomes valuable for large KMP applications.

# 35. Layering Does Not Mean Everything Must Be Sequential

A common misunderstanding is:

```text
Presentation → Domain → Data
```

and therefore every operation must pass through every layer.

That is not always necessary.

For example, application configuration may be handled directly by the application layer.

A platform integration may be used directly by a platform-specific adapter.

The architecture should prevent inappropriate dependencies, not force unnecessary ceremony.

---

# 36. Shared Utility vs Domain Logic

Another important distinction is between utilities and business logic.

A utility might be:

```kotlin
fun String.isValidEmail(): Boolean
```

A domain rule might be:

```kotlin
class CanSubmitLoanApplicationUseCase
```

The first is a generic technical capability.

The second represents a product decision.

Putting every reusable function into `domain` can make the domain layer meaningless.

Similarly, putting every helper into `core` can turn `core` into a dumping ground.

Ask:

> **Does this code represent a product rule, a technical capability, or a platform capability?**

The answer tells you where it belongs.

# 37. Layer Ownership Matrix

A useful reference:

| Concern | Presentation | Domain | Data | Platform |
|---|:---:|:---:|:---:|:---:|
| UI state | ✅ | | | |
| UI events | ✅ | | | |
| Business rules | | ✅ | | |
| Use cases | | ✅ | | |
| Domain models | | ✅ | | |

| API implementation | | | ✅ | |
| DTOs | | | ✅ | |
| Database entities | | | ✅ | |

| iOS APIs | | | | ✅ |

# 38. Common Mistake — Layers by File Type

A structure such as:

```text
models/
viewmodels/
repositories/
services/
utils/
```

can become difficult to navigate in a large application.

Why?

Because it organizes by technical type rather than feature responsibility.

For example:

```text
viewmodels/
├── LoginViewModel
├── OrderViewModel
├── ProfileViewModel
└── PaymentViewModel
```

and:

```text
repositories/
├── LoginRepository
├── OrderRepository
├── ProfileRepository
└── PaymentRepository
```

The code for one feature is spread across the entire project.

A feature-oriented structure keeps related code closer:

```text
features/
├── login/
├── orders/
├── profile/
└── payments/
```

Each feature can still contain layers internally.

---

# 39. Common Mistake — Too Many Layers

Architecture can also become excessive.

For example:

```text
Controller
↓
Presenter
↓
Coordinator
↓
Interactor
↓
UseCase
↓
Service
↓
Manager
↓
Repository
↓
DataSource
```

If every layer only forwards a method:

```kotlin
return nextLayer.execute(request)
```

the architecture may have more ceremony than value.

A useful layer should own a meaningful responsibility.

---

# 40. Common Mistake — Data Layer Becomes the Business Layer

Consider:

```kotlin
class OrderRepositoryImpl {

    suspend fun createOrder(order: Order): Order {

        if (order.items.isEmpty()) {
            // business rule
        }

        if (order.total > limit) {
            // business rule
        }

        // network
    }
}
```

The repository is now deciding business behavior.

A cleaner design can move the decision into the domain:

```text
CreateOrderUseCase
      │
      ├── Validate order
      ├── Apply business rules
      └── Call repository
              │
              ▼
        Data / Network
```

The repository focuses on data access.

---

# 41. Common Mistake — Domain Depends on Data Details

Avoid:

```kotlin
class GetOrderUseCase(
    private val retrofit: Retrofit
)
```

or:

```kotlin
class GetOrderUseCase(
    private val database: SqlDriver
)
```

The domain should depend on a capability:

```kotlin
class GetOrderUseCase(
    private val repository: OrderRepository
)
```

The implementation belongs elsewhere.

---

# 42. Common Mistake — Platform Conditions Everywhere

A problematic pattern is:

```kotlin
if (Platform.isAndroid) {
    // Android
} else if (Platform.isIOS) {
    // iOS
}
```

spread throughout shared business logic.

A better structure is:

```text
Shared Logic
     │
     ▼
Platform Contract
     │
 ┌───┴───┐
 ▼       ▼
Android  iOS
```

Platform differences should be concentrated at boundaries whenever practical.

---

# 43. Common Mistake — Treating Every Layer as Shared

A KMP project may have:

```text
Shared Domain
Shared Data
Shared Presentation State
```

while keeping:

```text
Android UI
iOS UI
```

native.

There is nothing architecturally wrong with that.

The purpose of KMP is to enable code sharing where it makes sense, not to remove platform identity.

# 44. Layers and Team Ownership

Layers can also improve team collaboration.

For example:

```text
Team A
└── Authentication

Team B
└── Orders

Team C
└── Platform / Core
```

Inside a feature:

```text
Orders
├── Presentation
├── Domain
└── Data
```

Ownership becomes easier to understand.

This becomes particularly useful in large codebases where multiple engineers work concurrently.

# 45. Layers and Code Review

A layered project gives reviewers useful questions.

Instead of reviewing only syntax, they can ask:

```text
Does this business rule belong in Domain?

Is this API-specific object leaking into Presentation?

Should this dependency be platform-specific?

Can this code move to commonMain?

Is this abstraction actually required?

Is the dependency direction correct?
```

The architecture becomes a shared vocabulary for technical discussions.

# 46. Layers and New Features

Suppose a new `Payments` feature is introduced.

A clean approach might be:

```text
payments/
├── presentation/
│   ├── PaymentState.kt
│   └── PaymentViewModel.kt
│
├── domain/
│   ├── Payment.kt

│
└── data/
    ├── PaymentApi.kt
    ├── PaymentDto.kt
    ├── PaymentRepositoryImpl.kt
    └── PaymentMapper.kt
```

```text

     │
     ▼

     ▲
     │
```

Platform-specific payment SDK integration can then sit behind:

```text
      │
 ┌────┴────┐
 ▼         ▼
```

# 47. Layers and Offline-First Architecture

Layering becomes especially useful for offline-first applications.

The flow can be:

```text
UI
 │
 ▼
Use Case
 │
 ▼
Repository
 │
 ├──────────────┐
 ▼              ▼
Local          Remote
Database       API
```

The repository can decide:

```text
Is cached data available?
        │
        ├── Yes → return local data
        │
        └── No → request remote data
```

The business layer does not need to know the storage implementation.

This is a strong example of why layers are useful beyond simple CRUD applications.

---

# 48. Layers and Synchronization

For applications that synchronize data:

```text
Presentation
      │
      ▼
Sync Use Case
      │
      ▼
Repository
      │
      ├── Local
      │
      └── Remote
```

A synchronization policy can live in the appropriate application/domain boundary:

```text
Local version
      │
      ▼
Conflict policy
      │
      ▼
Remote version
```

The network client itself should not own the product's conflict-resolution rules.

---

# 49. Layers and Security

Security is another area where boundaries matter.

For example:

```text
Domain
  │
  ▼
CredentialStore
  │
  ├── Android Keystore
  └── iOS Keychain
```

The business logic can request:

```kotlin
credentialStore.readToken()
```

without knowing:

```text
Where the token is stored
Which OS API is used
Which encryption mechanism is involved
```

The platform layer owns the platform security mechanism.

The domain owns the business decision about when credentials are required.

---

# 50. A Practical Rule for Every Layer

Each layer should be able to answer:

### Presentation

> What does the user need to see and how does the UI react?

### Domain

> What does the product require the application to do?

### Data

> How do we obtain, transform, cache, and persist information?

### Platform

> How does this operating system provide the required capability?

### Application

> How are the components assembled and started?

If a class cannot clearly answer where it belongs, that is often a signal that its responsibility is mixed.

# 53. The Most Important Layering Rule

The most useful rule is not:

> "Always use three layers."

It is:

> **A layer should exist when it creates a meaningful responsibility boundary.**

For a small application:

```text
shared/
├── domain/
├── data/
└── presentation/
```

may be enough.

For a larger product:

```text
core/
features/
platform/
androidApp/
iosApp/
```

may be more appropriate.

The architecture should grow with the system.

# 54. Part 3 Takeaways

Layers give a KMP project a clear vocabulary for responsibility.

Remember:

- A layer is a responsibility boundary, not automatically a Gradle module.
- Presentation owns user-facing state and interaction.
- Domain owns business rules and application decisions.
- Data owns retrieval, persistence, mapping, and infrastructure coordination.
- Platform owns operating-system-specific capabilities.
- Application/composition code assembles dependencies and startup behavior.
- Domain models should not be shaped entirely around API or UI requirements.
- DTOs, entities, domain models, and UI models can represent different boundaries.
- Mapping makes those boundaries explicit.
- Repository contracts help separate domain logic from data implementation.
- Source sets and layers answer different architectural questions.
- A single KMP module can contain multiple layers.
- Multiple Gradle modules can enforce stronger boundaries when the project becomes large.
- MVI and MVVM can live inside the presentation layer.
- Dependency injection connects layers but is not the architecture itself.
- Platform UI can remain native while domain and data logic are shared.
- Do not force every layer to become shared.
- Do not create layers that only forward calls without adding meaningful responsibility.
- Do not allow data or platform details to leak into the domain without a deliberate reason.
- Layering is ultimately about controlling dependencies and the impact of change.

The core mental model is:

```text
                PLATFORM UI
                     │
                     ▼
               PRESENTATION
                     │
                     ▼
                  DOMAIN
                     │
                     ▼
                   DATA
                ┌────┴────┐
                ▼         ▼
             NETWORK   DATABASE
                │
                ▼
          PLATFORM SERVICES
```

And the most important architectural boundary is:

```text
             BUSINESS POLICY
                    │
                    ▼
                 DOMAIN
                    │
              contracts
                    │
                    ▼
             IMPLEMENTATION
                    │
             ┌──────┴──────┐
             ▼             ▼
          Android          iOS
```

Layers are therefore not an exercise in creating folders.

They are a way of deciding **where decisions belong, who is allowed to depend on those decisions, and which details should remain replaceable**.
