# Chapter 10 — Project Structure

## Part 1 — Parts

A Kotlin Multiplatform project becomes easier to understand when its structure is viewed as a set of **parts**, rather than as one large application.

A useful mental model is:

```text
Kotlin Multiplatform Project
│
├── Shared / Multiplatform Part
│   ├── commonMain
│   ├── commonTest
│   ├── androidMain
│   ├── iosMain
│   └── other platform source sets
│
├── Android Application Part
│   ├── Android UI
│   ├── Android resources
│   └── Android-specific configuration
│
├── iOS Application Part
│   ├── iOS UI
│   ├── iOS resources
│   └── iOS-specific configuration
│
└── Build & Configuration Part
    ├── Gradle
    ├── version catalogs
    ├── plugins
    └── dependency management
```

The important point is that these are **different responsibilities inside the same product**.

KMP does not require every part of an application to become shared. Instead, it gives us a mechanism for deciding which part belongs in shared Kotlin code and which part remains platform-specific.

> [!IMPORTANT]
> **Multiplatform does not mean "everything must be common."**
>
> A healthy KMP project deliberately separates shared business logic from platform-specific application code.

---

## 1. What Does "Part" Mean?

In a KMP project, a **part** is a logical area of the project that owns a particular responsibility.

For example:

| Part | Primary responsibility |
|---|---|
| Shared domain | Business rules and domain models |
| Shared data | API, database, repositories |
| Shared presentation | State, use cases, presentation models |
| Android app | Android entry point and Android UI |
| iOS app | iOS entry point and iOS UI |
| Platform implementation | APIs that cannot be shared directly |
| Build configuration | Gradle and dependency configuration |
| Tests | Verification of shared and platform behavior |

This separation is more important than the directory names themselves.

A project can have beautiful folders and still have poor architecture if responsibilities are mixed together.

---

## 2. The Four Major Parts of a KMP Application

A practical KMP application can initially be understood through four major parts:

```text
                ┌──────────────────────────┐
                │       Product/App        │
                └────────────┬─────────────┘
                             │
          ┌──────────────────┼──────────────────┐
          │                  │                  │
          ▼                  ▼                  ▼
 ┌─────────────────┐ ┌─────────────────┐ ┌─────────────────┐
 │ Shared Kotlin   │ │ Android Part    │ │ iOS Part        │
 │                 │ │                 │ │                 │
 │ Domain          │ │ Android UI      │ │ iOS UI          │
 │ Data            │ │ Android APIs    │ │ iOS APIs        │
 │ Business Logic  │ │ Resources       │ │ Resources        │
 └─────────────────┘ └─────────────────┘ └─────────────────┘
          │
          ▼
 ┌──────────────────────────────┐
 │ Build & Dependency System    │
 │ Gradle / Plugins / Catalogs  │
 └──────────────────────────────┘
```

The shared part is where KMP provides the greatest reuse.

The platform parts are where each operating system can preserve its native capabilities and conventions.

# 3. Part 1: The Shared Multiplatform Part

The shared part is normally represented by a Kotlin Multiplatform module.

A simplified project may look like this:

```text
shared/
└── src/
    ├── commonMain/
    │   └── kotlin/
    │
    ├── commonTest/
    │   └── kotlin/
    │
    ├── androidMain/
    │   └── kotlin/
    │
    └── iosMain/
        └── kotlin/
```

This module is not simply a "common utilities" folder.

It can contain substantial application logic:

```text
shared/
└── src/
    └── commonMain/
        └── kotlin/
            ├── domain/
            ├── data/
            ├── presentation/
            ├── network/
            ├── database/
            └── platform/
```

The exact package layout depends on the application.

The architectural principle is more important:

```text
                 Shared Module
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
    Domain           Data       Presentation
       │              │              │
       └──────────────┼──────────────┘
                      ▼
              Shared Application Logic
```

# 4. `commonMain` — The Common Part

`commonMain` is the most important source set in a KMP project.

Code placed here is intended to be usable across supported targets.

Example:

```kotlin
class CalculateCartTotalUseCase {

    operator fun invoke(
        items: List<CartItem>
    ): Money {
        return items
            .map { it.price * it.quantity }
            .sum()
    }
}
```

This code does not need to know whether the caller is:

- Android
- iOS
- desktop
- another supported Kotlin target

The business rule is shared.

A typical `commonMain` package may contain:

```text
commonMain/
└── kotlin/
    └── com/example/shop/
        ├── domain/
        │   ├── model/
        │   └── usecase/
        │
        ├── data/
        │   ├── repository/
        │   └── datasource/
        │
        ├── presentation/
        │   ├── state/
        │   └── viewmodel/
        │
        └── network/
            ├── api/
            └── model/
```

The key question should always be:

> **Can this code express the product rule without depending on a specific platform?**

If the answer is yes, it is a strong candidate for `commonMain`.

---

# 5. `commonTest` — Testing the Shared Part

Shared code needs shared tests.

A corresponding structure might be:

```text
shared/
└── src/
    ├── commonMain/
    └── commonTest/
        └── kotlin/
            └── com/example/shop/
                ├── domain/
                ├── data/
                └── presentation/
```

Example:

```kotlin
class CalculateCartTotalUseCaseTest {

    @Test
    fun calculates_total_for_multiple_items() {
        val useCase = CalculateCartTotalUseCase()

        val result = useCase(
            listOf(
                CartItem(
                    productId = "101",
                    price = Money(100),
                    quantity = 2
                ),
                CartItem(
                    productId = "102",
                    price = Money(50),
                    quantity = 1
                )
            )
        )

        assertEquals(Money(250), result)
    }
}
```

The test validates a business rule rather than a platform UI.

This distinction is important.

```text
commonTest
    │
    ├── Business rules
    ├── Use cases
    ├── Mappers
    ├── Repository behavior
    ├── Validation
    └── Shared state logic
```

Platform-specific tests can remain in their respective source sets.

---

# 6. Android Part

The Android part contains functionality that belongs specifically to Android.

A common structure is:

```text
shared/
└── src/
    └── androidMain/
        └── kotlin/
            └── com/example/shop/
                ├── platform/
                ├── database/
                └── network/
```

There may also be a separate Android application module:

```text
androidApp/
├── src/
│   └── main/
│       ├── kotlin/
│       └── res/
└── build.gradle.kts
```

These two ideas should not be confused.

### `androidMain`

`androidMain` is a source set inside a KMP module.

It is useful when shared code needs an Android-specific implementation.

### `androidApp`

`androidApp` is an Android application module.

It normally owns things such as:

- Android application configuration
- Android entry points
- Android resources
- Android-specific UI
- Manifest configuration
- Application packaging

A simplified relationship looks like:

```text
                  Android Application
                         │
                         ▼
                    androidApp
                         │
                         ▼
                    shared KMP
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
         commonMain            androidMain
```

---

# 7. iOS Part

The iOS side has a similar relationship, although the project organization is different because iOS applications commonly use Xcode and Swift/SwiftUI.

Conceptually:

```text
iOS Application
      │
      ▼
Swift / SwiftUI
      │
      ▼
KMP Shared Framework
      │
      ▼
commonMain
```

An iOS-specific implementation can live in:

```text
shared/
└── src/
    └── iosMain/
        └── kotlin/
            └── com/example/shop/
                └── platform/
```

For example, suppose shared code needs a platform clock.

The shared contract can be declared in `commonMain`:

```kotlin
expect class PlatformClock {
    fun nowMillis(): Long
}
```

The iOS implementation can then live in `iosMain`:

```kotlin
actual class PlatformClock {

    actual fun nowMillis(): Long {
        return NSDate().timeIntervalSince1970
            .times(1000)
            .toLong()
    }
}
```

The application therefore has one shared contract and different platform implementations.

---

# 8. Parts Are Connected Through Contracts

The strongest KMP structures do not connect every part directly.

Instead, they use clear contracts.

Consider a repository:

```text
UI
 │
 ▼
Use Case
 │
 ▼
Repository Interface
 │
 ├─────────────── Android implementation
 │
 └─────────────── iOS implementation
```

The shared code knows the contract:

```kotlin
interface UserRepository {
    suspend fun getUser(id: String): User
}
```

The platform or data layer provides the implementation.

This gives us an important architectural boundary:

```text
                 CONTRACT
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
 Shared Consumer          Platform/Data
```

The consumer does not need to know how the implementation works.

---

# 9. Parts Should Have Clear Ownership

A useful way to evaluate a project structure is to ask:

> **Who owns this responsibility?**

For example:

| Responsibility | Natural owner |
|---|---|
| Business rule | Shared domain |
| API contract | Shared data/network |
| JSON mapping | Shared data |
| Repository abstraction | Shared domain/data |
| Android permission | Android |
| iOS permission | iOS |
| Android Activity | Android |
| SwiftUI screen | iOS |
| Shared validation | Shared |
| Android-specific storage | Android |
| iOS-specific storage | iOS |
| Dependency versions | Build configuration |

This prevents a common KMP problem:

```text
"Everything is shared"
        │
        ▼
Platform-specific code leaks
        │
        ▼
Shared module becomes difficult to maintain
```

# 10. A Practical Project Layout

A small-to-medium KMP project can start with:

```text
MyKmpApp/
│
├── androidApp/
│   └── src/
│       └── main/
│
├── iosApp/
│
├── shared/
│   └── src/
│       ├── commonMain/
│       ├── commonTest/
│       ├── androidMain/
│       └── iosMain/
│
├── gradle/
│   └── libs.versions.toml
│
├── build.gradle.kts
├── settings.gradle.kts
└── gradle.properties
```

This structure separates:

1. Android application concerns
2. iOS application concerns
3. Shared Kotlin concerns
4. Build-system concerns

As the application grows, the shared module can be divided further.

For example:

```text
MyKmpApp/
│
├── androidApp/
├── iosApp/
│
├── shared/
│
├── core/
│   ├── network/
│   ├── database/
│   └── common/
│
├── feature/
│   ├── login/
│   ├── profile/
│   └── orders/
│
└── build-logic/
```

This is where "parts" become more than platform source sets.

They become **independent architectural boundaries**.

---

# 11. Parts Can Exist at Different Levels

One of the most important concepts is that a "part" does not have to mean a Gradle module.

There are multiple levels.

```text
Project
│
├── Platform Part
│   ├── Android
│   └── iOS
│
├── Module Part
│   ├── shared
│   ├── core
│   └── feature
│
├── Source Set Part
│   ├── commonMain
│   ├── androidMain
│   └── iosMain
│
└── Package Part
    ├── domain
    ├── data
    └── presentation
```

These levels should not be mixed conceptually.

For example:

```text
feature/orders
```

may be a Gradle module.

Inside it:

```text
commonMain/
    domain/
    data/
    presentation/
```

may be packages.

And:

```text
androidMain/
iosMain/
```

are source sets.

They are all parts, but they represent different boundaries.

# 12. Parts and Dependency Direction

Project structure becomes much more useful when dependencies have a clear direction.

A feature-oriented KMP project might follow:

```text
                Application
                    │
                    ▼
                 Feature
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       Domain               Data
          │                   │
          └─────────┬─────────┘
                    ▼
                   Core
```

A more detailed example:

```text
orders
├── presentation
│
├── domain
│
└── data
     │
     ▼
    core
```

The dependency direction should be intentional.

A common anti-pattern is:

```text
core
  ↕
feature
  ↕
app
  ↕
platform
```

where everything depends on everything else.

That creates a project that may look modular but behaves like a single tightly coupled system.

# 13. Parts and Source Sets

Source sets are especially important in KMP because they determine where code is compiled.

A simplified view:

```text
                         Kotlin Multiplatform
                                  │
              ┌───────────────────┼───────────────────┐
              │                   │                   │
              ▼                   ▼                   ▼
         commonMain          androidMain          iosMain
              │                   │                   │
              │                   │                   │
              ▼                   ▼                   ▼
          Shared code        Android code        iOS code
```

A dependency available to `commonMain` must itself be compatible with the targets that consume it.

That means this is not enough:

```text
"I need this library."
```

The more useful question is:

```text
"Which part of my project needs this library,
and which targets must that part support?"
```

That question directly influences dependency placement.

---

# 14. Dependency Placement Is Part of Structure

Suppose an HTTP client is required by shared code.

The dependency belongs with the shared part:

```text
shared
└── commonMain
    └── HTTP client
```

If an Android-only library is required for an Android-specific implementation:

```text
shared
└── androidMain
    └── Android library
```

If a library belongs only to the Android application:

```text
androidApp
└── Android-only dependency
```

The same principle applies to iOS.

The project structure therefore communicates dependency intent.

---

# 15. Parts and Platform Boundaries

A KMP project usually contains two types of boundaries:

### Shared boundary

```text
commonMain
```

This is where portable application logic lives.

### Platform boundary

```text
androidMain
iosMain
```

This is where platform-specific behavior enters the shared architecture.

For example:

```text
                 Shared Business Logic
                         │
                         ▼
                  Platform Contract
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
        Android API              iOS API
```

The platform boundary should be deliberate.

It should not appear accidentally because a developer imported a platform API into shared code.

---

# 16. A Simple Example: Device Information

Suppose the application needs the operating system name.

The business logic should not directly depend on Android or iOS APIs.

Instead:

```kotlin
interface DeviceInfo {
    val platformName: String
}
```

The shared layer consumes:

```kotlin
class GetPlatformName(
    private val deviceInfo: DeviceInfo
) {
    operator fun invoke(): String {
        return deviceInfo.platformName
    }
}
```

Android can provide:

```kotlin
class AndroidDeviceInfo : DeviceInfo {
    override val platformName: String = "Android"
}
```

iOS can provide:

```kotlin
class IosDeviceInfo : DeviceInfo {
    override val platformName: String = "iOS"
}
```

The important part is not the string.

The important part is the boundary:

```text
Shared
  │
  │ DeviceInfo
  ▼
Contract
  │
  ├── Android implementation
  └── iOS implementation
```

This pattern scales to many platform concerns:

- secure storage
- device identifiers
- biometric authentication
- file access
- logging
- connectivity
- keychain/keystore
- platform clocks
- notifications

# 17. Parts and Feature Modules

As the product grows, a single `shared` module can become too large.

For example:

```text
shared/
└── commonMain/
    ├── login/
    ├── profile/
    ├── payments/
    ├── orders/
    ├── search/
    ├── notifications/
    └── settings/
```

The problem is not the number of folders.

The problem appears when unrelated features become strongly coupled.

A larger project may therefore evolve toward:

```text
features/
├── login/
├── profile/
├── orders/
└── payments/

core/
├── network/
├── database/
└── common/
```

Now the parts have clearer ownership.

```text
                 Application
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
     Login         Orders        Profile
       │             │             │
       └─────────────┼─────────────┘
                     ▼
                    Core
```

This is not mandatory for every project.

A small application may be easier to maintain with one shared module.

The important principle is to introduce boundaries when the existing boundary stops being useful.

# 18. Parts Should Reduce Cognitive Load

Good structure is not about having more folders.

It is about making questions easier to answer.

When looking at a project, a developer should quickly understand:

```text
Where is the business rule?
Where is the API?
Where is the database?
Where is the Android implementation?
Where is the iOS implementation?
Where is the feature?
Where are the tests?
Where is the build configuration?
```

A good structure answers these questions without requiring the developer to search the entire repository.

That is one of the practical benefits of architectural boundaries.

# 19. A KMP Part Is a Boundary of Responsibility

Think about a part like a contract.

```text
┌─────────────────────────────┐
│           Part A            │
│                             │
│  Owns a specific concern    │
│                             │
└──────────────┬──────────────┘
               │
          Public contract
               │
┌──────────────▼──────────────┐
│           Part B            │
│                             │
│  Uses the concern           │
│  without owning its details │
│                             │
└─────────────────────────────┘
```

This is more valuable than simply organizing files alphabetically.

For example:

```text
orders/
    domain/
    data/
    presentation/
```

communicates much more than:

```text
orders/
    File1.kt
    File2.kt
    File3.kt
    File4.kt
```

The first structure communicates responsibility.

The second primarily communicates storage.

# 20. GitHub View of a Well-Organized KMP Project

A repository can communicate its architecture directly through its top-level structure:

```text
📦 my-kmp-project
├── 📱 androidApp
├── 🍎 iosApp
├── 🧩 shared
├── 🧱 core
├── 🚀 features
│   ├── login
│   ├── profile

├── 📚 gradle
├── .gitignore
├── build.gradle.kts
```

The icons are only presentation.

> **A good project tree is executable documentation.**
>
> If the repository structure clearly communicates ownership and dependency direction, developers spend less time reverse-engineering the architecture.

# 21. Common Mistakes When Defining Parts

## Mistake 1 — One Giant Shared Module

```text
shared/
├── everything
├── everythingElse
└── moreEverything
```

This can work initially but becomes difficult when unrelated features start depending on one another.

---

## Mistake 2 — Putting Platform Code in `commonMain`

For example:

```kotlin
// commonMain

import android.content.Context
```

This breaks the fundamental target-neutral nature of the common source set.

The correct question is:

> Can the requirement be expressed through a shared abstraction?

If yes, the platform implementation can move behind that abstraction.

---

## Mistake 3 — Creating Modules Only for Folder Organization

More modules do not automatically mean better architecture.

This:

```text
module-a
module-b
module-c
module-d
module-e
```

is not automatically better than:

```text
shared
```

A module should normally have a meaningful reason to exist:

- ownership
- dependency isolation
- compilation boundary
- feature boundary
- reusable capability
- platform boundary

---

## Mistake 4 — Mixing Application and Library Responsibilities

For example:

```text
shared/
└── AndroidActivity.kt
```

An Android Activity belongs to the Android application boundary, not to generic shared business logic.

Keeping responsibilities separate makes the architecture easier to evolve.

---

## Mistake 5 — Allowing Dependencies to Cross Every Boundary

If every part can directly access every other part:

```text
A ↔ B ↔ C ↔ D ↔ E
```

the project becomes difficult to reason about.

A healthier structure creates controlled direction:

```text
App
 │
 ▼
Feature
 │
 ▼
Domain
 │
 ▼
Core
```

The exact dependency graph can vary, but unrestricted access should be avoided.

# 22. The Part Hierarchy

A useful way to remember the concept is:

```text
PROJECT
  │
  ├── APPLICATION PART
  │     ├── Android
  │     └── iOS
  │
  ├── SHARED PART
  │     ├── commonMain
  │     ├── commonTest
  │     ├── androidMain
  │     └── iosMain
  │
  ├── FEATURE PART
  │     ├── Login
  │     ├── Profile
  │     └── Orders
  │
  └── BUILD PART
        ├── Gradle
        ├── Plugins
        └── Dependency Management
```

These layers are not mutually exclusive.

A feature can contain shared and platform-specific code.

For example:

```text
feature/orders/
├── src/
│   ├── commonMain/
│   ├── commonTest/
│   ├── androidMain/
│   └── iosMain/
```

This is one of the strengths of KMP: the same structural idea can be applied at different scales.

# 23. The Most Important Rule

When deciding where a piece of code belongs, do not start with:

> "Which folder should contain this file?"

Start with:

> **"Which part owns this responsibility?"**

Then ask:

```text
1. Is the responsibility platform-independent?
        │
        ├── Yes → shared part
        │
        └── No  → platform part

2. Is it reusable across features?
        │
        ├── Yes → core/shared capability
        │
        └── No  → feature-specific part

3. Does it represent a business rule?
        │
        ├── Yes → domain
        │
        └── No  → data/presentation/platform as appropriate
```

This makes project structure a consequence of responsibility rather than an arbitrary folder convention.

# 24. Part 1 Takeaways

The first step toward understanding KMP project structure is understanding **parts and boundaries**.

Remember these principles:

- A KMP project is composed of multiple logical parts.
- `commonMain` contains portable shared Kotlin logic.
- `commonTest` validates shared behavior.
- `androidMain` contains Android-specific implementations inside a KMP module.
- `iosMain` contains iOS-specific implementations inside a KMP module.
- `androidApp` and `iosApp` represent application boundaries.
- A part is defined by responsibility, not merely by a folder.
- A Gradle module, source set, package, feature, and platform are different kinds of boundaries.
- Dependencies should follow intentional directions.
- Platform-specific behavior should enter shared code through clear contracts.
- More modules do not automatically produce better architecture.
- A good repository structure acts as architectural documentation.

The resulting mental model is simple:

```text
                  KMP PROJECT
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    SHARED          ANDROID           iOS
      PART            PART            PART
        │              │              │
        ▼              ▼              ▼
   commonMain       Android App     iOS App
   commonTest       Android APIs    iOS APIs
        │
        ▼
  Shared Contracts
        │
        ▼
 Platform Implementations
```

The goal is not to make every part identical.

The goal is to make every part **clear about what it owns**.
