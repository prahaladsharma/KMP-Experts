# Chapter 11 — Clean Architecture

## Part 4 — Dependency Rule

The previous parts established that a KMP project can be divided into parts and layers.

Now we reach one of the most important architectural rules:

> **The direction of dependencies matters more than the number of layers.**

A project can have:

```text
presentation/
domain/
data/
platform/
```

and still have poor architecture if everything depends on everything else.

The dependency rule gives those layers a direction.

A simplified view is:

```text
                 OUTER DETAILS
                      │
          ┌───────────┴───────────┐
          │                       │
          ▼                       ▼
       Platform                Data
          │                       │
          └───────────┬───────────┘
                      ▼
                 Application
                    Domain
                      ▲
                      │
                Presentation
```

The exact dependency graph can vary by architecture, but the central idea remains:

```text
Stable business rules
        ↑
        │
Replaceable details
```

The business rules should not become dependent on technical details merely because those details are convenient to use.

---

# 1. What Is a Dependency?

A dependency exists when one piece of code requires another piece of code to perform its work.

For example:

```kotlin
class OrderViewModel(
    private val repository: OrderRepository
)
```

`OrderViewModel` depends on `OrderRepository`.

That dependency can be represented as:

```text
OrderViewModel
      │
      ▼
OrderRepository
```

Now consider:

```kotlin
class OrderViewModel(
    private val retrofit: Retrofit
)
```

The ViewModel directly depends on an HTTP framework.

```text
OrderViewModel
      │
      ▼
   Retrofit
```

The second dependency is more specific.

It connects presentation directly to an infrastructure detail.

The architectural question is not simply:

> "Does this dependency work?"

The better question is:

> **"Is this dependency pointing in the right direction?"**

---

# 2. Dependency Direction

Suppose we have:

```text
Presentation
     ↓
Domain
     ↓
Data
```

This diagram suggests:

```text
Presentation depends on Domain
Domain depends on Data
```

That can be problematic when the domain represents the stable business rules.

A stronger design is:

```text
Presentation
     │
     ▼
   Domain
     ▲
     │
    Data
```

Here:

- Presentation uses the domain.
- Domain defines important contracts.
- Data implements those contracts.

For example:

```kotlin
interface UserRepository {
    suspend fun getUser(id: String): User
}
```

The domain owns the abstraction.

The data layer provides:

```kotlin
class UserRepositoryImpl(
    private val api: UserApi
) : UserRepository {
    // implementation
}
```

The direction becomes:

```text
             UserRepository
              ▲          │
              │          │
        implements      uses
              │          ▼
      UserRepositoryImpl
```

The implementation depends on the abstraction.

---

# 3. The Dependency Rule in One Sentence

A useful mental model is:

> **Outer layers may depend on inner abstractions; inner business rules should not depend on outer implementation details.**

Visualized:

```text
┌─────────────────────────────────────────────┐
│             OUTER / DETAILS                 │
│                                             │
│ Android / iOS / Network / Database / SDKs   │
│                    │                        │
│                    ▼                        │
│             ┌──────────────┐                │
│             │ Application  │                │
│             │   Logic      │                │
│             └──────┬───────┘                │
│                    ▼                        │
│             ┌──────────────┐                │
│             │    Domain    │                │
│             │ Business     │                │
│             │ Rules        │                │
│             └──────────────┘                │
│                                             │
└─────────────────────────────────────────────┘
```

The important property is that business rules remain independent of details.

---

# 4. Stable vs Unstable Dependencies

Not all dependencies are equally important.

Consider:

```text
Business Rule
     │
     ▼
Interface
```

versus:

```text
Business Rule
     │
     ▼
Specific Database SDK
```

The first is an abstraction.

The second is an implementation detail.

A useful architectural goal is:

```text
Stable
  ▲
  │
  │ dependencies
  │
Variable
```

Examples of frequently changing details include:

- UI framework
- HTTP library
- database technology
- analytics SDK
- platform API
- storage mechanism
- third-party SDK

Business rules often have a different rate of change.

The architecture should avoid unnecessarily coupling the two.

---

# 5. Why Dependency Direction Matters More in KMP

KMP has a unique challenge:

```text
One shared codebase
        │
        ├── Android
        └── iOS
```

If shared code depends directly on Android:

```text
commonMain
     │
     ▼
Android API
```

the common code is no longer genuinely common.

If it depends directly on an iOS API:

```text
commonMain
     │
     ▼
iOS API
```

the same problem appears.

KMP therefore encourages a stronger boundary:

```text
                 commonMain
                     │
                     ▼
              Shared Contract
                 │       │
                 ▼       ▼
              Android   iOS
```

The shared code depends on the capability.

The platform supplies the implementation.

---

# 6. Dependency Rule and `commonMain`

The `commonMain` source set is a natural place for code that must remain portable.

For example:

```kotlin
class CalculateOrderTotalUseCase(
    private val repository: OrderRepository
) {
    suspend operator fun invoke(
        orderId: String
    ): Money {
        val order = repository.getOrder(orderId)

        return order.items.sumOf {
            it.price * it.quantity
        }
    }
}
```

This code does not depend on:

```text
Android
iOS
Retrofit
Room
SwiftUI
Compose
```

That makes it suitable for `commonMain`.

The dependency graph is:

```text
commonMain
   │
   ├── Domain
   │
   └── Contracts
```

Platform details remain outside.

---

# 7. A Bad KMP Dependency

Imagine:

```kotlin
class LoginUseCase(
    private val context: Context
)
```

This is a strong warning sign if the context exists only because the implementation needs an Android API.

The dependency becomes:

```text
LoginUseCase
      │
      ▼
Android Context
```

Now:

```text
LoginUseCase
      │
      ├── Android
      │
      └── not naturally reusable on iOS
```

A better design might be:

```kotlin
interface CredentialStore {

    suspend fun saveToken(token: String)

    suspend fun getToken(): String?
}
```

Then:

```text
LoginUseCase
      │
      ▼
CredentialStore
      ▲
      │
 ┌────┴─────┐
 ▼          ▼
Android     iOS
```

The business logic remains portable.

---

# 8. Dependency Inversion

Dependency inversion is one of the most useful techniques for implementing the dependency rule.

Suppose the application needs to send analytics.

A direct dependency might be:

```kotlin
class CheckoutUseCase(
    private val analyticsSdk: SomeAnalyticsSdk
)
```

The domain now knows about a specific SDK.

Instead:

```kotlin
interface Analytics {
    fun track(event: AnalyticsEvent)
}
```

The use case depends on:

```kotlin
Analytics
```

The infrastructure provides:

```kotlin
class AnalyticsImpl(
    private val sdk: SomeAnalyticsSdk
) : Analytics {

    override fun track(
        event: AnalyticsEvent
    ) {
        // SDK implementation
    }
}
```

The graph becomes:

```text
CheckoutUseCase
      │
      ▼
  Analytics
      ▲
      │
      ▼
 AnalyticsImpl
      │
      ▼
 Analytics SDK
```

The dependency has been inverted.

---

# 9. Dependency Inversion Does Not Mean "Everything Gets an Interface"

A common mistake is to interpret dependency inversion as:

```text
Every class
    ↓
Interface
    ↓
Implementation
```

That creates unnecessary abstraction.

For example:

```kotlin
class PriceFormatter {
    fun format(price: Money): String {
        ...
    }
}
```

There may be no meaningful reason to create:

```kotlin
interface PriceFormatter
class PriceFormatterImpl : PriceFormatter
```

If the class is stable, local, and not crossing an architectural boundary, a direct dependency may be perfectly reasonable.

The goal is not maximum abstraction.

The goal is correct dependency direction.

---

# 10. Dependency Rule vs Dependency Injection

These concepts are related but different.

### Dependency Rule

Defines:

```text
Who is allowed to depend on whom?
```

### Dependency Injection

Defines:

```text
How are dependencies supplied?
```

For example:

```kotlin
class GetOrderUseCase(
    private val repository: OrderRepository
)
```

The dependency rule says:

```text
UseCase → Repository abstraction
```

Dependency Injection supplies:

```text
OrderRepositoryImpl
```

at runtime.

```text
             Architecture
                  │
                  ▼
         Dependency Direction
                  │
                  ▼
         Dependency Injection
                  │
                  ▼
            Object Graph
```

DI implements the graph.

It does not define the architecture.

---

# 11. Constructor Injection

Constructor injection is often the simplest way to make dependencies visible.

```kotlin
class GetProfileUseCase(
    private val repository: ProfileRepository
)
```

The dependency is explicit.

Compare this with:

```kotlin
class GetProfileUseCase {

    fun execute() {
        val repository = ServiceLocator
            .get<ProfileRepository>()

        // ...
    }
}
```

The second approach hides the dependency.

The first makes the architecture easier to understand and test.

---

# 12. Dependency Direction and Testability

Suppose:

```kotlin
class CalculatePriceUseCase(
    private val pricingRepository: PricingRepository
)
```

A test can provide:

```kotlin
class FakePricingRepository : PricingRepository {

    override suspend fun getPrice(
        productId: String
    ): Money {
        return Money(100)
    }
}
```

The use case can now be tested independently.

```text
Production
    │
    ▼
PricingRepositoryImpl

Test
    │
    ▼
FakePricingRepository
```

Both satisfy:

```text
PricingRepository
```

The use case does not care which implementation it receives.

That is the practical value of the dependency rule.

---

# 13. Dependency Direction and KMP Source Sets

KMP source sets provide another dimension of dependency control.

Consider:

```text
commonMain
   │
   ▼
androidMain
```

That is not normally how shared business code should be structured.

Instead:

```text
commonMain
    │
    ▼
Platform Contract
    ▲
    │
 ┌──┴───────┐
 ▼          ▼
androidMain iosMain
```

The platform-specific source sets implement platform capabilities.

The common source set remains portable.

---

# 14. `expect` / `actual` and Dependency Direction

KMP also provides `expect` / `actual`.

For example:

```kotlin
// commonMain

expect fun platformName(): String
```

Android:

```kotlin
// androidMain

actual fun platformName(): String {
    return "Android"
}
```

iOS:

```kotlin
// iosMain

actual fun platformName(): String {
    return "iOS"
}
```

Conceptually:

```text
                  commonMain
                      │
                      ▼
                    expect
                      │
              ┌───────┴───────┐
              ▼               ▼
          androidMain      iosMain
             actual           actual
```

The common code declares what it needs.

Each platform supplies the implementation.

---

# 15. Interfaces vs `expect` / `actual`

Both approaches can create a platform boundary.

### Interface

```kotlin
interface DeviceInfo {
    val model: String
}
```

Implementation:

```text
AndroidDeviceInfo
IosDeviceInfo
```

### `expect` / `actual`

```kotlin
expect fun deviceModel(): String
```

with platform-specific `actual` implementations.

A useful distinction is:

```text
Interface
    ↓
Object-level dependency
    ↓
Easy to inject and replace

expect/actual
    ↓
Source-set-level platform mechanism
    ↓
Useful for direct platform capabilities
```

Neither mechanism should be used merely because it exists.

Choose the boundary that communicates the responsibility clearly.

---

# 16. Dependency Direction in a Feature

Consider an Orders feature:

```text
features/orders/
├── presentation/
├── domain/
└── data/
```

The desired dependency direction can be:

```text
presentation
      │
      ▼
   domain
      ▲
      │
     data
```

Not:

```text
presentation
      ↕
     data
      ↕
   domain
```

The second graph allows implementation details to spread throughout the feature.

---

# 17. Dependency Direction Across Features

Suppose:

```text
features/
├── orders/
├── profile/
└── payments/
```

A dangerous structure is:

```text
orders → payments
payments → profile
profile → orders
```

This can create circular or tightly coupled features.

A better structure often introduces shared capabilities:

```text
          Orders
             │
             ▼
            Core
             ▲
             │
         Payments
```

For example:

```text
core/
├── authentication/
├── network/
└── money/
```

Features consume stable shared capabilities.

---

# 18. Avoid Feature-to-Feature Coupling When Possible

Imagine:

```kotlin
class OrderUseCase(
    private val paymentUseCase: PaymentUseCase
)
```

This may be valid in some products.

But if many features start directly depending on one another:

```text
Orders → Payments
Orders → Profile
Payments → Orders
Profile → Orders
```

the dependency graph becomes difficult to manage.

A better boundary may be:

```text
Orders
  │
  ▼
PaymentGateway
  ▲
  │
Payments
```

The Orders feature depends on a capability rather than the internal implementation of Payments.

---

# 19. Stable Contracts

A contract should expose what consumers need, not implementation details.

Good:

```kotlin
interface OrderRepository {
    suspend fun getOrder(id: String): Order
}
```

Less useful:

```kotlin
interface OrderRepository {
    suspend fun executeRetrofitCall(
        request: RetrofitRequest
    ): RetrofitResponse
}
```

The second interface leaks infrastructure.

The first expresses a business capability.

A strong contract uses domain language.

---

# 20. Domain Language vs Technical Language

Compare:

```text
getOrder()
cancelOrder()
calculateDiscount()
```

with:

```text
executeHttpRequest()
insertSqlRecord()
parseJson()
```

The first group describes application behavior.

The second describes implementation.

The domain layer should primarily speak in the first vocabulary.

The data and infrastructure layers can speak in the second.

---

# 21. Dependency Rule and API Design

Public APIs between modules should also follow the dependency rule.

Suppose a domain module exposes:

```kotlin
fun loadOrder(
    request: RetrofitRequest
)
```

The module has leaked Retrofit into its public contract.

A better API:

```kotlin
suspend fun getOrder(
    id: OrderId
): Order
```

Now the contract is technology-neutral.

This matters even more when the module is shared across platforms.

---

# 22. Dependency Rule and DTO Leakage

Avoid:

```kotlin
class OrderUseCase(
    private val repository: OrderRepository
) {

    suspend fun execute(): OrderDto {
        return repository.getOrder()
    }
}
```

If `OrderDto` is a network representation, the domain now knows about data infrastructure.

Prefer:

```kotlin
suspend fun execute(): Order
```

Then:

```text
DTO
 │
 ▼
Mapper
 │
 ▼
Domain Model
```

The DTO stays in the data boundary.

---

# 23. Dependency Rule and Database Entity Leakage

Similarly, avoid:

```kotlin
interface OrderRepository {
    suspend fun getOrder(): OrderEntity
}
```

if `OrderEntity` belongs to the database layer.

Prefer:

```kotlin
interface OrderRepository {
    suspend fun getOrder(): Order
}
```

Then:

```text
Database Entity
      │
      ▼
    Mapper
      │
      ▼
  Domain Model
```

The database representation remains replaceable.

---

# 24. Dependency Rule and UI Model Leakage

The domain should not return:

```kotlin
OrderUiModel
```

from a business use case.

Instead:

```kotlin
Order
```

and presentation maps:

```text
Domain Model
     │
     ▼
Presentation Mapper
     │
     ▼
UI Model
```

This keeps the domain independent of UI technology.

---

# 25. Dependency Rule and Error Types

Error types are another dependency boundary.

Avoid allowing infrastructure-specific exceptions to become the application's universal language:

```kotlin
throw HttpException(...)
```

inside domain logic.

Instead, the data layer can translate technical failures.

For example:

```kotlin
sealed interface RepositoryError {
    data object Unauthorized : RepositoryError
    data object NotFound : RepositoryError
    data object NetworkUnavailable : RepositoryError
}
```

The application can then decide how to represent these results.

---

# 26. Dependency Rule and Coroutines

Kotlin coroutines are part of the Kotlin ecosystem, but even here dependency boundaries can matter.

A domain use case can expose:

```kotlin
suspend operator fun invoke(): Order
```

without knowing which dispatcher or threading implementation performs network work.

Avoid unnecessarily hard-coding platform dispatchers inside business logic:

```kotlin
withContext(Dispatchers.IO) {
    ...
}
```

when the dispatcher choice belongs to infrastructure or composition.

The exact placement depends on the operation and architecture, but the principle remains:

> **Do not introduce a technical dependency into the business layer without a clear reason.**

---

# 27. Dependency Rule and Configuration

Configuration is another common source of leakage.

Avoid making business logic directly depend on Android resources:

```kotlin
context.getString(R.string.discount_message)
```

Instead, the domain can return semantic information:

```kotlin
sealed interface DiscountResult {
    data class Applied(
        val percentage: Int
    ) : DiscountResult

    data object NotEligible : DiscountResult
}
```

The presentation layer decides how that result is displayed.

```text
Domain Result
      │
      ▼
Presentation
      │
      ▼
Localized String
```

This keeps Android resources outside the domain.

---

# 28. Dependency Rule and Logging

Logging is another technical detail.

Avoid making domain logic depend directly on a platform logger:

```kotlin
AndroidLog.d("Order", "Order created")
```

Instead, if logging is genuinely required:

```kotlin
interface Logger {
    fun debug(message: String)
    fun error(message: String)
}
```

Then provide an implementation.

However, do not create a logger dependency in every domain class just because logging is available.

The abstraction should solve a real requirement.

---

# 29. Dependency Rule and Analytics

Analytics is usually an outer concern.

A business event can be represented semantically:

```kotlin
data class OrderCreated(
    val orderId: String
)
```

An analytics adapter can translate that into the specific SDK event.

```text
Domain Event
     │
     ▼
Analytics Boundary
     │
     ▼
SDK-specific Event
```

This prevents the domain from becoming coupled to a vendor's analytics API.

---

# 30. Dependency Rule and Security

Security boundaries are particularly important.

For example:

```text
Domain
  │
  ▼
TokenStore
  ▲
  │
 ┌┴──────────────┐
 ▼               ▼
Android        iOS
Keystore       Keychain
```

The domain knows:

```text
save token
read token
clear token
```

The platform implementation knows:

```text
how to securely store it
```

This separates the policy from the mechanism.

---

# 31. Dependency Rule and Platform Navigation

Navigation is often platform-specific.

Avoid placing:

```text
NavController
UIViewController
NavigationStack
```

inside shared domain logic.

Instead, the domain can produce a semantic result:

```kotlin
sealed interface LoginResult {
    data object Success : LoginResult
    data object InvalidCredentials : LoginResult
}
```

The platform presentation layer decides:

```text
Success
  ↓
Android navigation

Success
  ↓
iOS navigation
```

The business rule remains independent.

---

# 32. Dependency Rule and UI Frameworks

A shared ViewModel or presenter may be useful.

But domain code should not directly depend on:

```text
Compose
SwiftUI
UIKit
Android Views
```

For example, avoid:

```kotlin
class CalculateOrderUseCase {

    @Composable
    fun execute() {
        ...
    }
}
```

UI framework annotations belong at the presentation boundary.

---

# 33. Dependency Rule and Gradle Modules

Gradle can reinforce dependency direction.

For example:

```text
:feature:orders
      │
      ▼
:core:domain
```

and:

```text
:core:domain
      ✕
      │
      └── cannot depend on :androidApp
```

A possible module graph:

```text
                  androidApp
                      │
                      ▼
               feature:orders
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
    core:presentation       core:domain
                                  ▲
                                  │
                            feature:data
```

The exact graph depends on the project's organization.

The important thing is that the build system should not accidentally permit forbidden dependencies.

---

# 34. Enforcing the Rule with Modules

A folder structure says:

```text
Please don't import this.
```

A Gradle module can say:

```text
You cannot import this.
```

That is a significant difference.

For a small project:

```text
Folder boundaries
```

may be enough.

For a large project:

```text
Module boundaries
```

can make architectural rules enforceable.

---

# 35. Dependency Rule and Visibility

Visibility modifiers can also reinforce boundaries.

For example:

```kotlin
internal class OrderRemoteDataSource
```

can prevent consumers from directly using implementation details outside the module.

Public APIs can remain intentionally small:

```kotlin
public interface OrderRepository
```

This creates:

```text
Public Contract
       │
       ▼
Internal Implementation
```

The consumer sees the capability, not every internal component.

---

# 36. Dependency Rule and Package Structure

Packages can communicate ownership:

```text
com.example.orders.domain
com.example.orders.data
com.example.orders.presentation
```

But package names alone do not enforce dependency direction.

A developer can still write:

```kotlin
import com.example.orders.data.OrderDto
```

inside domain code.

Therefore:

```text
Package structure
       +
Code review
       +
Module boundaries
```

provide progressively stronger enforcement.

---

# 37. Dependency Rule and Circular Dependencies

One of the clearest signs of an unhealthy dependency graph is a cycle.

For example:

```text
A → B
B → C
C → A
```

In a feature architecture:

```text
Orders → Payments
Payments → Profile
Profile → Orders
```

The system becomes difficult to reason about.

A healthy dependency graph should generally move toward stable boundaries rather than creating cycles.

```text
Feature
   ↓
Core
```

is easier to understand than:

```text
Feature A
 ↕
Feature B
 ↕
Feature C
 ↕
Feature A
```

---

# 38. Dependency Rule and Dependency Cycles in KMP

KMP makes cycles particularly undesirable because the project already has multiple target boundaries.

Imagine:

```text
commonMain
    ↓
androidMain
    ↓
commonMain
```

or:

```text
Feature A
   ↓
Feature B
   ↓
Feature A
```

Such structures make ownership unclear.

The project should instead have deliberate direction:

```text
common abstraction
       ▲
       │
platform implementation
```

and:

```text
feature
   ↓
core
```

where appropriate.

---

# 39. Dependency Rule and Feature APIs

Large features can expose a small public API.

For example:

```kotlin
interface PaymentsFeature {
    suspend fun processPayment(
        request: PaymentRequest
    ): PaymentResult
}
```

The internal implementation can remain private:

```text
Payments Feature
├── Public API
└── Internal
    ├── Repository
    ├── Network
    ├── Mapping
    └── Platform SDK
```

Other features depend on the public capability.

They do not depend on the internal structure.

---

# 40. Dependency Rule and Build Logic

Build configuration also has dependencies.

For example:

```text
Application
    ↓
Feature
    ↓
Core
```

Gradle plugins and convention plugins can standardize these rules.

A project may use:

```text
build-logic/
├── android-library.gradle.kts
├── kotlin-multiplatform.gradle.kts
└── compose.gradle.kts
```

The build system itself becomes another layer of the project architecture.

The same principle applies:

> Keep shared build conventions separate from product implementation details.

---

# 41. Dependency Rule and Version Catalogs

A version catalog such as:

```text
gradle/libs.versions.toml
```

can centralize dependency versions.

That creates a build-level dependency boundary:

```text
Module
   │
   ▼
Version Catalog
   │
   ▼
Dependency Version
```

It prevents individual modules from independently defining inconsistent versions.

Again, the exact setup can vary, but centralization is useful when it reduces accidental divergence.

```text
                       ┌──────────────┐
                       │ Android App  │
                       └──────┬───────┘
                              │
                              ▼
                       ┌──────────────┐
                       │ iOS App      │
                       └──────┬───────┘
                              │
                     ┌────────┴────────┐
                     ▼                 ▼
               Presentation        Features
                     │                 │
                     └────────┬────────┘
                              ▼
                           Domain
                              ▲
                              │
                            Data
                              │

                              ▼
```

The exact arrows between Application, Presentation, and Features can differ.

The important architectural property is that platform and infrastructure details do not become the foundation of business logic.

```text
                     DOMAIN

               ┌────────┴────────┐

               ▼                 ▼
        Presentation        Data Contract
                                  ▲
                                  │
                             Data Details
                                  │
                    ┌─────────────┼─────────────┐
                    ▼             ▼             ▼
                 Network       Database      Storage
```

The domain defines what the application needs.

The outer layers determine how those needs are fulfilled.

---

# 44. The Dependency Rule and Change

The dependency rule is ultimately about controlling change.

Suppose the application changes its HTTP library:

```text
Ktor → another HTTP implementation
```

Ideally:

```text
Network implementation
        │
        ▼
Repository
```

changes while:

```text
Domain
Use Cases
Business Rules
```

remain stable.

Suppose the database changes:

```text
Database A → Database B
```

The impact should primarily remain in the data layer.

Suppose the UI changes:

```text
Compose → another Android UI approach
```

The domain should remain unaffected.

This is the practical meaning of dependency direction.

---

# 45. Dependency Rule as a Change Firewall

A useful mental model is:

```text
┌──────────────────────────────────────┐
│          Business Rules              │
│                                      │
│       SHOULD CHANGE WITH             │
│          BUSINESS NEEDS              │
└──────────────────┬───────────────────┘
                   │
             Contract Boundary
                   │
┌──────────────────▼───────────────────┐
│        Technical Details             │
│                                      │
│ Network / Database / Platform / UI   │
└──────────────────────────────────────┘
```

The boundary acts like a change firewall.

A technical change should not automatically force business code to change.

---

# 46. Common Mistake — Domain Depending on Retrofit

Bad:

```kotlin
class GetUserUseCase(
    private val api: RetrofitUserApi
)
```

Why?

Because the use case now knows:

```text
Network technology
API implementation
```

Better:

```kotlin
class GetUserUseCase(
    private val repository: UserRepository
)
```

The repository implementation can use Retrofit or another client.

---

# 47. Common Mistake — Domain Depending on Room

Bad:

```kotlin
class GetOrderUseCase(
    private val dao: OrderDao
)
```

The domain now depends on a database abstraction.

Better:

```kotlin
class GetOrderUseCase(
    private val repository: OrderRepository
)
```

The repository decides whether data comes from:

```text
Room
SQLDelight
File
Network
Memory
```

or a combination.

---

# 48. Common Mistake — Shared Code Depending on Android

Bad:

```kotlin
// commonMain

import android.content.Context
```

The shared code is no longer portable.

Better:

```text
commonMain
    │
    ▼
Platform Contract
    ▲
    │
 ┌──┴────┐
 ▼       ▼
Android  iOS
```

The shared code asks for a capability.

The platform supplies it.

---

# 49. Common Mistake — Passing Platform Objects Through the Domain

Avoid:

```kotlin
data class UploadRequest(
    val context: Context,
    val file: File
)
```

when `Context` exists only because Android is being used.

The domain should model the operation:

```kotlin
data class UploadDocument(
    val documentId: String
)
```

The data/platform boundary handles how the document is accessed.

---

# 50. Common Mistake — UI Dependency in Domain

Bad:

```kotlin
class PaymentUseCase {

    fun execute(): Color {
        // ...
    }
}
```

A color is a presentation concern.

Better:

```kotlin
sealed interface PaymentStatus {
    data object Successful : PaymentStatus
    data object Failed : PaymentStatus
}
```

The UI maps:

```text
PaymentStatus
      │
      ▼
Presentation
      │
      ▼
Color / Icon / Message
```

---

# 51. Common Mistake — Static Global Dependencies

Global objects can hide dependency direction:

```kotlin
object GlobalApi {
    val client = ...
}
```

Then:

```kotlin
class OrderUseCase {
    suspend fun execute() {
        GlobalApi.client.call()
    }
}
```

The dependency is invisible in the constructor.

A clearer design is:

```kotlin
class OrderUseCase(
    private val repository: OrderRepository
)
```

Explicit dependencies make architecture easier to understand.

---

# 52. Common Mistake — Service Locator Everywhere

A service locator can produce:

```text
Class
  ↓
Locator
  ↓
Unknown dependency
```

instead of:

```text
Class
  ↓
Explicit constructor dependency
```

For small applications, this may seem convenient.

As the project grows, hidden dependencies make the graph harder to reason about.

---

# 53. Common Mistake — Abstraction Leaks

An abstraction is not useful if it exposes implementation details.

Bad:

```kotlin
interface Storage {
    fun getRoomEntity(id: String): RoomEntity
}
```

This interface claims to be an abstraction while exposing a database-specific type.

Better:

```kotlin
interface OrderStorage {
    suspend fun getOrder(id: String): Order
}
```

The boundary should hide the mechanism.

---

# 54. Common Mistake — One-Way Rule Applied Mechanically

The dependency rule should not become:

```text
Every dependency must point to Domain.
```

Some infrastructure code naturally depends on other infrastructure code.

For example:

```text
Repository
   ↓
Remote Data Source
   ↓
HTTP Client
```

That is reasonable.

The architectural concern is whether these details leak into business policy.

---

# 55. Common Mistake — Forcing Everything Into Domain

Not every shared class belongs in domain.

For example:

```kotlin
JsonSerializer
HttpClientFactory
DatabaseDriverFactory
```

may be shared technical infrastructure.

Putting them in:

```text
domain/
```

because they are used by multiple platforms is incorrect.

Remember:

```text
Shared ≠ Domain
```

This is one of the most important distinctions in KMP.

---

# 56. Shared Does Not Mean Stable

A library can be shared across Android and iOS but still be an implementation detail.

For example:

```text
Shared HTTP Client
```

may be used by both platforms.

That does not mean:

```text
Domain → HTTP Client
```

is a good dependency.

Instead:

```text
Domain
   ▲
   │
Repository Contract
   ▲
   │
Shared Data
   │
   ▼
HTTP Client
```

The HTTP client is shared infrastructure, not business policy.

---

# 57. Dependency Rule and KMP Architecture

The complete picture becomes:

```text
                         KMP
                          │
          ┌───────────────┴───────────────┐
          ▼                               ▼
      Platform                        Shared Code
          │                               │
    Android / iOS                         ▼
                                  ┌──────────────┐
                                  │ Presentation │

                                  ┌──────────────┐
                                  │    Domain    │

                                  │ Rules        │
                                  └──────┬───────┘
                                         ▲
                                         │

                                         │
                              ┌───────────┼───────────┐
                              ▼           ▼           ▼
                           Network     Database     Cache
```

The dependency rule keeps the center protected from the details around it.

# 58. A Practical Dependency Checklist

When creating a dependency, ask:

```text
┌─────────────────────────────────────────────┐
│ Dependency Checklist                         │
├─────────────────────────────────────────────┤
│ 1. Who owns this dependency?                 │
│ 2. Is it business logic or implementation?   │
│ 3. Is it platform-specific?                  │
│ 4. Is it shared infrastructure?              │
│ 5. Does the consumer need the concrete type? │
│ 6. Can a contract express the capability?   │
│ 7. Will this create a dependency cycle?      │
│ 8. Does this leak DTO/entity/UI types?       │
│ 9. Can the dependency be tested independently│
│ 10. What changes if the implementation      │
│     changes?                                 │
└─────────────────────────────────────────────┘
```

These questions are often more valuable than memorizing architectural diagrams.

```text
    ├── domain/
```

Dependency direction:

```text
presentation
     │
     ▼
  domain
     ▲
     │
    data
```

Platform implementations:

```text
androidMain/platform
iosMain/platform
```

This is often enough.

# 60. Dependency Rule in a Large KMP Project

A large project may use:

```text
androidApp
iosApp

features/
├── orders
├── payments
└── profile

core/
├── domain
├── network
├── database
└── platform
```

The graph can be:

```text
             Applications
                  │
                  ▼
              Features
                  │
          ┌───────┴───────┐
          ▼               ▼
       Domain           Core

          │               ▼
```

```text

       ↑

Implementation details
```

# 61. Dependency Rule and API Stability

The smaller the public API between modules, the easier it is to control dependencies.

Instead of exposing:

```text
Repository
DataSource
DTO
Mapper
HTTP client
Database entity
```

a feature may expose only:

```kotlin
interface Orders {
    suspend fun getOrder(
        id: OrderId
    ): Order
}
```

Everything else can remain internal.

This reduces coupling.

---

# 62. Dependency Rule and Encapsulation

Encapsulation is therefore closely related to dependency direction.

A component should expose:

```text
What it can do
```

rather than:

```text
How it does it
```

For example:

```text
OrderRepository
```

should expose:

```text
getOrder()
cancelOrder()
```

rather than:

```text
RetrofitRequest
SqlQuery
CacheKey
```

The latter exposes implementation details.

# 63. Dependency Rule and Architecture Reviews

A dependency graph can be reviewed periodically.

Ask:

```text
Can Domain compile without Android?

Can Domain compile without iOS?

Can Domain compile without the database?

Can Domain compile without the network client?

Can Presentation avoid DTOs?

Can Features avoid internal implementation classes from other Features?

Can platform code change without rewriting business rules?
```

If the answer is mostly yes, the architecture has strong boundaries.

# 64. Dependency Rule and New Platform Support

Imagine the product later adds another target.

A healthy architecture looks like:

```text
                   Shared
                     │
                     ▼
             Platform Contract
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Android      iOS      New Platform
```

The shared business logic does not need to be rewritten.

A new platform mainly needs:

```text
Platform implementation
Application integration
Platform UI
```

This is one of the strongest arguments for dependency inversion in KMP.

# 65. Dependency Rule and Replaceability

Consider a repository:

```text
OrderRepository
```

It could be implemented by:

```text
OrderRepositoryImpl
```

or:

```text
FakeOrderRepository
```

or:

```text
OfflineOrderRepository
```

or:

```text
RemoteOnlyOrderRepository
```

The use case remains unchanged.

```text
                  OrderRepository
                  ▲      ▲      ▲
                  │      │      │
               Remote   Fake   Offline
```

The abstraction provides replaceability.

---

# 66. Dependency Rule and Offline Mode

Suppose the application switches between:

```text
Online
Offline
```

The domain should not need:

```kotlin
if (networkAvailable) {
    ...
}
```

if that decision belongs to the repository/data strategy.

Instead:

```text
Use Case
   │
   ▼
Repository
   │
   ├── Local
   └── Remote
```

The repository can implement the chosen data strategy.

The domain remains focused on business behavior.

---

# 67. Dependency Rule and Caching

Caching is another implementation detail.

Avoid:

```kotlin
class OrderUseCase(
    private val cache: OrderCache,
    private val api: OrderApi
)
```

unless caching itself is genuinely part of the business policy.

A simpler design:

```text
OrderUseCase
     │
     ▼
OrderRepository
     │
 ┌───┴────┐
 ▼        ▼
Cache    API
```

The repository controls data retrieval.

---

# 68. Dependency Rule and Retry Logic

Retry behavior can be technical or business-related.

For network failures:

```text
HTTP Client
   │
   ▼
Retry policy
```

may belong in infrastructure.

But if the business rule says:

```text
A payment operation may be attempted only three times
```

that rule may belong closer to the domain.

The key question is:

> **Is the decision caused by the business, or by the technical mechanism?**

That distinction determines the appropriate layer.

---

# 69. Dependency Rule and Transactions

Database transaction mechanics are infrastructure.

For example:

```text
Database transaction
```

belongs to the data layer.

But a business operation such as:

```text
Create order
Reserve inventory
Confirm payment
```

may represent a domain-level workflow.

The architecture should prevent database-specific transaction APIs from becoming the vocabulary of the domain unless they genuinely represent a business concept.

---

# 70. Dependency Rule and Concurrency

Similarly, concurrency implementation is often technical:

```text
Mutex
Coroutine Dispatcher
Thread
Actor
```

The business operation might simply be:

```text
SynchronizeOrders
```

The domain should express the operation.

The infrastructure determines how it is executed safely.

---

# 71. Dependency Rule and Platform Services

A platform service can be represented as a capability:

```kotlin
interface NetworkMonitor {
    fun isOnline(): Boolean
}
```

The platform supplies:

```text
AndroidNetworkMonitor
IosNetworkMonitor
```

The shared layer depends on:

```text
NetworkMonitor
```

rather than:

```text
ConnectivityManager
NWPathMonitor
```

This is a textbook KMP boundary.

---

# 72. Dependency Rule and File Access

Similarly:

```kotlin
interface FileStorage {
    suspend fun save(
        name: String,
        bytes: ByteArray
    )
}
```

Platform implementations can use:

```text
Android file APIs
iOS file APIs
```

The shared business code does not need to know where the bytes are physically stored.

# 73. Dependency Rule and Notifications

A notification requirement can be represented as:

```kotlin
interface NotificationService {
    fun notify(
        notification: AppNotification
    )
}
```

Android and iOS can implement their respective mechanisms.

The domain can decide:

```text
When should a notification-worthy business event occur?
```

The platform decides:

```text
How should it be displayed?
```

That is a clean separation of policy and mechanism.

# 74. Dependency Rule and Authentication

Authentication illustrates the boundary particularly well.

```text
                    LoginUseCase
                          │
                          ▼
                   AuthRepository
                          │
                 ┌────────┴────────┐
                 ▼                 ▼
             Remote API       Secure Storage
```

The domain decides:

```text

```

The data/platform layers decide:

```text
How credentials are transmitted and stored.
```

Large projects can use build tooling or static analysis to detect forbidden dependencies.

```text

Platform → Contracts

Forbidden:

Domain → Retrofit
Domain → Database
Feature A → Feature B internal
```

The specific tooling can vary.

> **If a rule is important enough to enforce manually every day, consider whether the build system can enforce it automatically.**

# 81. A Dependency Matrix

For a simple KMP architecture:

| Consumer ↓ / Dependency → | Presentation | Domain | Data | Platform |
|---|---:|---:|---:|---:|
| Presentation | — | ✅ | ❌ | ⚠️ |
| Domain | ❌ | — | ❌* | ❌ |
| Data | ❌ | ✅ | — | ⚠️ |
| Platform | ❌ | ⚠️ | ⚠️ | — |

`⚠️` means the dependency may be valid depending on the boundary.

`❌*` is intentionally simplified: data implementations may implement domain contracts, but the domain should not depend on concrete data implementations.

The important relationship is:

```text
Presentation → Domain
Data → Domain abstractions
Platform → Platform contracts
```

# 83. The Dependency Rule in One Example

Consider an order cancellation feature.

### Domain

```kotlin
class CancelOrderUseCase(
    private val repository: OrderRepository
) {

    suspend operator fun invoke(
        order: Order
    ) {
        require(order.status == OrderStatus.Pending)

        repository.cancelOrder(order.id)
    }
}
```

### Data

```kotlin
class OrderRepositoryImpl(
    private val api: OrderApi
) : OrderRepository {

    override suspend fun cancelOrder(
        id: String
    ) {
        api.cancelOrder(id)
    }
}
```

### Presentation

```kotlin
class OrderViewModel(
    private val cancelOrder: CancelOrderUseCase
)
```

### Platform UI

```text
Android Compose
        │
        ▼
OrderViewModel
        │
        ▼
CancelOrderUseCase
        │
        ▼
OrderRepository
        │
        ▼
OrderRepositoryImpl
        │
        ▼
OrderApi
```

Each layer has a clear role.

# 85. What Changes If Android UI Changes?

```text

```

```text

Data

```

This is the value of separating platform UI from shared logic.


The domain contract remains:


The use case remains:

```kotlin

```

This is what a good dependency boundary is designed to achieve.

# 88. Dependency Rule and Architectural Fitness

A useful architecture test is not:

> "Does the project have Clean Architecture folders?"

Instead ask:

```text
Can the domain be tested without Android?

Can business rules run without a real database?

Can the API client be replaced?

Can the UI framework change?

Can a platform service be mocked?

Can a new platform implement the shared contracts?

Can a feature evolve without touching unrelated features?
```

If these answers are positive, the architecture is providing practical value.

# 89. Part 4 Takeaways

The dependency rule is the foundation that makes the previous structural concepts meaningful.

Remember:

- Dependencies should have a deliberate direction.
- Business rules should remain independent of implementation details.
- Presentation can depend on domain abstractions.
- Data implementations can depend on domain contracts.
- Platform implementations can satisfy shared contracts.
- `commonMain` should not become coupled to Android or iOS details.
- `expect` / `actual` can establish platform boundaries.
- Interfaces can establish object-level dependency boundaries.
- Dependency Injection supplies dependencies; it does not define architecture.
- Constructor injection makes dependencies explicit.
- DTOs, database entities, and UI models should not leak into the domain without a deliberate reason.
- Shared infrastructure is not the same thing as domain logic.
- `core` should contain meaningful stable capabilities, not miscellaneous code.
- Feature-to-feature dependencies should be controlled.
- Circular dependencies are strong signals that boundaries need review.
- Gradle modules can enforce architectural boundaries more strongly than folders.
- Visibility modifiers and small public APIs can protect internal implementation details.
- Not every class needs an interface.
- Not every shared class belongs in the domain layer.
- The dependency rule is ultimately about controlling change.

The central mental model is:

```text
                 STABLE BUSINESS RULES
                           ▲
                           │
                    abstractions
                           │
            ┌──────────────┼──────────────┐
            │              │              │
            ▼              ▼              ▼
        Presentation      Data         Platform
                           │              │
                           ▼              ▼
                        Network        OS APIs
                        Database       Native SDKs
```

Or, more simply:

```text
        DETAILS
          │
          ▼
      IMPLEMENTATION
          │
          ▼
       CONTRACT
          ▲
          │
        DOMAIN
          ▲
          │
    BUSINESS POLICY
```

The dependency rule is therefore not about preventing dependencies.

It is about **placing dependencies where they preserve the independence of the most important parts of the system**.

**The strongest KMP dependency graph is not the one with the fewest dependencies. It is the one where dependencies point toward stable contracts, implementation details remain replaceable, and shared business logic does not become a hostage to any single platform or technology.**
