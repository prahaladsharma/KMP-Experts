# Chapter 11 — Clean Architecture

## Part 5 — Enterprise Design

A small KMP application can often live comfortably inside a few modules:

```text
androidApp/
iosApp/
shared/
```

That structure can be enough for an early product.

Enterprise applications are different.

They may contain:

- dozens of features
- multiple teams
- hundreds of developers
- several applications
- multiple backend systems
- shared platform capabilities
- strict security requirements
- independent release cycles
- different ownership boundaries
- large test suites
- long-lived legacy code

At that scale, project structure becomes more than organization.

It becomes a **system for controlling change**.

A useful enterprise mental model is:

```text
                         ENTERPRISE PRODUCT
                                │
             ┌──────────────────┼──────────────────┐
             │                  │                  │
             ▼                  ▼                  ▼
         Applications        Features            Core
             │                  │                  │
      ┌──────┴──────┐      ┌────┴────┐      ┌─────┴─────┐
      ▼             ▼      ▼         ▼      ▼           ▼
   Android         iOS   Orders    Payments Network   Platform
```

The objective is not to create the largest possible module tree.

The objective is to create boundaries that allow a large organization to evolve without turning every change into a repository-wide event.

> [!IMPORTANT]
> **Enterprise architecture is primarily about managing change, ownership, and dependencies at scale.**
>
> A structure that works for five developers may become expensive when fifty teams depend on it.

---

# 1. Enterprise Design Is a Scaling Problem

As an application grows, several dimensions increase simultaneously:

```text
Code Size
   +
Feature Count
   +
Team Count
   +
Platform Count
   +
Dependency Count
   +
Release Complexity
   +
Build Time
   ↓
Architectural Pressure
```

A project that worked well when it contained:

```text
10,000 lines
```

may become difficult when it reaches:

```text
1,000,000+ lines
```

The architecture must therefore scale along more than one dimension.

A useful model is:

```text
                    SCALE
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
     Code           Teams         Features
       │              │              │
       └──────────────┼──────────────┘
                      ▼
               Module Boundaries
```

---

# 2. Enterprise Design Starts with Boundaries

In a large KMP project, boundaries can exist at several levels:

```text
Enterprise
   │
   ├── Application
   │
   ├── Feature
   │
   ├── Domain
   │
   ├── Platform
   │
   ├── Infrastructure
   │
   └── Build
```

Each boundary answers a different question.

| Boundary | Main question |
|---|---|
| Application | Which product/application owns this? |
| Feature | Which business capability owns this? |
| Domain | Which business rules belong here? |
| Platform | Which operating system provides this? |
| Infrastructure | Which technical system implements this? |
| Build | Which Gradle/module boundary owns compilation and dependencies? |

Enterprise design becomes manageable when these boundaries are explicit.

---

# 3. From One Shared Module to a Modular Platform

A project may begin with:

```text
MyKmpApp/
├── androidApp/
├── iosApp/
└── shared/
```

As it grows:

```text
MyKmpApp/
├── androidApp/
├── iosApp/
├── shared/
├── core/
└── features/
```

Eventually:

```text
MyKmpApp/
├── apps/
├── core/
├── features/
├── platform/
├── integrations/
└── build-logic/
```

The shared module gradually becomes a platform made of smaller capabilities.

```text
                  KMP Platform
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
      Core          Features       Platform
        │              │              │
        ▼              ▼              ▼
   Reusable        Business       OS-specific
   capabilities    capabilities   capabilities
```

This is a common evolution path for large systems.

---

# 4. Enterprise Design Is Not "More Modules"

One of the easiest mistakes is assuming:

```text
More modules = better architecture
```

That is not true.

Consider:

```text
module-a
module-b
module-c
module-d
module-e
module-f
module-g
module-h
```

If every module depends on every other module:

```text
A ↔ B ↔ C
↕   ↕   ↕
D ↔ E ↔ F
```

the project has many modules but few meaningful boundaries.

A better enterprise structure might have fewer but stronger boundaries:

```text
Application
    │
    ▼
Features
    │
    ▼
Stable Core
    │
    ▼
Infrastructure
```

The goal is **controlled dependency**, not module count.

---

# 5. Feature Modules

Feature modules are one of the most useful enterprise boundaries.

For example:

```text
features/
├── authentication/
├── profile/
├── orders/
├── payments/
├── inventory/
├── notifications/
└── settings/
```

Each feature owns a business capability.

A feature can internally contain:

```text
orders/
├── presentation/
├── domain/
└── data/
```

Or, for a more modular setup:

```text
orders/
├── api/
├── domain/
├── data/
└── presentation/
```

The exact structure depends on how much isolation the enterprise requires.

---

# 6. Feature Ownership

A feature module becomes especially valuable when ownership is aligned with it.

For example:

```text
Orders Team
    │
    ▼
features/orders
```

```text
Payments Team
    │
    ▼
features/payments
```

```text
Identity Team
    │
    ▼
features/authentication
```

Now architecture and organizational ownership reinforce each other.

```text
Team Boundary
      │
      ▼
Code Ownership
      │
      ▼
Module Boundary
      │
      ▼
Dependency Boundary
```

This is one of the most important enterprise architecture ideas.

---

# 7. Conway's Law and Project Structure

Organizations naturally influence software structure.

If ten teams all modify one giant module:

```text
shared/
```

the module becomes a shared coordination point.

If teams have clearer boundaries:

```text
authentication/
orders/
payments/
profile/
```

the code can reflect organizational ownership.

The goal is not to blindly copy the organization chart.

The goal is to reduce unnecessary coordination.

A healthy enterprise structure makes it clear:

```text
Who owns this?
Who can change this?
Who consumes this?
What is the public API?
```

# 8. Feature APIs

Large features should expose small public APIs.

For example:

```kotlin
interface Payments {

    suspend fun process(
        request: PaymentRequest
    ): PaymentResult
}
```

The internal implementation can remain hidden:

```text
payments/
├── api/
│   └── Payments.kt
│
└── internal/
    ├── PaymentRepository.kt
    ├── PaymentApi.kt
    ├── PaymentMapper.kt
    └── PaymentSdkAdapter.kt
```

Other features should consume:

```text
Payments API
```

rather than:

```text
PaymentRepositoryImpl
PaymentApi
PaymentSdkAdapter
```

This drastically reduces coupling.

---

# 9. Public API vs Internal Implementation

An enterprise module can be thought of as:

```text
┌─────────────────────────────────────────┐
│              Feature Module             │
│                                         │
│   ┌─────────────────────────────────┐   │
│   │          Public API             │   │
│   │                                 │   │
│   │   Small / Stable / Intentional  │   │
│   └────────────────┬────────────────┘   │
│                    │                    │
│                    ▼                    │
│   ┌─────────────────────────────────┐   │
│   │        Internal Details         │   │
│   │                                 │   │
│   │ Repository / API / Mapping      │   │
│   │ SDK / Database / Helpers        │   │
│   └─────────────────────────────────┘   │
│                                         │
└─────────────────────────────────────────┘
```

The smaller the public surface, the easier it is to change the internals.

# 10. Enterprise Core Modules

Most enterprise KMP projects need some form of shared core.

A practical structure might be:

```text
core/
├── common/
├── domain/
├── network/
├── database/
├── security/
├── logging/
├── analytics/
└── platform/
```

Each module should have a clear reason to exist.

For example:

```text
core/network
```

owns shared networking infrastructure.

```text
core/security
```

owns security-related infrastructure and contracts.

```text
core/platform
```

owns platform integration boundaries.

---

# 11. The Core Dumping Ground

The most common enterprise mistake is:

```text
core/
└── everything
```

Eventually:

```text
core/
├── Utils.kt
├── Helpers.kt
├── CommonManager.kt
├── AppConstants.kt
├── FeatureHelper.kt
├── NetworkHelper.kt
├── PaymentHelper.kt
└── Misc.kt
```

This creates a giant dependency magnet.

Soon:

```text
Every feature
      │
      ▼
     core
```

and eventually:

```text
core
 ↕
features
```

with excessive coupling.

A strong enterprise core should be small, stable, and intentional.

---

# 12. Stable Core vs Fast-Changing Features

A useful enterprise model is:

```text
                  Stable
                    ▲
                    │
                  Core
                    │
                    │
               Contracts
                    │
                    │
                Features
                    │
                    ▼
                 Change
```

Core capabilities should not be rewritten every time a feature changes.

Features can evolve more rapidly.

This naturally suggests:

```text
Core
  ▲
  │
Features
  ▲
  │
Applications
```

with controlled dependency direction.

# 13. Enterprise Dependency Graph

A practical large-scale graph can look like:

```text
                         Applications
                              │
               ┌──────────────┼──────────────┐
               ▼              ▼              ▼
            Android          iOS       Other Targets
               │              │
               └──────┬───────┘
                      ▼
                   Features
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
      Orders      Payments    Profile
          │           │           │
          └───────────┼───────────┘
                      ▼
                     Core
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
    Network        Database       Security
```

The graph should be intentionally directional.

---

# 14. Feature-to-Feature Dependencies

Feature dependencies are sometimes necessary.

For example:

```text
Orders
   ↓
Payments
```

But unrestricted feature coupling can create a dependency web:

```text
Orders → Payments
Orders → Profile
Payments → Orders
Profile → Orders
Profile → Payments
```

This becomes difficult to maintain.

A better approach is often to introduce a stable capability:

```text
Orders
   │
   ▼
Payment Contract
   ▲
   │
Payments
```

The consuming feature depends on the contract, not the internal implementation.

---

# 15. Shared Contracts Module

For larger systems, contracts can be separated:

```text
contracts/
├── authentication/
├── payments/
├── orders/
└── profile/
```

For example:

```kotlin
interface PaymentGateway {

    suspend fun authorize(
        request: PaymentRequest
    ): PaymentResult
}
```

The feature can implement the contract.

```text
Consumer
   │
   ▼
PaymentGateway
   ▲
   │
Payments Implementation
```

This can reduce feature-to-feature coupling.

# 18. Platform-Specific Enterprise Integrations

Enterprise applications often depend on SDKs that are platform-specific.

Examples include:

- identity providers
- payment SDKs
- device security services
- biometric APIs
- enterprise analytics
- push notification services
- document scanners
- hardware integrations

These should generally be isolated.

For example:

```text
payments/
├── commonMain/
│   └── PaymentGateway.kt
│
├── androidMain/
│   └── AndroidPaymentGateway.kt
│
└── iosMain/
    └── IosPaymentGateway.kt
```

The shared feature depends on:

```kotlin
PaymentGateway
```

rather than directly on the SDK.

---

# 19. Enterprise SDK Adapter Pattern

A platform SDK should often sit behind an adapter.

```text
Feature
  │
  ▼
Platform Contract
  │
  ▼
SDK Adapter
  │
  ▼
Third-Party SDK
```

Example:

```kotlin
interface BiometricAuthenticator {

    suspend fun authenticate(): AuthResult
}
```

Android:

```kotlin
class AndroidBiometricAuthenticator(
    private val biometricManager: BiometricManager
) : BiometricAuthenticator {
    // Android implementation
}
```

iOS:

```kotlin
class IosBiometricAuthenticator(
    private val context: LAContext
) : BiometricAuthenticator {
    // iOS implementation
}
```

The business feature does not need to understand the SDK.

# 20. Enterprise Design and Security Boundaries

Enterprise systems usually have stronger security requirements.

Security-sensitive capabilities should have explicit boundaries:

```text
Security
├── Credential Store
├── Token Provider
├── Encryption
├── Device Integrity
└── Authentication
```

For example:

```text
Application
    │
    ▼
Authentication Contract
    │
    ▼
Security Module
    │
 ┌──┴──────────┐
 ▼             ▼
Android       iOS
Keystore      Keychain
```

This makes security infrastructure easier to audit and replace.

# 21. Enterprise Design and Authentication

Authentication is rarely just a UI concern.

A large application may have:

```text
Authentication
├── Login
├── Token Refresh
├── Session
├── Logout
├── MFA
└── Device Trust
```

The architecture should separate:

```text
Business authentication state
```

from:

```text
Platform credential storage
```

For example:

```text
Auth Domain
     │
     ▼
Auth Repository
     │
     ├── Remote Identity Provider
     │
     └── Secure Token Storage
```

# 22. Enterprise Design and API Gateways

Large applications may communicate with multiple backend systems:

```text
Orders API
Payments API
Profile API
Inventory API
Identity API
```

A feature should not necessarily know about all network infrastructure.

Instead:

```text
Feature
  │
  ▼
Feature Repository
  │
  ▼
Network Module
  │
  ├── Orders API
  ├── Payments API
  └── Profile API
```

The network module can standardize:

- authentication
- serialization
- retry behavior
- headers
- logging
- connectivity
- request policies

while features remain focused on product behavior.

---

# 23. Enterprise Design and API Models

Large organizations often have multiple API contracts.

Avoid allowing raw API models to travel throughout the application.

```text
Backend DTO
      │
      ▼
API Mapper
      │
      ▼
Domain Model
      │
      ▼
Feature
```

This becomes particularly important when:

```text
Backend Team
```

and:

```text
Mobile Team
```

release independently.

The mobile architecture should not make backend representation the application's internal model.

---

# 24. Enterprise Design and Data Ownership

A large application may have:

```text
Remote Data
Local Cache
User Preferences
Secure Storage
Temporary State
```

Each should have clear ownership.

For example:

```text
core/database
core/security
feature/orders/data
feature/profile/data
```

Avoid one giant:

```text
DatabaseManager
```

that every feature accesses directly.

Instead:

```text
Orders
   │
   ▼
OrderRepository
   │
   ▼
OrderDataSource
```

The feature owns its data behavior.

# 25. Enterprise Design and Offline-First Systems

Large enterprise mobile applications often need to work under unreliable connectivity.

A common structure:

```text
UI
 │
 ▼
Use Case
 │
 ▼
Repository
 │
 ├───────────────┐
 ▼               ▼
Local            Remote
 │               │
 ▼               ▼
Database         API
```

The repository becomes the boundary between business behavior and synchronization infrastructure.

This makes offline support an architectural concern rather than a collection of UI conditions.

---

# 26. Enterprise Design and Synchronization

Synchronization can become its own capability:

```text
core/sync/
├── SyncEngine
├── SyncScheduler
├── ConflictResolver
└── SyncState
```

A feature might expose:

```kotlin
interface OrderSynchronizer {
    suspend fun sync()
}
```

The implementation handles:

```text
Local changes
      ↓
Upload
      ↓
Remote changes
      ↓
Conflict resolution
      ↓
Local update
```

The feature should not need to understand every infrastructure detail.

---

# 27. Enterprise Design and Background Work

Background work can be isolated:

```text
core/background/
├── Scheduler
├── Worker
└── Task
```

Platform implementations:

```text
Android
└── WorkManager

iOS
└── Background Tasks
```

Shared application logic:

```text
SyncOrdersUseCase
```

The architecture becomes:

```text
Shared Use Case
      │
      ▼
Background Contract
      │
 ┌────┴────┐
 ▼         ▼
Android    iOS
```

This keeps scheduling mechanics separate from business work.

# 28. Enterprise Design and Observability

Large systems need observability.

Common capabilities:

```text
Logging
Metrics
Tracing
Analytics
Crash Reporting
```

These should not leak into every business class as vendor-specific dependencies.

A useful structure:

```text
core/observability/
├── Logger
├── Metrics
├── Tracer
└── Analytics
```

Vendor-specific adapters remain outside the business layer.

```text
Application Event
       │
       ▼
Observability Contract
       │
       ▼
Vendor Adapter
```

# 29. Enterprise Design and Feature Flags

Feature flags are common in enterprise systems.

A naive implementation is:

```kotlin
if (FirebaseRemoteConfig...) {
    ...
}
```

inside business logic.

A better abstraction:

```kotlin
interface FeatureFlags {

    fun isEnabled(
        flag: FeatureFlag
    ): Boolean
}
```

The business logic depends on the capability.

The implementation can use:

```text
Remote Config
Local Configuration
Experiment Platform
Static Defaults
```

The vendor remains outside the core logic.

```text
├── BuildConfiguration
└── RuntimeConfiguration
```

Avoid scattering:

```text

FEATURE_FLAG
ENVIRONMENT
```

throughout the project.

A centralized configuration boundary makes environment changes safer.

A repository can evolve into:

```text
apps/
├── consumer/

├── domain/
├── network/
├── security/
└── platform/

features/
├── authentication/
├── payments/
```

```text

    └── reporting
```

# 34. Enterprise Design and Versioning

When modules become shared across many applications, API stability matters.

For example:

```text
core:authentication
```

may be consumed by:

```text
consumer
employee
partner
```

Changing its public API can affect all three.

Therefore:

```text
Public API
    ↓
Compatibility
    ↓
Migration Cost
```

Enterprise modules should expose stable, intentionally designed contracts.

---

# 35. Enterprise Design and Semantic Versioning

Internal modules may not always require public semantic versioning.

However, the same principle applies:

```text
Breaking change
     ↓
Consumer impact
```

Before changing a shared API:

```text
Who consumes it?
What is the migration path?
Can the change be backward compatible?
Can the API be deprecated first?
```

This is architecture as change management.

---

# 36. Enterprise Design and Deprecation

Instead of immediately deleting:

```kotlin
fun oldLogin()
```

a shared module can temporarily provide:

```kotlin
@Deprecated(
    message = "Use authenticate() instead"
)
fun oldLogin()
```

Then consumers migrate gradually.

This becomes especially valuable when many applications consume the same capability.

---

# 37. Enterprise Design and Build Performance

Large projects can become slow because of:

```text
Too many dependencies
Large modules
Frequent invalidation
Heavy annotation processing
Large test suites
```

Module boundaries can help reduce unnecessary compilation.

For example:

```text
feature-orders
```

should not force unrelated:

```text
feature-profile
```

to rebuild every time.

A well-designed module graph can improve incremental development.

---

# 38. Module Size vs Module Count

There is a balance.

Too few modules:

```text
One giant module
```

can produce:

- large compilation units
- weak boundaries
- high coupling
- broad invalidation

Too many modules:

```text
Hundreds of tiny modules
```

can produce:

- Gradle complexity
- dependency management overhead
- slower configuration
- difficult navigation

The goal is:

```text
Meaningful Module
```

not:

```text
Smallest Possible Module
```

---

# 39. Enterprise Design and Build Logic

As modules grow, Gradle configuration can become repetitive:

```kotlin
plugins {
    kotlin("multiplatform")
    ...
}
```

Enterprise projects can centralize conventions:

```text
build-logic/
├── kotlin-multiplatform.gradle.kts
├── android-library.gradle.kts
├── compose.gradle.kts
└── testing.gradle.kts
```

This creates consistency.

A module can then apply a convention:

```kotlin
plugins {
    id("company.kotlin.multiplatform")
}
```

The exact plugin naming is project-specific.

The architectural idea is to keep build conventions centralized.

# 40. Enterprise Design and Dependency Catalogs

A centralized catalog can provide:

```text

```

with:

```text

Compose
KMP libraries
Testing libraries

```

This reduces version drift.

But the catalog should not become a list of every dependency in the company without ownership.

Dependency ownership still matters.

# 41. Enterprise Design and Testing Architecture

Large projects need layered tests.

```text
                 Test Pyramid
                     ▲
                    / \
                   / UI\
                  /─────\
                 /Feature\
                /─────────\
               /  Domain   \
              /─────────────\
             / Unit / Shared \
            /_________________\
```

A practical KMP distribution can be:

```text
commonTest
    │
    ├── Domain tests
    ├── Repository tests
    ├── Mapper tests
    └── Shared presentation tests

Platform Tests
    │
    ├── Android
    └── iOS

UI Tests
    │
    ├── Android
    └── iOS
```

The architecture should make the majority of business behavior testable without UI infrastructure.

# 42. Enterprise Design and Test Ownership

A feature team should generally own its tests:

```text
├── commonTest/
├── androidMain/
```


For example:

```text

        │
        ▼

        ▲
        │
Payments Implementation
```

Tests can validate:


KMP can share UI in some architectures, but enterprise design should still distinguish:

```text
Business logic
Presentation
Design system
Platform UI
```

A button component should not know:

```text
OrderRepository
PaymentApi
AuthenticationState
```

UI components should remain reusable presentation infrastructure.

---

# 105. Enterprise Design and Domain Boundaries

A feature should own its domain language.

For example:

```text
Orders
├── Order
├── OrderStatus
├── CancelOrder
└── OrderRepository
```

Payments should own:

```text
Payment
PaymentStatus
AuthorizePayment
PaymentRepository
```

Avoid a giant global domain:

```text
domain/
├── Order
├── Payment
├── User
├── Inventory
├── Notification
├── ...
```

when those concepts have different ownership and change patterns.

---

# 106. Enterprise Design and Bounded Contexts

This idea is closely related to bounded contexts.

For example:

```text
Order Context
     │
     ├── Order
     ├── OrderStatus
     └── OrderRules

Payment Context
     │
     ├── Payment
     ├── PaymentStatus
     └── PaymentRules
```

The same word may mean different things in different contexts.

For example:

```text
Customer
```

may have different representations in:

```text
Orders
Payments
Identity
Support
```

Do not force every feature to share one universal model if their meanings differ.

---

# 107. Enterprise Design and Model Translation

A feature boundary can translate between contexts:

```text
Orders Customer
      │
      ▼
Customer Adapter
      │
      ▼
Identity Customer
```

This avoids creating a giant enterprise-wide model that every team must depend on.

---

# 108. Enterprise Design and the "God Model"

A common enterprise mistake is:

```text
UniversalUser
UniversalOrder
UniversalCustomer
```

with hundreds of fields used by many teams.

These models become difficult to change.

A better approach is context-specific models:

```text
OrdersUser
PaymentsCustomer
ProfileCustomer
```

with explicit mappings when needed.

---

# 109. Enterprise Design and Stable Domain Concepts

The domain should contain concepts that are meaningful to the feature.

For example:

```kotlin
data class OrderId(
    val value: String
)
```

This can be more expressive than:

```kotlin
String
```

everywhere.

Strong domain types can prevent accidental mixing:

```text
OrderId
PaymentId
CustomerId
```

This becomes valuable in large codebases.

---

# 110. Enterprise Design and API Boundaries

The same principle applies to APIs:

```kotlin
interface OrderRepository {
    suspend fun getOrder(
        id: OrderId
    ): Order
}
```

rather than:

```kotlin
interface OrderRepository {
    suspend fun get(
        id: String
    ): Any
}
```

A strong contract communicates meaning.

---

# 111. Enterprise Design and Error Boundaries

Large systems should also have clear error ownership.

For example:

```text
Infrastructure Error
      │
      ▼
Data Error
      │
      ▼
Domain/Application Result
      │
      ▼
Presentation State
```

This prevents:

```text
HTTP 500
```

from becoming the universal application error model.

Each layer translates errors into the vocabulary appropriate to its responsibility.

---

# 112. Enterprise Design and Failure Isolation

A strong architecture can isolate failures.

For example:

```text
Analytics SDK fails
      │
      ▼
Analytics Adapter
      │
      ✕
Order Creation
```

The business operation should not necessarily fail because an optional analytics service is unavailable.

Likewise:

```text
Profile API unavailable
```

should not automatically prevent:

```text
Local Orders
```

from functioning if the architecture allows independent data flows.

This is one benefit of clear module boundaries.

---

# 113. Enterprise Design and Resilience

Resilience strategies can live at appropriate boundaries:

```text
Network
├── Retry
├── Timeout
└── Connectivity

Repository
├── Cache
├── Fallback
└── Synchronization

Domain
├── Business validation
└── Business recovery decisions
```

The layers cooperate without collapsing into one giant service.

---

# 114. Enterprise Design and Observability Boundaries

When a feature performs:

```text
CreateOrder
```

the application may record:

```text
OrderCreated
```

Observability infrastructure can attach:

```text
duration
success
failure
network
```

without requiring the business rule to know which monitoring vendor is used.

This makes instrumentation consistent and replaceable.

# 115. Enterprise Design and Documentation of Dependencies

A mature project can maintain a simple dependency policy:

```text
Allowed:

app → feature
feature → core
feature → feature API
data → domain contract
platform → platform contract

Avoid:

domain → platform
domain → database
domain → network client
feature → feature internal

```

This can become part of the project's architecture documentation.

# 116. Enterprise Design and Code Review Checklist

Before merging a new module or feature, ask:

```text

□ Does it represent a real capability?
```

# 117. Common Enterprise Mistake — The Mega Shared Module

```text
├── everything
├── everything
└── everything
```

```text
Ownership becomes unclear.
Builds become expensive.
```

Migration:

```text

  ↓
identify capabilities
  ↓

  ↓
```

# 118. Common Enterprise Mistake — Too Many Tiny Modules

Example:

```text

UserFormatterModule
UserValidatorModule
```

# 119. Common Enterprise Mistake — Shared Core as a Dumping Ground

Bad:

```text

├── OrderHelper
├── PaymentHelper
├── ProfileHelper
└── RandomUtils
```

Better:


Put code where it is owned.

# 120. Common Enterprise Mistake — Direct Feature Internals

Bad:

```kotlin

```

from Orders.

The feature has bypassed the public API.

Better:

```kotlin

```

This preserves the boundary.

# 121. Common Enterprise Mistake — Platform SDK in Feature Logic

Bad:


Better:

```text

      │
      ▼

      │
      ▼

```

# 122. Common Enterprise Mistake — Enterprise-Wide Global Models

Bad:

```text
UniversalUser
UniversalCustomer
UniversalAccount
```

used by every team.

This creates:

```text

    ↓
One model
    ↓
Every change
    ↓
Everyone affected
```

Prefer context-specific models with explicit mappings.

# 123. Common Enterprise Mistake — Architecture by Committee

If every small change requires:

```text
Architecture Board
Platform Team
Security Team
Mobile Team
Backend Team
```

the architecture may be creating too much coordination.

Good boundaries should allow teams to make local decisions safely.

Govern the boundaries.

Do not centrally control every implementation detail.

# 124. Common Enterprise Mistake — Rewriting Everything

Large codebases often tempt teams to say:

```text
"The architecture is old.
Let's rewrite everything."
```

A safer strategy is often:

```text
Old
 │
 ▼
Adapter
 │
 ▼
New Boundary
 │
 ▼
New Feature
```

Then migrate gradually.

Enterprise architecture must support incremental modernization.

---

# 125. Common Enterprise Mistake — Ignoring Build Architecture

A project can have beautiful code boundaries but terrible build performance.

If every module depends on:

```text
giant-core
```

then:

```text
Change one feature
     ↓
giant-core affected
     ↓
many modules affected
     ↓
large rebuild
```

The dependency graph should be designed with build impact in mind.

# 126. Common Enterprise Mistake — Ignoring Ownership

A module without a clear owner eventually becomes:

```text
Everyone's responsibility
        ↓
Nobody's responsibility
```

Every important enterprise module should have:

```text

Documentation
Tests
API policy
Maintenance responsibility
```

# 127. Common Enterprise Mistake — Optimizing for Reuse Too Early

A team may create:

```text

```

because:

```text
"Maybe another feature will need this."
```

This can create premature coupling.

A better rule:

> **Extract shared capabilities when reuse is demonstrated and the abstraction is stable enough to deserve a boundary.**

Reuse is valuable.

Premature reuse can be expensive.

# 134. Enterprise Design and Lifecycle Boundaries

# 156. Part 5 Takeaways

Enterprise KMP architecture is fundamentally about **scaling boundaries**.

Remember:

- Enterprise design is a scaling problem across code, teams, features, platforms, and releases.
- A large project needs meaningful boundaries, not merely more folders.
- Feature modules are useful for business ownership.
- Core modules should represent stable shared capabilities.
- `core` should never become a miscellaneous dumping ground.
- Public APIs should be small, stable, and intentional.
- Internal implementation details should remain hidden.
- Feature-to-feature dependencies should be controlled.
- Contracts can reduce direct coupling between teams and features.
- KMP source sets provide an additional platform boundary inside modules.
- Platform SDKs should generally be isolated behind contracts or adapters.
- Security, analytics, networking, database, and observability are good candidates for explicit infrastructure boundaries.
- Multiple applications can share an enterprise KMP platform without sharing every feature.
- Build logic is part of enterprise architecture.
- Module boundaries can improve build isolation and ownership.
- Too few modules can create a monolith; too many can create Gradle complexity.
- Team ownership should align with meaningful code boundaries.
- Architecture should support incremental migration from legacy systems.
- Context-specific domain models are often safer than universal enterprise models.
- Shared code should be created where sharing reduces duplication without creating excessive coupling.
- Public APIs are organizational contracts, not just Kotlin interfaces.
- Enterprise architecture should support local team autonomy within stable global rules.
- Architecture documentation, ownership, and automated checks become increasingly important as the organization grows.

The central mental model is:

```text
                    ENTERPRISE
                         │
                 ┌───────┴────────┐
                 ▼                ▼
            Applications       Platform
                 │                │
                 ▼                ▼
              Features        Infrastructure
                 │                │
                 └───────┬────────┘
                         ▼
                    Stable Core
                         │
                         ▼
                 Shared Contracts
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
          Android                    iOS
```

The most important enterprise principle is:

> **Scale the boundaries before the codebase forces you to.**

Not every project needs dozens of modules on day one.

But every growing project eventually needs clear answers to:

```text
Who owns this?
What does it expose?
What can it depend on?
What depends on it?
What changes independently?
```

When those answers are encoded in the project structure, KMP becomes more than a code-sharing technology.

It becomes a foundation for building a large, maintainable, multi-platform product.
