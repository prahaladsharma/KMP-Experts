# Chapter 11 — Clean Architecture

## Part 6 — Scaling

A project structure that works for a small KMP application does not automatically work for an enterprise product.

As the application grows, several things grow with it:

```text
Features
   +
Developers
   +
Modules
   +
Dependencies
   +
Platforms
   +
Tests
   +
Build Time
   +
Release Complexity
```

At some point, project structure stops being a matter of organization.

It becomes a mechanism for **scaling change**.

A useful mental model is:

```text
                KMP PROJECT
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
       Code       Teams       Platforms
        │           │           │
        └───────────┼───────────┘
                    ▼
              Boundaries
                    │
                    ▼
             Controlled Change
```

> [!IMPORTANT]
> **Scaling architecture does not mean adding more folders or modules. It means creating boundaries that allow the system to grow without allowing every change to affect everything else.**

---

# 1. What Does "Scaling" Mean?

When developers hear "scaling," they often think about backend traffic.

Architecture has another kind of scaling problem:

```text
Organizational Scaling
```

A KMP codebase must scale across:

- source code
- features
- developers
- teams
- platforms
- applications
- dependencies
- build systems
- testing
- releases
- ownership

Consider the progression:

```text
5 developers
    ↓
20 developers
    ↓
50 developers
    ↓
200 developers
```

The code does not simply become larger.

The number of interactions grows.

A simple approximation:

```text
More teams
    ↓
More possible dependencies
    ↓
More coordination
    ↓
More architectural pressure
```

The project structure exists partly to control that coordination cost.

---

# 2. Scaling Is About Controlling Change

Suppose a project contains:

```text
100 features
```

If every feature depends on every other feature:

```text
Feature A ↔ Feature B
Feature A ↔ Feature C
Feature B ↔ Feature D
Feature C ↔ Feature D
...
```

the number of relationships becomes difficult to reason about.

Instead:

```text
Features
   │
   ▼
Stable Core
```

can reduce unnecessary relationships.

The architecture is therefore not merely organizing files.

It is controlling the **blast radius of change**.

---

# 3. The Blast Radius of a Change

Imagine changing:

```text
Network Client
```

In a tightly coupled project:

```text
Network Client
     │
     ├── Feature A
     ├── Feature B
     ├── Feature C
     ├── Feature D
     ├── Feature E
     └── Feature F
```

One change can affect many features.

In a better structure:

```text
Network Client
      │
      ▼
Network Boundary
      │
      ▼
Repositories
      │
      ▼
Features
```

The implementation can change behind the boundary.

The goal is:

```text
Small Change
     ↓
Small Blast Radius
```

---

# 4. Scaling Dimensions

A KMP architecture may need to scale across several dimensions simultaneously.

| Dimension | Scaling pressure |
|---|---|
| Code | More classes and modules |
| Features | More business capabilities |
| Teams | More independent contributors |
| Platforms | Android, iOS, desktop, web, etc. |
| Applications | Multiple products |
| Dependencies | More libraries and integrations |
| Builds | Longer compilation and testing |
| Releases | More coordination |
| Ownership | More teams and boundaries |
| Legacy | More historical decisions |

A good architecture considers these dimensions together.

---

# 5. Vertical Scaling vs Horizontal Scaling

There are two useful ways to think about architecture growth.

### Vertical scaling

A single feature becomes larger:

```text
Orders
  │
  ├── Search
  ├── Details
  ├── History
  ├── Cancellation
  ├── Returns
  └── Tracking
```

### Horizontal scaling

The number of features increases:

```text
Orders
Payments
Profile
Inventory
Support
Notifications
Reports
```

A scalable architecture must handle both.

```text

```

A larger application becomes:

```text
core/

```

A multi-product enterprise may eventually become:

```text
platform/
```

This is an important transition:

```text

     ↓
Modular Application
     ↓
Shared Platform
```

KMP can participate in all of these stages.

# 7. Scaling the Project Structure

A simple project:

```text
MyApp/
├── androidApp/
├── iosApp/
└── shared/
```

A growing project:

```text
MyApp/
├── androidApp/
├── iosApp/
├── core/
└── features/
```

A larger product:

```text
MyApp/
├── apps/
├── features/
├── core/
├── integrations/
├── platform/
└── build-logic/
```

A multi-application platform:

```text
Enterprise/
├── apps/
├── products/
├── features/
├── platform/
├── integrations/
├── tooling/
└── build-logic/
```

Each transition should be driven by a real scaling problem.

---

# 8. Do Not Scale the Architecture Too Early

A common mistake is creating:

```text
30 modules
```

for an application that has:

```text
3 features
```

because:

> "This is how enterprise architecture works."

The result can be:

```text
Too many abstractions
Too many Gradle files
Too many dependencies
Too much ceremony
```

A better principle:

> **Introduce a boundary when the current structure starts creating a real cost.**

Architecture should evolve with the system.

---

# 9. The Evolutionary Architecture Model

A practical progression is:

```text
Stage 1
Single shared module
        ↓
Stage 2
Feature packages
        ↓
Stage 3
Feature modules
        ↓
Stage 4
Core platform modules
        ↓
Stage 5
Multiple applications
        ↓
Stage 6
Enterprise platform
```

Not every project needs all six stages.

The architecture should stop where the product's complexity stops.

---

# 10. Scaling Through Features

Feature modularization is one of the most common scaling strategies.

```text
features/
├── authentication/
├── orders/
├── payments/
├── profile/
├── inventory/
├── search/
└── notifications/
```

Each feature can evolve independently.

For example:

```text
Orders Team
      │
      ▼
features/orders
```

The team can work mostly inside its boundary.

---

# 11. Feature Boundaries Reduce Cognitive Load

Without boundaries:

```text
Developer
   │
   ▼
Entire Repository
```

With meaningful boundaries:

```text
Developer
   │
   ▼
Feature
   │
   ▼
Relevant Core Modules
```

The developer still needs to understand the architecture.

But they do not need to understand every implementation detail.

This is a major scaling benefit.

---

# 12. Scaling Team Ownership

Suppose one team owns:

```text
Orders
```

and another owns:

```text
Payments
```

The architecture can represent:

```text
Team A
  │
  ▼
Orders Module

Team B
  │
  ▼
Payments Module
```

Now the dependency graph also becomes an ownership graph.

This helps answer:

```text
Who reviews this?
Who maintains it?
Who approves API changes?
```

---

# 13. Scaling Across Multiple Teams

As teams increase:

```text
Team A
Team B
Team C
Team D
```

the architecture should avoid requiring everyone to coordinate for every change.

A healthy graph:

```text
           Stable Core
          ▲     ▲     ▲
          │     │     │
       Team A Team B Team C
```

A problematic graph:

```text
Team A ↔ Team B
  ↕         ↕
Team C ↔ Team D
```

The second graph creates high coordination cost.

---

# 14. Scaling the Dependency Graph

A project can be represented as a directed graph:

```text
A → B
B → C
C → D
```

This is relatively easy to reason about.

A dense graph:

```text
A → B, C, D
B → A, C, D
C → A, B, D
D → A, B, C
```

is much harder.

As the number of nodes increases, dependency density becomes increasingly important.

A scalable architecture therefore tries to keep the graph intentional and relatively sparse.

---

# 15. Dependency Density

Consider:

```text
10 modules
```

with:

```text
8 dependencies
```

versus:

```text
10 modules
```

with:

```text
45 dependencies
```

Both have ten modules.

But the second architecture is significantly more coupled.

Therefore:

```text
Module Count
```

is not enough to evaluate scalability.

Also examine:

```text
Dependency Density
```

---

# 16. Stable Core Architecture

A scalable system often has:

```text
                 Core
          ┌───────┼───────┐
          ▼       ▼       ▼
       Domain   Network  Security
          ▲       ▲       ▲
          │       │       │
       Feature Feature Feature
```

The core should remain relatively stable.

Features can evolve faster.

This creates a useful asymmetry:

```text
High Stability
      ▲
      │
     Core
      │
      ▼
   Features
      │
      ▼
High Change
```

---

# 17. Scaling Core Modules

As the project grows, a single:

```text
core/
```

may become too broad.

It can evolve into:

```text
core/
├── domain/
├── network/
├── database/
├── security/
├── observability/
├── platform/
└── testing/
```

But each module should have a clear responsibility.

Avoid:

```text
core/common
```

becoming:

```text
everything shared
```

---

# 18. Scaling the Domain

A large domain can itself become modular.

Instead of:

```text
domain/
├── Order
├── Payment
├── User
├── Inventory
└── Notification
```

consider business boundaries:

```text
domain/
├── orders/
├── payments/
├── identity/
├── inventory/
└── notifications/
```

This can improve ownership and reduce accidental coupling.

---

# 19. Scaling by Bounded Context

Large enterprises often contain different business contexts.

For example:

```text
Order Management
Payment Processing
Customer Identity
Inventory Management
```

Each context can have its own vocabulary.

```text
Orders
└── Order

Payments
└── Payment

Identity
└── Customer
```

Do not assume that a single global model is always the best abstraction.

---

# 20. Scaling the Data Layer

A feature's data layer can become complex:

```text
Repository
    │
    ├── Remote Data Source
    ├── Local Data Source
    ├── Cache
    ├── Mapper
    └── Synchronization
```

At scale, each responsibility should have clear ownership.

A useful structure:

```text
feature/orders/
└── data/
    ├── repository/
    ├── remote/
    ├── local/
    ├── mapper/
    └── sync/
```

The feature owns the business-specific data behavior.

Core can provide generic infrastructure.

---

# 21. Scaling the Network Layer

A large application may have:

```text
Identity API
Orders API
Payments API
Inventory API
Analytics API
```

A centralized network module can provide:

```text
HTTP Client
Authentication
Serialization
Timeouts
Logging
Metrics
Connectivity
```

while feature-specific API interfaces remain inside their feature.

```text
core/network
      │
      ├── HTTP infrastructure
      │
      └── shared policies

feature/orders
      │
      └── OrderApi
```

This prevents the network module from owning feature business logic.

---

# 22. Scaling API Clients

Avoid one giant:

```text
ApiService
```

containing:

```text
getUser()
getOrder()
pay()
search()
upload()
download()
...
```

Instead:

```text
OrderApi
PaymentApi
ProfileApi
InventoryApi
```

The network infrastructure remains shared.

API ownership remains feature-specific.

---

# 23. Scaling Database Ownership

Avoid:

```text
GlobalDatabaseManager
```

with every feature accessing every table.

Instead:

```text
Orders
   │
   ▼
OrderDataSource
   │
   ▼
Database

Payments
   │
   ▼
PaymentDataSource
   │
   ▼
Database
```

A central database engine can be shared.

Data ownership remains feature-oriented.

---

# 24. Scaling Persistence

Large applications may contain:

```text
User preferences
Secure credentials
Orders
Cached APIs
Search history
Offline queues
```

These have different requirements.

For example:

```text
Secure credentials
    → secure storage

Orders
    → database

Temporary state
    → memory

Offline queue
    → durable local storage
```

Do not force every persistence requirement into one generic abstraction.

---

# 25. Scaling Platform Services

A KMP platform layer can grow:

```text
platform/
├── secure-storage/
├── notifications/
├── biometrics/
├── device-info/
├── connectivity/
├── file-system/
└── background-work/
```

Each capability should have a small contract.

For example:

```kotlin
interface SecureStorage {
    suspend fun put(
        key: String,
        value: String
    )

    suspend fun get(
        key: String
    ): String?

    suspend fun remove(
        key: String
    )
}
```

Android and iOS implement the contract independently.

---

# 26. Scaling Platform Implementations

A mature KMP project may contain:

```text
commonMain/
androidMain/
iosMain/
```

Later, more targets may appear:

```text
desktopMain/
wasmJsMain/
jsMain/
```

The architecture should avoid assuming:

```text
There are exactly two platforms.
```

Instead:

```text
Common Capability
       │
       ├── Android
       ├── iOS
       ├── Desktop
       └── Web
```

where the business and technical requirements justify those targets.

---

# 27. Scaling Through `expect` / `actual`

For direct platform capabilities:

```kotlin
expect fun currentPlatform(): Platform
```

can scale across targets.

The important architectural boundary is:

```text
commonMain
      │
      ▼
Expected capability
      │
 ┌────┼────┬────┐
 ▼    ▼    ▼    ▼
Android iOS Desktop Web
```

The common layer defines the requirement.

Targets define the mechanism.

---

# 28. Scaling Interfaces Across Platforms

For more complex dependencies:

```kotlin
interface SecureStorage
```

may be preferable.

The graph becomes:

```text
Feature
   │
   ▼
SecureStorage
   ▲
   │
   ├── AndroidSecureStorage
   ├── IosSecureStorage
   └── DesktopSecureStorage
```

This is especially useful when the capability needs:

- multiple methods
- lifecycle management
- dependency injection
- mocking
- multiple implementations

---

# 29. Scaling Dependency Injection

As modules grow, manual construction becomes difficult.

For example:

```text
Application
  │
  ├── Network
  ├── Database
  ├── Security
  ├── Analytics
  ├── Orders
  ├── Payments
  └── Profile
```

A dependency injection strategy can make the graph manageable.

The important architectural principle remains:

```text
Composition Root
       │
       ▼
Object Graph
       │
       ▼
Modules
```

The business classes should not construct their own infrastructure dependencies.

---

# 30. Scaling DI Without Creating a Global Container

A common mistake is:

```text
Everything
   ↓
Global Container
```

and then:

```kotlin
container.get<Anything>()
```

everywhere.

This hides dependencies.

Prefer:

```text
Composition Root
      │
      ▼
Explicit Construction
      │
      ▼
Constructor Injection
```

The DI framework should help manage the graph, not hide it.

---

# 31. Scaling Application State

Large applications may contain:

```text
Authentication State
Cart State
Order State
Profile State
Connectivity State
Feature Flag State
```

Do not automatically place everything in:

```text
GlobalAppState
```

Instead, define ownership:

```text
Authentication → Auth module
Orders → Orders feature
Profile → Profile feature
Connectivity → Platform/Core
```

This keeps state close to the capability that owns it.

---

# 32. Scaling State Across Features

Sometimes a state genuinely crosses features.

For example:

```text
Authentication
```

may affect:

```text
Orders
Payments
Profile
```

Instead of every feature owning its own copy:

```text
Auth State
     │
     ▼
Stable Auth Contract
     │
 ┌───┼────┐
 ▼   ▼    ▼
Orders Payments Profile
```

This creates one clear source of truth.

---

# 33. Scaling Event Communication

Direct feature calls can become expensive:

```text
A → B
A → C
A → D
```

Sometimes an event can reduce coupling:

```text
A
│
▼
Business Event
│
├── B
├── C
└── D
```

For example:

```kotlin
data class OrderCompleted(
    val orderId: OrderId
)
```

Consumers can react without Orders knowing every consumer.

Use this carefully.

Events introduce their own complexity.

---

# 34. Scaling Event Systems

An enterprise event system may need:

```text
Event
 ↓
Dispatcher
 ↓
Subscribers
 ↓
Retry
 ↓
Logging
 ↓
Metrics
```

At this point it becomes infrastructure.

The domain should not depend on the mechanics of event delivery.

It should express the business event.

---

# 35. Scaling Asynchronous Work

A feature may need:

```text
Upload
Sync
Retry
Background processing
Notifications
```

The architecture can separate:

```text
Business Operation
```

from:

```text
Scheduling Mechanism
```

For example:

```text
SyncOrdersUseCase
        ▲
        │
Background Scheduler
        │
 ┌──────┴──────┐
 ▼             ▼
Android       iOS
```

The same business operation can be invoked from multiple environments.

---

# 36. Scaling Offline-First Architecture

Offline-first systems often grow into:

```text
UI
 │
 ▼
Use Case
 │
 ▼
Repository
 │
 ├── Local Database
 │
 ├── Remote API
 │
 ├── Sync Queue
 │
 └── Conflict Resolver
```

The repository boundary becomes critical.

Without it, UI code can become responsible for:

```text
network availability
database queries
retry
sync
conflict resolution
```

which does not scale.

---

# 37. Scaling Synchronization

Synchronization logic can be modeled as:

```text
                 Sync Engine
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Upload     Download   Conflict
          │          │          │
          └──────────┼──────────┘
                     ▼
                  Database
```

Each feature may own feature-specific synchronization rules.

Core infrastructure can provide generic scheduling and networking support.

---

# 38. Scaling Caching

Caching can become layered:

```text
Memory Cache
     ↓
Local Database
     ↓
Network
```

The architecture should define:

```text
Who owns cache policy?
Who invalidates?
What is the source of truth?
What happens offline?
```

A cache should not silently become a second business database.

---

# 39. Scaling Testing

As modules increase, testing should become more localized.

A scalable testing model:

```text
Feature
 ├── commonTest
 ├── platform tests
 └── integration tests

Core
 ├── unit tests
 └── contract tests

Application
 └── UI / end-to-end tests
```

The majority of business behavior should be testable without launching the entire application.

---

# 40. Scaling Test Execution

Suppose:

```text
features/orders
```

changes.

A smart build pipeline can prioritize:

```text
Orders tests
   ↓
Affected integration tests
   ↓
Application tests
```

rather than immediately running every test for every local change.

CI may still run the complete suite before release.

The goal is fast developer feedback without sacrificing release confidence.

---

# 41. Scaling Test Ownership

A feature should generally own:

```text
Feature Tests
```

Core teams own:

```text
Core Tests
```

Platform teams own:

```text
Platform Adapter Tests
```

This creates a clear responsibility chain.

---

# 42. Scaling Build Performance

Build time becomes a major concern as a project grows.

Common sources of build pressure:

```text
Large modules
Too many dependencies
Unnecessary module coupling
Heavy processors
Large generated code
Large test suites
```

A good module graph can reduce unnecessary recompilation.

---

# 43. Scaling with Gradle Modules

A module boundary can isolate compilation:

```text
feature-orders
feature-payments
feature-profile
```

If:

```text
feature-orders
```

changes, unrelated modules may remain unaffected depending on the dependency graph.

This can improve the developer feedback loop.

---

# 44. Scaling Without Creating a Module Explosion

A project with:

```text
500 tiny modules
```

may have worse developer experience than:

```text
50 meaningful modules
```

The correct question is not:

> "Can this become another module?"

Ask:

> **"Does this boundary create meaningful independence?"**

Meaningful independence may include:

```text
Ownership
Build isolation
Release isolation
Testing isolation
Dependency control
Business capability
```

---

# 45. Scaling Build Logic

As module count grows:

```text
build.gradle.kts
```

files can become repetitive.

Convention plugins can standardize:

```text
KMP setup
Android setup
Compose setup
Testing
Lint
Publishing
```

Example:

```text
build-logic/
├── kmp-library.gradle.kts
├── android-library.gradle.kts
├── testing.gradle.kts
└── publishing.gradle.kts
```

Then modules consume conventions rather than duplicating configuration.

---

# 46. Scaling Dependency Management

Large projects need centralized dependency governance.

A version catalog can define:

```text
Kotlin
Compose
Coroutines
Testing
Network
Database
```

For example:

```toml
[versions]
kotlin = "..."
coroutines = "..."

[libraries]
kotlin-coroutines = { ... }
```

The exact versions belong to the project.

The architectural principle is centralized dependency ownership.

---

# 47. Scaling Third-Party Dependencies

Every dependency adds:

```text
Build cost
Security risk
Upgrade work
Compatibility risk
Maintenance cost
```

Therefore enterprise projects should periodically review:

```text
Who uses this?
Why do we use it?
Can it be removed?
Is it maintained?
Is it required in commonMain?
```

A dependency should have an owner.

---

# 48. Scaling Dependency Updates

A large repository should avoid updating every dependency manually in every module.

Instead:

```text
Version Catalog
      │
      ▼
Shared Dependency Version
      │
 ┌────┼────┐
 ▼    ▼    ▼
Module A B Module C
```

This reduces version drift.

But centralized versions should still be changed deliberately because one upgrade can affect many modules.

---

# 49. Scaling API Compatibility

Suppose:

```text
core:authentication
```

has:

```kotlin
interface AuthService
```

and fifty consumers depend on it.

Changing:

```kotlin
authenticate()
```

can become expensive.

A scalable API strategy uses:

```text
Small API
+
Explicit versioning
+
Deprecation
+
Migration path
```

The public surface should be intentionally narrow.

---

# 50. Scaling Backward Compatibility

For widely consumed modules:

```text
Old API
   │
   ├── deprecated
   │
   ▼
New API
```

Consumers migrate gradually.

This avoids:

```text
Big Bang Migration
```

across the entire enterprise.

---

# 51. Scaling Through Independent Release Boundaries

Not every module needs an independent artifact.

But if a capability is consumed by:

```text
Multiple applications
```

an independent release boundary may become valuable.

For example:

```text
security-platform
```

can be released independently from:

```text
consumer-app
```

when the organizational and technical setup justifies it.

---

# 52. Scaling Multi-Application KMP

An enterprise may eventually have:

```text
apps/
├── consumer/
├── employee/
├── partner/
└── admin/
```

Shared capabilities:

```text
core/
features/
platform/
```

Each application selects what it needs.

```text
Consumer
 ├── Authentication
 ├── Orders
 └── Profile

Employee
 ├── Authentication
 ├── Inventory
 └── Reporting
```

This is more scalable than putting every feature into every application.

---

# 53. Scaling Product Variants

Sometimes one application serves multiple products.

For example:

```text
Enterprise App
 ├── Customer A
 ├── Customer B
 └── Customer C
```

The architecture should distinguish:

```text
Shared capability
```

from:

```text
Customer-specific behavior
```

Avoid filling business logic with:

```kotlin
if (customer == A) ...
else if (customer == B) ...
```

everywhere.

Instead, create controlled configuration or strategy boundaries.

---

# 54. Scaling Configuration-Based Behavior

For product-specific behavior:

```kotlin
interface ProductConfiguration {
    val features: Set<Feature>
}
```

Then:

```text
Product A
    ↓
Configuration A

Product B
    ↓
Configuration B
```

The business architecture remains stable.

---

# 55. Scaling Feature Flags

Feature flags can support gradual rollout:

```text
Feature
   │
   ▼
FeatureFlag
   │
 ┌─┴─────────┐
 ▼           ▼
Enabled    Disabled
```

This can help with:

```text
A/B testing
Gradual rollout
Emergency disablement
Migration
```

But excessive feature flags create hidden complexity.

Every flag should have:

```text
Owner
Purpose
Default
Lifecycle
Removal plan
```

---

# 56. Scaling Team Boundaries with APIs

Suppose:

```text
Orders Team
```

needs:

```text
Payments Team
```

The architecture can expose:

```kotlin
interface PaymentGateway
```

rather than allowing:

```text
Orders → Payments internals
```

The API becomes the collaboration boundary.

This reduces the amount of implementation knowledge teams must share.

---

# 57. Scaling Code Ownership

A useful repository tree:

# 58. Scaling Architecture Governance

Govern a few important rules:

```text

Module dependency rules
Platform boundaries
Security boundaries
Public API rules
Build conventions
```

Do not create a process where every implementation detail needs central approval.

Good governance protects boundaries.

It does not eliminate team autonomy.

# 59. Scaling Architecture Checks

Automated checks can verify:

```text

Domain cannot import database implementation

Forbidden modules cannot be used
Cycles cannot be introduced
```

```text

       ↓

       ↓
```

This is much stronger than relying only on documentation.

# 60. Scaling Through Dependency Analysis

As the project grows, periodically inspect:

```text
Platform dependencies spreading
```



The graph tells you where to investigate.

# 61. Scaling Core Without Creating a Bottleneck

```text

     ↓
```

Instead:

```text

 ├── core:network
 ├── core:security
 └── core:database
```

Consumers depend only on what they actually need.

# 83. Scaling Architecture Through Contracts

Contracts become increasingly important as the number of consumers grows.

For one consumer:

```text

```

may be sufficient.

For many consumers:

```text

```

becomes more valuable.

A simple rule:

```text
More consumers
     ↓
Higher cost of change
     ↓
Greater value of stable API
```

# 84. Scaling with Consumer-Driven Contracts

If many features consume a capability:

```text

```

the consumers can define what behavior they actually need.

Avoid exposing unnecessary methods:

```kotlin

    fun pay()
    fun refund()
    fun tokenize()
    fun validate()
    fun ...
}
```

if most consumers only need:

```kotlin
fun authorize()
```

Smaller interfaces scale better.


# 113. Scaling Change Review

A useful review question:

> **How many boundaries does this change cross?**

For example:

```text

    → low coordination

Feature + Core
    → moderate coordination

Feature + Core + Platform + Other Features
    → high coordination
```

The more boundaries crossed, the more carefully the change should be evaluated.

# 114. Scaling with Change Budgets

Architecture can be thought of as managing change budgets.

A feature should be able to change:

```text
Frequently
```

without requiring:

```text
Core changes
Platform changes
Multiple team approvals
```

Core should change:

```text
Less frequently
```

because it has many consumers.

This creates:

```text
High Change
   ↓
Features

Low Change
   ↓
Core Contracts
```

```text

        ↓

        ↓

        ↓
```

For example:

```text

```

should not require:


# 116. Scaling and Dependency Stability

The most widely consumed modules should generally be the most stable.



# 120. Scaling and Architectural Drift

Architectural drift happens when:

```text
Initial Architecture
       ↓
Small Exceptions
       ↓
More Exceptions
       ↓
Copied Exceptions
       ↓
Architecture Becomes Inconsistent
```

For example:

```text
"Just this one feature can access the database directly."
```

Later:

```text
Five features do it.
```

Eventually:

```text
Repository boundary no longer means anything.
```

Small exceptions can accumulate into systemic coupling.

# 121. Scaling and Controlled Exceptions

Not every rule should be absolute.

If a feature genuinely needs a platform capability:

```text
Document why
Define the boundary
Limit the dependency
Test it
```

The problem is not an exception.

The problem is an undocumented exception becoming the default.

---

# 208. Scaling and Network Evolution

Backend APIs also evolve.

A resilient client architecture isolates:

```text
API representation
```

from:

```text
Domain representation
```

Then:

```text
API v1
```

can coexist temporarily with:

```text
API v2
```

through adapters or repository logic.

---

# 209. Scaling and Contract Evolution

A contract should evolve deliberately.

For example:

```kotlin
interface PaymentGateway {
    suspend fun authorize(
        request: PaymentRequest
    ): PaymentResult
}
```

If consumers need new behavior:

```kotlin
suspend fun refund(...)
```

consider whether:

```text
Existing contract
```

should grow or whether:

```text
RefundGateway
```

should be a separate capability.

Smaller capabilities often evolve more independently.

---

# 210. Scaling and Interface Segregation

Large interfaces become expensive because every consumer inherits every change.

Prefer:

```text
Authentication
Profile
Account
```

instead of:

```text
UserEverythingService
```

This keeps dependency surfaces small.

---

# 211. Scaling and Dependency Surface

A useful mental model:

```text
Module
  │
  ├── Public API
  ├── Dependencies
  └── Consumers
```

Scaling becomes easier when:

```text
Public API ↓
Unnecessary Dependencies ↓
Local Reasoning ↑
```

---

# 212. Scaling and the Stable Abstraction Principle

A useful enterprise principle is:

> **Stable components should depend on stable abstractions.**

If a stable core module depends directly on a rapidly changing implementation:

```text
Core → Vendor SDK
```

the stable module becomes unstable.

Instead:

```text
Core → Contract
          ▲
          │
      Vendor Adapter
```

The dependency direction protects stability.

---

# 213. Scaling and Stable Dependencies

A high-level module should not depend on a lower-level module merely because the lower-level implementation is convenient.

Instead:

```text
High-Level Policy
       ↓
Abstraction
       ↑
Low-Level Detail
```

This is the same dependency inversion principle applied at enterprise scale.

# 214. Scaling and Architecture Layers

A large KMP system may contain:


# 215. Scaling and Architectural Boundaries

Every boundary should answer:

```text
What does it hide?
What does it expose?
Who owns it?
What changes independently?
```

If these questions have no meaningful answers, the boundary may not be necessary.

# 216. Scaling and the Principle of Least Knowledge

A feature should know only what it needs.

For example:

```text
Orders
  ↓
PaymentGateway
```

It should not need to know:

```text
Payment SDK
Payment database
Payment API endpoint
Payment tokenization
Payment logging
```

This reduces coupling.

---

# 217. Scaling and Information Hiding

A strong module hides:

```text
Implementation
Data structures
Vendor APIs
Platform APIs
Internal algorithms
```

and exposes:

```text
Capabilities
```

This is one of the oldest and most durable ideas in software architecture.

---

# 218. Scaling and Architecture Smells

At scale, watch for:

```text
🚨 Giant core module
🚨 Giant API interface
🚨 Global state
🚨 Direct database access
🚨 Cross-feature internals
🚨 Platform checks everywhere
🚨 Vendor SDK everywhere
🚨 Circular dependencies
🚨 Slow builds
🚨 Large shared models
🚨 No ownership
🚨 No migration strategy
```

These are signals of scaling pressure.

---

# 219. Scaling and the "God Module"

A God Module knows:

```text
Everything
```

and is used by:

```text
Everything
```

For example:

```text
AppManager
```

containing:

```text
Auth
Network
Database
Navigation
Analytics
Payments
Orders
```

This becomes difficult to test, change, and own.

Prefer focused capabilities.

---

# 220. Scaling and the "God Interface"

Similarly:

```kotlin
interface AppService {
    fun login()
    fun logout()
    fun order()
    fun pay()
    fun profile()
    fun search()
    fun notify()
}
```

This interface becomes a dependency bottleneck.

Split it by capability.

---

# 221. Scaling and Global State

Global state often becomes:

```text
Everything
     ↓
GlobalState
```

Then every feature depends on it.

Instead:

```text
AuthState
OrderState
ProfileState
```

should be owned by their respective capabilities.

Only genuinely cross-cutting state should be centralized.

---

# 222. Scaling and Global Utilities

Similarly:

```text
GlobalUtils
```

often becomes a dumping ground.

Prefer:

```text
MoneyFormatter
DateProvider
IdGenerator
NetworkMonitor
```

with clear ownership.

---

# 223. Scaling and Utility Placement

A simple rule:

```text
Used by one feature
    → Keep local

Used by several features
    → Consider shared capability

Stable cross-cutting capability
    → Core

Platform-specific
    → Platform
```

This avoids premature extraction.

# 224. Scaling and Architecture Evolution Signals

Consider modularization when you see:

```text
Builds becoming slow
Teams frequently editing the same module
Features importing internals
Repeated infrastructure
Core growing rapidly
Cross-team coordination increasing
Tests becoming difficult to isolate
```

These are signals that boundaries may need to evolve.

# 225. Scaling and the First Refactoring Signal

One strong signal is:

> **"Every change requires touching the same shared module."**

For example:

```text

      ↓
shared/
      ↓
conflicts
      ↓
coordination
```

That often indicates the shared module is too broad.

---

# 226. Scaling and the Second Refactoring Signal

Another signal:

> **"Developers cannot tell where code belongs."**

If engineers ask:

```text

shared?
utils?
common?
feature?
platform?
```

the boundaries are not communicating responsibility clearly.

---

# 227. Scaling and the Third Refactoring Signal

Another signal:

> **"Changing one feature breaks unrelated features."**

This indicates:

```text

```

Investigate:

```text

Shared models
Shared database access
Global services
Feature internals
```

---

# 228. Scaling and the Fourth Refactoring Signal

Another signal:

> **"The build is slow even when the change is tiny."**

Investigate:

```text
Large modules
Dependency fan-out
Generated code
Shared core
Unnecessary dependencies
```

Build architecture is often the solution.

---

# 229. Scaling and the Fifth Refactoring Signal

Another signal:

> **"Every team waits for the platform team."**

This may indicate:

```text
Platform bottleneck
```

The solution may be:

```text
Better APIs
Self-service tooling
Documentation
Stable contracts
Team-owned adapters
```

not simply adding more platform engineers.

# 230. Scaling and Architecture as Feedback

# 232. Scaling and Affected Modules

One particularly useful metric is:

```text

```

If:

```text

   ↓

```

If:

```text
Feature change
   ↓
3 modules affected
```

the architecture may have better isolation.

The number alone is not a verdict, but it is a useful signal.

# 233. Scaling and Dependency Fan-Out

Another metric:

```text

```

A module with:

```text

```

```text

Careful releases
```

# 234. Scaling and Dependency Fan-In

Likewise:

```text
How many dependencies does this module have?
```

A feature with:

```text
20 dependencies
```

may be too tightly coupled.

The architecture should investigate whether those dependencies can be reduced.

# 235. Scaling and Dependency Fan-In/Fan-Out

A useful graph view:

```text

  ↓

  ↓
How many dependencies?
```

High fan-in modules:

```text

```

High fan-out modules:

```text

```

These are useful architectural signals.

# 236. Scaling and Architecture Review Questions

# 237. Scaling and Dependency Hotspots

# 260. Part 6 Takeaways

Scaling a KMP project is fundamentally about **controlling change as complexity increases**.

Remember:

- Scaling is not simply adding modules.
- Scaling means controlling code, dependency, team, build, and platform complexity.
- The goal is to reduce the blast radius of change.
- Feature boundaries reduce cognitive load and improve ownership.
- Stable core modules should remain intentionally small and focused.
- `core` should not become a universal dependency bucket.
- Dependency density matters more than raw module count.
- High fan-in modules need stronger API discipline.
- High fan-out modules deserve dependency review.
- Public APIs should remain small and stable.
- Feature internals should remain private.
- KMP source sets provide an additional platform boundary.
- Platform SDKs should be isolated behind focused capabilities.
- Interfaces should represent meaningful capabilities, not technical abstractions for their own sake.
- Shared code should be valuable shared code, not maximum shared code.
- Native UI can remain platform-specific while business logic is shared.
- Build architecture is part of scaling architecture.
- Convention plugins and version catalogs reduce build duplication.
- Too many modules can be as harmful as too few.
- Architecture should evolve incrementally as real scaling pressures appear.
- Legacy systems should be migrated through boundaries and adapters rather than requiring a full rewrite.
- Technical debt should be visible, owned, and given a migration path.
- Feature flags and compatibility layers should have removal plans.
- Architecture checks can be automated.
- Ownership should be visible through repository structure and tooling.
- Platform teams should provide stable foundations without becoming a bottleneck.
- High-leverage modules deserve stronger testing, documentation, and compatibility policies.
- The architecture should optimize for local reasoning.
- The ultimate goal is predictable change.

The central mental model is:

```text
                    SYSTEM GROWTH
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
         Code          Teams        Platforms
          │              │              │
          └──────────────┼──────────────┘
                         ▼
                   Boundaries
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
          Features      Core      Platform
             │           │           │
             └───────────┼───────────┘
                         ▼
                 Controlled Change
                         │
                         ▼
                 Smaller Blast Radius
```

The most important enterprise scaling principle is:

> **As the system grows, increase the quality of boundaries faster than the number of dependencies.**
