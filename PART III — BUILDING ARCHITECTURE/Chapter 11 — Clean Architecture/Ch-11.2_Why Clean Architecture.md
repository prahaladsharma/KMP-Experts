# Chapter 10 — Project Structure

## Part 2 — Why Clean Architecture

Clean Architecture is often introduced as a collection of layers:

```text
Presentation
     ↓
Domain
     ↓
Data
```

That diagram is useful, but it does not explain **why** the structure exists.

In a Kotlin Multiplatform project, the more important question is:

> **How do we keep business decisions independent from the platform that executes them?**

Android and iOS are different application environments.

They have different:

- UI frameworks
- lifecycle models
- operating-system APIs
- storage mechanisms
- dependency ecosystems
- build systems
- platform conventions

At the same time, the product may have the same:

- business rules
- validation
- workflows
- domain models
- API contracts
- synchronization rules
- state transitions

Clean Architecture provides a way to separate these concerns.

```text
                    PRODUCT
                       │
          ┌────────────┴────────────┐
          │                         │
       BUSINESS                  PLATFORM
       RULES                     DETAILS
          │                         │
          ▼                         ├── Android
       DOMAIN                      ├── iOS
          │                         ├── Database
          ▼                         ├── Network
      USE CASES                    └── OS APIs
          │
          ▼
     APPLICATION
        LOGIC
```

The purpose is not to create more folders.

The purpose is to **control dependency direction**.

---

# 1. The Core Problem Clean Architecture Solves

Imagine an application where business logic directly depends on Android classes.

```kotlin
class CheckoutService(
    private val context: Context
) {

    fun checkout(order: Order): Boolean {
        // Business logic
        // Android API calls
        // Storage
        // Logging
        // Network
    }
}
```

At first, this may look convenient.

But the business rule is now tied to:

```text
CheckoutService
      │
      ▼
 Android Context
      │
      ▼
 Android platform
```

The same logic becomes difficult to reuse from iOS.

A KMP project needs a different relationship:

```text
                Business Rule
                      │
                      ▼
                  Use Case
                      │
                      ▼
               Domain Contract
                      │
            ┌─────────┴─────────┐
            ▼                   ▼
        Android               iOS
```

The business rule remains independent.

The platform supplies the implementation.

---

# 2. Clean Architecture Is About Dependency Direction

The most important principle is:

> **Dependencies should point toward the policies of the application, not toward external implementation details.**

A simplified representation:

```text
┌───────────────────────────────────────┐
│              Platform                 │
│ Android / iOS / Frameworks / APIs     │
└───────────────────┬───────────────────┘
                    │
                    ▼
┌───────────────────────────────────────┐
│            Infrastructure             │
│ Network / Database / Storage / SDKs   │
└───────────────────┬───────────────────┘
                    │
                    ▼
┌───────────────────────────────────────┐
│              Domain                   │
│ Business Rules / Models / Use Cases   │
└───────────────────────────────────────┘
```

The arrows in a real implementation should be designed carefully.

The domain should not need to know whether data comes from:

- Retrofit
- Ktor
- SQLDelight
- Core Data
- Room
- Keychain
- Android Keystore
- iOS Keychain

The domain cares about the business capability.

For example:

```kotlin
interface UserRepository {

    suspend fun getUser(
        id: String
    ): User
}
```

The use case depends on the abstraction:

```kotlin
class GetUserUseCase(
    private val repository: UserRepository
) {

    suspend operator fun invoke(
        id: String
    ): User {
        return repository.getUser(id)
    }
}
```

The implementation can change without changing the use case.

# 3. Clean Architecture in KMP

A KMP application can map Clean Architecture concepts onto multiplatform source sets.

```text
                       KMP
                        │
          ┌─────────────┴─────────────┐
          │                           │
     Shared Logic                Platform Logic
          │                           │
          ▼                           ├── Android
     commonMain                       └── iOS
          │
     ┌────┼────┐
     ▼    ▼    ▼
  Domain Data Presentation
```

A typical shared module might contain:

```text
shared/
└── src/
    ├── commonMain/
    │   └── kotlin/
    │       └── com/example/app/
    │           ├── domain/
    │           ├── data/
    │           └── presentation/
    │
    ├── commonTest/
    │
    ├── androidMain/
    │   └── kotlin/
    │       └── com/example/app/
    │           └── platform/
    │
    └── iosMain/
        └── kotlin/
            └── com/example/app/
                └── platform/
```

The exact structure can differ.

The architectural rule remains:

```text
Business policy
      ↓
Shared abstraction
      ↓
Platform implementation
```

# 4. The Three Common Layers

A practical Clean Architecture implementation often begins with three logical layers.

```text
┌───────────────────────────────┐
│         Presentation          │
│ UI State / ViewModel / Events │
└───────────────┬───────────────┘
                │
                ▼
┌───────────────────────────────┐
│            Domain             │
│ Use Cases / Business Rules    │
│ Domain Models / Contracts     │
└───────────────┬───────────────┘
                │
                ▼
┌───────────────────────────────┐
│             Data              │
│ Repository / API / Database   │
│ DTO / Mapping / Cache         │
└───────────────────────────────┘
```

These are **logical boundaries**, not necessarily three Gradle modules.

A small project may use:

```text
shared/
└── commonMain/
    ├── presentation/
    ├── domain/
    └── data/
```

A larger project might use:

```text
feature-orders/
core-domain/
core-data/
core-network/
```

Both can follow Clean Architecture.

---

# 5. Presentation Layer

The presentation layer deals with application state and user interaction.

For example:

```kotlin
data class LoginUiState(
    val username: String = "",
    val password: String = "",
    val isLoading: Boolean = false,
    val error: String? = null
)
```

A presentation component can invoke a domain use case:

```kotlin
class LoginPresenter(
    private val loginUseCase: LoginUseCase
) {

    suspend fun login(
        username: String,
        password: String
    ) {
        loginUseCase(
            username = username,
            password = password
        )
    }
}
```

The presentation layer should not need to understand how authentication is implemented.

It should care about:

```text
User Action
    ↓
Presentation
    ↓
Use Case
    ↓
Result
    ↓
UI State
```

This makes the presentation layer easier to adapt to different UI technologies.

For example:

```text
                 Shared Presentation Logic
                           │
                ┌──────────┴──────────┐
                ▼                     ▼
         Jetpack Compose          SwiftUI
             Android                iOS
```

The UI framework can change without rewriting the business rule.

---

# 6. Domain Layer

The domain layer contains the rules that define how the product behaves.

Examples include:

- eligibility rules
- pricing rules
- validation
- order state transitions
- authentication decisions
- business calculations
- workflow rules

Example:

```kotlin
data class Order(
    val id: String,
    val total: Money,
    val status: OrderStatus
)
```

A domain use case:

```kotlin
class CanCancelOrderUseCase {

    operator fun invoke(
        order: Order
    ): Boolean {
        return order.status == OrderStatus.Pending
    }
}
```

This code does not need:

```kotlin
Context
Activity
UIViewController
SwiftUI
Retrofit
Room
SQLDelight
```

That independence is the important part.

---

# 7. Data Layer

The data layer is responsible for obtaining and transforming data.

A simplified structure:

```text
data/
├── repository/
├── remote/
├── local/
├── mapper/
└── model/
```

For example:

```kotlin
class UserRepositoryImpl(
    private val remoteDataSource: UserRemoteDataSource,
    private val localDataSource: UserLocalDataSource
) : UserRepository {

    override suspend fun getUser(
        id: String
    ): User {
        val cached = localDataSource.getUser(id)

        if (cached != null) {
            return cached.toDomain()
        }

        val response = remoteDataSource.getUser(id)

        val user = response.toDomain()

        localDataSource.saveUser(user.toLocal())

        return user
    }
}
```

The domain layer sees:

```kotlin
UserRepository
```

The data layer knows:

```text
API
Database
Cache
DTO
Mapper
```

This is a useful boundary.

---

# 8. Domain vs Data

One of the most common mistakes is putting everything into the data layer.

Consider:

```text
UserDto
UserEntity
User
```

These represent different concerns.

```text
UserDto
   │
   │ API representation
   ▼
Mapper
   │
   ▼
User
   │
   │ Domain representation
   ▼
Business Logic
```

The domain model should not be shaped entirely around an API response.

For example, an API may return:

```json
{
  "user_id": "123",
  "first_name": "Alex",
  "last_name": "Smith",
  "account_status": "ACTIVE"
}
```

The domain may need:

```kotlin
data class User(
    val id: UserId,
    val name: String,
    val isActive: Boolean
)
```

The mapper creates the boundary:

```kotlin
fun UserDto.toDomain(): User {
    return User(
        id = UserId(userId),
        name = "$firstName $lastName",
        isActive = accountStatus == "ACTIVE"
    )
}
```

The API contract can change without forcing the entire domain model to change.

---

# 9. Why This Matters More in KMP

KMP exists specifically to share code across platforms.

If shared code is tightly coupled to one platform, the value of sharing decreases.

Without boundaries:

```text
Android assumptions
       ↓
Shared code
       ↓
iOS adaptation
       ↓
More platform conditions
       ↓
More complexity
```

With boundaries:

```text
                  Shared Domain
                       │
                       ▼
                Shared Contracts
                  │           │
                  ▼           ▼
              Android         iOS
```

This is one reason Clean Architecture fits naturally with KMP.

Both approaches encourage us to isolate responsibilities.

---

# 10. Clean Architecture Does Not Mean "Everything Is Shared"

This distinction is critical.

A common misconception is:

```text
KMP + Clean Architecture
          =
100% shared code
```

That is not the goal.

A better model is:

```text
              Application
                   │
       ┌───────────┴───────────┐
       │                       │
   Shared Core             Native UI
       │                       │
       ├── Domain              ├── Android UI
       ├── Use Cases           └── iOS UI
       ├── Data contracts
       └── Shared logic
```

Some things are intentionally platform-specific.

For example:

```text
Android
├── Activity
├── Notification APIs
├── Android permissions
└── Android-specific UI

iOS
├── App lifecycle
├── Notification APIs
├── iOS permissions
└── SwiftUI/UIKit UI
```

Trying to force all of these into shared code can make the architecture harder to understand.

---

# 11. The Dependency Rule

A useful dependency rule is:

```text
Presentation
      │
      ▼
   Domain
      ▲
      │
     Data
```

The arrows need explanation.

Presentation uses domain.

Data implements contracts defined for the domain or application.

For example:

```kotlin
// domain

interface OrderRepository {
    suspend fun getOrder(id: String): Order
}
```

Then:

```kotlin
// data

class OrderRepositoryImpl(
    private val api: OrderApi
) : OrderRepository {

    override suspend fun getOrder(
        id: String
    ): Order {
        return api.getOrder(id).toDomain()
    }
}
```

And:

```kotlin
// domain

class GetOrderUseCase(
    private val repository: OrderRepository
) {
    suspend operator fun invoke(
        id: String
    ): Order {
        return repository.getOrder(id)
    }
}
```

The important dependency is:

```text
GetOrderUseCase
       │
       ▼
OrderRepository
```

not:

```text
GetOrderUseCase
       │
       ▼
Retrofit / HTTP implementation
```

---

# 12. Dependency Inversion in KMP

Dependency inversion becomes particularly useful when a shared capability requires a platform implementation.

Consider secure storage.

The domain or shared application code can define:

```kotlin
interface SecureStorage {

    suspend fun save(
        key: String,
        value: String
    )

    suspend fun read(
        key: String
    ): String?
}
```

Android can implement it using an Android-specific mechanism.

iOS can implement it using an iOS-specific mechanism.

```text
                    SecureStorage
                         │
                ┌────────┴────────┐
                ▼                 ▼
        Android implementation   iOS implementation
```

The shared code does not need to know the implementation details.

This is dependency inversion in practical KMP architecture.

# 13. Use Cases as Application Boundaries

A use case represents an action the application can perform.

Examples:

```text
Login
Logout
GetProfile
CreateOrder
CancelOrder
CalculatePrice
SyncOrders
UploadDocument
```

Example:

```kotlin
class CreateOrderUseCase(
    private val repository: OrderRepository
) {

    suspend operator fun invoke(
        cart: Cart
    ): Order {
        require(cart.items.isNotEmpty()) {
            "Cart cannot be empty"
        }

        return repository.createOrder(cart)
    }
}
```

The use case contains the business decision:

```text
Cart
 │
 ├── Is it empty?
 │
 ├── Is it valid?
 │
 └── Create order
```

The repository handles data access.

That separation prevents business rules from spreading into:

- UI
- API clients
- database classes
- platform implementations

# 14. Clean Architecture and MVI

Clean Architecture and MVI solve different problems.

They can work together.

```text
                  MVI
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
     Intent       State      Effect
                   │
                   ▼
             Clean Architecture
                   │
             ┌─────┴─────┐
             ▼           ▼
           Domain       Data
```

For example:

```kotlin
sealed interface LoginIntent {
    data class UsernameChanged(
        val value: String
    ) : LoginIntent

    data class PasswordChanged(
        val value: String
    ) : LoginIntent

    data object Submit : LoginIntent
}
```

The presentation layer processes the intent:

```text
Intent
  ↓
MVI Processor
  ↓
Use Case
  ↓
Repository
  ↓
Result
  ↓
State
```

The UI architecture and application architecture are therefore complementary.

# 15. Clean Architecture and MVVM

The same applies to MVVM.

```text
View
 │
 ▼
ViewModel
 │
 ▼
Use Case
 │
 ▼
Repository
 │
 ▼
Data Source
```

The ViewModel should coordinate presentation state.

It should not become the place where every business rule and API implementation is stored.

A large ViewModel such as:

```text
LoginViewModel
├── API calls
├── JSON parsing
├── database operations
├── validation
├── business rules
├── navigation
├── analytics
└── UI state
```

is a sign that multiple responsibilities have accumulated in one component.

A cleaner model is:

```text
LoginViewModel
      │
      ▼
LoginUseCase
      │
      ▼
AuthRepository
      │
      ▼
Remote / Local
```

Consider a user opening an order screen.

The request might flow like this:

```text
Android / iOS UI
       │
       ▼

       │
       ▼
GetOrderUseCase
       │
       ▼

       │
       ▼
OrderRepositoryImpl
       │
       ├───────────────┐
       ▼               ▼
    Remote            Local
       │               │
       ▼               ▼
      API            Database
```

The returned data moves in the opposite direction:

```text
API / Database
      │
      ▼

      │
      ▼
Repository
      │
      ▼

      │
      ▼
Presentation State
      │
      ▼
Android / iOS UI
```

Each part has a reason to exist.

# 17. Clean Architecture Does Not Require a Huge Folder Tree

A common misunderstanding is:

```text
Clean Architecture
        =
        50 folders
```

It does not.

A small application could be:

```text
shared/
└── commonMain/
    └── com/example/app/
        ├── domain/
        ├── data/
        └── presentation/
```

That can be enough.

A large enterprise application may evolve into:

```text
core/
├── domain/
├── network/
├── database/
└── platform/

features/
├── authentication/
├── profile/
├── orders/
├── payments/
└── notifications/

androidApp/
iosApp/
```

The structure should follow complexity.

Do not create architecture for complexity that does not exist.

# 18. Feature-Oriented Clean Architecture

As the application grows, feature-based organization can be more effective than one global layer directory.

Instead of:

```text
shared/
├── domain/
│   ├── LoginUseCase.kt
│   ├── OrderUseCase.kt
│   └── ProfileUseCase.kt
│
├── data/
│   ├── LoginRepository.kt
│   ├── OrderRepository.kt
│   └── ProfileRepository.kt
│
└── presentation/
    ├── LoginViewModel.kt
    ├── OrderViewModel.kt
    └── ProfileViewModel.kt
```

a feature-oriented structure can be:

```text
features/
├── login/
│   ├── presentation/
│   ├── domain/
│   └── data/
│
├── orders/
│   ├── presentation/
│   ├── domain/
│   └── data/
│
└── profile/
    ├── presentation/
    ├── domain/
    └── data/
```

This keeps feature-specific responsibilities together.

The benefit becomes more visible when multiple teams work on different features.

# 19. Core vs Feature

Not every class belongs inside a feature.

A useful distinction is:

```text
                    Application
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
           Features                Core
              │                     │
       ┌──────┼──────┐       ┌──────┼──────┐
       ▼      ▼      ▼       ▼      ▼      ▼
     Login  Orders Profile  Network Database Platform
```

A feature contains product-specific behavior.

Core contains capabilities shared across features.

For example:

```text
core/network
core/database
core/logging
core/platform
```

But avoid turning `core` into a dumping ground.

If a class is used by only one feature, it probably does not belong in core merely because it feels reusable.

---

# 20. The "Core" Dumping Ground Problem

A project can slowly become:

```text
core/
├── Utils.kt
├── Common.kt
├── Helper.kt
├── Manager.kt
├── Service.kt
├── Constants.kt
├── Extensions.kt
└── Misc.kt
```

This is technically a module.

Architecturally, it says very little.

A better core structure communicates capabilities:

```text
core/
├── network/
├── database/
├── logging/
├── authentication/
└── platform/
```

Each area has a recognizable responsibility.

# 21. Clean Architecture and `expect` / `actual`

KMP's `expect` / `actual` mechanism can support platform boundaries.

Suppose shared code requires a platform-specific UUID provider.

In `commonMain`:

```kotlin
expect fun platformUuid(): String
```

Android:

```kotlin
actual fun platformUuid(): String {
    return UUID.randomUUID().toString()
}
```

iOS:

```kotlin
actual fun platformUuid(): String {
    return NSUUID().UUIDString
}
```

The common code depends on the shared declaration:

```text
commonMain
    │
    ▼
expect declaration
    │
    ├── Android actual
    └── iOS actual
```

This is useful when the abstraction is naturally represented as a platform API.

However, not every dependency should automatically become `expect` / `actual`.

Sometimes an injected interface is clearer:

```kotlin
interface UuidProvider {
    fun generate(): String
}
```

Then:

```text
Shared logic
    │
    ▼
UuidProvider
    │
    ├── Android implementation
    └── iOS implementation
```

The right choice depends on the responsibility and desired boundary.

---

# 22. Clean Architecture and Dependency Injection

Dependency Injection helps enforce architectural boundaries.

For example:

```kotlin
class GetOrdersUseCase(
    private val repository: OrderRepository
)
```

The use case does not construct:

```kotlin
OrderRepositoryImpl()
```

itself.

Instead, the composition layer supplies the implementation.

```text
              Composition Root
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
   OrderRepositoryImpl    GetOrdersUseCase
          │                     │
          └──────────┬──────────┘
                     ▼
                 Application
```

In KMP, the composition can be shared or platform-specific depending on the dependency.

The key principle is:

> **Business logic should not decide how its infrastructure dependencies are constructed.**

# 23. Clean Architecture and Testing

Architecture becomes especially valuable when testing.

Consider:

```kotlin
class GetOrderUseCase(
    private val repository: OrderRepository
)
```

A test can provide a fake repository:

```kotlin
class FakeOrderRepository : OrderRepository {

    override suspend fun getOrder(
        id: String
    ): Order {
        return Order(
            id = id,
            status = OrderStatus.Pending
        )
    }
}
```

Then:

```kotlin
@Test
fun returns_order_from_repository() {
    val repository = FakeOrderRepository()
    val useCase = GetOrderUseCase(repository)

    // Test business behavior
}
```

No Android device is required.

No iOS simulator is required.

No network connection is required.

This is one of the practical benefits of keeping business logic independent.

# 24. Architecture as a Dependency Graph

Instead of thinking only in folders, think in graphs.

A healthy dependency graph might be:

```text
                 Android UI
                     │
                     ▼
               Presentation
                     │
                     ▼
                  Domain
                     ▲
                     │
                   Data
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       Network               Database
```

A problematic graph might look like:

```text
Android UI ───────► Database
    │                  ▲
    ▼                  │
ViewModel ────────► Retrofit
    │                  ▲
    ▼                  │
UseCase ───────────► Android API
    │
    └──────────────► iOS-specific code
```

The second graph makes responsibilities difficult to control.

The first graph provides stronger boundaries.

# 25. Clean Architecture Is About Change

One of the best ways to understand Clean Architecture is to ask:

> **What happens when something changes?**

Suppose the backend API changes.

With a clean boundary:

```text
API response changes
       │
       ▼
DTO / Mapper
       │
       ▼
Domain remains stable
       │
       ▼
Presentation remains stable
```

Suppose the Android UI changes:

```text
Compose UI changes
       │
       ▼
Presentation contract remains stable
       │
       ▼
Domain remains stable
```

Suppose iOS moves from one UI approach to another:

```text
iOS UI changes
       │
       ▼
Shared domain remains stable
```

This does not mean changes never propagate.

It means the architecture **controls the blast radius**.

---

# 26. Change Scenarios

A useful architectural test is to examine common changes.

| Change | Ideally affected |
|---|---|
| API field renamed | DTO + mapper |
| Database technology changed | Data layer |
| Android UI framework changed | Android presentation/UI |
| iOS UI changed | iOS presentation/UI |
| Business rule changed | Domain |
| Network library changed | Network/data |
| Storage mechanism changed | Platform/data |
| New platform added | Platform implementation + integration |
| New feature added | New feature boundary |

The table is not a guarantee.

Real systems have dependencies.

But a well-defined architecture tries to keep unrelated changes from spreading unnecessarily.

---

# 27. Clean Architecture and KMP Do Not Eliminate Coupling

No architecture eliminates coupling.

The goal is to make coupling:

```text
intentional
visible
controlled
```

rather than:

```text
accidental
hidden
everywhere
```

For example:

```text
OrderUseCase
     │
     ▼
OrderRepository
```

is intentional coupling.

But:

```text
OrderUseCase
     │
     ├── Android Context
     ├── Retrofit
     ├── Room
     ├── Compose
     └── iOS API
```

is uncontrolled coupling.

# 28. Common Clean Architecture Mistakes in KMP

## Mistake 1 — Treating Clean Architecture as Folder Naming

This:

```text
domain/
data/
presentation/
```

does not automatically create Clean Architecture.

The dependencies matter more than the names.

---

## Mistake 2 — Domain Depending on Frameworks

For example:

```kotlin
class CalculatePriceUseCase(
    private val context: Context
)
```

If the context is not part of the business rule, it should not be there.

---

## Mistake 3 — Repository Containing Business Decisions

A repository should coordinate data access.

If it starts accumulating rules such as:

```text
if premium user
if holiday
if inventory available
if payment status
if retry count
```

the business logic may be moving into the wrong boundary.

---

## Mistake 4 — Giant ViewModels

A ViewModel should not become:

```text
UI
+ Business Logic
+ Network
+ Database
+ Mapping
+ Validation
+ Analytics
```

Use cases and repositories can provide clearer boundaries.

---

## Mistake 5 — Over-Abstraction

Not every class needs:

```text
Interface
Implementation
Factory
Provider
Manager
Wrapper
Adapter
```

Abstractions should solve a real boundary problem.

Creating interfaces for every class can make a small codebase harder to understand.

---

## Mistake 6 — Sharing Code That Should Remain Native

A KMP project may intentionally share:

```text
Business logic
Data models
Networking
Persistence abstraction
Validation
State management
```

while keeping:

```text
Native UI
```

# 32. A Useful Rule for KMP Teams

When adding a new class, ask four questions:

```text
1. Who owns this responsibility?

2. Is it platform-independent?

3. Which part should depend on it?

4. What should this class NOT know about?
```

The fourth question is particularly useful.

For example:

```text
OrderUseCase should NOT know:
    ├── Android Context
    ├── SwiftUI
    ├── Retrofit
    ├── SQLDelight
    └── platform storage
```

Instead:

```text
OrderUseCase should know:
    └── OrderRepository
```

That single distinction can prevent a large amount of accidental coupling.

# 34. Part 2 Takeaways

Clean Architecture is useful in KMP because it gives shared code a stable center while allowing platforms to evolve independently.

Remember:

- Clean Architecture is primarily about **dependency direction**.
- It separates business policies from implementation details.
- `commonMain` is a natural home for portable business logic.
- Android and iOS can keep their native application concerns.
- Domain code should not depend directly on platform frameworks.
- Use cases express application actions and business decisions.
- Repositories provide data-access abstractions.
- Data sources handle infrastructure details.
- DTOs and domain models serve different purposes.
- Dependency inversion allows shared logic to work with platform-specific implementations.
- `expect` / `actual` is one mechanism for platform boundaries, not a requirement for every abstraction.
- Dependency injection helps keep construction concerns outside business logic.
- Clean Architecture and MVI/MVVM address different concerns and can be combined.
- Feature-based organization becomes useful as the product grows.
- `core` should contain genuinely shared capabilities, not become a miscellaneous folder.
- More modules do not automatically mean better architecture.
- Architecture should evolve with project complexity.
- The goal is not maximum code sharing; the goal is appropriate code sharing with clear boundaries.

The mental model is:

```text
                         KMP APPLICATION
                                │
               ┌────────────────┴────────────────┐
               │                                 │
        PLATFORM-SPECIFIC                  SHARED LOGIC
               │                                 │
        ┌──────┴──────┐                  ┌───────┴────────┐
        ▼             ▼                  ▼                ▼
     Android          iOS            Presentation       Domain
        │             │                  │                │
        │             │                  └───────┬────────┘
        │             │                          ▼
        │             │                         Data
        │             │                          │
        └─────────────┴──────────────────────────┘
                              │
                              ▼
                       Platform Contracts
```

The strongest KMP architecture is therefore not the one with the most shared code.

It is the one where each responsibility has a clear home, dependencies have an intentional direction, and platform differences remain isolated at the boundaries.
