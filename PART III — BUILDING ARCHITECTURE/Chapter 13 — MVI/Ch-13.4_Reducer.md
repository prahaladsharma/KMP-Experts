# 1. What Is a Reducer?

A **reducer** is the part of an MVI architecture responsible for
converting a current state and an input result into a new state.

Conceptually:

``` text
Current State
      +
    Result
      │
      ▼
   Reducer
      │
      ▼
  New State
```

In Kotlin, that can be as simple as:

``` kotlin
fun reduce(
    state: LoginState,
    result: LoginResult
): LoginState {
    // ...
}
```

The reducer should not need to know:

-   which screen triggered the event,
-   which HTTP client was used,
-   whether the data came from a database,
-   which platform is running the code,
-   or how the UI is rendered.

Its job is narrow:

> **Given the current state and a result, calculate the next state.**

That narrow responsibility is what makes reducers so useful.

------------------------------------------------------------------------

# 2. The Reducer in the MVI Loop

The complete MVI flow can be represented as:

``` mermaid
flowchart LR
    U[User] --> V[View]
    V --> I[Intent]
    I --> L[Feature Logic]
    L --> O[Operation]
    O --> R[Result]
    R --> RED[Reducer]
    RED --> S[New State]
    S --> V
```

The reducer sits near the end of the state transition pipeline.

For example:

``` text
User
 ↓
LoginClicked
 ↓
Login Use Case
 ↓
LoginResult.Success
 ↓
Reducer
 ↓
LoginState(isLoggedIn = true)
 ↓
UI
```

This separation prevents the reducer from becoming a networking or
business-operation layer.

# 3. State Transition as a Function

The cleanest way to understand a reducer is mathematically.

Let:

``` text
S = current state
A = action/result
S' = next state
```

Then:

``` text
S' = reduce(S, A)
```

For example:

``` text
State:
count = 5

Result:
Incremented

Reducer:

5 + 1 = 6

New State:
count = 6
```

In Kotlin:

``` kotlin
fun reduce(
    state: CounterState,
    result: CounterResult
): CounterState {
    return when (result) {
        CounterResult.Incremented ->
            state.copy(
                count = state.count + 1
            )

        CounterResult.Decremented ->
            state.copy(
                count = state.count - 1
            )
    }
}
```

The reducer is therefore a **state transformation function**.

------------------------------------------------------------------------

# 4. Pure Functions and Reducers

A good reducer is a pure function.

A pure function has two important characteristics:

1.  It produces the same output for the same input.
2.  It does not create observable side effects.

For example:

``` kotlin
fun reduce(
    state: CounterState,
    result: CounterResult
): CounterState {
    return when (result) {
        CounterResult.Incremented ->
            state.copy(count = state.count + 1)

        CounterResult.Decremented ->
            state.copy(count = state.count - 1)
    }
}
```

Given:

``` text
CounterState(5)
+
Incremented
```

the result will always be:

``` text
CounterState(6)
```

------------------------------------------------------------------------

## Why purity matters

A pure reducer can be:

-   tested without Android,
-   tested without iOS,
-   tested without a database,
-   tested without a network,
-   executed repeatedly,
-   debugged from state snapshots,
-   shared in KMP `commonMain`.

This is a major architectural advantage.

# 5. Intent vs Result

One subtle but important question is:

> Should the reducer receive Intent directly?

It can.

For simple features:

``` kotlin
fun reduce(
    state: CounterState,
    intent: CounterIntent
): CounterState
```

can be perfectly reasonable.

But for asynchronous features, separating **Intent** from **Result**
often produces a cleaner architecture.

Consider:

``` text
Intent:
LoginClicked
```

This does not tell us whether login succeeded.

The operation may produce:

``` text
LoginResult.Loading
LoginResult.Success
LoginResult.Failure
```

So the flow becomes:

``` text
Intent
  ↓
Processor
  ↓
Use Case
  ↓
Result
  ↓
Reducer
  ↓
State
```

This gives the reducer information about the outcome rather than the
original UI action.

# 6. A Simple Counter Reducer

Let's start with a complete small example.

### State

``` kotlin
data class CounterState(
    val count: Int = 0
)
```

### Intent

``` kotlin
sealed interface CounterIntent {

    data object Increment : CounterIntent

    data object Decrement : CounterIntent

    data object Reset : CounterIntent
}
```

For this simple feature, Intent can directly drive the reducer:

``` kotlin
fun reduce(
    state: CounterState,
    intent: CounterIntent
): CounterState {
    return when (intent) {

        CounterIntent.Increment ->
            state.copy(
                count = state.count + 1
            )

        CounterIntent.Decrement ->
            state.copy(
                count = state.count - 1
            )

        CounterIntent.Reset ->
            CounterState()
    }
}
```

The transition is explicit:

``` text
CounterState(0)
       │
       │ Increment
       ▼
CounterState(1)
       │
       │ Increment
       ▼
CounterState(2)
       │
       │ Decrement
       ▼
CounterState(1)
       │
       │ Reset
       ▼
CounterState(0)
```

# 7. Reducer With Loading, Success, and Error

Real applications usually have asynchronous operations.

Consider a profile screen.

### State

``` kotlin
data class ProfileState(
    val profile: Profile? = null,
    val isLoading: Boolean = false,
    val error: AppError? = null
)
```

### Result

``` kotlin
sealed interface ProfileResult {

    data object Loading : ProfileResult

    data class Success(
        val profile: Profile
    ) : ProfileResult

    data class Failure(
        val error: AppError
    ) : ProfileResult
}
```

### Reducer

``` kotlin
fun reduce(
    state: ProfileState,
    result: ProfileResult
): ProfileState {

    return when (result) {

        ProfileResult.Loading ->
            state.copy(
                isLoading = true,
                error = null
            )

        is ProfileResult.Success ->
            state.copy(
                profile = result.profile,
                isLoading = false,
                error = null
            )

        is ProfileResult.Failure ->
            state.copy(
                isLoading = false,
                error = result.error
            )
    }
}
```

The reducer now defines the screen's state transitions.

------------------------------------------------------------------------

# 8. Why Side Effects Do Not Belong in a Reducer

A reducer should not perform operations such as:

``` text
HTTP request
Database write
Navigation
Analytics
Logging to external systems
File I/O
```

For example, avoid:

``` kotlin
fun reduce(
    state: ProfileState,
    result: ProfileResult
): ProfileState {

    repository.save(result.profile)

    return state.copy(
        profile = result.profile
    )
}
```

The reducer now has a side effect.

That creates several problems:

-   tests become harder,
-   execution becomes less predictable,
-   reducer calls may unexpectedly perform work,
-   KMP reuse becomes harder,
-   state calculation is no longer isolated.

Prefer:

``` text
Operation
   ↓
Result
   ↓
Reducer
   ↓
State
```

and keep side effects outside the reducer.

------------------------------------------------------------------------

# 9. Reducer and Repository Boundaries

The repository is responsible for data access.

The reducer is responsible for state transformation.

These responsibilities should not overlap.

``` text
┌───────────────────┐
│      Intent       │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ Feature Processor │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│    Repository     │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│      Result       │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│     Reducer       │
└─────────┬─────────┘
          ▼
┌───────────────────┐
│       State       │
└───────────────────┘
```

This separation creates clean boundaries.

# 10. Immutable State Updates

Reducers should normally return a new state rather than mutating the
existing state.

Prefer:

``` kotlin
state.copy(
    isLoading = true
)
```

Avoid:

``` kotlin
state.isLoading = true
```

assuming the state is mutable.

For example:

``` kotlin
data class SearchState(
    val query: String = "",
    val results: List<SearchResult> = emptyList(),
    val isLoading: Boolean = false
)
```

Reducer:

``` kotlin
fun reduce(
    state: SearchState,
    result: SearchResultEvent
): SearchState {

    return when (result) {

        is SearchResultEvent.QueryUpdated ->
            state.copy(
                query = result.query
            )

        SearchResultEvent.Loading ->
            state.copy(
                isLoading = true
            )

        is SearchResultEvent.Success ->
            state.copy(
                results = result.items,
                isLoading = false
            )
    }
}
```

The previous state remains a valid snapshot.

# 11. Reducer as a State Machine

Reducers make state-machine behavior explicit.

Consider:

``` kotlin
sealed interface CheckoutState {

    data object Cart : CheckoutState

    data object Processing : CheckoutState

    data class Success(
        val orderId: String
    ) : CheckoutState

    data class Failure(
        val error: AppError
    ) : CheckoutState
}
```

The transitions might be:

``` text
Cart
  │
  │ Submit
  ▼
Processing
  │
  ├──── Success ────► Success
  │
  └──── Failure ────► Failure
                         │
                         │ Retry
                         ▼
                     Processing
```

The reducer becomes the explicit definition of valid transitions.

This makes complex workflows easier to reason about.

# 12. Modeling Results

A Result represents the outcome of an operation.

For example:

``` kotlin
sealed interface ProductResult {

    data object Loading : ProductResult

    data class Success(
        val products: List<Product>
    ) : ProductResult

    data class Failure(
        val error: AppError
    ) : ProductResult
}
```

The result is usually generated by feature logic after executing a use
case or repository operation.

``` text
Intent
  ↓
Use Case
  ↓
ProductResult
```

Then:

``` text
ProductResult
  ↓
Reducer
  ↓
ProductState
```

This separation makes the architecture easier to test.

# 13. Result vs Effect

Result and Effect solve different problems.

### Result

Describes the outcome of processing.

``` text
Loading
Success
Failure
```

It normally contributes to State.

### Effect

Represents a one-time action.

``` text
NavigateToDetails
ShowSnackbar
OpenExternalUrl
```

A useful model is:

``` text
Intent
   ↓
Processor
   ├───────────────┐
   ▼               ▼
 Result          Effect
   │               │
   ▼               ▼
Reducer            UI
   │
   ▼
State
```

For example:

``` kotlin
sealed interface LoginResult {
    data object Loading : LoginResult
    data object Success : LoginResult
    data class Failure(
        val error: AppError
    ) : LoginResult
}
```

and:

``` kotlin
sealed interface LoginEffect {
    data object NavigateToHome : LoginEffect
    data class ShowMessage(
        val message: String
    ) : LoginEffect
}
```

# 14. A Complete Feature Flow

Let's connect the pieces.

### Intent

``` kotlin
data object LoginClicked : LoginIntent
```

### Processor

``` kotlin
suspend fun processLogin() {

    emitResult(LoginResult.Loading)

    val result = loginUseCase.execute(
        email = state.value.email,
        password = state.value.password
    )

    when (result) {

        is Result.Success -> {
            emitResult(
                LoginResult.Success
            )

            emitEffect(
                LoginEffect.NavigateToHome
            )
        }

        is Result.Failure -> {
            emitResult(
                LoginResult.Failure(
                    result.error
                )
            )
        }
    }
}
```

### Reducer

``` kotlin
fun reduce(
    state: LoginState,
    result: LoginResult
): LoginState {
    return when (result) {

        LoginResult.Loading ->
            state.copy(
                isLoading = true,
                error = null
            )

        LoginResult.Success ->
            state.copy(
                isLoading = false,
                isLoggedIn = true
            )

        is LoginResult.Failure ->
            state.copy(
                isLoading = false,
                error = result.error
            )
    }
}
```

The responsibilities are now clearly separated:

``` text
Intent  → input
Processor → work
Result  → outcome
Reducer → state transition
Effect  → one-time action
State   → UI truth
```

# 15. Reducer With Kotlin StateFlow

A simple MVI store can combine a reducer with `StateFlow`.

``` kotlin
class CounterStore {

    private val _state =
        MutableStateFlow(CounterState())

    val state: StateFlow<CounterState> =
        _state.asStateFlow()

    fun dispatch(intent: CounterIntent) {

        _state.update { current ->
            reduce(
                current,
                intent
            )
        }
    }
}
```

Reducer:

``` kotlin
private fun reduce(
    state: CounterState,
    intent: CounterIntent
): CounterState {

    return when (intent) {

        CounterIntent.Increment ->
            state.copy(
                count = state.count + 1
            )

        CounterIntent.Decrement ->
            state.copy(
                count = state.count - 1
            )

        CounterIntent.Reset ->
            CounterState()
    }
}
```

This is a minimal but complete MVI loop.

``` text
dispatch(Intent)
      ↓
current State
      ↓
Reducer
      ↓
new State
      ↓
StateFlow
      ↓
UI
```

# 16. Reducer Composition

Large applications can have large states.

Instead of one enormous reducer:

``` kotlin
fun reduce(
    state: HugeApplicationState,
    result: HugeApplicationResult
): HugeApplicationState
```

you can compose smaller reducers.

For example:

``` text
ApplicationState
 ├── ProfileState
 ├── CartState
 └── NotificationState
```

Each feature can own its state transition logic.

``` kotlin
data class ApplicationState(
    val profile: ProfileState,
    val cart: CartState,
    val notifications: NotificationState
)
```

Then:

``` kotlin
fun reduce(
    state: ApplicationState,
    result: ApplicationResult
): ApplicationState {
    return state.copy(
        profile = reduceProfile(
            state.profile,
            result
        ),
        cart = reduceCart(
            state.cart,
            result
        ),
        notifications = reduceNotifications(
            state.notifications,
            result
        )
    )
}
```

This keeps feature reducers focused.

# 17. Nested Feature State

Consider a checkout screen:

``` kotlin
data class CheckoutState(
    val cart: CartState,
    val address: AddressState,
    val payment: PaymentState,
    val order: OrderState
)
```

Each sub-state can have its own reducer.

``` text
CheckoutReducer
       │
       ├── CartReducer
       ├── AddressReducer
       ├── PaymentReducer
       └── OrderReducer
```

This is especially useful when features become large.

However, do not split reducers merely to increase the number of files.

The boundary should reflect a meaningful feature or responsibility.

# 18. Handling Multiple Operations

A screen can have multiple operations running independently.

For example:

``` text
Load profile
Load recommendations
Load notifications
```

A single:

``` kotlin
isLoading
```

may no longer be sufficient.

Instead:

``` kotlin
data class HomeState(
    val profile: ProfileState,
    val recommendations: RecommendationState,
    val notifications: NotificationState
)
```

Each operation gets a meaningful state model.

The reducer updates only the relevant part.

``` kotlin
state.copy(
    recommendations = reduceRecommendations(
        state.recommendations,
        result
    )
)
```

This prevents unrelated state from being overwritten.

# 19. Concurrency and Reducer Ordering

When multiple asynchronous operations finish at different times, reducer
ordering matters.

Imagine:

``` text
Request A starts
Request B starts
```

Then:

``` text
B completes
A completes
```

Results arrive:

``` text
BResult
AResult
```

The reducer processes results in the order they are received.

Therefore, the architecture should decide whether result ordering
matters.

For independent operations:

``` text
AResult → update A state
BResult → update B state
```

is usually straightforward.

For dependent operations, the feature logic may need stronger
coordination.

# 20. Stale Results

Search provides a classic stale-result problem.

Suppose the user enters:

``` text
Kotlin
```

then quickly changes to:

``` text
Kotlin Multiplatform
```

Two requests may exist:

``` text
Request A → Kotlin
Request B → Kotlin Multiplatform
```

If A finishes after B:

``` text
BResult arrives
AResult arrives
```

a naïve reducer might show the old Kotlin results.

This is not necessarily a reducer problem.

The feature processor should often ensure stale work is cancelled or
ignored.

Possible strategies include:

``` text
debounce
distinctUntilChanged
flatMapLatest
request identifiers
generation numbers
```

For example:

``` kotlin
data class SearchResult(
    val requestId: Long,
    val query: String,
    val items: List<SearchItem>
)
```

The processor can ensure only the current request is allowed to update
state.

data class ProductListState(

data class LoginState(

sealed interface LoginResult {

is LoginResult.EmailUpdated ->

# 24. Reducer and One-Time Effects

A reducer should generally produce State.

It should not perform navigation.

For example:

``` text
LoginResult.Success
```

may produce:

``` text
New State:
isLoggedIn = true

Effect:
NavigateToHome
```

The processor can coordinate both:

``` kotlin
when (result) {

    LoginOutcome.Success -> {
        updateState(
            LoginResult.Success
        )

        emitEffect(
            LoginEffect.NavigateToHome
        )
    }

    // ...
}
```

This gives a clear separation:

``` text
Reducer → State
Effect emitter → One-time action
```

# 25. Testing a Reducer

Reducer tests should be small and deterministic.

Consider:

``` kotlin
@Test
fun loading_should_clear_previous_error() {

    val state = ProfileState(
        profile = null,
        isLoading = false,
        error = AppError.Network
    )

    val result = ProfileResult.Loading

    val actual = reduce(
        state,
        result
    )

    assertEquals(
        ProfileState(
            profile = null,
            isLoading = true,
            error = null
        ),
        actual
    )
}
```

No UI is required.

No network is required.

No coroutine is required.

------------------------------------------------------------------------

## Success test

``` kotlin
@Test
fun success_should_store_profile() {

    val profile = Profile(
        id = "123",
        name = "Prahalad"
    )

    val state = ProfileState(
        isLoading = true
    )

    val actual = reduce(
        state,
        ProfileResult.Success(profile)
    )

    assertEquals(
        profile,
        actual.profile
    )

    assertEquals(
        false,
        actual.isLoading
    )

    assertEquals(
        null,
        actual.error
    )
}
```

------------------------------------------------------------------------

## Failure test

``` kotlin
@Test
fun failure_should_stop_loading() {

    val state = ProfileState(
        isLoading = true
    )

    val error = AppError.Network

    val actual = reduce(
        state,
        ProfileResult.Failure(error)
    )

    assertEquals(
        false,
        actual.isLoading
    )

    assertEquals(
        error,
        actual.error
    )
}
```

These tests directly document the state machine.

# 26. Property-Based Thinking

Even without a property-based testing framework, it is useful to think
about reducer invariants.

For example:

> Loading should never leave an old error visible.

``` text
Loading
→ isLoading = true
→ error = null
```

Another invariant:

> Successful loading should stop loading.

``` text
Success
→ isLoading = false
```

Another:

> Pagination should not remove previously loaded items.

``` text
Page 1 + Page 2
→ items contain both pages
```

Thinking in invariants helps identify state bugs early.

# 27. Reducer in Kotlin Multiplatform

Reducers are excellent candidates for `commonMain`.

Example:

``` text
shared/
└── src/
    └── commonMain/
        └── kotlin/
            └── feature/
                └── profile/
                    ├── ProfileState.kt
                    ├── ProfileResult.kt
                    └── ProfileReducer.kt
```

Reducer:

``` kotlin
fun reduce(
    state: ProfileState,
    result: ProfileResult
): ProfileState {
    // platform-independent state transition
}
```

No Android APIs.

No iOS APIs.

No platform UI.

This makes the reducer naturally portable.

# 28. Android Compose Integration

Compose consumes the state generated by the reducer.

For example:

``` kotlin
@Composable
fun ProfileScreen(
    state: ProfileState,
    onIntent: (ProfileIntent) -> Unit
) {
    when {
        state.isLoading -> {
            LoadingView()
        }

        state.error != null -> {
            ErrorView(
                onRetry = {
                    onIntent(
                        ProfileIntent.Retry
                    )
                }
            )
        }

        state.profile != null -> {
            ProfileContent(
                profile = state.profile
            )
        }
    }
}
```

The reducer does not know Compose exists.

It only produces:

``` text
ProfileState
```

Compose decides how to render it.

# 30. Common Reducer Mistakes

## Mistake 1 --- Calling the repository from the reducer

Bad:

``` kotlin
fun reduce(...) {
    repository.load()
}
```

The reducer should transform state.

------------------------------------------------------------------------

## Mistake 2 --- Launching coroutines inside the reducer

Bad:

``` kotlin
fun reduce(...) {
    scope.launch {
        // work
    }
}
```

Coroutine orchestration belongs to feature logic.

------------------------------------------------------------------------

## Mistake 3 --- Performing navigation

Bad:

``` kotlin
fun reduce(...) {
    navController.navigate(...)
}
```

Navigation is an effect.

------------------------------------------------------------------------

## Mistake 4 --- Mutating state

Bad:

``` kotlin
state.items.add(item)
```

Prefer:

``` kotlin
state.copy(
    items = state.items + item
)
```

------------------------------------------------------------------------

## Mistake 5 --- Putting business operations in the reducer

Bad:

``` kotlin
if (state.balance > amount) {
    repository.transfer(amount)
}
```

The business operation belongs in a use case/domain layer.

The reducer should represent its result.

------------------------------------------------------------------------

## Mistake 6 --- One enormous reducer

A reducer handling:

``` text
Login
Profile
Cart
Search
Notifications
Checkout
Payments
```

can become difficult to maintain.

Prefer meaningful feature boundaries and composition.

------------------------------------------------------------------------

## Mistake 7 --- Using reducers as general-purpose utility functions

A reducer should have a clear state-transition responsibility.

Do not turn it into:

``` text
formatter
validator
repository
navigation handler
analytics manager
```

all at once.

------------------------------------------------------------------------

# 31. A Practical Reducer Checklist

Before adding logic to a reducer, ask:

### Does it only transform state?

If yes, good.

If it performs I/O, reconsider the boundary.

### Is the reducer deterministic?

Same input should produce the same output.

### Is state immutable?

Prefer:

``` kotlin
copy(...)
```

### Can it be unit tested without UI?

It should usually be possible.

### Does it handle all meaningful results?

Use exhaustive `when` for sealed result types.

### Are effects separated?

Navigation and one-time actions should generally not be hidden inside
state reduction.

### Is the reducer too large?

If yes, consider feature-specific reducers.

### Is it platform-independent?

For KMP, keep reducers in `commonMain` whenever possible.

------------------------------------------------------------------------

## Reducer Design Formula

A useful formula is:

``` text
Reducer
=
Pure State Transformation
+
Immutable State
+
Deterministic Behavior
+
No I/O
+
No Navigation
+
No Platform Dependency
```

In its simplest form:

``` kotlin
fun reduce(
    state: State,
    result: Result
): State
```

That simplicity is a feature, not a limitation.

# 32. Part 4 Summary

The Reducer is the **state-transition engine of MVI**.

The most important principles are:

### 1. Reducer transforms state

``` text
Current State + Result
        ↓
      Reducer
        ↓
    New State
```

### 2. Reducers should be pure

They should not:

``` text
call APIs
write databases
launch coroutines
navigate
```

### 3. Separate Intent from Result when useful

For asynchronous workflows:

``` text
Intent
 ↓
Operation
 ↓
Result
 ↓
Reducer
 ↓
State
```

### 4. Keep State immutable

Use:

``` kotlin
state.copy(...)
```

rather than mutation.

### 5. Reducers define state-machine transitions

They make valid transitions explicit.

### 6. Effects are separate

``` text
State  → current UI truth
Effect → one-time UI action
```

### 7. Reducers are ideal for KMP

They can usually live entirely in:

``` text
commonMain
```

and be shared by Android and iOS.

### 8. Reducers are highly testable

A reducer test can often be nothing more than:

``` text
Given State
+
Given Result
=
Expected State
```

# The MVI Architecture After Part 4

The architecture now has a complete core loop:

``` mermaid
flowchart TB
    UI[Platform UI]
    I[Intent]
    P[Feature Processor]
    UC[Use Case]
    R[Result]
    RED[Reducer]
    S[State]
    E[Effect]
    DATA[Repository / Data Source]

    UI --> I
    I --> P
    P --> UC
    UC --> DATA
    DATA --> UC
    UC --> R
    R --> RED
    RED --> S
    S --> UI
    P --> E
    E --> UI
```

The responsibilities are now clearly separated:

  Component        Responsibility
  ---------------- --------------------------------------
  **UI**           Render State and emit Intent
  **Intent**       Describe an input
  **Processor**    Interpret Intent and coordinate work
  **Use Case**     Execute business operation
  **Repository**   Access data
  **Result**       Describe operation outcome
  **Reducer**      Transform State
  **State**        Represent current UI truth
  **Effect**       Represent one-time UI action

------------------------------------------------------------------------

## Key Takeaway

> **A reducer should be boring---and that is a good thing.**

A reducer that simply takes:

``` text
State + Result
```

and produces:

``` text
New State
```

is predictable, testable, reusable, and easy to share across platforms.

In a Kotlin Multiplatform architecture, this makes the reducer one of
the strongest candidates for shared `commonMain` logic.
