# 1. Why Navigation Needs Special Treatment in MVI

Navigation looks simple from the UI:

``` text
User taps Login
       ↓
Open Home
```

But in a real application, navigation usually depends on application
state and business rules.

For example:

``` text
Login successful
      ↓
Is MFA required?
      ├── Yes → MFA screen
      └── No  → Home
```

Another example:

``` text
Product selected
      ↓
Is the product available?
      ├── Yes → Product details
      └── No  → Error / unavailable screen
```

Navigation therefore should not become random UI code scattered across
screens.

A well-designed MVI architecture gives navigation a predictable path:

``` text
UI Action
   ↓
Intent
   ↓
MVI Processor
   ↓
Repository / Use Case
   ↓
Result
   ↓
State + Effect
           ↓
       Navigation
```

The important distinction is:

> **State describes what the screen is. Effect describes what the
> application should do next.**

Navigation is usually an **effect**.

------------------------------------------------------------------------

# 2. Navigation Is Not UI State

This is one of the most important concepts in MVI.

Consider:

``` kotlin
data class LoginState(
    val isLoading: Boolean = false,
    val username: String = "",
    val password: String = "",
    val isLoggedIn: Boolean = false
)
```

A common implementation is:

``` kotlin
if (state.isLoggedIn) {
    navigateToHome()
}
```

It may work, but it mixes two different concepts.

`isLoggedIn` is application state.

`navigateToHome()` is an action.

They are not the same thing.

### State

State can be observed repeatedly.

``` text
LoginState(
    isLoggedIn = true
)
```

If the UI is recreated, the state can still be true.

### Effect

Navigation should normally happen once.

``` text
Navigate(Home)
```

The system should not repeatedly execute:

``` text
Navigate(Home)
Navigate(Home)
Navigate(Home)
```

because a state remains `isLoggedIn = true`.

This gives us a useful rule:

> **Persistent information belongs in State. One-time actions belong in
> Effects.**

# 3. The MVI Navigation Flow

A clean MVI navigation architecture looks like this:

``` mermaid
flowchart TD
    UI[UI Interaction]
    INTENT[Intent]
    VM[MVI Processor / ViewModel]
    USECASE[Use Case]
    REPO[Repository]
    RESULT[Operation Result]
    REDUCER[Reducer]
    STATE[State]
    EFFECT[Navigation Effect]
    NAV[Platform Navigator]
    SCREEN[Destination Screen]

    UI --> INTENT
    INTENT --> VM
    VM --> USECASE
    USECASE --> REPO
    REPO --> RESULT
    RESULT --> REDUCER
    REDUCER --> STATE
    RESULT --> EFFECT
    STATE --> UI
    EFFECT --> NAV
    NAV --> SCREEN
```

Notice something important:

The reducer does not directly call the navigation framework.

Instead:

``` text
Reducer / Processor
        ↓
   Navigation Effect
        ↓
Platform UI
        ↓
Navigation framework
```

This keeps the shared business logic independent of Android Navigation,
UIKit, or SwiftUI navigation APIs.

# 4. Model Navigation as an Effect

In Part 5, we established that effects represent one-time actions.

Navigation fits naturally into that model.

For example:

``` kotlin
sealed interface AppEffect {

    data object NavigateToHome : AppEffect

    data object NavigateToLogin : AppEffect

    data class NavigateToProduct(
        val productId: String
    ) : AppEffect

    data object GoBack : AppEffect
}
```

The shared MVI layer does not need to know whether navigation is
implemented using:

-   Android Navigation
-   Compose Navigation
-   SwiftUI NavigationStack
-   UIKit navigation
-   another navigation framework

It only communicates the intent to navigate.

------------------------------------------------------------------------

# 5. Defining Navigation Effects

A scalable application should avoid a giant navigation effect type when
possible.

Instead, navigation can be modeled at the feature or application level.

For example:

``` kotlin
sealed interface LoginEffect {

    data object NavigateToHome : LoginEffect

    data object NavigateToForgotPassword : LoginEffect

    data object NavigateToSignUp : LoginEffect
}
```

For a product feature:

``` kotlin
sealed interface ProductEffect {

    data class OpenProduct(
        val productId: String
    ) : ProductEffect

    data object GoBack : ProductEffect
}
```

This makes ownership clear.

### Feature-owned navigation

``` text
LoginFeature
 ├── LoginIntent
 ├── LoginState
 ├── LoginResult
 └── LoginEffect
        ├── NavigateToHome
        ├── SignUp
        └── ForgotPassword
```

The feature decides **what should happen**.

The platform decides **how it happens**.

That separation is extremely useful in KMP.

# 6. Intent → Result → Effect

Consider a login operation.

The user sends:

``` kotlin
LoginIntent.Submit
```

The MVI processor performs authentication.

The result could be:

``` kotlin
sealed interface LoginResult {

    data object Loading : LoginResult

    data object Success : LoginResult

    data class Failure(
        val message: String
    ) : LoginResult
}
```

The successful result can produce:

``` kotlin
LoginEffect.NavigateToHome
```

The complete flow becomes:

``` mermaid
sequenceDiagram
    participant UI
    participant MVI
    participant Auth
    participant Reducer
    participant Navigator

    UI->>MVI: LoginIntent.Submit
    MVI->>Auth: authenticate()
    Auth-->>MVI: Success
    MVI->>Reducer: LoginResult.Success
    Reducer-->>MVI: Updated State
    MVI->>Navigator: NavigateToHome
    Navigator-->>UI: Home Screen
```

This gives us two separate outputs:

``` text
Result
 ├── State update
 └── Effect
```

For example:

``` text
Success
 ├── State → authenticated = true
 └── Effect → NavigateToHome
```

# 7. A Login Navigation Example

Let's build a complete shared example.

## Intent

``` kotlin
sealed interface LoginIntent {

    data class UsernameChanged(
        val value: String
    ) : LoginIntent

    data class PasswordChanged(
        val value: String
    ) : LoginIntent

    data object Submit : LoginIntent
}
```

## State

``` kotlin
data class LoginState(
    val username: String = "",
    val password: String = "",
    val isLoading: Boolean = false,
    val error: String? = null,
    val isAuthenticated: Boolean = false
)
```

## Effect

``` kotlin
sealed interface LoginEffect {

    data object NavigateToHome : LoginEffect

    data object NavigateToForgotPassword : LoginEffect
}
```

## Reducer

``` kotlin
fun reduce(
    state: LoginState,
    result: LoginResult
): LoginState {
    return when (result) {

        LoginResult.Loading ->
            state.copy(
                isLoading = true,
                error = null
            )

        LoginResult.Success ->
            state.copy(
                isLoading = false,
                isAuthenticated = true
            )

        is LoginResult.Failure ->
            state.copy(
                isLoading = false,
                error = result.message
            )
    }
}
```

## Processor

Conceptually:

``` kotlin
suspend fun process(intent: LoginIntent) {

    when (intent) {

        LoginIntent.Submit -> {

            emitResult(LoginResult.Loading)

            val result = repository.login(
                username = state.value.username,
                password = state.value.password
            )

            when (result) {

                is LoginResponse.Success -> {
                    emitResult(LoginResult.Success)
                    emitEffect(LoginEffect.NavigateToHome)
                }

                is LoginResponse.Failure -> {
                    emitResult(
                        LoginResult.Failure(
                            result.message
                        )
                    )
                }
            }
        }

        is LoginIntent.UsernameChanged -> {
            updateState {
                it.copy(username = intent.value)
            }
        }

        is LoginIntent.PasswordChanged -> {
            updateState {
                it.copy(password = intent.value)
            }
        }
    }
}
```

The UI receives:

``` text
State
 ├── loading
 ├── username
 ├── password
 ├── error
 └── authenticated

Effect
 └── NavigateToHome
```

The UI does not need to understand authentication internals.

# 8. Why Navigation Should Not Live Inside the Reducer

A reducer should be deterministic.

Given:

``` text
Current State + Result
```

it should produce:

``` text
New State
```

For example:

``` kotlin
fun reduce(
    state: LoginState,
    result: LoginResult
): LoginState
```

The reducer should not contain:

``` kotlin
navController.navigate("home")
```

or:

``` kotlin
navigationController.pushView(...)
```

That creates several problems.

## Problem 1 --- Platform dependency

The reducer becomes tied to a UI framework.

## Problem 2 --- Difficult testing

A pure reducer is easy to test.

A reducer that controls navigation requires navigation infrastructure.

## Problem 3 --- Hidden side effects

Calling navigation from a state transition makes the reducer no longer
pure.

## Problem 4 --- KMP coupling

Shared code should not depend directly on Android or iOS navigation
APIs.

The better design is:

``` text
Reducer
   ↓
State

Processor
   ↓
Effect

Platform UI
   ↓
Navigation
```

------------------------------------------------------------------------

# 9. Navigation and State Restoration

Navigation becomes more interesting when configuration changes, process
recreation, or view recreation occur.

Imagine:

``` text
Login
  ↓
Home
  ↓
Product Details
```

The application state may survive differently from the UI lifecycle.

This is another reason not to represent navigation purely as:

``` kotlin
data class State(
    val destination: String
)
```

If the state is replayed after recreation:

``` text
destination = Home
```

the UI may accidentally execute:

``` text
navigate(Home)
```

again.

Instead, distinguish:

``` text
Persistent state
```

from:

``` text
One-time navigation event
```

For example:

``` kotlin
data class LoginState(
    val isAuthenticated: Boolean = false
)
```

and:

``` kotlin
sealed interface LoginEffect {
    data object NavigateToHome : LoginEffect
}
```

This allows state restoration without replaying an old navigation
command unintentionally.

# 10. Navigation Arguments

Navigation often requires data.

For example:

``` text
ProductList
     ↓
ProductDetails(productId = "P1001")
```

Represent this explicitly:

``` kotlin
sealed interface ProductEffect {

    data class OpenDetails(
        val productId: String
    ) : ProductEffect
}
```

The UI receives:

``` kotlin
ProductEffect.OpenDetails(
    productId = "P1001"
)
```

and maps it to its platform-specific route.

For example, conceptually:

``` text
OpenDetails("P1001")
        ↓
Android
product/P1001

        ↓
iOS
ProductDetails(id: P1001)
```

The shared layer owns the semantic meaning.

The platform owns the route representation.

------------------------------------------------------------------------

# 11. Typed Navigation

String-based navigation can become fragile.

For example:

``` kotlin
navController.navigate(
    "product/$productId"
)
```

has several risks:

-   spelling errors
-   malformed parameters
-   inconsistent route names
-   manual serialization
-   difficult refactoring

A typed effect is safer:

``` kotlin
sealed interface AppNavigation {

    data object Home : AppNavigation

    data object Settings : AppNavigation

    data class ProductDetails(
        val id: String
    ) : AppNavigation

    data object Login : AppNavigation
}
```

Now the shared code expresses:

``` kotlin
AppNavigation.ProductDetails("P1001")
```

instead of:

``` kotlin
"product/P1001"
```

The platform adapter can decide how to encode it.

------------------------------------------------------------------------

# 12. Nested Navigation and Feature Ownership

Large applications usually contain multiple navigation areas.

For example:

``` text
Application
│
├── Authentication
│   ├── Login
│   ├── Sign Up
│   └── Forgot Password
│
├── Main
│   ├── Home
│   ├── Search
│   └── Profile
│
└── Checkout
    ├── Cart
    ├── Address
    ├── Payment
    └── Confirmation
```

Do not let every screen navigate directly to every other screen.

Instead, navigation should follow feature boundaries.

``` text
Login Feature
      ↓
Authentication Coordinator
      ↓
Main Feature
```

or:

``` text
Product Feature
      ↓
Application Navigation Contract
      ↓
Product Details
```

A useful rule is:

> **A feature should express where it wants to go without knowing the
> implementation details of the global navigation system.**

# 13. Back Navigation

Back navigation is also an intent.

For example:

``` kotlin
sealed interface ProductIntent {

    data object BackClicked : ProductIntent

    data class LoadProduct(
        val id: String
    ) : ProductIntent
}
```

The effect could be:

``` kotlin
sealed interface ProductEffect {

    data object GoBack : ProductEffect
}
```

The flow becomes:

``` text
Back button
     ↓
BackClicked
     ↓
MVI
     ↓
GoBack
     ↓
Platform navigator
```

However, not every back action needs to go through shared business
logic.

If back behavior is purely navigation-stack behavior, the platform UI
may handle it directly.

For example:

``` text
System Back
   ↓
Navigation Controller
```

The key question is:

> **Does the business feature need to make a decision about back
> navigation?**

If no, keep it in the navigation layer.

If yes, model the decision explicitly.

------------------------------------------------------------------------

# 14. Navigation Guards

Sometimes navigation requires a condition.

For example:

``` text
Checkout
   ↓
Payment
```

but payment requires an address.

The application may need:

``` text
Address exists?
 ├── Yes → Payment
 └── No  → Address
```

The MVI layer can express this decision:

``` kotlin
sealed interface CheckoutEffect {

    data object NavigateToPayment : CheckoutEffect

    data object NavigateToAddress : CheckoutEffect
}
```

The decision belongs to application logic.

The actual navigation remains outside the shared business logic.

This creates a clean boundary:

``` text
Business Rule
     ↓
Navigation Decision
     ↓
Effect
     ↓
Platform Navigation
```

# 15. Authentication and Root Navigation

Authentication is a common example where state and navigation interact.

Consider:

``` text
Application
     │
     ├── Not Authenticated
     │       ↓
     │     Login
     │
     └── Authenticated
             ↓
            Home
```

A tempting approach is:

``` kotlin
if (state.isAuthenticated) {
    navController.navigate("home")
}
```

But root navigation is often better modeled as an application-level
decision.

For example:

``` kotlin
sealed interface RootEffect {

    data object ShowLogin : RootEffect

    data object ShowMainApp : RootEffect
}
```

Or, when the root UI can derive the current graph entirely from
persistent authentication state:

``` kotlin
data class SessionState(
    val status: SessionStatus
)
```

where:

``` kotlin
sealed interface SessionStatus {

    data object Unknown : SessionStatus

    data object LoggedOut : SessionStatus

    data object LoggedIn : SessionStatus
}
```

The root navigation layer can render the appropriate graph.

This is different from one-time navigation.

### Important distinction

``` text
SessionState
    → Which navigation graph should exist?

NavigationEffect
    → What one-time navigation action should happen?
```

These should not automatically be treated as the same problem.

# 16. Deep Links

Deep links introduce another input into an MVI architecture.

For example:

``` text
myapp://product/P1001
```

A deep link is effectively an external intent entering the application.

Conceptually:

``` text
Deep Link
    ↓
Application Router
    ↓
Navigation Intent
    ↓
Feature
    ↓
State / Effect
```

A deep link might be translated into:

``` kotlin
sealed interface AppIntent {

    data class OpenProduct(
        val productId: String
    ) : AppIntent
}
```

The shared application logic can then process:

``` kotlin
AppIntent.OpenProduct("P1001")
```

This prevents deep-link parsing from being scattered across individual
screens.

# 17. Navigation in KMP

KMP creates an important architectural question:

> Should the shared module own navigation?

There is no single answer.

A strong default is:

``` text
Shared KMP
 ├── Intent
 ├── State
 ├── Result
 ├── Effect
 └── Navigation Contract

Android
 └── Navigation Adapter

iOS
 └── Navigation Adapter
```

The shared module owns the **meaning** of navigation.

The platform owns the **implementation**.

### Shared

``` kotlin
sealed interface AppNavigation {

    data object Home : AppNavigation

    data object Login : AppNavigation

    data class ProductDetails(
        val id: String
    ) : AppNavigation
}
```

### Android

``` text
AppNavigation.ProductDetails("P1001")
             ↓
Compose Navigation route
```

### iOS

``` text
AppNavigation.ProductDetails("P1001")
             ↓
SwiftUI NavigationPath
```

This is one of the strongest patterns for keeping KMP architecture
platform-neutral.

# 18. Android Compose Integration

Suppose the shared MVI layer exposes:

``` kotlin
val effects: Flow<LoginEffect>
```

The Compose screen can collect effects.

Conceptually:

``` kotlin
@Composable
fun LoginScreen(
    viewModel: LoginViewModel,
    onNavigateToHome: () -> Unit
) {
    val state by viewModel.state.collectAsState()

    LaunchedEffect(Unit) {
        viewModel.effects.collect { effect ->

            when (effect) {
                LoginEffect.NavigateToHome ->
                    onNavigateToHome()

                LoginEffect.NavigateToForgotPassword ->
                    // Navigate to forgot password
                    Unit
            }
        }
    }

    LoginContent(
        state = state,
        onIntent = viewModel::onIntent
    )
}
```

Notice the separation:

``` text
LoginScreen
    ↓
renders State

LoginScreen
    ↓
collects Effect

Navigation Host
    ↓
performs actual navigation
```

The MVI layer never needs a `NavController`.

# 19. iOS SwiftUI Integration

The same shared effect can be consumed by SwiftUI.

Conceptually:

``` text
Shared Kotlin
      ↓
LoginEffect.NavigateToHome
      ↓
SwiftUI
      ↓
NavigationStack
```

A SwiftUI adapter might translate:

``` text
NavigateToHome
```

into:

``` text
NavigationPath.append(HomeRoute)
```

The important idea is not the exact Swift syntax.

The architectural boundary is:

``` text
Shared MVI
     ↓
Semantic Navigation Effect
     ↓
iOS Adapter
     ↓
SwiftUI Navigation
```

This keeps platform-specific navigation APIs outside the shared feature
logic.

# 20. Platform-Neutral Navigation Contracts

A good navigation contract should answer:

> Where should the application go?

It should not answer:

> Which navigation framework API should be called?

Good:

``` kotlin
data class ProductDetails(
    val productId: String
)
```

Less desirable inside shared code:

``` kotlin
navController.navigate(
    "product/$productId"
)
```

The first is platform-neutral.

The second is an Android implementation detail.

This distinction becomes increasingly valuable as the application grows.

------------------------------------------------------------------------

# 21. Avoiding Navigation Logic in Shared UI

Shared UI and shared business logic should not become responsible for
the entire application navigation graph.

For example, avoid:

``` kotlin
@Composable
fun ProductScreen(
    navController: NavController
) {
    // Business UI + global navigation
}
```

This makes the feature harder to reuse.

Prefer:

``` kotlin
@Composable
fun ProductScreen(
    state: ProductState,
    onIntent: (ProductIntent) -> Unit,
    onNavigate: (ProductNavigation) -> Unit
)
```

Or even better, keep navigation effect collection at the appropriate
navigation boundary.

``` text
Feature
  ↓
Effect
  ↓
Feature Host
  ↓
Application Navigator
```

This creates a clean dependency direction.

------------------------------------------------------------------------

# 22. Handling Duplicate Navigation Events

Duplicate navigation is one of the most common real-world MVI problems.

Imagine:

``` text
LoginEffect.NavigateToHome
LoginEffect.NavigateToHome
```

The UI might execute:

``` text
Home
Home
```

or push the same destination twice.

Common causes include:

-   multiple collectors
-   incorrect lifecycle handling
-   retry logic
-   duplicated intents
-   emitting an effect from multiple paths
-   recreating collectors incorrectly

## Protect the architecture

First, make effect production explicit.

``` kotlin
emitEffect(
    LoginEffect.NavigateToHome
)
```

Then ensure there is a single appropriate collector for the feature.

The UI should also treat effects as events rather than persistent state.

Avoid:

``` kotlin
data class State(
    val navigateToHome: Boolean = false
)
```

because the flag can survive recreation.

Prefer:

``` kotlin
sealed interface Effect {
    data object NavigateToHome : Effect
}
```

------------------------------------------------------------------------

# 23. Navigation Failures

Navigation itself can fail.

Examples:

-   destination no longer exists
-   invalid navigation argument
-   navigation happens after the screen is disposed
-   duplicate navigation
-   invalid deep link
-   stale navigation state

Navigation failures should not normally crash the entire MVI layer.

A platform navigation adapter can handle them:

``` text
Navigation Effect
      ↓
Platform Navigator
      ↓
Success / Failure
```

For example:

``` text
Open Product P1001
       ↓
Navigator
       ↓
Destination unavailable
       ↓
Navigation fallback
```

The fallback might be:

``` text
Product unavailable
```

or:

``` text
Go back
```

The important point is that the shared feature does not need to know
every navigation framework failure mode.

------------------------------------------------------------------------

# 24. Testing Navigation

Navigation is much easier to test when it is represented as an effect.

Suppose:

``` kotlin
sealed interface LoginEffect {
    data object NavigateToHome : LoginEffect
}
```

A test can assert:

``` kotlin
@Test
fun `successful login emits home navigation`() = runTest {

    val effects = mutableListOf<LoginEffect>()

    viewModel.effects
        .onEach { effects += it }
        .launchIn(backgroundScope)

    viewModel.onIntent(
        LoginIntent.UsernameChanged("user")
    )

    viewModel.onIntent(
        LoginIntent.PasswordChanged("password")
    )

    viewModel.onIntent(
        LoginIntent.Submit
    )

    advanceUntilIdle()

    assertTrue(
        effects.contains(
            LoginEffect.NavigateToHome
        )
    )
}
```

The test does not need:

-   Android navigation framework
-   Compose UI
-   actual navigation controller
-   iOS runtime

It tests the application behavior.

------------------------------------------------------------------------

## Testing the Reducer Separately

The reducer should test state transitions.

``` kotlin
@Test
fun `login success updates authenticated state`() {

    val state = LoginState(
        isLoading = true
    )

    val result = LoginResult.Success

    val newState = reduce(
        state = state,
        result = result
    )

    assertTrue(newState.isAuthenticated)
    assertFalse(newState.isLoading)
}
```

Then test navigation separately:

``` text
Result
  ↓
Effect
  ↓
Navigation
```

This separation keeps tests focused.

# 25. Common Navigation Mistakes in MVI

## Mistake 1 --- Navigation inside the reducer

``` kotlin
fun reduce(...) {
    navController.navigate("home")
}
```

**Why it is wrong:**\
The reducer is no longer pure.

**Better:**

``` text
Reducer → State
Processor → Effect
UI → Navigation
```

------------------------------------------------------------------------

## Mistake 2 --- Navigation as a Boolean

``` kotlin
data class State(
    val navigateToHome: Boolean
)
```

**Why it is risky:**\
The value is persistent while navigation is normally one-time.

**Better:**

``` kotlin
sealed interface Effect {
    data object NavigateToHome : Effect
}
```

------------------------------------------------------------------------

## Mistake 3 --- Shared code directly depends on Android navigation

``` kotlin
NavController
```

inside common code creates platform coupling.

**Better:**

``` kotlin
NavigateToHome
```

and let Android interpret it.

------------------------------------------------------------------------

## Mistake 4 --- Every feature knows every route

``` text
Login → Product
Product → Settings
Settings → Checkout
Checkout → Login
```

This creates a navigation web that becomes difficult to maintain.

Prefer clear ownership and application-level navigation boundaries.

------------------------------------------------------------------------

## Mistake 5 --- Passing navigation controllers everywhere

Avoid:

``` kotlin
Screen(
    navController = navController
)
```

through every feature layer.

It couples presentation code to a navigation implementation.

------------------------------------------------------------------------

## Mistake 6 --- Using raw strings as the shared navigation contract

Avoid:

``` kotlin
"product/123"
```

inside shared business logic.

Prefer typed navigation models.

------------------------------------------------------------------------

## Mistake 7 --- Ignoring duplicate effects

One-time events need a deliberate delivery mechanism.

Otherwise:

``` text
Navigate
Navigate
```

can become a production bug.

------------------------------------------------------------------------

## Mistake 8 --- Mixing session state with navigation events

These are different concepts:

``` text
Authenticated
```

and:

``` text
Navigate to Home
```

The first describes application state.

The second requests a one-time action.

------------------------------------------------------------------------

# 26. Practical Navigation Checklist

Before finalizing navigation in an MVI feature, ask:

### State

-   [ ] Is persistent information represented as state?
-   [ ] Is navigation avoided as a boolean flag?
-   [ ] Can the state be restored safely?

### Intent

-   [ ] Is user-driven navigation represented appropriately?
-   [ ] Are navigation decisions based on business rules handled by MVI?

### Effect

-   [ ] Are one-time navigation actions modeled as effects?
-   [ ] Are effects typed?
-   [ ] Are navigation arguments explicit?

### Reducer

-   [ ] Is the reducer free from navigation framework calls?
-   [ ] Is the reducer deterministic?
-   [ ] Can it be tested without a UI framework?

### KMP

-   [ ] Is shared code platform-neutral?
-   [ ] Does Android map effects to its navigation system?
-   [ ] Does iOS map effects to its navigation system?

### Lifecycle

-   [ ] Is there an appropriate effect collector?
-   [ ] Can the same effect accidentally be collected twice?
-   [ ] Is recreation handled safely?

### Architecture

-   [ ] Does each feature own its local navigation decisions?
-   [ ] Is global navigation coordinated at the application boundary?
-   [ ] Are raw route strings kept out of business logic?

------------------------------------------------------------------------

# 27. Summary

Navigation is one of the places where an MVI architecture can either
become beautifully predictable or slowly turn into a collection of
lifecycle bugs.

The key distinction is simple:

``` text
State
  ↓
What is true?

Effect
  ↓
What should happen once?

Navigation
  ↓
A common type of one-time effect
```

A strong MVI navigation flow looks like:

``` mermaid
flowchart LR
    USER[User Action]
    INTENT[Intent]
    PROCESSOR[Processor]
    RESULT[Result]
    REDUCER[Reducer]
    STATE[State]
    EFFECT[Navigation Effect]
    ADAPTER[Platform Adapter]
    NAV[Navigator]
    DEST[Destination]

    USER --> INTENT
    INTENT --> PROCESSOR
    PROCESSOR --> RESULT
    RESULT --> REDUCER
    REDUCER --> STATE
    PROCESSOR --> EFFECT
    EFFECT --> ADAPTER
    ADAPTER --> NAV
    NAV --> DEST
```

For KMP, the boundary becomes even more valuable:

``` text
                 Shared KMP
┌─────────────────────────────────────┐
│ Intent                              │
│ State                               │
│ Result                              │
│ Reducer                             │
│ Effect                              │
│ Navigation Contract                │
└──────────────────┬──────────────────┘
                   │
          ┌────────┴────────┐
          │                 │
       Android             iOS
          │                 │
   Compose Navigation   SwiftUI
          │                 │
          └───────┬─────────┘
                  │
             User Journey
```

The goal is not to make navigation itself "shared" at all costs.

The goal is to share the **navigation decision** while keeping the
**navigation implementation** native to each platform.

> **MVI should decide what needs to happen. The platform should decide
> how navigation happens.**

That boundary keeps the architecture testable, predictable,
lifecycle-aware, and well suited for Kotlin Multiplatform.
