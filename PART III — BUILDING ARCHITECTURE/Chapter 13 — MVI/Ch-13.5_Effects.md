# 1. What Is an Effect?

In MVI, an **Effect represents a one-time action that should be
performed by the UI or platform layer**.

Examples include:

``` text
Navigate to another screen
Show a Snackbar
Show a Toast
Open a browser
Open a deep link
Request a permission
Launch a share sheet
Open a file picker
Start a platform-specific action
```

These actions are different from ordinary UI state.

For example:

``` text
State:
isLoading = true
```

describes a condition.

But:

``` text
NavigateToHome
```

describes something that should happen.

A useful mental model is:

``` text
State
→ What is true?

Effect
→ What should happen once?
```

------------------------------------------------------------------------

# 2. Why State Is Not Enough

Suppose login succeeds.

You may want the application to:

1.  update the state,
2.  navigate to Home.

State could represent:

``` kotlin
data class LoginState(
    val isLoggedIn: Boolean = false
)
```

But if the UI reacts to:

``` kotlin
isLoggedIn == true
```

and navigation is triggered directly from that state, the navigation can
become difficult to control.

Consider:

``` text
Login succeeds
     ↓
isLoggedIn = true
     ↓
Navigate Home
```

Now the UI is recreated.

It observes:

``` text
isLoggedIn = true
```

Should it navigate again?

Usually not.

The state remains true.

The navigation should happen once.

That is exactly where an Effect is useful.

------------------------------------------------------------------------

# 3. State vs Effect

This distinction should become second nature when designing MVI.

  State                        Effect
  ---------------------------- ----------------------------------
  Persistent condition         One-time action
  Can be rendered repeatedly   Usually consumed once
  Represents UI truth          Represents an instruction/action
  `isLoading`                  `NavigateToHome`
  `errorMessage`               `ShowSnackbar`
  `items`                      `OpenUrl`
  `selectedTab`                `RequestPermission`

For example:

``` kotlin
data class ProfileState(
    val profile: Profile? = null,
    val isLoading: Boolean = false
)
```

and:

``` kotlin
sealed interface ProfileEffect {

    data object NavigateToEdit : ProfileEffect

    data class ShowMessage(
        val message: String
    ) : ProfileEffect
}
```

The state describes the screen.

The effect describes a one-time action.

------------------------------------------------------------------------

# 4. Common Effect Examples

Effects are especially useful for actions that should not be represented
as persistent state.

### Navigation

``` kotlin
NavigateToHome

NavigateBack
```

### Transient messages

``` kotlin
ShowSnackbar("Saved successfully")
ShowToast("Copied")
```

### External applications

``` kotlin
OpenBrowser(url)
OpenEmail(address)
OpenMaps(latitude, longitude)
```

### System actions

``` kotlin
RequestCameraPermission
RequestNotificationPermission
```

### Platform UI

``` kotlin
ShowDatePicker
ShowFilePicker
OpenShareSheet
```

The exact effect set depends on the feature.

# 5. Modeling Effects With Sealed Interfaces

Kotlin sealed interfaces work well for typed Effects.

For example:

``` kotlin
sealed interface LoginEffect {

    data object NavigateToHome : LoginEffect

    data class ShowMessage(
        val message: String
    ) : LoginEffect

    data object ClearCredentials : LoginEffect
}
```

The UI can exhaustively handle them:

``` kotlin
when (effect) {

    LoginEffect.NavigateToHome -> {
        navigateToHome()
    }

    is LoginEffect.ShowMessage -> {
        showMessage(effect.message)
    }

    LoginEffect.ClearCredentials -> {
        clearCredentials()
    }
}
```

This provides:

-   type safety,
-   discoverability,
-   exhaustive handling,
-   easy testing,
-   platform-independent modeling.

------------------------------------------------------------------------

# 6. Navigation as an Effect

Navigation is one of the most common uses of Effects.

Consider:

``` kotlin
sealed interface ProductEffect {

    data class NavigateToDetails(
        val productId: String
    ) : ProductEffect

    data object NavigateBack : ProductEffect
}
```

The shared feature does not need to know whether Android uses:

``` text
Navigation Compose
```

or iOS uses:

``` text
SwiftUI NavigationStack
```

The shared layer only says:

``` text
NavigateToDetails(productId)
```

The platform decides how to execute it.

------------------------------------------------------------------------

## Navigation flow

``` mermaid
sequenceDiagram
    participant User
    participant UI
    participant Store
    participant Domain

    User->>UI: Select product
    UI->>Store: ProductSelected(id)
    Store->>Domain: Load/validate product
    Domain-->>Store: Success
    Store-->>UI: NavigateToDetails(id)
    UI->>UI: Perform platform navigation
```

This keeps navigation outside the reducer.

------------------------------------------------------------------------

# 7. Snackbar and Toast Effects

Transient messages are another common Effect.

For example:

``` kotlin
sealed interface CartEffect {

    data class ShowSnackbar(
        val message: String
    ) : CartEffect
}
```

After adding an item:

``` text
Intent:
AddToCartClicked

Result:
AddToCartSuccess

Effect:
ShowSnackbar("Added to cart")
```

The message is not necessarily part of permanent screen state.

Why?

Because after it is displayed, the application does not need to keep:

``` text
showSnackbar = true
```

forever.

------------------------------------------------------------------------

# 8. Dialogs and Bottom Sheets

Dialogs can also be modeled as effects when they represent a one-time UI
request.

For example:

``` kotlin
sealed interface AccountEffect {

    data object ShowLogoutConfirmation : AccountEffect
}
```

The UI receives:

``` text
ShowLogoutConfirmation
```

and displays the platform-specific dialog.

After the user responds, the UI can emit another Intent:

``` kotlin
LogoutConfirmed
```

The flow becomes:

``` text
Intent
  ↓
Effect
  ↓
Dialog
  ↓
User response
  ↓
Intent
  ↓
State / another Effect
```

This keeps the interaction loop explicit.

------------------------------------------------------------------------

# 9. External Actions

Effects are useful whenever the platform must perform an action outside
the shared feature.

For example:

``` kotlin
sealed interface ProfileEffect {

    data class OpenUrl(
        val url: String
    ) : ProfileEffect

    data class SendEmail(
        val address: String
    ) : ProfileEffect

    data object OpenShareSheet : ProfileEffect
}
```

The shared layer does not launch the browser itself.

It emits:

``` text
OpenUrl(url)
```

Android can use an `Intent`.

iOS can use an appropriate URL-opening API.

The shared MVI architecture remains platform-independent.

------------------------------------------------------------------------

# 10. Permissions and Platform Actions

Permissions are particularly platform-specific.

Avoid putting Android permission APIs directly inside shared MVI logic.

Instead:

``` kotlin
sealed interface CameraEffect {

    data object RequestCameraPermission : CameraEffect
}
```

The Android UI handles:

``` text
RequestCameraPermission
```

using Android's permission mechanism.

The iOS UI can handle the same conceptual effect using its own platform
APIs.

This creates a useful boundary:

``` text
Shared feature
      │
      ▼
RequestCameraPermission
      │
 ┌────┴────┐
 ▼         ▼
Android   iOS
```

The effect is shared.

The execution is platform-specific.

------------------------------------------------------------------------

# 11. Effects Are Not State

This deserves special attention.

Avoid:

``` kotlin
data class LoginState(
    val navigateToHome: Boolean = false
)
```

and:

``` kotlin
data class LoginState(
    val showSnackbar: Boolean = false
)
```

These values describe events rather than durable conditions.

A better design is:

``` kotlin
data class LoginState(
    val isLoading: Boolean = false,
    val isLoggedIn: Boolean = false
)
```

plus:

``` kotlin
sealed interface LoginEffect {
    data object NavigateToHome : LoginEffect
}
```

The state tells the UI:

``` text
The user is logged in.
```

The effect tells the UI:

``` text
Perform navigation now.
```

------------------------------------------------------------------------

# 12. The Duplicate Effect Problem

Effects introduce their own challenge:

> What happens if an Effect is delivered more than once?

Consider:

``` text
NavigateToHome
```

If the UI receives it twice:

``` text
Home
Home again
```

That can produce broken navigation behavior.

Similarly:

``` text
ShowSnackbar("Saved")
```

twice may display duplicate messages.

Therefore, effect delivery must be designed carefully.

------------------------------------------------------------------------

# 13. Why Boolean Event Flags Are Dangerous

A common workaround is:

``` kotlin
data class State(
    val showSuccessMessage: Boolean = false
)
```

Then:

``` text
showSuccessMessage = true
```

The UI shows a message and sets it back to false.

This creates several problems:

-   UI now mutates application state,
-   event consumption becomes state mutation,
-   recreation can repeat or lose the event,
-   multiple events can collapse into one Boolean,
-   ownership becomes unclear.

Imagine:

``` text
ShowMessage A
ShowMessage B
```

A Boolean cannot represent both.

A stream of Effects can.

------------------------------------------------------------------------

# 14. Flow for Effects

A common Kotlin approach is to expose Effects through a `Flow`.

For example:

``` kotlin
private val _effects =
    MutableSharedFlow<LoginEffect>()

val effects: SharedFlow<LoginEffect> =
    _effects.asSharedFlow()
```

Then emit:

``` kotlin
_effects.emit(
    LoginEffect.NavigateToHome
)
```

The UI collects:

``` kotlin
effects.collect { effect ->
    when (effect) {
        LoginEffect.NavigateToHome -> {
            navigateToHome()
        }

        is LoginEffect.ShowMessage -> {
            showMessage(effect.message)
        }
    }
}
```

This creates a separate stream:

``` text
State → persistent UI condition

Effect → transient UI action
```

------------------------------------------------------------------------

# 15. Channel for Effects

Another common option is Kotlin `Channel`.

For example:

``` kotlin
private val effectChannel =
    Channel<LoginEffect>(
        capacity = Channel.BUFFERED
    )

val effects =
    effectChannel.receiveAsFlow()
```

Emit:

``` kotlin
effectChannel.send(
    LoginEffect.NavigateToHome
)
```

The receiving side observes:

``` kotlin
effects.collect { effect ->
    handleEffect(effect)
}
```

Channels provide queue-like semantics.

This can be useful when each effect should be delivered as an individual
item to a consumer.

------------------------------------------------------------------------

# 16. SharedFlow vs Channel

Both can be useful.

A simplified comparison:

  Concern               `SharedFlow`             `Channel`
  --------------------- ------------------------ ------------------------------------
  Model                 Hot flow                 Queue-like communication primitive
  Multiple collectors   Supported                Consumption semantics require care
  Replay                Configurable             Not a replay mechanism
  Buffering             Configurable             Explicit channel capacity
  Typical use           Broadcast-style events   Point-to-point event delivery
  MVI effects           Common choice            Also common

There is no universal rule that says:

> "MVI must use Channel."

or:

> "MVI must use SharedFlow."

Choose based on the required delivery semantics.

The important architectural rule is:

> **Make effect delivery intentional.**

------------------------------------------------------------------------

# 17. Effect Delivery and Lifecycle

Lifecycle creates a subtle problem.

Suppose:

``` text
View starts collecting
       ↓
Effect emitted
       ↓
View handles it
```

Now the View disappears.

Later, the View returns.

Should it receive the old Effect?

For navigation:

``` text
Usually no.
```

For durable application state:

``` text
Usually yes.
```

This is one reason State and Effects need separate models.

State is normally replayable.

Effects are normally transient.

------------------------------------------------------------------------

## Lifecycle timeline

``` text
UI Active
   │
   │ collect
   ▼
Effect emitted
   │
   ▼
Effect handled
   │
   ▼
UI inactive
```

The architecture must decide what happens if the UI is inactive at
emission time.

There is no single correct answer for every product.

------------------------------------------------------------------------

# 18. Collecting Effects in Compose

A Compose screen can collect effects in a lifecycle-aware manner.

A simplified example:

``` kotlin
@Composable
fun LoginRoute(
    state: LoginState,
    effects: Flow<LoginEffect>,
    onIntent: (LoginIntent) -> Unit
) {
    LaunchedEffect(Unit) {

        effects.collect { effect ->

            when (effect) {

                LoginEffect.NavigateToHome -> {
                    // Navigate
                }

                is LoginEffect.ShowMessage -> {
                    // Show snackbar
                }
            }
        }
    }

    LoginScreen(
        state = state,
        onIntent = onIntent
    )
}
```

In a production application, effect collection should be aligned with
the appropriate lifecycle strategy.

The key idea is:

``` text
Composable
   ↓
Collect Effect
   ↓
Perform UI action
```

The reducer should not perform the action.

------------------------------------------------------------------------

# 19. Collecting Effects on iOS

The same conceptual model applies to SwiftUI.

``` text
Shared Effects
      ↓
KMP/Swift bridge
      ↓
SwiftUI observation
      ↓
Handle Effect
```

For example:

``` text
NavigateToDetails(id)
        ↓
SwiftUI
        ↓
Navigation
```

or:

``` text
ShowMessage(message)
        ↓
SwiftUI
        ↓
Alert / Snackbar-like UI
```

The exact bridging implementation depends on the project's KMP
architecture.

The important point is that the effect model remains platform-neutral.

# 20. Effects in Kotlin Multiplatform

Effects are often excellent candidates for `commonMain`.

For example:

``` kotlin
sealed interface CheckoutEffect {

    data object NavigateToSuccess : CheckoutEffect

    data class ShowMessage(
        val message: String
    ) : CheckoutEffect

    data object RequestPaymentAuthentication : CheckoutEffect
}
```

The shared layer can emit these effects.

The platform layer decides how to execute them.

``` text
                   Shared
                     │
              CheckoutEffect
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       Android                 iOS
          │                     │
     Android API           iOS API
```

This keeps platform-specific execution at the edge.

------------------------------------------------------------------------

# 21. Keeping Effects Platform-Neutral

Avoid effects like:

``` kotlin
data class StartAndroidActivity(
    val intent: android.content.Intent
)
```

This makes the shared module Android-specific.

Prefer:

``` kotlin
data class OpenUrl(
    val url: String
) : ProfileEffect
```

The platform decides how to open it.

Similarly, avoid:

``` kotlin
ShowAndroidToast
```

Prefer:

``` kotlin
ShowMessage("Saved successfully")
```

The Android and iOS layers can render the message using their native UI
mechanisms.

------------------------------------------------------------------------

# 22. Effect Payload Design

Effect payloads should be small and meaningful.

Good:

``` kotlin
data class NavigateToDetails(
    val productId: String
) : ProductEffect
```

Potentially excessive:

``` kotlin
data class NavigateToDetails(
    val product: Product,
    val user: User,
    val recommendations: List<Product>,
    val rawResponse: String
)
```

Only pass what the receiver needs to perform the action.

------------------------------------------------------------------------

## Avoid UI objects

Do not pass:

``` text
NavController
Activity
UIViewController
Context
Compose State
SwiftUI View
```

inside shared effects.

Effects should describe actions, not carry platform execution objects.

------------------------------------------------------------------------

# 23. Effect Ordering

Suppose login succeeds and the application wants to:

1.  show a message,
2.  navigate.

The order matters.

``` text
LoginSuccess
   ↓
ShowMessage
   ↓
Navigate
```

But the UI may navigate immediately, making the message invisible.

Perhaps the desired order is:

``` text
LoginSuccess
   ↓
Navigate
```

and the message belongs on the destination screen.

This illustrates an important point:

> Effects are part of user experience design, not merely technical
> events.

When multiple effects exist, define their ordering intentionally.

------------------------------------------------------------------------

# 24. Concurrent Effects

Multiple operations can emit effects at nearly the same time.

For example:

``` text
Upload completed
Session expired
Notification received
```

Possible effects:

``` text
ShowUploadSuccess
NavigateToLogin
ShowNotification
```

The application needs sensible prioritization.

One option is to keep effect emission centralized.

Another is to model higher-level feature effects:

``` kotlin
sealed interface AppEffect {

    data object SessionExpired : AppEffect

    data class ShowMessage(
        val message: String
    ) : AppEffect
}
```

The important point is to avoid having unrelated features compete
unpredictably for navigation.

------------------------------------------------------------------------

# 25. Effect Failures

Effects themselves can fail.

For example:

``` text
OpenUrl
```

may fail because the device has no suitable application.

The shared feature should decide how much of that failure belongs in the
shared layer.

A platform handler might report:

``` text
OpenUrlFailed
```

back into the feature as an Intent:

``` kotlin
data class ExternalActionFailed(
    val reason: ExternalActionError
) : ProfileIntent
```

Then:

``` text
Effect
 ↓
Platform
 ↓
Failure
 ↓
Intent
 ↓
State / Effect
```

This maintains the MVI loop.

------------------------------------------------------------------------

# 26. State + Effect in a Login Flow

Let's put everything together.

### Intent

``` kotlin
sealed interface LoginIntent {

    data object LoginClicked : LoginIntent

    data object RetryClicked : LoginIntent
}
```

### State

``` kotlin
data class LoginState(
    val isLoading: Boolean = false,
    val isLoggedIn: Boolean = false,
    val error: AppError? = null
)
```

### Result

``` kotlin
sealed interface LoginResult {

    data object Loading : LoginResult

    data object Success : LoginResult

    data class Failure(
        val error: AppError
    ) : LoginResult
}
```

### Effect

``` kotlin
sealed interface LoginEffect {

    data object NavigateToHome : LoginEffect

    data class ShowMessage(
        val message: String
    ) : LoginEffect
}
```

### Flow

``` mermaid
flowchart TD
    A[LoginClicked] --> B[Feature Processor]
    B --> C[Login Use Case]
    C --> D[LoginResult.Success]
    D --> E[Reducer]
    E --> F[LoginState isLoggedIn=true]
    D --> G[LoginEffect.NavigateToHome]
    F --> H[UI renders]
    G --> I[UI navigates]
```

Notice that State and Effect have separate responsibilities.

data class DeleteClicked(

# 28. Testing Effects

Effects should be testable independently.

Suppose:

``` kotlin
sealed interface LoginEffect {
    data object NavigateToHome : LoginEffect
}
```

Test:

``` text
Given:
Valid credentials

When:
LoginClicked

Then:
LoginResult.Success

And:
NavigateToHome effect is emitted
```

The test should not need to launch an actual navigation controller.

It verifies the architectural contract.

------------------------------------------------------------------------

## Effect sequence test

Suppose the feature should emit:

``` text
ShowMessage
NavigateToHome
```

A test can verify the sequence:

``` kotlin
assertEquals(
    listOf(
        LoginEffect.ShowMessage("Welcome"),
        LoginEffect.NavigateToHome
    ),
    effects
)
```

This can catch subtle ordering bugs.

------------------------------------------------------------------------

# 29. Testing State and Effects Together

A realistic feature test may verify both outputs.

Input:

``` text
LoginClicked
```

Expected:

``` text
State:
isLoading = false
isLoggedIn = true

Effect:
NavigateToHome
```

Conceptually:

``` text
              LoginClicked
                   │
                   ▼
             Feature Logic
                   │
             Login Success
             ┌─────┴─────┐
             ▼           ▼
           State       Effect
             │           │
             ▼           ▼
        Logged In    Navigate Home
```

Testing both outputs gives a much more complete picture of feature
behavior.

# 30. Common Effect Mistakes

## Mistake 1 --- Using State for one-time events

Bad:

``` kotlin
navigateToHome = true
```

Prefer:

``` kotlin
NavigateToHome
```

effect.

------------------------------------------------------------------------

## Mistake 2 --- Performing navigation in the reducer

Bad:

``` kotlin
fun reduce(...) {
    navController.navigate(...)
}
```

Reducer should return state.

------------------------------------------------------------------------

## Mistake 3 --- Platform-specific effect models

Bad:

``` kotlin
data class ShowAndroidToast(
    val context: Context
)
```

Prefer:

``` kotlin
data class ShowMessage(
    val message: String
)
```

------------------------------------------------------------------------

## Mistake 4 --- Huge effect payloads

Avoid sending entire domain graphs.

Pass only what the platform needs.

------------------------------------------------------------------------

## Mistake 5 --- Ignoring duplicate delivery

If an effect can be emitted or collected twice, navigation and transient
UI can break.

Define delivery semantics.

------------------------------------------------------------------------

## Mistake 6 --- Using a Boolean for an event

Bad:

``` kotlin
showSnackbar = true
```

A Boolean cannot represent:

``` text
Message A
Message B
Message C
```

as a sequence.

------------------------------------------------------------------------

## Mistake 7 --- Hiding important business state inside effects

An effect should not be used to communicate information that the UI
needs to continuously render.

For example:

``` text
Current user balance
```

belongs in State.

Not:

``` text
BalanceUpdatedEffect
```

if the UI needs to display the balance continuously.

------------------------------------------------------------------------

# 31. A Practical Effect Checklist

Before creating an Effect, ask:

### Is this a one-time action?

If yes, Effect may be appropriate.

### Is it persistent UI information?

If yes, it probably belongs in State.

### Does it require platform APIs?

If yes, describe the action in a platform-neutral way.

### Does it need a payload?

Pass only the minimum required information.

### Can it be delivered twice safely?

If not, carefully define collection and delivery semantics.

### Does ordering matter?

If multiple effects exist, define the expected sequence.

### Can it be tested without real navigation or platform UI?

It should usually be possible.

### Does the Effect belong in commonMain?

If its meaning is platform-neutral, usually yes.

------------------------------------------------------------------------

## Effect Design Formula

A useful mental model is:

``` text
Good Effect
=
One-Time Action
+
Small Typed Payload
+
Platform-Neutral Meaning
+
Explicit Delivery Semantics
```

For example:

``` kotlin
data class NavigateToDetails(
    val productId: String
) : ProductEffect
```

is a strong Effect model.

------------------------------------------------------------------------

# 32. Part 5 Summary

Effects complete an important part of the MVI architecture.

### State answers:

> **What is true right now?**

### Intent answers:

> **What happened?**

### Reducer answers:

> **How should State change?**

### Effect answers:

> **What one-time action should happen?**

The complete flow becomes:

``` text
UI
 ↓
Intent
 ↓
Feature Logic
 ↓
Result
 ├───────────────┐
 ▼               ▼
Reducer        Effect
 ↓               ↓
State            UI Action
 ↓
UI
```

The most important principles are:

### 1. Effects represent transient actions

``` text
Navigation
Snackbar
Toast
External URL
Permission request
Share sheet
```

### 2. Effects are different from State

``` text
State  → persistent/replayable condition
Effect → transient action
```

### 3. Effects should be typed

Prefer:

``` kotlin
sealed interface Effect
```

over generic strings.

### 4. Effects should remain platform-neutral

Use:

``` text
OpenUrl
NavigateToDetails
RequestPermission
```

rather than Android/iOS implementation objects.

### 5. Delivery semantics matter

Choose an appropriate mechanism such as:

``` text
SharedFlow
Channel
```

based on the desired behavior.

### 6. Effects should be testable

You should be able to verify:

``` text
Input
 ↓
Expected State
 +
Expected Effect
```

without launching real platform UI.

# The Complete MVI Model After Part 5

At this point, the complete architecture looks like:

``` mermaid
flowchart TB
    UI[Platform UI]

    I[Intent]
    P[Feature Processor]
    UC[Use Case]
    DATA[Repository / Data Source]
    R[Result]
    RED[Reducer]
    S[State]
    E[Effect]

    UI --> I
    I --> P
    P --> UC
    UC --> DATA
    DATA --> UC
    UC --> R
    R --> RED
    RED --> S
    S --> UI

    P --> E
    E --> UI
```

Each component has one clear responsibility:

  Component        Responsibility
  ---------------- ------------------------------
  **UI**           Render State and emit Intent
  **Intent**       Describe an input
  **Processor**    Coordinate feature behavior
  **Use Case**     Execute business logic
  **Repository**   Access data
  **Result**       Describe operation outcome
  **Reducer**      Produce new State
  **State**        Represent current UI truth
  **Effect**       Trigger one-time UI actions

## The Four Questions of MVI

A useful way to remember the architecture is:

``` text
┌─────────────┬──────────────────────────────────┐
│ Intent      │ What happened?                   │
├─────────────┼──────────────────────────────────┤
│ State       │ What is true right now?          │
├─────────────┼──────────────────────────────────┤
│ Reducer     │ How does state change?           │
├─────────────┼──────────────────────────────────┤
│ Effect      │ What should happen once?         │
└─────────────┴──────────────────────────────────┘
```

Once these four concepts are separated clearly, MVI becomes much easier
to reason about.

------------------------------------------------------------------------

## Key Takeaway

> **State represents the truth of the screen; Effects represent actions
> that should happen once. Keeping those two concepts separate prevents
> navigation, messages, permissions, and other transient behavior from
> becoming accidental application state.**

For Kotlin Multiplatform, this separation is even more valuable: the
shared layer can describe **what should happen**, while Android and iOS
remain responsible for deciding **how it happens on their platform**.
