# 1. Why MVI?

Modern mobile applications rarely have simple screens.

A screen may need to:

-   load data from a remote API,
-   read cached data from a local database,
-   react to user actions,
-   display loading and error states,
-   support retry,
-   handle pagination,
-   process one-time events,
-   survive configuration changes,
-   work offline,
-   coordinate multiple asynchronous operations,
-   and remain testable.

As an application grows, the difficult part is often no longer drawing
the UI.

The difficult part is **managing state and the transitions that change
that state**.

This is where **MVI --- Model--View--Intent** becomes useful.

MVI encourages us to think about a screen as a state machine:

``` text
             User action
                  │
                  ▼
             ┌─────────┐
             │ Intent  │
             └────┬────┘
                  │
                  ▼
             ┌─────────┐
             │  Logic  │
             └────┬────┘
                  │
                  ▼
             ┌─────────┐
             │  State  │
             └────┬────┘
                  │
                  ▼
             ┌─────────┐
             │   UI    │
             └────┬────┘
                  │
                  └──────► User action
```

The important idea is not the acronym.

The important idea is:

> **A user action enters the system, application logic processes it, and
> the UI renders the resulting state.**

That gives us a predictable direction of data flow.

------------------------------------------------------------------------

# 2. The Problem MVI Tries to Solve

Consider a login screen.

A user enters:

``` text
Email
Password
```

and presses:

``` text
Login
```

The application may need to:

1.  validate the fields,
2.  call the authentication API,
3.  show a loading indicator,
4.  handle success,
5.  store authentication information,
6.  navigate to the home screen,
7.  handle an API error,
8.  allow retry,
9.  handle network failure.

Without a clear state model, the screen can quickly accumulate
independent variables:

``` kotlin
var email: String
var password: String
var isLoading: Boolean
var showError: Boolean
var errorMessage: String?
var loginSuccessful: Boolean
var isRetrying: Boolean
```

Now imagine another developer changes:

``` kotlin
isLoading = false
```

but forgets to reset:

``` kotlin
showError
```

The UI can enter a contradictory state.

For example:

``` text
isLoading = false
showError = true
loginSuccessful = true
```

What should the UI display?

MVI encourages us to represent the screen through a **single coherent
state**.

For example:

``` kotlin
data class LoginState(
    val email: String = "",
    val password: String = "",
    val isLoading: Boolean = false,
    val errorMessage: String? = null,
    val isLoggedIn: Boolean = false
)
```

The UI now observes one state representation.

------------------------------------------------------------------------

# 3. MVI in One Picture

A practical MVI architecture can be represented like this:

``` mermaid
flowchart LR
    U[User] --> V[View]
    V --> I[Intent]
    I --> VM[MVI Logic]
    VM --> R[Reducer]
    R --> S[State]
    S --> V

    VM --> E[Effects]
    E --> DATA[Repository / Use Case]
    DATA --> VM
```

There are two important flows here.

### State flow

``` text
Intent
   ↓
Business/UI logic
   ↓
Reducer
   ↓
State
   ↓
View
```

### Side-effect flow

``` text
Intent
   ↓
Business/UI logic
   ↓
Repository / Use Case
   ↓
Result
   ↓
State update
```

The UI should not decide how application state changes.

Instead, the UI communicates:

> "This happened."

The MVI layer decides:

> "Given that event, what should the new state be?"

------------------------------------------------------------------------

# 4. The Three Core Concepts

MVI implementations can differ significantly.

Some frameworks use:

-   Intent
-   Action
-   Event
-   Message
-   State
-   Effect
-   Result
-   Reducer
-   Store

The terminology changes, but the underlying ideas remain similar.

For this chapter, we will use:

``` text
Intent → Logic → State
```

with side effects represented separately.

------------------------------------------------------------------------

## Intent

An **Intent** represents something that happened or something the user
wants the application to do.

Examples:

``` kotlin
sealed interface LoginIntent {

    data class EmailChanged(
        val value: String
    ) : LoginIntent

    data class PasswordChanged(
        val value: String
    ) : LoginIntent

    data object LoginClicked : LoginIntent

    data object RetryClicked : LoginIntent
}
```

An Intent should describe **what happened**, not how it should be
implemented.

Good:

``` kotlin
LoginIntent.LoginClicked
```

Less desirable:

``` kotlin
LoginIntent.CallLoginApi
```

The first describes user/application intent.

The second leaks implementation details into the UI event model.

------------------------------------------------------------------------

## State

State represents everything the UI needs to render the current screen.

Example:

``` kotlin
data class LoginState(
    val email: String = "",
    val password: String = "",
    val isLoading: Boolean = false,
    val errorMessage: String? = null,
    val isLoggedIn: Boolean = false
)
```

The UI should be able to answer:

> "What should I display right now?"

by looking at the state.

For example:

``` text
State
 ├── email
 ├── password
 ├── isLoading
 ├── errorMessage
 └── isLoggedIn
```

------------------------------------------------------------------------

## Model / Reducer

Historically, the "Model" part of MVI has been interpreted differently
by different implementations.

In modern Android/KMP architectures, it is often more useful to
separate:

-   state,
-   business logic,
-   side effects,
-   and state reduction.

A **reducer** takes:

``` text
Current State + Result
```

and produces:

``` text
New State
```

Conceptually:

``` text
reduce(
    currentState,
    result
) -> newState
```

For example:

``` kotlin
fun reduce(
    state: LoginState,
    result: LoginResult
): LoginState {
    return when (result) {
        LoginResult.Loading ->
            state.copy(
                isLoading = true,
                errorMessage = null
            )

        LoginResult.Success ->
            state.copy(
                isLoading = false,
                isLoggedIn = true
            )

        is LoginResult.Failure ->
            state.copy(
                isLoading = false,
                errorMessage = result.message
            )
    }
}
```

This is powerful because the reducer can be deterministic.

Given the same:

``` text
State + Result
```

it should produce the same:

``` text
State
```

# 5. Unidirectional Data Flow

The heart of MVI is **unidirectional data flow**.

The data moves in one direction:

``` text
        ┌─────────────┐
        │     View    │
        └──────┬──────┘
               │
               │ Intent
               ▼
        ┌─────────────┐
        │    Logic    │
        └──────┬──────┘
               │
               │ Result
               ▼
        ┌─────────────┐
        │   Reducer   │
        └──────┬──────┘
               │
               │ New State
               ▼
        ┌─────────────┐
        │     View    │
        └─────────────┘
```

There should not be a hidden second path such as:

``` text
View ───────────────► Repository
```

while the main flow is:

``` text
View → MVI → Repository
```

The more paths state can travel through, the harder it becomes to reason
about the application.

------------------------------------------------------------------------

## Why unidirectional flow helps

### Predictability

A developer can trace:

``` text
User action
    ↓
Intent
    ↓
Logic
    ↓
State change
    ↓
UI
```

without searching through multiple callbacks.

### Testability

You can test state transitions independently:

``` text
Given state X
When event Y occurs
Then state should become Z
```

### Debuggability

State changes can be logged:

``` text
Intent: LoginClicked
State: Loading

Intent: LoginResponse(Success)
State: LoggedIn
```

### Consistency

The UI becomes a renderer of state rather than a collection of
independent state mutations.

------------------------------------------------------------------------

# 6. MVI vs MVVM

MVI and MVVM are not completely unrelated architectures.

In fact, a well-designed MVVM implementation can have many MVI
characteristics.

Consider a typical MVVM flow:

``` text
View
  ↓
ViewModel
  ↓
Repository
  ↓
ViewModel
  ↓
State
  ↓
View
```

An MVI-style implementation makes the state transitions more explicit:

``` text
View
  ↓
Intent
  ↓
ViewModel / Store
  ↓
Result
  ↓
Reducer
  ↓
State
  ↓
View
```

### The major conceptual difference

MVVM often focuses on:

> View + ViewModel + observable state.

MVI focuses more strongly on:

> Intent + state transitions + unidirectional data flow.

------------------------------------------------------------------------

## Comparison

  Concern             MVVM                          MVI
  ------------------- ----------------------------- -----------------------------------
  UI state            Usually observable            Explicit central state
  User actions        Methods/callbacks             Intents/events
  Data flow           Often one-way, but flexible   Strongly one-way
  State transitions   Can be distributed            Usually centralized
  Reducer             Optional                      Common
  Debugging           Good                          Very good for state-heavy screens
  Boilerplate         Usually lower                 Can be higher
  Complex UI state    Good                          Excellent
  KMP suitability     Excellent                     Excellent

MVI should not be selected merely because it is a popular pattern.

It is especially useful when the application has **complex state
transitions**.

------------------------------------------------------------------------

# 7. A Small Kotlin Example

Let's start with a deliberately small example.

We have a counter.

The user can:

``` text
Increment
Decrement
Reset
```

### Intent

``` kotlin
sealed interface CounterIntent {

    data object Increment : CounterIntent

    data object Decrement : CounterIntent

    data object Reset : CounterIntent
}
```

### State

``` kotlin
data class CounterState(
    val count: Int = 0
)
```

### Reducer

``` kotlin
fun reduce(
    state: CounterState,
    intent: CounterIntent
): CounterState {
    return when (intent) {
        CounterIntent.Increment ->
            state.copy(
                count = state.count + 1
            )

        CounterIntent.Decrement ->
            state.copy(
                count = state.count - 1
            )

        CounterIntent.Reset ->
            CounterState()
    }
}
```

The state transition becomes explicit.

``` text
Initial State
count = 0

      │
      │ Increment
      ▼

count = 1

      │
      │ Increment
      ▼

count = 2

      │
      │ Decrement
      ▼

count = 1

      │
      │ Reset
      ▼

count = 0
```

The reducer does not need:

-   Android APIs,
-   Compose,
-   UIKit,
-   networking,
-   database code,
-   lifecycle code.

That makes it highly reusable and highly testable.

# 8. Modeling UI State

One of the most important MVI design decisions is how you model state.

A weak state model might look like:

``` kotlin
data class UserState(
    val loading: Boolean,
    val error: String?,
    val user: User?
)
```

This allows contradictory combinations.

For example:

``` text
loading = true
error != null
user != null
```

Is that valid?

Maybe.

Maybe not.

The state model should make invalid combinations difficult to represent.

------------------------------------------------------------------------

## Sealed state model

For mutually exclusive screen states, a sealed hierarchy can be clearer:

``` kotlin
sealed interface UserScreenState {

    data object Loading : UserScreenState

    data class Content(
        val user: User
    ) : UserScreenState

    data class Error(
        val message: String
    ) : UserScreenState
}
```

Now the screen is one of:

``` text
Loading
Content
Error
```

rather than an arbitrary combination of flags.

------------------------------------------------------------------------

## Composite state

Real applications often need more than three states.

For example:

``` kotlin
data class UserState(
    val screen: UserScreenState = UserScreenState.Loading,
    val isRefreshing: Boolean = false,
    val selectedTab: Int = 0
)
```

This gives the state model flexibility while keeping major states
explicit.

------------------------------------------------------------------------

## State should describe UI reality

Avoid storing data simply because it exists somewhere in the
application.

Ask:

> Does the UI need this value to render or make a UI decision?

If not, it may not belong in UI state.

For example, an internal repository cache key usually does not belong
in:

``` kotlin
UserState
```

unless the UI actually depends on it.

------------------------------------------------------------------------

# 9. Modeling User Intent

Intents should be meaningful.

For a product screen:

``` kotlin
sealed interface ProductIntent {

    data object ScreenOpened : ProductIntent

    data object RetryClicked : ProductIntent

    data class QuantityChanged(
        val quantity: Int
    ) : ProductIntent

    data object AddToCartClicked : ProductIntent
}
```

This gives the architecture a clear vocabulary.

The UI says:

``` kotlin
onIntent(ProductIntent.AddToCartClicked)
```

rather than directly calling:

``` kotlin
viewModel.addProductToCart()
```

The distinction becomes valuable when the screen grows.

------------------------------------------------------------------------

## Intent naming

Prefer names that describe an event:

``` text
LoginClicked
RetryClicked
SearchChanged
ProductSelected
ScreenOpened
```

Avoid overly technical names:

``` text
ExecuteLoginRequest
InvokeRepository
StartRetrofitCall
```

The Intent belongs to the **interaction boundary**, not the
implementation layer.

# 10. Reducers and Pure State Transitions

A reducer is easiest to understand as a pure function.

``` text
State + Event
      │
      ▼
   Reducer
      │
      ▼
 New State
```

For example:

``` kotlin
data class CartState(
    val itemCount: Int = 0,
    val total: Double = 0.0
)

sealed interface CartResult {

    data class ItemAdded(
        val price: Double
    ) : CartResult

    data class ItemRemoved(
        val price: Double
    ) : CartResult
}
```

Reducer:

``` kotlin
fun reduce(
    state: CartState,
    result: CartResult
): CartState {
    return when (result) {

        is CartResult.ItemAdded ->
            state.copy(
                itemCount = state.itemCount + 1,
                total = state.total + result.price
            )

        is CartResult.ItemRemoved ->
            state.copy(
                itemCount = (state.itemCount - 1).coerceAtLeast(0),
                total = (state.total - result.price).coerceAtLeast(0.0)
            )
    }
}
```

Notice what the reducer does **not** do.

It does not:

``` text
call an API
write to a database
launch a coroutine
navigate
show a Toast
read Android Context
```

Its job is state transformation.

That separation is one of the strongest properties of MVI.

# 11. Side Effects and Effects

Not every operation should become part of persistent UI state.

Consider:

``` text
Show Snackbar
Navigate to another screen
Open browser
Share content
Request permission
Trigger analytics
```

These are often **one-time effects**.

A common MVI model therefore separates:

``` text
State
```

from:

``` text
Effect
```

For example:

``` kotlin
sealed interface LoginEffect {

    data class ShowError(
        val message: String
    ) : LoginEffect

    data object NavigateToHome : LoginEffect
}
```

Then:

``` text
State
→ describes what the UI currently is

Effect
→ describes something the UI should do
```

This distinction is important.

------------------------------------------------------------------------

## State vs Effect

### State

State can be observed repeatedly.

``` text
isLoading = true
```

If the UI is recreated, it should still know:

``` text
I am loading.
```

### Effect

An effect is usually consumed once.

``` text
NavigateToHome
```

We do not want a configuration change to repeatedly navigate to Home.

------------------------------------------------------------------------

## A useful mental model

``` text
               ┌──────────────┐
               │    Intent    │
               └──────┬───────┘
                      │
                      ▼
               ┌──────────────┐
               │ MVI Logic    │
               └──────┬───────┘
                      │
             ┌────────┴─────────┐
             ▼                  ▼
       ┌──────────┐       ┌──────────┐
       │  State   │       │  Effect  │
       └────┬─────┘       └────┬─────┘
            │                  │
            ▼                  ▼
           UI              UI Action
```

# 12. MVI in KMP

MVI becomes especially interesting in **Kotlin Multiplatform**.

The goal is not necessarily to share every line of UI code.

Instead, we can share:

-   state definitions,
-   intents,
-   reducers,
-   business rules,
-   use cases,
-   repository contracts,
-   networking abstractions,
-   data transformation,
-   validation,
-   domain logic.

A simplified architecture could look like:

``` text
                    sharedMain
                       │
          ┌────────────┼────────────┐
          │            │            │
       Intent         State       Reducer
          │            │            │
          └────────────┼────────────┘
                       │
                    ViewModel
                       │
                 Use Case / Domain
                       │
                   Repository
                  ┌────┴────┐
                  │         │
               Remote     Local
```

Android and iOS can then consume the same state model.

------------------------------------------------------------------------

## Android

``` text
Compose UI
    ↓
Android ViewModel / Store
    ↓
Shared MVI logic
```

## iOS

``` text
SwiftUI
   ↓
Observable bridge
   ↓
Shared MVI logic
```

The exact integration can vary.

The important architectural boundary is:

``` text
Platform UI
      ↓
Shared state + logic
      ↓
Shared domain/data
```

# 13. Recommended Package Structure

For a KMP project, an MVI feature can be organized like this:

``` text
shared/
└── src/
    └── commonMain/
        └── kotlin/
            └── feature/
                └── login/
                    ├── LoginIntent.kt
                    ├── LoginState.kt
                    ├── LoginEffect.kt
                    ├── LoginResult.kt
                    ├── LoginReducer.kt
                    └── LoginViewModel.kt
```

For a larger application:

``` text
shared/
└── src/
    └── commonMain/
        └── kotlin/
            ├── core/
            │   ├── network/
            │   ├── database/
            │   └── common/
            │
            ├── domain/
            │   ├── model/
            │   ├── repository/
            │   └── usecase/
            │
            └── feature/
                ├── login/
                ├── home/
                ├── profile/
                └── cart/
```

A feature-oriented structure makes it easier to locate the complete
state flow of a feature.

# 14. Common MVI Mistakes

MVI is powerful, but it is easy to over-engineer.

## Mistake 1 --- Creating an Intent for everything

Not every internal function needs an Intent.

Bad:

``` kotlin
LoadRepository
MapResponse
UpdateInternalCache
```

These are implementation details.

Better:

``` kotlin
ScreenOpened
RetryClicked
Refresh
```

------------------------------------------------------------------------

## Mistake 2 --- Putting business logic inside the reducer

A reducer should primarily transform state.

Avoid:

``` kotlin
fun reduce(state: State): State {
    repository.load()
    return ...
}
```

Prefer:

``` text
Intent
   ↓
Use Case
   ↓
Result
   ↓
Reducer
   ↓
State
```

------------------------------------------------------------------------

## Mistake 3 --- Turning every value into state

Do not blindly put:

``` text
repository objects
API clients
platform contexts
database connections
```

into UI state.

State should represent the UI's meaningful observable condition.

------------------------------------------------------------------------

## Mistake 4 --- Mixing State and Effect

Avoid using:

``` kotlin
showSnackbar = true
```

as a permanent state flag when the real requirement is:

``` text
show Snackbar once
```

Use an effect/event mechanism where appropriate.

------------------------------------------------------------------------

## Mistake 5 --- Creating too many layers

MVI can become unnecessarily complicated:

``` text
Intent
→ Action
→ Command
→ Processor
→ Handler
→ Result
→ Reducer
→ State
```

Architecture should reduce complexity, not rename it.

For many features, this is enough:

``` text
Intent
   ↓
Logic
   ↓
Result
   ↓
Reducer
   ↓
State
```

------------------------------------------------------------------------

## Mistake 6 --- Treating MVI as a framework

MVI is primarily an architectural approach.

You do not need a large library to understand or implement it.

A few Kotlin types can already express the core concepts:

``` kotlin
sealed interface Intent
data class State(...)
sealed interface Effect
fun reduce(...)
```

Frameworks can provide infrastructure, but the architectural principles
should remain understandable without them.

------------------------------------------------------------------------

# 15. Part 1 Summary

MVI is fundamentally about **predictable state management**.

The most important concepts from Part 1 are:

### 1. Intent

Represents what happened.

``` text
User → Intent
```

### 2. State

Represents what the UI should display.

``` text
State → UI
```

### 3. Reducer

Transforms one state into another.

``` text
Old State + Result → New State
```

### 4. Unidirectional flow

The data should move predictably:

``` text
UI
 ↓
Intent
 ↓
Logic
 ↓
Result
 ↓
Reducer
 ↓
State
 ↓
UI
```

### 5. Effects

One-time actions should generally be modeled separately from persistent
UI state.

``` text
State  → what the UI is
Effect → what the UI should do
```

### 6. KMP advantage

MVI can provide a strong shared architecture for:

``` text
Android + iOS + shared business logic
```

while allowing each platform to retain its native UI technology.

                  ▼
             ┌──────────┐

          │                │

The implementation will focus on **real Kotlin code**, immutable state,

> **MVI is not about adding more classes. It is about making state

Once that mental model is clear, implementing MVI in Kotlin
Multiplatform becomes much easier.
