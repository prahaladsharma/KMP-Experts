# 1. What Is an Intent?

In MVI, an **Intent represents an input entering the state-management
system**.

That input may come from:

-   a user interaction,
-   a lifecycle event,
-   a system event,
-   a retry action,
-   a timer,
-   another component,
-   or an application-level trigger.

For example:

``` kotlin
sealed interface LoginIntent {

    data object ScreenOpened : LoginIntent

    data class EmailChanged(
        val value: String
    ) : LoginIntent

    data class PasswordChanged(
        val value: String
    ) : LoginIntent

    data object LoginClicked : LoginIntent

    data object RetryClicked : LoginIntent
}
```

These intents describe **what happened**.

They do not describe the implementation details of what the application
should do next.

That distinction is fundamental.

------------------------------------------------------------------------

## A simple mental model

Think of an MVI feature as a state machine.

``` text
                ┌───────────────┐
                │     Intent    │
                └───────┬───────┘
                        │
                        ▼
                ┌───────────────┐
                │ Feature Logic │
                └───────┬───────┘
                        │
                        ▼
                ┌───────────────┐
                │     State     │
                └───────┬───────┘
                        │
                        ▼
                     UI
```

Intent is therefore the **input boundary** of the feature.

------------------------------------------------------------------------

# 2. Intent Is an Input, Not an Instruction

One of the easiest mistakes in MVI is treating Intent as a command
containing implementation details.

Consider:

``` kotlin
data object CallLoginApi : LoginIntent
```

This is technically possible, but it is not an ideal intent.

Why?

Because the UI should not need to know that login is implemented through
an API.

The UI knows:

> "The user pressed Login."

The UI does not need to know:

> "The next operation should be an HTTP request."

A better intent is:

``` kotlin
data object LoginClicked : LoginIntent
```

The feature logic decides what `LoginClicked` means.

``` text
LoginClicked
     │
     ▼
Validate fields
     │
     ├── invalid → update State
     │
     └── valid
          │
          ▼
      Login Use Case
          │
          ▼
       API call
```

This keeps the UI independent of the implementation.

------------------------------------------------------------------------

# 3. Intent as a User Interaction Contract

Intent creates a contract between the UI and the feature logic.

For example:

``` kotlin
sealed interface ProductIntent {

    data object ScreenOpened : ProductIntent

    data class ProductSelected(
        val productId: String
    ) : ProductIntent

    data object AddToCartClicked : ProductIntent

    data object RetryClicked : ProductIntent
}
```

The UI can communicate using this vocabulary:

``` text
ScreenOpened
ProductSelected(productId)
AddToCartClicked
RetryClicked
```

The feature logic can then decide how to handle each one.

This creates a useful separation:

``` text
┌────────────────────┐
│        UI          │
│                    │
│ "Product selected" │
└─────────┬──────────┘
          │
          │ Intent
          ▼
┌────────────────────┐
│   Feature Logic    │
│                    │
│ "What should this  │
│  event cause?"     │
└────────────────────┘
```

The UI communicates **facts and interactions**.

The feature logic determines **behavior**.

------------------------------------------------------------------------

# 4. Why Sealed Interfaces Work Well

Kotlin's `sealed interface` is particularly useful for representing a
finite set of intents.

``` kotlin
sealed interface HomeIntent {

    data object ScreenOpened : HomeIntent

    data object Refresh : HomeIntent

    data object Retry : HomeIntent

    data class ItemSelected(
        val id: String
    ) : HomeIntent
}
```

Now the compiler knows the known implementations.

This works naturally with `when`:

``` kotlin
fun handle(intent: HomeIntent) {
    when (intent) {
        HomeIntent.ScreenOpened -> load()
        HomeIntent.Refresh -> refresh()
        HomeIntent.Retry -> retry()
        is HomeIntent.ItemSelected -> select(intent.id)
    }
}
```

The compiler can help detect missing branches.

------------------------------------------------------------------------

## Why not a large enum?

An enum is useful when every event has no additional data:

``` kotlin
enum class SimpleIntent {
    Refresh,
    Retry,
    Logout
}
```

But real applications usually need data:

``` text
SearchChanged("kotlin")
ProductSelected("P123")
QuantityChanged(4)
PageRequested(3)
```

A sealed hierarchy supports both:

``` kotlin
data object Refresh : Intent

data class SearchChanged(
    val query: String
) : Intent
```

That makes it more expressive than a simple enum.

# 5. Designing a Login Intent

Let's build a realistic login feature.

``` kotlin
sealed interface LoginIntent {

    data object ScreenOpened : LoginIntent

    data class EmailChanged(
        val value: String
    ) : LoginIntent

    data class PasswordChanged(
        val value: String
    ) : LoginIntent

    data object LoginClicked : LoginIntent

    data object RetryClicked : LoginIntent

    data object PasswordVisibilityToggled : LoginIntent
}
```

The intent hierarchy describes the interaction surface of the screen.

------------------------------------------------------------------------

## Mapping interactions

  UI interaction                Intent
  ----------------------------- -----------------------------
  Screen becomes active         `ScreenOpened`
  Email changes                 `EmailChanged`
  Password changes              `PasswordChanged`
  Login button pressed          `LoginClicked`
  Retry pressed                 `RetryClicked`
  Password visibility changed   `PasswordVisibilityToggled`

This mapping should be easy to understand.

If a developer sees:

``` kotlin
LoginIntent.EmailChanged(value)
```

they should immediately understand where it came from.

# 6. Events vs Commands

Terminology can become confusing.

Some MVI implementations call these:

``` text
Intent
Action
Event
Message
Command
```

They are not always equivalent.

A useful distinction is:

### Event

Describes something that happened.

``` text
LoginClicked
EmailChanged
ProductSelected
```

### Command

Describes something the system should perform.

``` text
CallLoginApi
NavigateToHome
PersistSession
```

For MVI input, event-oriented names are often cleaner:

``` kotlin
LoginClicked
```

rather than:

``` kotlin
ExecuteLogin
```

The application logic can convert the event into commands or side
effects internally.

``` text
UI Event
   ↓
Intent
   ↓
Decision
   ↓
Command / Side Effect
```

This keeps the UI boundary clean.

# 7. Naming Intents

Intent names should be:

-   clear,
-   short,
-   domain-oriented,
-   independent of implementation,
-   easy to read in logs.

Good examples:

``` kotlin
ScreenOpened
RetryClicked
RefreshRequested
SearchChanged
ItemSelected
QuantityChanged
SubmitClicked
```

Less useful examples:

``` kotlin
ExecuteRepositoryRequest
InvokeGetUserApi
PerformNetworkOperation
CallUseCase
```

------------------------------------------------------------------------

## Clicked vs Requested

Both can be valid.

For UI-specific interactions:

``` kotlin
SubmitClicked
```

is explicit.

For more general application input:

``` kotlin
RefreshRequested
```

can be better.

The important point is consistency.

Do not mix arbitrary naming conventions across every feature.

------------------------------------------------------------------------

# 8. Intents With Data

Most real intents carry information.

For example:

``` kotlin
data class SearchChanged(
    val query: String
) : SearchIntent
```

Another example:

``` kotlin
data class ProductSelected(
    val productId: String
) : ProductIntent
```

Another:

``` kotlin
data class QuantityChanged(
    val quantity: Int
) : CartIntent
```

The payload should contain the information necessary to interpret the
interaction.

------------------------------------------------------------------------

## Avoid unnecessary payloads

Suppose we have:

``` kotlin
data class ProductSelected(
    val productId: String,
    val productName: String,
    val productPrice: Double,
    val imageUrl: String
)
```

If the feature only needs:

``` text
productId
```

then passing the entire product object creates unnecessary coupling.

Prefer:

``` kotlin
data class ProductSelected(
    val productId: String
) : ProductIntent
```

The feature can load the rest of the information when required.

------------------------------------------------------------------------

# 9. Intent Granularity

A common architectural question is:

> How many intents should a screen have?

There is no universal number.

The right question is:

> Does each intent represent a meaningful input to the feature?

For a search screen:

``` kotlin
sealed interface SearchIntent {

    data class QueryChanged(
        val query: String
    ) : SearchIntent

    data object SearchSubmitted : SearchIntent

    data object ClearClicked : SearchIntent

    data object RetryClicked : SearchIntent

    data object LoadNextPage : SearchIntent
}
```

This is reasonable.

But creating intents for implementation details is unnecessary:

``` kotlin
StartCoroutine
MapResponse
UpdateCache
EmitLoading
```

Those are internal operations.

------------------------------------------------------------------------

## Too coarse

This is too vague:

``` kotlin
data class UserAction(
    val type: String,
    val value: Any?
) : Intent
```

Now the compiler cannot help us.

We lose type safety.

------------------------------------------------------------------------

## Too fragmented

This can also become excessive:

``` text
EmailTextChanged
EmailFocusChanged
EmailCursorChanged
EmailKeyboardOpened
EmailKeyboardClosed
```

unless the feature genuinely needs those events.

The goal is not maximum granularity.

The goal is **meaningful granularity**.

------------------------------------------------------------------------

# 10. From UI Action to Intent

Consider Jetpack Compose.

A login screen might receive:

``` kotlin
@Composable
fun LoginScreen(
    state: LoginState,
    onIntent: (LoginIntent) -> Unit
) {
    // UI
}
```

When the user changes the email:

``` kotlin
TextField(
    value = state.email,
    onValueChange = {
        onIntent(
            LoginIntent.EmailChanged(it)
        )
    }
)
```

When the user taps Login:

``` kotlin
Button(
    onClick = {
        onIntent(
            LoginIntent.LoginClicked
        )
    }
) {
    Text("Login")
}
```

The UI does not directly call:

``` kotlin
repository.login()
```

or:

``` kotlin
viewModel.callApi()
```

It sends an Intent.

------------------------------------------------------------------------

## The complete flow

``` mermaid
sequenceDiagram
    participant User
    participant UI
    participant MVI
    participant Repository

    User->>UI: Tap Login
    UI->>MVI: LoginClicked
    MVI->>MVI: Validate state
    MVI->>Repository: Login request
    Repository-->>MVI: Result
    MVI->>MVI: Reduce state
    MVI-->>UI: New State
    UI-->>User: Render result
```

The UI remains focused on rendering and interaction.

# 11. Processing Intents

A simple processor can look like:

``` kotlin
class LoginViewModel(
    private val loginUseCase: LoginUseCase
) {

    fun onIntent(intent: LoginIntent) {
        when (intent) {

            LoginIntent.ScreenOpened -> {
                // Load initial data
            }

            is LoginIntent.EmailChanged -> {
                // Update email state
            }

            is LoginIntent.PasswordChanged -> {
                // Update password state
            }

            LoginIntent.LoginClicked -> {
                // Validate and perform login
            }

            LoginIntent.RetryClicked -> {
                // Retry
            }

            LoginIntent.PasswordVisibilityToggled -> {
                // Update visibility
            }
        }
    }
}
```

This is only the beginning.

A production implementation normally separates:

``` text
Intent handling
Business operation
Result handling
State reduction
Effect emission
```

That separation becomes important as the feature grows.

------------------------------------------------------------------------

# 12. Intent and State Are Different

Intent and State are related, but they are not the same thing.

Consider:

``` text
Intent:
LoginClicked
```

This is an event.

The resulting state might be:

``` text
State:
isLoading = true
```

After the API succeeds:

``` text
State:
isLoading = false
isLoggedIn = true
```

The Intent is temporary.

The State represents the current condition.

------------------------------------------------------------------------

## Think in time

``` text
t0
State:
isLoading = false

        │
        │ LoginClicked
        ▼

t1
State:
isLoading = true

        │
        │ LoginSuccess
        ▼

t2
State:
isLoading = false
isLoggedIn = true
```

`LoginClicked` does not become part of the state.

It causes a transition.

This distinction becomes extremely important when designing state
models.

------------------------------------------------------------------------

# 13. Intent Does Not Mean Side Effect

An Intent can cause a side effect.

It should not itself perform the side effect.

Avoid:

``` kotlin
data object LoginClicked : LoginIntent {

    suspend fun execute() {
        // API call
    }
}
```

An Intent should be data.

For example:

``` kotlin
data object LoginClicked : LoginIntent
```

Then the processor handles it:

``` kotlin
private suspend fun handleLoginClicked() {
    val result = loginUseCase.execute(...)
}
```

This makes the Intent:

-   immutable,
-   serializable in principle,
-   easy to log,
-   easy to test,
-   independent of platform APIs.

------------------------------------------------------------------------

# 14. Handling Asynchronous Intents

Many intents trigger asynchronous work.

For example:

``` text
Refresh
Login
Load Profile
Search
Load Next Page
```

The general flow is:

``` text
Intent
  ↓
Start operation
  ↓
Loading state
  ↓
Suspend operation
  ↓
Result
  ↓
Reduce
  ↓
Final state
```

Example:

``` kotlin
private fun handleLogin() {
    viewModelScope.launch {

        reduce {
            it.copy(
                isLoading = true,
                errorMessage = null
            )
        }

        val result = loginUseCase.execute(
            email = state.value.email,
            password = state.value.password
        )

        when (result) {
            is Result.Success -> {
                reduce {
                    it.copy(
                        isLoading = false,
                        isLoggedIn = true
                    )
                }
            }

            is Result.Failure -> {
                reduce {
                    it.copy(
                        isLoading = false,
                        errorMessage = result.message
                    )
                }
            }
        }
    }
}
```

The exact implementation can differ, but the architectural flow remains:

``` text
Intent → Async operation → Result → State
```

# 15. Duplicate Intents and Concurrency

Intent processing becomes more interesting when users can trigger the
same event multiple times.

Consider:

``` text
User taps Login
User taps Login again
User taps Login again
```

Three intents may arrive:

``` text
LoginClicked
LoginClicked
LoginClicked
```

Should the application execute three network calls?

Usually not.

The architecture needs an explicit policy.

------------------------------------------------------------------------

## Option 1 --- Disable the UI

The state can expose:

``` kotlin
val isLoading: Boolean
```

and the UI can prevent another submission:

``` kotlin
Button(
    enabled = !state.isLoading,
    onClick = {
        onIntent(LoginIntent.LoginClicked)
    }
)
```

This is useful, but it should not be the only protection.

------------------------------------------------------------------------

## Option 2 --- Ignore duplicate work

The processor can check:

``` kotlin
if (state.value.isLoading) {
    return
}
```

This prevents another login operation.

------------------------------------------------------------------------

## Option 3 --- Cancel previous work

For search, cancellation can be desirable.

``` text
SearchChanged("k")
SearchChanged("ko")
SearchChanged("kot")
SearchChanged("kotlin")
```

You do not necessarily want five network requests.

Instead:

``` text
k       → cancelled
ko      → cancelled
kot     → cancelled
kotlin  → executed
```

This is where coroutine operators such as `debounce`,
`distinctUntilChanged`, and `flatMapLatest` can become useful.

------------------------------------------------------------------------

# 16. Intent Validation

Intent validation depends on where the validation belongs.

Suppose:

``` kotlin
data class QuantityChanged(
    val quantity: Int
) : CartIntent
```

You may receive:

``` text
quantity = -10
```

Should the Intent reject it?

Usually, the input model can be kept simple:

``` kotlin
QuantityChanged(-10)
```

and feature logic determines the valid state.

For example:

``` kotlin
private fun handle(
    intent: CartIntent
) {
    when (intent) {
        is CartIntent.QuantityChanged -> {
            val quantity = intent.quantity.coerceAtLeast(1)

            updateState {
                it.copy(
                    quantity = quantity
                )
            }
        }
    }
}
```

------------------------------------------------------------------------

## Validation layers

A useful architecture separates:

### UI-level validation

Useful for immediate interaction behavior.

``` text
Empty field
Invalid format
```

### Domain validation

Business rules belong here.

``` text
Quantity cannot exceed inventory
Account cannot transfer more than available balance
```

### Data validation

Data-source-specific rules belong here.

``` text
Malformed API response
Invalid database record
```

Intent should not become a dumping ground for every validation rule.

------------------------------------------------------------------------

# 17. Intents for Search

Search is a classic example where Intent modeling matters.

``` kotlin
sealed interface SearchIntent {

    data class QueryChanged(
        val query: String
    ) : SearchIntent

    data object SearchSubmitted : SearchIntent

    data object ClearClicked : SearchIntent

    data object RetryClicked : SearchIntent
}
```

The user types:

``` text
K
Ko
Kot
Kotl
Kotlin
```

The UI emits:

``` text
QueryChanged("K")
QueryChanged("Ko")
QueryChanged("Kot")
QueryChanged("Kotl")
QueryChanged("Kotlin")
```

The feature may then apply:

``` text
debounce
+
distinctUntilChanged
+
flatMapLatest
```

Conceptually:

``` mermaid
flowchart LR
    A[QueryChanged] --> B[Debounce]
    B --> C[Distinct Query]
    C --> D[Cancel Previous Search]
    D --> E[Repository]
    E --> F[Search Result]
    F --> G[Reducer]
    G --> H[State]
```

The Intent remains simple.

The asynchronous processing strategy belongs to the feature logic.

sealed interface RegistrationIntent {

# 19. Intents for Lists and Pagination

Lists commonly need intents such as:

``` kotlin
sealed interface ProductListIntent {

    data object ScreenOpened : ProductListIntent

    data object Refresh : ProductListIntent

    data object LoadNextPage : ProductListIntent

    data object Retry : ProductListIntent

    data class ProductSelected(
        val id: String
    ) : ProductListIntent
}
```

The important thing is that pagination should not be treated as a random
UI callback.

It is a meaningful input to the feature.

The state might contain:

``` kotlin
data class ProductListState(
    val items: List<Product> = emptyList(),
    val isInitialLoading: Boolean = false,
    val isRefreshing: Boolean = false,
    val isLoadingNextPage: Boolean = false,
    val hasNextPage: Boolean = true,
    val errorMessage: String? = null
)
```

Now each intent can produce a predictable transition.

# 20. Intents for Refresh

Refresh often looks simple:

``` kotlin
data object Refresh : ProductListIntent
```

But it can have different semantics from initial loading.

Initial loading:

``` text
ScreenOpened
   ↓
Empty UI
   ↓
Loading
   ↓
Content
```

Refresh:

``` text
Existing Content
   ↓
Refresh
   ↓
Content + Refresh indicator
   ↓
Updated Content
```

This distinction matters.

Do not automatically replace the entire state with:

``` text
Loading
```

during refresh if the desired UX is to keep the existing content
visible.

Intent design gives the feature a clear input:

``` text
Refresh
```

State design determines the correct user experience.

------------------------------------------------------------------------

# 21. Intents for Navigation

Navigation can be modeled carefully.

For example:

``` kotlin
data class ProductSelected(
    val productId: String
) : ProductIntent
```

The feature can emit:

``` kotlin
sealed interface ProductEffect {

    data class NavigateToDetails(
        val productId: String
    ) : ProductEffect
}
```

Flow:

``` text
ProductSelected(id)
        ↓
Feature Logic
        ↓
NavigateToDetails(id)
        ↓
Platform UI
```

This is preferable to putting a navigation controller inside shared
business logic.

The shared layer describes:

> "The user selected product X."

The platform layer decides:

> "How should navigation happen on this platform?"

# 22. Intents in Kotlin Multiplatform

Intent types are excellent candidates for `commonMain`.

For example:

``` text
shared/
└── src/
    └── commonMain/
        └── kotlin/
            └── feature/
                └── profile/
                    └── ProfileIntent.kt
```

``` kotlin
sealed interface ProfileIntent {

    data object ScreenOpened : ProfileIntent

    data object Refresh : ProfileIntent

    data object EditClicked : ProfileIntent

    data object LogoutClicked : ProfileIntent
}
```

Both Android and iOS can produce these same intents.

``` text
             Android UI
                 │
                 │ ProfileIntent
                 ▼
          ┌───────────────┐
          │ Shared KMP    │
          │ Feature Logic │
          └───────┬───────┘
                  ▲
                  │ ProfileIntent
                  │
              iOS UI
```

This is one of the cleanest benefits of modeling interaction as typed
data.

# 23. Android Compose Example

A Compose UI can expose only the intent boundary.

``` kotlin
@Composable
fun ProfileScreen(
    state: ProfileState,
    onIntent: (ProfileIntent) -> Unit
) {
    Column {

        Text(
            text = state.name
        )

        Button(
            onClick = {
                onIntent(
                    ProfileIntent.Refresh

            }

        }

        Button(
            onClick = {
                onIntent(
                    ProfileIntent.EditClicked
                )
            }

            Text("Edit")
        }
    }
}
```

The UI does not need to know:

``` text
Repository
Use Case
Retrofit
SQL
Coroutine
HTTP status
```

It only knows the Intent contract.

------------------------------------------------------------------------

## ViewModel boundary

``` kotlin
class ProfileViewModel(
    private val store: ProfileStore
) {

    fun onIntent(intent: ProfileIntent) {
        store.accept(intent)
    }
}
```

This is intentionally simple.

The more complex processing can remain inside the shared feature layer.

# 24. SwiftUI and KMP Conceptual Flow

``` text

   ↓

   ↓
Shared KMP Store
   ↓
Shared State
   ↓
SwiftUI observes state
```

The syntax for bridging Kotlin state into Swift will depend on the

``` text

    └── emits ProfileIntent

    └── emits ProfileIntent

             ↓

       Shared Feature

             ↓

       Shared State
```

MVI therefore provides a useful boundary between platform UI and shared
application behavior.

# 25. Testing Intents

One of the biggest benefits of typed Intent is testability.

Consider:

``` kotlin
sealed interface CounterIntent {

    data object Increment : CounterIntent

    data object Decrement : CounterIntent

    data object Reset : CounterIntent
}
```

We can test:

``` text
Initial state:
count = 0

Intent:
Increment

Expected:
count = 1
```

Another:

``` text
Initial state:
count = 5

Intent:
Decrement

Expected:
count = 4
```

------------------------------------------------------------------------

## State transition test

A reducer test might look conceptually like:

``` kotlin
@Test
fun increment_shouldIncreaseCount() {

    val state = CounterState(count = 4)

    val result = reduce(
        state,
        CounterIntent.Increment
    )

    assertEquals(
        5,
        result.count
    )
}
```

The test is small because the Intent is small.

------------------------------------------------------------------------

## Intent handling test

For asynchronous features:

``` text
Given:
LoginState(email, password)

When:
LoginClicked

Then:
Loading state is emitted

And:
Login use case is invoked

And:
Success produces logged-in state
```

This is much easier to reason about than testing a UI callback chain
containing multiple hidden operations.

# 26. Common Intent Design Mistakes

## Mistake 1 --- Passing View objects

Avoid:

``` kotlin
data class ButtonClicked(
    val button: Button
) : Intent
```

The shared layer should not depend on platform UI objects.

Prefer:

``` kotlin
data object LoginClicked : Intent
```

------------------------------------------------------------------------

## Mistake 2 --- Passing Context

Avoid:

``` kotlin
data class DownloadClicked(
    val context: Context
) : Intent
```

`Context` is an Android platform concern.

Prefer:

``` kotlin
data object DownloadClicked : Intent
```

and keep platform-specific behavior behind an appropriate abstraction.

------------------------------------------------------------------------

## Mistake 3 --- Passing huge objects

Avoid:

``` kotlin
data class ItemSelected(
    val item: CompleteItemWithEverything
) : Intent
```

when all you need is:

``` kotlin
data class ItemSelected(
    val id: String
) : Intent
```

Smaller intent payloads reduce coupling.

------------------------------------------------------------------------

## Mistake 4 --- Intent performing work

Avoid:

``` kotlin
data object Refresh : Intent {
    suspend fun execute() { ... }
}
```

Intent should remain data.

------------------------------------------------------------------------

## Mistake 5 --- Generic `Any`

Avoid:

``` kotlin
data class UserAction(
    val action: String,
    val payload: Any?
)
```

This removes type safety.

Prefer:

``` kotlin
sealed interface UserIntent {
    data object Refresh : UserIntent

    data class UserSelected(
        val id: String
    ) : UserIntent
}
```

------------------------------------------------------------------------

## Mistake 6 --- Using state as an event

Avoid:

``` kotlin
data class State(
    val loginClicked: Boolean
)
```

A click is an event, not persistent state.

Use:

``` kotlin
data object LoginClicked : LoginIntent
```

and let the event cause a state transition.

------------------------------------------------------------------------

## Mistake 7 --- Exposing implementation details

Avoid:

``` kotlin
data object CallRetrofitLoginApi : LoginIntent
```

Prefer:

``` kotlin
data object LoginClicked : LoginIntent
```

The implementation can change from:

``` text
Retrofit
```

to:

``` text
Ktor
```

without changing the UI contract.

------------------------------------------------------------------------

# 27. A Practical Intent Checklist

Before adding an Intent, ask:

### Does it describe an input?

``` text
Yes → Good candidate
No  → It may belong inside the implementation
```

### Is it meaningful to the feature?

``` text
ProductSelected → Yes
MapResponse → No
```

### Does it contain only necessary data?

``` text
ProductSelected(productId)
```

is usually better than:

``` text
ProductSelected(entire product graph)
```

### Is it platform-independent?

Avoid:

``` text
Context
View
Activity
UIViewController
NavController
```

in shared Intent types.

### Can the Intent be tested easily?

A good Intent should be simple data.

### Is it named after the interaction?

Prefer:

``` text
Refresh
RetryClicked
ItemSelected
```

over:

``` text
ExecuteRepository
```

------------------------------------------------------------------------

## Intent Design Formula

A useful formula is:

``` text
Intent
=
Meaningful Input
+
Small Typed Payload
+
No Side Effect
+
No Platform Dependency
```

For example:

``` kotlin
data class SearchChanged(
    val query: String
) : SearchIntent
```

This is:

-   meaningful,
-   typed,
-   small,
-   platform-independent,
-   side-effect free.

# 28. Part 2 Summary

Intent is the **input boundary of an MVI feature**.

The most important principles are:

### 1. Intent represents what happened

``` text
LoginClicked
ProductSelected
SearchChanged
Refresh
```

### 2. Intent should not contain implementation logic

Avoid:

``` text
CallApi
ExecuteRepository
StartRetrofit
```

### 3. Use typed models

Prefer:

``` kotlin
sealed interface Intent
```

over:

``` kotlin
String + Any?
```

### 4. Keep payloads small

Pass the information required to interpret the event.

``` kotlin
ProductSelected(productId)
```

rather than an unnecessarily large object graph.

### 5. Keep Intent platform-independent

This is particularly important in KMP.

``` text
commonMain
   ↓
Intent
   ↓
Shared Feature Logic
```

### 6. Intent is different from State

``` text
Intent → temporary input
State  → current UI condition
```

### 7. Intent is different from Effect

``` text
Intent → what happened
Effect → what the UI should do once
```

### 8. Intent enables predictable testing

``` text
Given State
   +
Intent
   ↓
Expected State / Effect
```

  ↓

built.

## Key Takeaway

> **An Intent should be a small, typed, platform-independent description
> of an input---not a command that knows how the application works.**

When Intents are modeled well, the rest of the MVI architecture becomes
easier to reason about, easier to test, and easier to share across
Android and iOS.
