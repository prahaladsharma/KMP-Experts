# 1. What Is State in MVI?

In MVI, **State represents the current condition of the feature as
required by the UI**.

If the UI asks:

> "What should I render right now?"

the answer should come from State.

For example:

``` kotlin
data class LoginState(
    val email: String = "",
    val password: String = "",
    val isLoading: Boolean = false,
    val errorMessage: String? = null,
    val isLoggedIn: Boolean = false
)
```

The UI can use this state to determine:

``` text
Email field value
Password field value
Loading indicator
Error message
Login success
```

The state is therefore not simply a collection of variables.

It is a **model of the UI's current reality**.

------------------------------------------------------------------------

# 2. State Is the UI's Source of Truth

A well-designed MVI screen follows a simple rule:

> **The UI renders State; it does not independently invent its own
> application state.**

Consider a login button.

Instead of maintaining:

``` kotlin
var isLoading by remember { mutableStateOf(false) }
```

while the ViewModel separately maintains another loading value, prefer a
single authoritative state:

``` kotlin
data class LoginState(
    val isLoading: Boolean = false
)
```

Then:

``` kotlin
Button(
    enabled = !state.isLoading,
    onClick = {
        onIntent(LoginIntent.LoginClicked)
    }
)
```

The UI renders:

``` text
State → UI
```

rather than creating another competing source of truth.

------------------------------------------------------------------------

## Single source of truth

``` mermaid
flowchart LR
    I[Intent] --> L[Feature Logic]
    L --> R[Reducer]
    R --> S[State]
    S --> UI[UI]
    UI --> I
```

The state sits at the center of the rendering model.

------------------------------------------------------------------------

# 3. State Is Not an Event

This distinction is one of the most important concepts in MVI.

An event happens.

State remains.

For example:

``` text
LoginClicked
```

is an event.

It happens at a particular moment.

But:

``` text
isLoading = true
```

is state.

It describes the current condition.

------------------------------------------------------------------------

## Timeline

``` text
Initial
isLoading = false

        │
        │ LoginClicked
        ▼

Loading
isLoading = true

        │
        │ LoginSuccess
        ▼

Logged In
isLoading = false
isLoggedIn = true
```

The event does not need to be stored as:

``` kotlin
loginClicked = true
```

Doing that often creates confusion.

------------------------------------------------------------------------

# 4. Immutable State

MVI works particularly well with immutable state.

Instead of:

``` kotlin
state.isLoading = true
```

prefer:

``` kotlin
state = state.copy(
    isLoading = true
)
```

For example:

``` kotlin
data class ProfileState(
    val name: String = "",
    val isLoading: Boolean = false
)
```

Update:

``` kotlin
val newState = oldState.copy(
    isLoading = true
)
```

The original state remains unchanged.

------------------------------------------------------------------------

## Why immutability matters

Immutable state provides:

-   predictable transitions,
-   easier testing,
-   safer concurrency,
-   easier debugging,
-   clearer state history,
-   simpler reasoning.

Conceptually:

``` text
State A
   │
   │ transition
   ▼
State B
```

rather than:

``` text
One mutable object
   ├── changed here
   ├── changed there
   └── changed somewhere else
```

------------------------------------------------------------------------

# 5. Why Data Classes Work Well

Kotlin `data class` is a natural fit for state.

``` kotlin
data class HomeState(
    val items: List<Item> = emptyList(),
    val isLoading: Boolean = false,
    val errorMessage: String? = null
)
```

The generated `copy()` function makes immutable updates convenient:

``` kotlin
state.copy(
    isLoading = true
)
```

Equality is also useful for tests:

``` kotlin
assertEquals(
    expectedState,
    actualState
)
```

And state snapshots become easy to inspect in logs.

------------------------------------------------------------------------

# 6. Designing a Good State Model

A good state model should answer:

> What does the UI need to know to render correctly?

For a product list:

``` kotlin
data class ProductListState(
    val products: List<Product> = emptyList(),
    val isLoading: Boolean = false,
    val errorMessage: String? = null,
    val isRefreshing: Boolean = false,
    val isLoadingMore: Boolean = false
)
```

This is reasonable if all these values genuinely affect the UI.

But do not automatically copy every domain object into UI state.

------------------------------------------------------------------------

## State should be UI-oriented

Suppose the API returns:

``` kotlin
data class ProductDto(
    val id: String,
    val internalWarehouseCode: String,
    val auditToken: String,
    val name: String
)
```

The UI may only need:

``` kotlin
data class ProductUiModel(
    val id: String,
    val name: String
)
```

Then:

``` kotlin
data class ProductListState(
    val products: List<ProductUiModel> = emptyList()
)
```

This keeps UI state focused.

------------------------------------------------------------------------

# 7. Boolean Flags and Impossible States

Boolean properties are convenient.

For example:

``` kotlin
data class UserState(
    val isLoading: Boolean,
    val hasError: Boolean,
    val hasContent: Boolean
)
```

But this can produce many combinations.

For example:

``` text
isLoading = true
hasError = true
hasContent = true
```

Is that valid?

Maybe not.

As the number of Boolean flags increases, the number of possible
combinations grows rapidly.

With three Boolean flags:

``` text
2³ = 8 combinations
```

With five:

``` text
2⁵ = 32 combinations
```

Only a subset may represent valid UI states.

This is a sign that a more explicit state model may be useful.

------------------------------------------------------------------------

# 8. Sealed UI States

When states are mutually exclusive, a sealed hierarchy can model them
clearly.

``` kotlin
sealed interface ProductScreenState {

    data object Loading : ProductScreenState

    data object Empty : ProductScreenState

    data class Content(
        val products: List<ProductUiModel>
    ) : ProductScreenState

    data class Error(
        val message: String
    ) : ProductScreenState
}
```

Now the screen has a clearly defined state:

``` text
Loading
Empty
Content
Error
```

Instead of:

``` text
loading = ?
empty = ?
error = ?
content = ?
```

------------------------------------------------------------------------

## Rendering becomes explicit

``` kotlin
when (val screen = state.screen) {

    ProductScreenState.Loading -> {
        LoadingView()
    }

    ProductScreenState.Empty -> {
        EmptyView()
    }

    is ProductScreenState.Content -> {
        ProductList(screen.products)
    }

    is ProductScreenState.Error -> {
        ErrorView(screen.message)
    }
}
```

The compiler helps make the UI state model visible.

------------------------------------------------------------------------

# 9. Composite State

Not every screen can be represented by one mutually exclusive sealed
state.

A realistic screen may have:

``` text
Main content
+
refresh indicator
+
selected tab
+
search query
```

A composite state works well:

``` kotlin
data class HomeState(
    val screen: HomeScreenState = HomeScreenState.Loading,
    val searchQuery: String = "",
    val selectedTab: HomeTab = HomeTab.Home,
    val isRefreshing: Boolean = false
)
```

Where:

``` kotlin
sealed interface HomeScreenState {

    data object Loading : HomeScreenState

    data object Empty : HomeScreenState

    data class Content(
        val items: List<Item>
    ) : HomeScreenState

    data class Error(
        val message: String
    ) : HomeScreenState
}
```

This provides both:

-   explicit major screen states,
-   independent UI properties.

------------------------------------------------------------------------

# 10. State as a State Machine

A powerful way to think about MVI state is as a state machine.

Consider:

``` text
                  ┌─────────┐
                  │ Loading │
                  └────┬────┘
                       │
               success│failure
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        ┌─────────┐         ┌─────────┐
        │ Content │         │  Error  │
        └────┬────┘         └────┬────┘
             │                   │
          refresh              retry
             │                   │
             └────────┬──────────┘
                      ▼
                 ┌─────────┐
                 │ Loading │
                 └─────────┘
```

The important question becomes:

> Which transitions are valid?

For example:

``` text
Loading → Content
Loading → Error
Content → Refreshing
Error → Loading
```

The state model makes these transitions explicit.

------------------------------------------------------------------------

# 11. Loading State

Loading is more complicated than it first appears.

A screen can be loading:

-   for the first time,
-   during refresh,
-   while loading the next page,
-   while submitting a form,
-   while performing a secondary action.

These should not always be represented by one Boolean.

For example:

``` kotlin
data class ProductState(
    val screen: ProductScreenState,
    val isRefreshing: Boolean,
    val isLoadingNextPage: Boolean
)
```

This gives the UI enough information to render the right indicator.

------------------------------------------------------------------------

## Initial loading

``` text
No content
   ↓
Loading
   ↓
Content
```

A full-screen progress indicator may be appropriate.

------------------------------------------------------------------------

# 12. Content State

Content state represents usable data.

For example:

``` kotlin
data class Content(
    val products: List<ProductUiModel>
) : ProductScreenState
```

The UI can render:

``` kotlin
LazyColumn {
    items(
        items = screen.products
    ) { product ->
        ProductRow(product)
    }
}
```

The important principle is:

> Content state should contain what the UI needs to render content.

Avoid forcing the UI to reconstruct application state from raw API
responses.

------------------------------------------------------------------------

# 13. Empty State

Empty is often different from loading and error.

``` text
Loading
```

means:

> We do not know the result yet.

``` text
Empty
```

means:

> We know the result, and there is no content.

For example:

``` kotlin
data object Empty : ProductScreenState
```

The UI can then show:

``` text
No products found
```

rather than:

``` text
Loading...
```

------------------------------------------------------------------------

## Empty vs Error

These are also different.

``` text
Empty:
Request succeeded.
There is no data.

Error:
Request failed.
We do not have the expected data.
```

That distinction should remain visible in the state model.

------------------------------------------------------------------------

# 14. Error State

An error state should provide enough information for the UI.

Simple:

``` kotlin
data class Error(
    val message: String
) : ProductScreenState
```

More structured:

``` kotlin
data class Error(
    val type: ErrorType,
    val message: String
) : ProductScreenState
```

For example:

``` kotlin
enum class ErrorType {
    Network,
    Unauthorized,
    Server,
    Unknown
}
```

The UI can decide whether to display:

``` text
Retry
Login Again
Try Later
```

based on the state.

------------------------------------------------------------------------

## Avoid platform-specific errors in shared state

Avoid putting:

``` text
Android Exception
NSError
UIViewController
Context
```

into shared UI state.

Prefer a platform-neutral representation:

``` kotlin
sealed interface AppError {
    data object Network : AppError
    data object Unauthorized : AppError
    data object Server : AppError
    data object Unknown : AppError
}
```

------------------------------------------------------------------------

# 15. Refreshing vs Initial Loading

This is one of the most useful state distinctions in production
applications.

Suppose the user already has content:

``` text
Products A
Products B
Products C
```

They pull to refresh.

It is often better to keep content visible:

``` text
Products A
Products B
Products C
        ↻
   refreshing
```

rather than replacing the entire screen with:

``` text
Loading...
```

So:

``` kotlin
data class ProductListState(
    val items: List<ProductUiModel> = emptyList(),
    val isInitialLoading: Boolean = false,
    val isRefreshing: Boolean = false
)
```

allows the UI to distinguish the two situations.

------------------------------------------------------------------------

# 16. Pagination State

Pagination introduces another state dimension.

For example:

``` kotlin
data class ProductListState(
    val items: List<ProductUiModel> = emptyList(),
    val isInitialLoading: Boolean = false,
    val isRefreshing: Boolean = false,
    val isLoadingNextPage: Boolean = false,
    val hasNextPage: Boolean = true,
    val error: AppError? = null
)
```

Now the UI can display:

``` text
Initial load:
Full-screen progress

Refresh:
Pull-to-refresh indicator

Next page:
Bottom loading indicator
```

All three represent different operations.

------------------------------------------------------------------------

## Pagination transition

``` text
Page 1
  │
  │ LoadNextPage
  ▼
Page 1 + Loading
  │
  │ Success
  ▼
Page 1 + Page 2
```

State makes this process explicit.

------------------------------------------------------------------------

# 17. Form State

Forms are another area where state modeling matters.

Consider:

``` kotlin
data class RegistrationState(
    val name: String = "",
    val email: String = "",
    val password: String = "",
    val confirmPassword: String = "",
    val isSubmitting: Boolean = false,
    val errors: Map<RegistrationField, String> = emptyMap()
)
```

The UI can render directly from this state.

``` text
Name
Email
Password
Confirm Password
Validation errors
Submit progress
```

------------------------------------------------------------------------

## Form state and validation

Instead of:

``` text
emailIsValid
passwordIsValid
nameIsValid
confirmPasswordIsValid
```

you can model validation errors:

``` kotlin
data class FieldError(
    val field: RegistrationField,
    val message: String
)
```

or:

``` kotlin
val errors: Map<RegistrationField, String>
```

This scales better when validation rules become more complex.

------------------------------------------------------------------------

# 18. Derived State

Not every UI value needs to be stored directly.

Suppose:

``` kotlin
data class CartState(
    val items: List<CartItem>
)
```

The UI may need:

``` text
total item count
total price
```

These can often be derived:

``` kotlin
val itemCount: Int
    get() = items.sumOf { it.quantity }

val totalPrice: Double
    get() = items.sumOf {
        it.price * it.quantity
    }
```

This avoids storing redundant values:

``` kotlin
data class CartState(
    val items: List<CartItem>,
    val itemCount: Int,
    val totalPrice: Double
)
```

If all three are independently mutable, they can become inconsistent.

------------------------------------------------------------------------

## The consistency problem

Imagine:

``` text
items = 3
itemCount = 5
```

Which one is correct?

Derived state avoids this class of problem when the calculation is cheap
and deterministic.

------------------------------------------------------------------------

# 19. State and Business Rules

State should describe the current UI condition.

Business rules should not be hidden inside random UI mutations.

Suppose:

``` text
User can buy maximum 5 units.
```

The rule should live in domain/application logic.

The resulting state might contain:

``` kotlin
data class CartState(
    val quantity: Int,
    val canIncreaseQuantity: Boolean
)
```

Or `canIncreaseQuantity` can be derived from the domain rules.

The important separation is:

``` text
Intent
   ↓
Business Rule
   ↓
State
   ↓
UI
```

not:

``` text
UI
   ↓
if (quantity < 5)
   ↓
random mutation
```

------------------------------------------------------------------------

# 20. StateFlow as an MVI State Holder

Kotlin `StateFlow` is a natural fit for exposing state.

Example:

``` kotlin
private val _state =
    MutableStateFlow(LoginState())

val state: StateFlow<LoginState> =
    _state.asStateFlow()
```

The ViewModel/store owns the mutable state.

Consumers receive the read-only flow.

``` text
MutableStateFlow
      │
      │ internal
      ▼
Feature Logic
      │
      ▼
StateFlow
      │
      │ read-only
      ▼
UI
```

This gives the architecture a clear ownership boundary.

------------------------------------------------------------------------

# 21. Updating State Safely

Prefer atomic updates when multiple operations may update state.

``` kotlin
_state.update { current ->
    current.copy(
        isLoading = true
    )
}
```

Instead of:

``` kotlin
_state.value =
    _state.value.copy(
        isLoading = true
    )
```

The `update` form expresses:

> Take the current value and produce the next value.

This is particularly useful when state updates can happen from
concurrent coroutine work.

------------------------------------------------------------------------

## State ownership

A useful rule:

``` text
Store/ViewModel
    owns MutableStateFlow

UI
    receives StateFlow
```

Avoid exposing:

``` kotlin
val state: MutableStateFlow<LoginState>
```

to the UI.

The UI should not be able to mutate application state directly.

------------------------------------------------------------------------

# 22. State and Coroutines

MVI state often changes because of asynchronous operations.

For example:

``` kotlin
fun loadProfile() {
    scope.launch {

        _state.update {
            it.copy(isLoading = true)
        }

        val result = repository.getProfile()

        when (result) {

            is Result.Success -> {
                _state.update {
                    it.copy(
                        isLoading = false,
                        profile = result.data
                    )
                }
            }

            is Result.Failure -> {
                _state.update {
                    it.copy(
                        isLoading = false,
                        error = result.error
                    )
                }
            }
        }
    }
}
```

The state becomes the visible representation of asynchronous progress.

------------------------------------------------------------------------

## State transitions are more important than coroutine details

The coroutine is an implementation mechanism.

The architectural contract is:

``` text
Start
 ↓
Loading
 ↓
Success
```

or:

``` text
Start
 ↓
Loading
 ↓
Error
```

This makes the feature easier to test without depending on the exact
coroutine implementation.

------------------------------------------------------------------------

# 23. State Persistence

Not every state value should survive process death or application
restart.

For example:

``` text
isLoading
```

usually should not be persisted.

But:

``` text
selectedTheme
```

might be.

Similarly:

``` text
draft form data
```

may need persistence depending on the product requirements.

The important question is:

> Is this UI state temporary, restorable, or durable application data?

------------------------------------------------------------------------

## Three useful categories

### Ephemeral state

Exists only while the feature is active.

``` text
isLoading
showInlineError
isRefreshing
```

### Restorable UI state

May be restored after recreation.

``` text
selectedTab
searchQuery
scroll position
draft input
```

### Persistent application data

Belongs to durable storage.

``` text
user profile
authentication session
cached products
preferences
```

These should not all be treated as the same kind of state.

------------------------------------------------------------------------

# 24. State Restoration vs Data Persistence

These concepts are related but different.

### State restoration

Restores the user's UI context.

``` text
User was on tab 3.
Search query was "Kotlin".
```

### Data persistence

Stores application information.

``` text
User account
Shopping cart
Database records
```

MVI state may be reconstructed from persistent data rather than
persisted directly.

For example:

``` text
Database
   ↓
Repository
   ↓
Use Case
   ↓
MVI State
   ↓
UI
```

This is often cleaner than trying to serialize the entire feature state.

------------------------------------------------------------------------

# 25. State in Kotlin Multiplatform

State models are excellent candidates for `commonMain`.

Example:

``` kotlin
data class ProfileState(
    val profile: ProfileUiModel? = null,
    val isLoading: Boolean = false,
    val error: AppError? = null
)
```

The state contains no Android-specific code.

It can therefore be consumed by:

``` text
Android Compose
```

and:

``` text
iOS SwiftUI
```

------------------------------------------------------------------------

## Shared state architecture

``` mermaid
flowchart TB
    subgraph Shared["KMP commonMain"]
        I[Intent]
        L[Feature Logic]
        S[State]
        R[Repository]
    end

    A[Android Compose] --> I
    I --> L
    L --> R
    R --> L
    L --> S
    S --> A

    IOS[iOS SwiftUI] --> I
    S --> IOS
```

The UI technology changes.

The state contract does not.

------------------------------------------------------------------------

# 26. Android Compose and State

Compose works naturally with immutable UI state.

For example:

``` kotlin
@Composable
fun ProductScreen(
    state: ProductListState,
    onIntent: (ProductListIntent) -> Unit
) {
    when {

        state.isInitialLoading -> {
            LoadingView()
        }

        state.error != null -> {
            ErrorView(
                onRetry = {
                    onIntent(
                        ProductListIntent.Retry
                    )
                }
            )
        }

        state.items.isEmpty() -> {
            EmptyView()
        }

        else -> {
            ProductList(
                items = state.items
            )
        }
    }
}
```

The composable does not need to know how the data was loaded.

It receives state and renders it.

------------------------------------------------------------------------

## State-driven rendering

The relationship is:

``` text
State
 ↓
Composable
 ↓
Pixels
```

When state changes:

``` text
New State
   ↓
Recomposition
   ↓
Updated UI
```

This fits naturally with MVI's unidirectional model.

------------------------------------------------------------------------

# 27. iOS and Shared State

On iOS, the same shared state can conceptually become an observable
model.

The exact bridge may vary depending on whether the project uses:

-   Kotlin/Native interoperability,
-   a Flow-to-Swift bridge,
-   a KMP framework,
-   a shared ViewModel layer,
-   or another state observation mechanism.

The architectural goal remains:

``` text
Shared State
     ↓
SwiftUI observation
     ↓
Native UI
```

The iOS UI should not need to understand:

``` text
Retrofit
Room
Android Context
Android lifecycle
```

The shared state remains platform-neutral.

------------------------------------------------------------------------

# 28. Testing State

State is one of the easiest MVI concepts to test because it can be
represented as ordinary Kotlin values.

Suppose:

``` kotlin
data class CounterState(
    val count: Int = 0
)
```

Reducer:

``` kotlin
fun reduce(
    state: CounterState,
    intent: CounterIntent
): CounterState {
    return when (intent) {
        CounterIntent.Increment ->
            state.copy(
                count = state.count + 1
            )

        CounterIntent.Decrement ->
            state.copy(
                count = state.count - 1
            )
    }
}
```

Test:

``` kotlin
@Test
fun increment_should_update_state() {

    val initial = CounterState(
        count = 10
    )

    val actual = reduce(
        initial,
        CounterIntent.Increment
    )

    assertEquals(
        CounterState(count = 11),
        actual
    )
}
```

No UI is required.

No Android device is required.

No network is required.

------------------------------------------------------------------------

## State sequence testing

For an API-driven feature, test the sequence:

``` text
Initial
 ↓
Loading
 ↓
Content
```

and:

``` text
Initial
 ↓
Loading
 ↓
Error
```

and:

``` text
Content
 ↓
Refreshing
 ↓
Updated Content
```

These tests describe the behavior of the feature much more clearly than
isolated Boolean assertions.

# 29. Common State Modeling Mistakes

## Mistake 1 --- Too many Boolean flags

Avoid:

``` kotlin
isLoading
isError
isEmpty
isSuccess
isRefreshing
isRetrying
```

when these represent mutually exclusive states.

Prefer a sealed state model where appropriate.

------------------------------------------------------------------------

## Mistake 2 --- Mutable collections

Avoid exposing mutable collections:

``` kotlin
val items: MutableList<Product>
```

Prefer:

``` kotlin
val items: List<Product>
```

The state should not be modified from outside.

------------------------------------------------------------------------

## Mistake 3 --- Exposing MutableStateFlow

Avoid:

``` kotlin
val state: MutableStateFlow<State>
```

Prefer:

``` kotlin
private val _state = MutableStateFlow(State())

val state = _state.asStateFlow()
```

------------------------------------------------------------------------

## Mistake 4 --- Storing redundant data

Avoid:

``` kotlin
items
itemCount
totalPrice
```

if all three can be derived reliably from `items`.

Redundant state creates consistency problems.

------------------------------------------------------------------------

## Mistake 5 --- Putting navigation flags in persistent state

Avoid:

``` kotlin
data class State(
    val navigateToHome: Boolean
)
```

for a one-time navigation action.

A one-time effect is usually a better fit.

------------------------------------------------------------------------

## Mistake 6 --- Putting platform types in shared state

Avoid:

``` kotlin
Bitmap
Context
UIView
Activity
UIViewController
```

in `commonMain` state.

Keep shared state platform-neutral.

------------------------------------------------------------------------

## Mistake 7 --- Making state a copy of the backend response

The UI rarely needs the entire API response.

Create a state model based on UI requirements.

------------------------------------------------------------------------

# 30. A Practical State Checklist

Before creating a State property, ask:

### Does the UI need it?

If no, it probably does not belong in UI state.

### Is it persistent state or an event?

If it happens once, it may be an Intent or Effect.

### Can it be derived?

If yes, avoid storing duplicate information.

### Can invalid combinations occur?

If yes, consider a sealed state model.

### Is it mutable?

Prefer immutable data.

### Is it platform-independent?

Especially important for KMP `commonMain`.

### Who owns the state?

Usually:

``` text
Store/ViewModel → MutableStateFlow
UI → StateFlow
```

### Can the state be tested without UI?

A strong state model should usually be testable as plain Kotlin data.

------------------------------------------------------------------------

## State Design Formula

A useful way to think about state is:

``` text
Good State
=
UI-relevant information
+
Immutable representation
+
Valid combinations
+
Predictable transitions
+
Platform independence
```

For example:

``` kotlin
data class ProductListState(
    val screen: ProductScreenState,
    val isRefreshing: Boolean,
    val isLoadingNextPage: Boolean
)
```

is much more meaningful than a collection of unrelated flags.

------------------------------------------------------------------------

# 31. Part 3 Summary

State is the **current truth of the UI**.

The most important principles are:

### 1. State describes the current condition

``` text
State → UI
```

### 2. State is not an event

``` text
Intent → transition
State  → current condition
```

### 3. Prefer immutable state

``` kotlin
state.copy(...)
```

rather than mutating shared objects.

### 4. Model mutually exclusive states explicitly

Use sealed hierarchies when they make invalid combinations impossible.

``` text
Loading
Empty
Content
Error
```

### 5. Avoid redundant state

If something can be safely derived, consider deriving it.

### 6. Distinguish loading modes

``` text
Initial loading
Refreshing
Loading next page
Submitting
```

may represent different UI conditions.

### 7. Use `StateFlow` for observable state

``` kotlin
private val _state = MutableStateFlow(...)
val state = _state.asStateFlow()
```

### 8. Keep shared state platform-independent

This is especially valuable in KMP:

``` text
commonMain
   ↓
Shared State
   ↓
Android + iOS
```

### 9. Test state transitions

State should be easy to verify without requiring a UI test.

# The MVI Loop So Far

With Parts 1--3, the core MVI loop is now visible:

``` mermaid
flowchart LR
    U[User] --> V[View]
    V --> I[Intent]
    I --> L[Feature Logic]
    L --> R[Reducer]
    R --> S[Immutable State]
    S --> V
```

And when asynchronous work is involved:

``` text
               ┌───────────────┐
               │     Intent    │
               └───────┬───────┘
                       │
                       ▼
               ┌───────────────┐
               │ Feature Logic │
               └───────┬───────┘
                       │
                ┌──────┴───────┐
                │              │
                ▼              ▼
          Side Effect       Reducer
                │              │
                ▼              ▼
          Repository        New State
                │              │
                └──────┬───────┘
                       ▼
                      UI
```

The architecture now has three clearly defined concepts:

  Concept       Question it answers
  ------------- -------------------------
  **Intent**    What happened?
  **State**     What is true right now?
  **Reducer**   How does state change?

That distinction is the foundation for everything that follows.

## Key Takeaway

> **Good MVI State does more than hold values. It describes the UI's
> current truth in a way that makes invalid combinations, accidental
> mutation, and hidden state transitions harder to create.**

In Kotlin Multiplatform, a carefully designed immutable state model can
become one of the strongest shared contracts between Android, iOS, and
the common business layer.
