## 1. What Exceptions Mean

An exception signals that an operation could not continue normally. Kotlin uses exceptions for invalid arguments, failed I/O, parsing errors, and unexpected runtime conditions.

```kotlin
fun parseAge(raw: String): Int = raw.toInt()
```

A valid integer string returns an `Int`; `"unknown"` throws `NumberFormatException`. Kotlin does not require callers to declare every exception in the function signature, so important failure behavior should be clear through API design, documentation, and tests.

Exceptions can indicate very different things:

- **Invalid usage:** a caller violates a function's preconditions.
- **Operational failure:** a network or storage operation cannot complete.
- **Domain rejection:** a business operation is not permitted.
- **Unexpected defect:** an invariant or assumption is broken.
- **Cancellation:** a coroutine is being asked to stop.

These categories should not share one automatic handling policy. A timeout may justify a retry; invalid input may need correction; a defect should remain diagnosable; cancellation should normally propagate.

> **Principle:** Catch an exception only when you can recover, translate it, add useful context, or handle it at a deliberate boundary.

## 2. Different Failure Categories

| Category | Example | Typical policy |
|---|---|---|
| Invalid argument | Required ID is blank | Validate or return a typed validation outcome |
| Data-format error | Malformed JSON or invalid number | Reject input and map to a meaningful failure |
| I/O failure | Socket or file operation fails | Translate known cases; recover when appropriate |
| Remote-service rejection | Access denied | Map response semantics to an application outcome |
| Invariant violation | Impossible internal state | Preserve diagnostics and fix the defect |
| Cancellation | Coroutine job is cancelled | Propagate cancellation |
| Unknown exception | Unclassified runtime failure | Do not pretend it is a known recoverable failure |

Kotlin does not enforce Java-style checked exceptions. A Kotlin function generally does not need a `throws` declaration for ordinary Kotlin callers to compile. This makes the language concise, but it also means API authors must communicate important failure behavior through clear contracts.

### Do not use exceptions for every normal branch

```kotlin
fun findProduct(id: String): Product? = products[id]
```

If “not found” is an expected outcome, a nullable result, `Result`, or sealed domain type may be clearer than throwing `NoSuchElementException`. In another context, a missing value might violate an invariant and justify an exception. Choose based on the meaning of the operation.

## 3. `try`, `catch`, and `finally`

Kotlin's `try` can be an expression:

```kotlin
fun parseQuantity(raw: String): Int? =
    try {
        raw.trim().toInt()
    } catch (_: NumberFormatException) {
        null
    }
```

This is reasonable if invalid input is intentionally represented by `null`. If callers must distinguish multiple validation failures, use a richer result model.

### Catch the narrowest meaningful exception

```kotlin
try {
    writeSettings()
} catch (exception: IOException) {
    reportSettingsWriteFailure(exception)
}
```

This is usually safer than catching `Exception` and treating every problem as a storage failure. A broad catch may hide programming defects or swallow cancellation in coroutine code.

### Use `finally` for cleanup

```kotlin
try {
    performOperation()
} finally {
    releaseTemporaryResource()
}
```

For supported `Closeable` or `AutoCloseable` resources, Kotlin's `use` extension can be clearer:

```kotlin
openResource().use { resource ->
    useResource(resource)
}
```

Check the resource type and target libraries when writing common KMP code. Avoid returning from `finally`, because it can override an earlier return or exception and obscure the original failure.

## 4. Throwing Exceptions Intentionally

Throw an exception when a function cannot satisfy its contract and the caller is expected to handle or propagate the failure.

### Validate preconditions

```kotlin
fun calculateDiscount(price: Double, percentage: Double): Double {
    require(price >= 0.0) { "Price must not be negative" }
    require(percentage in 0.0..100.0) {
        "Percentage must be between 0 and 100"
    }

    return price * percentage / 100.0
}
```

`require` throws `IllegalArgumentException` when a precondition is false.

### Validate internal state

```kotlin
fun currentSession(): Session =
    session ?: error("Session must be initialized before use")
```

`error` throws `IllegalStateException`. Use it for a violated internal assumption, not as a substitute for handling a normal signed-out state.

### Model expected business outcomes explicitly

```kotlin
sealed interface CancelOrderResult {
    data object Cancelled : CancelOrderResult
    data object AlreadyShipped : CancelOrderResult
    data object NotFound : CancelOrderResult
}
```

A business outcome such as “already shipped” may be expected control flow, not a programming defect. A sealed type makes those outcomes visible and encourages exhaustive handling.

### Custom exceptions

```kotlin
class InvalidDocumentException(
    message: String,
    cause: Throwable? = null
) : Exception(message, cause)
```

A custom exception is useful when it adds stable meaning or lets callers catch a meaningful category. Preserve the original `cause` when wrapping a lower-level exception. Avoid creating a new class for every minor variation when the distinction does not change handling.

## 5. Catch at the Right Boundary

Catch at the first layer that can do something meaningful with the failure.

```text
Platform API / Network / Database
              │
              ▼
          Data source
              │ technical exceptions
              ▼
          Repository
              │ stable failure category
              ▼
           Use case
              │ business outcome
              ▼
       ViewModel / Presenter
              │ UI state and actions
              ▼
          Platform UI
```

- **Data source:** understands response codes, serialization, transport, and database exceptions.
- **Repository:** coordinates sources, maps known technical failures, and may use a valid cache fallback.
- **Use case:** applies business rules without depending on a particular HTTP client.
- **Presentation:** converts outcomes into loading, content, validation, sign-in, retry, or error state.
- **Application boundary:** reports unexpected failures; it should not make every exception look like success.

Do not catch an exception merely because the current function can catch it. Catching is useful when the code has a deliberate response.

## 6. Exceptions in KMP Architecture

Shared Kotlin code should not force the domain model to depend on platform-specific exception classes.

```kotlin
interface ProfileDataSource {
    suspend fun fetchProfile(): Profile
}
```

This contract may throw, but document the important failure behavior. A repository can translate technical failures into a common model:

```kotlin
sealed interface ProfileFailure {
    data object Unauthenticated : ProfileFailure
    data object NotFound : ProfileFailure
    data object TemporarilyUnavailable : ProfileFailure
    data object InvalidPayload : ProfileFailure
    data object Unknown : ProfileFailure
}
```

Avoid putting `android.content.Context`, UIKit types, or a JVM-only networking exception in a common domain contract.

Use platform-specific mapping when target APIs genuinely differ. Keep the shared contract stable and implement platform details in the appropriate source set or behind a common interface. Do not add `expect`/`actual` abstractions where no meaningful platform difference exists.

A networking library may expose different exception types on JVM, Native, and JavaScript. A mapper in `commonMain` must use common APIs; target-specific exception mapping belongs in platform source sets or behind an abstraction.

## 7. Coroutine Cancellation

`CancellationException` is a coroutine control-flow signal. It should normally not be converted into an ordinary application failure.

Cancellation can occur when a user leaves a screen, a parent scope is cancelled, a newer request replaces an older request, or a timeout stops work.

### Dangerous catch-all

```kotlin
suspend fun loadProfile(): Profile? =
    try {
        dataSource.fetchProfile()
    } catch (_: Exception) {
        null
    }
```

This can catch cancellation and return `null`. The caller may continue as if the operation simply had no data, even though the coroutine was cancelled.

### Preserve cancellation

```kotlin
suspend fun loadProfile(): Result<Profile> =
    try {
        Result.success(dataSource.fetchProfile())
    } catch (cancelled: CancellationException) {
        throw cancelled
    } catch (exception: Exception) {
        Result.failure(exception)
    }
```

Use the cancellation type appropriate to the coroutine dependency and source set in your project.

### Be careful with `runCatching`

`runCatching` catches `Throwable`, so it can convert cancellation into `Result.failure(...)`:

```kotlin
suspend fun loadProfile(): Result<Profile> =
    runCatching {
        dataSource.fetchProfile()
    }
```

For suspending work, prefer an explicit `try/catch` that rethrows cancellation, or a carefully tested helper with the same guarantee.

Do not classify every `CancellationException` as a timeout. User-initiated cancellation and a timeout may require different behavior. Convert a known timeout into a typed failure only at a boundary where the cause is known.

## 8. Structured Concurrency

Structured concurrency ties child coroutine lifetimes to their parent scope. Error handling must respect those relationships.

```kotlin
suspend fun loadDashboard(): Dashboard = coroutineScope {
    val profile = async { loadProfile() }
    val alerts = async { loadAlerts() }

    Dashboard(
        profile = profile.await(),
        alerts = alerts.await()
    )
}
```

If one child throws, `coroutineScope` can cancel its sibling. That is appropriate when both results are required for a valid dashboard.

Use `supervisorScope` when sibling tasks should be allowed to fail independently. Each child still needs its own failure policy, and the output model should represent partial success where necessary.

### `launch` and `async`

- `launch` returns a `Job`; it does not return a result value.
- `async` returns a `Deferred<T>`; its result or exception is observed through `await()`.
- An unhandled `launch` exception is not handled merely by ignoring the returned job.
- `async` does not automatically isolate a failure; the parent job hierarchy still matters.

`CoroutineExceptionHandler` is a last-resort handler for uncaught exceptions in supported contexts. It is not a replacement for local recovery and does not make a failed operation successful.

## 9. Exceptions with `Flow`

A flow can fail during collection. Its error behavior should be intentional.

```kotlin
fun observeProfile(): Flow<Profile> =
    profileDataSource.observeProfile()
        .catch { exception ->
            emit(Profile.fallback())
        }
```

This is appropriate only if the fallback is truthful and valid. A fake profile can hide a real storage or network failure.

Prefer a state model when the UI needs to represent unavailable content:

```kotlin
sealed interface ProfileState {
    data object Loading : ProfileState
    data class Content(val profile: Profile) : ProfileState
    data object Unavailable : ProfileState
}
```

The `catch` operator handles upstream failures; it does not catch exceptions thrown by downstream collection code. It also respects cancellation in the normal coroutine cancellation path.

Retries should be bounded and based on failure type. Do not retry permanent authorization or validation failures indefinitely. For writes, consider idempotency and the possibility that a server completed an operation before the client observed a failure.

## 10. Platform Interoperability

KMP code may be consumed by Swift, Java, JavaScript, or other environments. Exception behavior at these boundaries requires deliberate API design.

### Kotlin to Swift

Kotlin exceptions do not automatically become a universal Swift `throws` contract for every exported API. Behavior depends on the declaration, compiler configuration, and interop mechanism.

- Prefer stable, documented outcomes for expected business failures.
- Verify how the current Kotlin/Native compiler exports the API.
- Where appropriate, use supported `@Throws` declarations and follow documented Swift error-bridging behavior.
- Do not assume arbitrary Kotlin exceptions will appear as conventional Swift errors.
- Test the generated framework/API that you actually ship.

A shared sealed result or stable DTO may be more ergonomic than asking Swift callers to interpret an implementation-specific exception class.

### Java and JavaScript

Java callers may encounter exceptions from Kotlin APIs even when the Kotlin signature does not express a checked exception contract. Use relevant JVM annotations where appropriate for Java-facing declarations and document actual behavior.

JavaScript interop has different promise and exception semantics. If a suspend function is exposed through an adapter, make rejected promises and error objects part of a deliberate contract.

**Interop rule:** Test errors through the generated platform API, not only through `commonTest`.

## 11. Translate Exceptions into Application Meaning

The UI needs to know what the user can do next, not which HTTP client class was thrown.

```kotlin
sealed interface AppFailure {
    data object NetworkUnavailable : AppFailure
    data object TimedOut : AppFailure
    data object Unauthorized : AppFailure
    data object Forbidden : AppFailure
    data object NotFound : AppFailure
    data object InvalidResponse : AppFailure
    data object Unknown : AppFailure
}
```

A response mapper might look like this:

```kotlin
fun mapStatusCode(statusCode: Int): AppFailure =
    when (statusCode) {
        401 -> AppFailure.Unauthorized
        403 -> AppFailure.Forbidden
        404 -> AppFailure.NotFound
        503 -> AppFailure.NetworkUnavailable
        else -> AppFailure.Unknown
    }
```

This is illustrative, not a universal HTTP policy. A `404` may mean “no search results” for one endpoint and “resource not found” for another. A `503` means the service is unavailable; it does not prove the device has no network connection.

### Preserve causes when wrapping

```kotlin
class ProfileLoadException(
    message: String,
    cause: Throwable
) : Exception(message, cause)
```

Wrap an exception only when the new exception adds meaningful context. Excessive wrapping can obscure useful type information.

### Separate user copy from diagnostics

User-facing messages should be short, safe, localized, and actionable:

- “Check your connection and try again.”
- “Your session has expired. Sign in again.”
- “We couldn't load this information right now.”
- “This item is no longer available.”

Do not show stack traces, raw server responses, access tokens, database messages, or exception text directly to users.

## 12. Logging and Observability

Logging should make failures diagnosable without turning logs into a source of sensitive information.

Useful, non-sensitive context may include:

- Operation name.
- Stable failure category.
- App version and platform.
- Correlation/request ID, where safe.
- Whether a retry was attempted.
- Whether cached data was used.
- A sanitized cause or stack trace in a protected diagnostic channel.

Avoid logging the same exception at every layer. Add context when crossing a meaningful boundary and report it at the appropriate observability layer.

Never log passwords, authentication tokens, full payment details, or sensitive payloads by default. Exception messages can contain user input or backend details, so sanitize before sending them to telemetry.

Useful metrics include failure rate by operation/category, timeout rate, retry success rate, cache fallback frequency, and authentication refresh failures. Prefer stable categories over arbitrary exception-message strings.

## 13. Testing Exception Behavior

Tests should verify observable contracts: what is returned, what propagates, whether cancellation remains effective, and how the UI responds.

### Test a mapped exception

```kotlin
@Test
fun ioFailureBecomesExpectedFailure() = runTest {
    val dataSource = FakeProfileDataSource(
        failure = IOException("Connection reset")
    )
    val repository = ProfileRepositoryImpl(dataSource)

    val result = repository.loadProfile()

    assertEquals(AppFailure.NetworkUnavailable, result)
}
```

This is an illustrative outline; adapt the assertion to the actual repository contract. If the repository returns `AppResult`, assert its typed failure directly rather than converting it back from an exception.

### Test cancellation propagation

```kotlin
@Test
fun cancellationIsNotConvertedToOrdinaryFailure() = runTest {
    val dataSource = FakeProfileDataSource(
        failure = CancellationException("Cancelled")
    )
    val repository = ProfileRepositoryImpl(dataSource)

    assertFailsWith<CancellationException> {
        repository.loadProfile()
    }
}
```

The fake should throw cancellation from the suspending operation. Also test cancelling the parent job while the operation is suspended.

### Test flow and interop behavior

Verify that:

- Upstream failure produces the intended state or propagates.
- Cancellation is not emitted as an ordinary error state.
- Retry stops at the configured limit.
- Downstream collector exceptions are not treated as upstream failures.
- A fallback is emitted only when the product contract allows it.
- Exported Swift/JavaScript APIs expose failures as documented.

A `commonTest` assertion alone does not prove how a Swift or JavaScript caller will observe an exception.

## 14. Common Anti-Patterns

| Anti-pattern | Risk | Better approach |
|---|---|---|
| Catching and ignoring exceptions | Caller may believe the operation succeeded | Propagate or return an explicit outcome |
| Catching `Throwable` for routine recovery | Can swallow serious failures and cancellation | Catch meaningful exception types |
| Parsing exception messages | Messages are unstable and may leak data | Map structured types or response codes |
| Returning fake success, such as `emptyList()` | Hides failed retrieval | Keep failure distinct from empty success |
| Retrying every exception | Permanent failures waste resources; writes may duplicate | Define bounded, operation-aware retry policy |
| Logging at every layer | Creates duplicate noisy reports | Log at meaningful boundaries |
| Treating cancellation as a normal error | Cancelled work may continue | Rethrow cancellation |
| Assuming platform behavior is identical | Interop contracts can differ | Test each exported platform API |

### A particularly dangerous pattern

```kotlin
try {
    repository.saveChanges()
} catch (_: Exception) {
    // Ignore.
}
```

The UI may show success even when no data was saved. The catch can also swallow cancellation.

A better contract either lets the failure propagate or returns an explicit result that the caller must handle.

## 15. Production Checklist

### API contracts
- [ ] Important failure behavior is documented.
- [ ] Expected business outcomes use typed contracts where appropriate.
- [ ] Custom exceptions add meaningful context.
- [ ] Causes are preserved when wrapping adds value.

### Catching and recovery
- [ ] Exceptions are caught only where translation or recovery is possible.
- [ ] Catch blocks target meaningful exception categories.
- [ ] Unknown failures are not silently turned into success.
- [ ] Retry policy distinguishes transient from permanent failures.
- [ ] Cleanup does not mask the original exception.

### Coroutines and flows
- [ ] `CancellationException` is rethrown when caught.
- [ ] `runCatching` around suspending work is cancellation-safe.
- [ ] Child coroutine failure behavior matches the intended scope.
- [ ] Upstream and downstream flow failures are not confused.
- [ ] Retry behavior is bounded and tested.

### KMP and security
- [ ] Common code avoids accidental dependencies on platform-only exception classes.
- [ ] Platform-specific mappings live in appropriate source sets.
- [ ] Exported Swift/JavaScript/Java APIs have documented error behavior.
- [ ] User-facing messages do not expose raw exception details.
- [ ] Logs exclude secrets and sensitive payloads.
- [ ] Duplicate logging is minimized.

---

## 16. Summary

Exceptions are useful, but reliable error handling depends on how the application uses them.

1. Distinguish operational failures, business outcomes, programming defects, and cancellation.
2. Catch only when you can translate, recover, clean up, or report meaningfully.
3. Keep technical exception types near the boundaries that understand them.
4. Use platform-neutral failure contracts in shared KMP code.
5. Preserve coroutine cancellation.
6. Treat `runCatching` carefully because it captures `Throwable`.
7. Design structured concurrency and `Flow` behavior intentionally.
8. Test exceptions through actual platform interoperability boundaries.
9. Log enough to diagnose failures without exposing sensitive data.

The goal is not to eliminate exceptions. It is to give each exception a predictable path through the system—handling expected failures without hiding defects.
