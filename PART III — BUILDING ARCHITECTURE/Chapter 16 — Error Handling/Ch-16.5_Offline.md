## 1. What Offline-First Really Means

An offline-first application treats local data as a primary way to serve the user, not merely as a fallback after a request fails.

A conventional network-first flow often looks like this:

```text
Screen opens
    │
    ▼
Request remote API
    │
    ├── Success ──► Render response
    │
    └── Failure ──► Show error screen
```

This flow can be appropriate for data that must always be current, but it makes the whole experience dependent on network availability.

An offline-first flow is different:

```text
Screen opens
    │
    ▼
Observe local database
    │
    ├── Local data available ──► Render immediately
    │
    └── No local data ─────────► Show useful empty/loading state
    │
    ▼
Refresh remote data when possible
    │
    ├── Success ──► Save to database ──► UI updates from local data
    │
    └── Failure ──► Keep local data and expose sync/error status
```

The local database provides a stable source for rendering. The remote service updates that local state when synchronization succeeds.

### Offline-first is useful when

- Users need to view previously loaded content.
- Forms or tasks should be saved before a connection returns.
- Network access is intermittent or expensive.
- Background synchronization is part of the product.
- The app must recover gracefully after process death.
- Users need to understand whether their changes are saved locally or confirmed by the server.

Offline-first does **not** mean every feature must work offline. Authentication, live inventory, financial transactions, or other authoritative operations may require connectivity. The application should make those constraints explicit.

## 2. Offline Is a State, Not Just an Exception

A failed request is an event. Being offline is a condition that can affect many operations, but the two are not identical.

A request can fail while the device has a network connection because the server is unavailable, DNS fails, a certificate is rejected, or the request times out. A device can also report a network connection while the service itself is unreachable.

Avoid treating every exception as “no internet.”

### Model the outcome accurately

```kotlin
sealed interface RefreshOutcome {
    data object Updated : RefreshOutcome
    data object Offline : RefreshOutcome
    data object FailedTemporarily : RefreshOutcome
    data object Unauthorized : RefreshOutcome
    data object InvalidResponse : RefreshOutcome
}
```

This is an example domain model. Adapt the cases to the application and map transport-specific errors into them at the data boundary.

### Keep three concepts distinct

| Concept | Meaning | Example |
|---|---|---|
| Data state | What content is available locally? | Cached list with 12 items |
| Connectivity state | What network path appears available? | Connected to Wi-Fi |
| Synchronization state | Has local and remote data been reconciled? | Refresh failed; cached data remains |

These states can coexist. An app may have cached content, a connected network, and a failed synchronization attempt.

### Do not erase useful data on refresh failure

If a refresh fails, retain the last valid local data unless the product's data-retention or security requirements say otherwise. Report the failure separately so the UI can show a non-blocking message such as “Showing saved data — couldn't refresh.”

## 3. The Local Source of Truth

The **local source of truth** is the source from which the UI reads its current data. In many mobile applications, that source is a local database such as SQLDelight or Room, depending on the project's platform and architecture.

The remote API is a synchronization partner. It supplies updates, accepts eligible writes, and may remain the authority for server-owned business rules.

### Why not render directly from the network response?

If the UI reads directly from network responses, it must coordinate loading, refresh, cache fallback, and local edits across several code paths. It may also briefly show stale data from one source and newer data from another.

With a local source of truth:

1. The UI observes a local query.
2. The repository requests remote updates when appropriate.
3. The repository validates and persists remote data.
4. The database emits updated rows.
5. The UI reacts to the local stream.

```text
Remote API ──► Mapper ──► Local database
                                │
                                ▼
                         Observable query
                                │
                                ▼
                               UI
```

### Important consistency decisions

Decide how the app handles:

- **Freshness:** When should remote data be refreshed?
- **Staleness:** How old can cached content be before it is marked stale?
- **Deletion:** How are server-side deletions reflected locally?
- **Pagination:** How are cached pages and refresh boundaries represented?
- **Account changes:** Which cached records belong to which user?
- **Conflicts:** What happens when local edits overlap remote changes?
- **Invalidation:** When should cached data be removed or refreshed?

A database is not automatically a good source of truth just because it exists. The repository and sync rules must define what its contents mean.

## 4. A KMP Offline-First Architecture

A practical Kotlin Multiplatform design shares the policies that benefit from consistent behavior while allowing each platform to integrate with its own lifecycle and background scheduler.

```text
┌──────────────────────────────────────────┐
│ Shared UI / Platform UI                  │
│ Observes application state               │
└────────────────────┬─────────────────────┘
                     │
┌────────────────────▼─────────────────────┐
│ Shared domain                            │
│ Use cases, validation, sync policy       │
└────────────────────┬─────────────────────┘
                     │
┌────────────────────▼─────────────────────┐
│ Shared repository                        │
│ Local source of truth + refresh rules    │
└──────────────┬──────────────────┬────────┘
               │                  │
┌──────────────▼────────┐  ┌──────▼────────────┐
│ Local data source     │  │ Remote data source│
│ SQLDelight / Room*    │  │ HTTP API          │
└──────────────┬────────┘  └──────┬────────────┘
               │                  │
               └─────────┬────────┘
                         │
               ┌─────────▼────────┐
               │ Sync coordinator │
               │ Queue, retry,    │
               │ conflict policy  │
               └──────────────────┘
```

<text color="secondary" size="sm">*Choose a database strategy supported by your target platforms and project setup. Room supports KMP configurations for supported targets; SQLDelight is another cross-platform option.</text>

### Shared code can own

- Domain error types.
- Repository contracts and policies.
- Data mapping and validation.
- Local/remote synchronization rules.
- Retry classification and bounded backoff.
- Conflict resolution rules that are genuinely cross-platform.
- Tests for deterministic business behavior.

### Platform code may own

- Database driver or platform database configuration.
- Network monitoring implementation.
- Android WorkManager integration.
- iOS background execution integration.
- Secure storage and platform-specific credentials.
- Platform lifecycle and permission behavior.

Use interfaces at genuine platform boundaries. Do not introduce `expect`/`actual` abstractions merely to wrap simple shared logic that already works in common code.

## 5. Separate Data, Connectivity, and Sync State

One Boolean such as `isOffline` cannot represent the complete state of an offline-first feature.

A small model can separate the concepts:

```kotlin
enum class SyncStatus {
    Idle,
    Syncing,
    Synced,
    PendingChanges,
    Failed
}

data class CachedContent<T>(
    val data: T,
    val updatedAtEpochMillis: Long?,
    val isStale: Boolean
)
```

`CachedContent` describes locally available content. `SyncStatus` describes synchronization progress. Connectivity should be represented separately if the UI needs to display it.

### Prefer state derived from meaningful events

For example:

- A local database query emits cached content.
- A refresh begins and sync status becomes `Syncing`.
- The API succeeds and the repository persists its response.
- The local query emits the updated content.
- Sync status becomes `Synced`.
- If refresh fails, content remains available and sync status becomes `Failed`.

Avoid duplicating state in multiple layers if it can be derived from a single source. For example, do not keep independent mutable copies of the same list in the repository, ViewModel, and UI unless there is a clear reason.

### Timestamps need a defined meaning

`updatedAtEpochMillis` should specify whether it records the last successful server refresh, local modification, or last synchronization. These are different timestamps. Name them distinctly when more than one is needed.

## 6. Repository Design

A repository should expose data from the local source and provide an explicit refresh operation.

The following example is intentionally independent of any database or HTTP library:

```kotlin
interface ArticleLocalDataSource {
    fun observeArticles(): Flow<List<Article>>
    suspend fun replaceArticles(articles: List<Article>)
}

interface ArticleRemoteDataSource {
    suspend fun fetchArticles(): List<Article>
}

interface ArticleRepository {
    fun observeArticles(): Flow<List<Article>>
    suspend fun refresh(): RefreshOutcome
}
```

A repository implementation can read locally while attempting a refresh:

```kotlin
class DefaultArticleRepository(
    private val local: ArticleLocalDataSource,
    private val remote: ArticleRemoteDataSource
) : ArticleRepository {

    override fun observeArticles(): Flow<List<Article>> =
        local.observeArticles()

    override suspend fun refresh(): RefreshOutcome {
        return try {
            val remoteArticles = remote.fetchArticles()
            local.replaceArticles(remoteArticles)
            RefreshOutcome.Updated
        } catch (cancelled: CancellationException) {
            throw cancelled
        } catch (failure: IOException) {
            RefreshOutcome.Offline
        } catch (failure: Exception) {
            RefreshOutcome.FailedTemporarily
        }
    }
}
```

This is a teaching example, not a complete production classifier. It assumes `Article`, the data-source interfaces, and the `RefreshOutcome` model are defined in the project. In production:

- Map transport errors precisely rather than labeling every `IOException` as offline.
- Do not map every unexpected exception to a temporary failure without logging or reporting it.
- Handle authentication, validation, and server errors separately.
- Ensure database writes are transactional where consistency requires it.
- Preserve cancellation by rethrowing `CancellationException`.
- Avoid logging sensitive response bodies or credentials.

### Why return an outcome instead of throwing every expected failure?

A refresh operation commonly has expected outcomes such as unavailable network or rejected authorization. A typed outcome makes these states explicit to the caller.

Unexpected programming defects should not be silently converted into a normal offline state. Define a clear boundary between expected operational failures and unexpected exceptions.

### Refresh and observation are separate operations

`observeArticles()` should not unexpectedly trigger a network request every time a collector starts unless that behavior is an explicit contract. A separate `refresh()` method gives the caller control over when remote work occurs and makes both behaviors easier to test.

## 7. Handling Network Failures Without Losing Data

The safest offline-first read path does not depend on a successful refresh to produce useful content.

### Read path

```text
Observe local data
    │
    ├── Cached records exist ──► Render records
    │
    └── No records ───────────► Render empty/loading state
    │
    ▼
Try refresh according to policy
    │
    ├── Success ──► Persist records ──► UI observes new data
    │
    └── Failure ──► Keep current records
                    Update refresh status
```

### Do not clear the database before a request

This pattern is dangerous:

```kotlin
// Avoid this pattern.
suspend fun refresh() {
    local.clearArticles()
    val latest = remote.fetchArticles()
    local.replaceArticles(latest)
}
```

If the network request fails after the clear, the user loses the cached content.

Prefer fetching and validating first, then applying the update transactionally:

```kotlin
suspend fun refresh() {
    val latest = remote.fetchArticles()
    local.replaceArticles(latest)
}
```

The local data source should make `replaceArticles` atomic if readers must never observe a partially applied replacement.

### Empty is not the same as unavailable

An empty list can mean “the server returned no articles” or “the local database has never been populated.” Those states should not be confused.

If the distinction matters, track whether a successful initial load has occurred, or expose a richer local-data state.

## 8. Offline Writes and the Outbox Pattern

Offline reads are usually easier than offline writes. A write may need to reach a server that owns authoritative state, and the client must survive restarts without losing the user's intent.

A common approach is the **outbox pattern**:

1. Validate the user's action locally.
2. Persist the intended change and a pending operation in one local transaction.
3. Update the local view so the UI reflects the pending change.
4. When synchronization is possible, send the operation to the server.
5. Mark the operation as acknowledged or record a conflict.
6. Reconcile local state with the server's response.

```text
User edits an item
       │
       ▼
Local transaction
  ├── Update local item
  └── Insert pending outbox operation
       │
       ▼
UI shows "Pending sync"
       │
       ▼
Sync worker sends operation
       │
       ├── Accepted ──► Mark acknowledged / reconcile
       ├── Transient failure ──► Retry later
       └── Conflict ──► Apply conflict policy
```

### Model pending operations

```kotlin
enum class OutboxStatus {
    Pending,
    InFlight,
    Acknowledged,
    NeedsResolution
}

data class PendingOperation(
    val operationId: String,
    val entityId: String,
    val operationType: String,
    val payload: String,
    val createdAtEpochMillis: Long,
    val status: OutboxStatus
)
```

This is an illustrative model. Real implementations should use typed payloads or a versioned serialization format, define status transitions, and avoid storing sensitive data unnecessarily.

### Persist the operation before reporting it as saved

If the application says “Saved” immediately after updating only in-memory state, process termination can lose the change. For an offline-capable write, persist it locally first.

The UI should distinguish these meanings:

- **Saved on this device:** local persistence succeeded.
- **Waiting to sync:** the operation is durable locally but not confirmed by the server.
- **Synced:** the server acknowledged the operation.
- **Needs attention:** the operation cannot be applied automatically.

Do not label a locally queued write as server-confirmed.

## 9. Synchronization, Retries, and Conflicts

Offline-first behavior and retry policy are closely related, but they solve different problems.

- **Offline-first** determines where the UI reads data and how local changes are preserved.
- **Retry** determines when a failed operation should be attempted again.
- **Synchronization** determines how local and remote states converge.
- **Conflict resolution** determines what to do when both sides change the same logical data.

### A durable sync loop

A background sync process commonly:

1. Selects eligible pending operations.
2. Claims them safely so concurrent workers do not process the same operation unintentionally.
3. Sends operations using stable identifiers or idempotency keys.
4. Classifies the result.
5. Marks acknowledged operations or schedules a bounded retry.
6. Records conflicts for resolution.
7. Updates local data and sync status transactionally where possible.

A durable queue should tolerate process death between any two steps. In particular, a request may reach the server while the client dies before recording the acknowledgement. The next worker may send it again, so server-side idempotency or deduplication is important.

### Conflict-resolution strategies

| Strategy | Appropriate when | Risk |
|---|---|---|
| Server wins | Server state is authoritative | Local edits may be discarded |
| Client wins | Local intent is explicitly prioritized | May overwrite newer remote changes |
| Last-write-wins | Timestamp semantics are reliable and acceptable | Clock skew can produce incorrect ordering |
| Field-level merge | Fields can be merged independently | Relationships and invariants can become inconsistent |
| Manual resolution | Data is important or changes conflict meaningfully | Adds user interaction and implementation complexity |
| Domain-specific merge | The business rules define how changes combine | Requires explicit, well-tested rules |

Do not choose last-write-wins simply because timestamps are convenient. Device clocks can be wrong, and two changes may not be safely ordered by time alone.

### Keep retry budgets across restarts when necessary

For durable background work, an in-memory attempt counter resets when the process restarts. If the business requires a persistent retry budget, store relevant attempt metadata and last-attempt timestamps in durable storage. Avoid persisting every low-level transport retry if the platform scheduler already owns that retry policy.

## 10. Modeling UI State

A ViewModel should expose enough information for the UI to show local content and communicate refresh status without making the UI infer network details.

```kotlin
data class ArticleScreenState(
    val articles: List<Article> = emptyList(),
    val isInitialLoading: Boolean = true,
    val isRefreshing: Boolean = false,
    val hasLoadedBefore: Boolean = false,
    val refreshMessage: String? = null,
    val pendingSyncCount: Int = 0
)
```

The model is illustrative; use immutable state and avoid keeping fields that can be derived reliably from other state.

### Suggested UI behavior

| Situation | User experience |
|---|---|
| No local data; initial load running | Show a loading state |
| Local data available; refresh running | Keep content visible and show subtle refresh progress |
| Refresh fails; cached data exists | Keep content and show a non-blocking stale/offline message |
| No local data; refresh fails | Show an error state with a retry action |
| Local edit saved but not synced | Show “Pending sync” or an equivalent indicator |
| Server rejects a local edit | Explain the issue and offer the appropriate next action |
| Sync succeeds | Update status and remove pending indicators |

### Avoid turning a refresh failure into a full-screen failure

If cached data is valid, a failed refresh usually should not replace the whole screen with an error. The UI can show content and refresh status together.

### Make manual retry explicit

A user action should trigger the repository or use case again. It should not mutate UI state to pretend that synchronization succeeded.

```kotlin
fun onRetryRefresh() {
    viewModelScope.launch {
        refreshArticles()
    }
}
```

This is a simplified example; `refreshArticles()` represents the ViewModel's actual use-case invocation.

## 11. Connectivity Is Only a Hint

Network monitoring can help decide when to attempt synchronization, but it cannot guarantee that an API call will succeed.

A network may be reported as available while:

- DNS resolution fails.
- The service is down.
- A captive portal blocks access.
- A VPN or proxy interferes.
- TLS validation fails.
- The server rate-limits the client.
- The connection drops after the status check.

Therefore, avoid logic that assumes:

```kotlin
if (connectivity.isConnected()) {
    // This request is guaranteed to succeed. (It is not.)
}
```

Instead, treat connectivity as a scheduling hint:

- When a network appears available, consider scheduling eligible sync work.
- When the request runs, classify its actual result.
- On transient failure, use bounded backoff.
- On permanent failure, stop automatic retries and surface the required action.
- On cancellation, stop promptly.

Do not make every repository call wait for a connectivity monitor before attempting the request unless the product and transport policy specifically require it. The actual request result remains authoritative for that attempt.

## 12. Platform Responsibilities in KMP

Kotlin Multiplatform shares code, not identical operating-system behavior. Offline-first architecture should account for each platform's storage, lifecycle, and background-execution rules.

### Android

- Use a local database supported by the application's architecture.
- Use WorkManager for suitable persistent background synchronization.
- Define network constraints and backoff through the scheduler where appropriate.
- Ensure workers are idempotent and safe to execute more than once.
- Do not depend on a foreground screen's coroutine to finish durable synchronization.

### iOS

- Use a database and storage configuration supported by the iOS target.
- Treat background execution as constrained and opportunistic.
- Use platform background-task APIs where the product requires eligible background work.
- Persist pending operations before expecting a later sync.
- Assume the process may be suspended or terminated before the operation finishes.

### Shared KMP code

Shared code is a good place for the repository contract, sync state, mapping, retry classification, and deterministic conflict rules. Platform-specific schedulers should invoke the shared sync use case rather than duplicating business rules.

A shared coroutine does not override operating-system lifecycle restrictions. Durable work requires durable state and a platform-supported execution mechanism.

## 13. Security and Data Freshness

Offline support increases the amount of data stored on a device. It also creates situations where data can be stale or belong to a previous session.

### Secure local storage

- Store only the data the app needs offline.
- Use platform-appropriate protection for sensitive records and credentials.
- Do not store access tokens in ordinary application tables unless the design explicitly provides the required protection.
- Scope cached data and pending operations to the correct account or tenant.
- Define logout behavior for cached private data and pending writes.
- Avoid putting sensitive payloads in logs or analytics events.

### Handle account changes deliberately

If one user signs out and another signs in, the app must not expose the previous user's cached records or upload their pending operations under the new account.

A robust design associates local data and outbox records with an account or tenant identifier and defines how those records are handled during sign-out. The exact policy depends on whether pending work should be retained, cancelled, or securely removed.

### Communicate freshness

A cached record can be available but stale. If the information affects a critical decision—such as available inventory, a price, or a permission—do not present stale data as authoritative.

Use timestamps, freshness indicators, or feature-specific rules. For sensitive actions, require server validation when necessary and explain why the action cannot be completed offline.

## 14. Testing Offline Behavior

Offline-first code should be testable without depending on the physical network. Use fake data sources and a deterministic clock or scheduler where practical.

### Test cases to cover

| Scenario | Expected behavior |
|---|---|
| Cached records exist and refresh succeeds | Local data updates from the remote result |
| Cached records exist and refresh fails | Existing records remain available |
| No cached records and refresh fails | UI receives an appropriate initial-load error state |
| Offline write is submitted | Local data and outbox operation are persisted |
| Sync succeeds | Operation is acknowledged and state reconciles |
| Sync fails transiently | Operation remains pending and retry is scheduled |
| Server rejects an operation permanently | Automatic retries stop and a meaningful status is exposed |
| Process dies after server acceptance | Repeated delivery does not create duplicate effects |
| Account changes | Previous-account data is not exposed or uploaded as the new account |
| Local and remote versions conflict | Documented conflict policy is applied |
| Coroutine is cancelled | Work stops without swallowing cancellation |

### Example: preserve cached data on failure

```kotlin
@Test
fun refreshFailureDoesNotDeleteCachedArticles() = runTest {
    val cached = listOf(article(id = "local-1"))
    val local = FakeArticleLocalDataSource(initial = cached)
    val remote = FakeArticleRemoteDataSource(
        failure = IOException("Network unavailable")
    )
    val repository = DefaultArticleRepository(local, remote)

    val outcome = repository.refresh()
    val currentArticles = local.observeArticles().first()

    assertEquals(RefreshOutcome.Offline, outcome)
    assertEquals(cached, currentArticles)
}
```

This example assumes test fakes and an `article` fixture are defined, and that the production repository maps this specific failure to `Offline`. In a real test suite, also verify that no destructive database operation occurred before the remote response was validated.

### Test sync idempotency at the contract level

A client-side unit test cannot prove that a remote service deduplicates operations correctly. Test the API contract with integration tests or a controlled server implementation that receives the same operation identifier more than once and verifies the intended single effect.

### Avoid testing implementation details only

The most valuable assertions concern user-visible guarantees:

- Cached data remains readable.
- Pending writes survive recreation.
- Failed operations remain recoverable.
- Permanent failures do not retry forever.
- Duplicate delivery does not duplicate effects.
- UI status accurately describes local versus server-confirmed state.

## 15. Common Anti-Patterns

| Anti-pattern | Problem | Better approach |
|---|---|---|
| Network response is the only UI data source | Screen fails whenever the request fails | Observe local persisted data |
| Clearing cache before refresh | Failed refresh can erase valid content | Fetch, validate, then update transactionally |
| One `isOffline` Boolean for everything | Conflates network, data, and sync states | Model the states separately |
| Treating all exceptions as no internet | Hides authorization, parsing, and server failures | Classify failures at the data boundary |
| In-memory-only pending writes | Process death can lose user intent | Persist an outbox or durable work record |
| Calling a local write “synced” | Misrepresents server acknowledgement | Distinguish saved locally from confirmed remotely |
| Infinite retry loop in a screen scope | Wastes resources and may stop with the UI | Use bounded foreground retries or durable scheduling |
| Assuming network availability guarantees success | Network status can change immediately | Handle actual request outcomes |
| Last-write-wins for every conflict | Can discard valid changes | Choose a domain-appropriate merge policy |
| Uploading pending data after account switch | Can leak or misattribute data | Scope queue entries to account/tenant |
| Storing every server response indefinitely | Can expose sensitive or stale data | Define retention, protection, and invalidation rules |

## 16. Production Checklist

### Data and architecture
- [ ] The UI reads from a defined local source of truth.
- [ ] Remote responses are validated and persisted before the UI depends on them.
- [ ] Cache replacement is atomic where required.
- [ ] Empty, loading, stale, and unavailable states are distinguishable.
- [ ] Shared business policies are separated from platform scheduling.

### Failure handling
- [ ] Offline, timeout, authorization, parsing, and server failures are not conflated.
- [ ] Cached content remains available when a refresh fails, unless product policy says otherwise.
- [ ] Cancellation is propagated.
- [ ] Automatic retry has a bounded policy.
- [ ] Permanent failures stop automatic retries.

### Offline writes and synchronization
- [ ] User intent is persisted before it is reported as saved.
- [ ] Pending operations survive process death.
- [ ] Repeated delivery is safe or protected by idempotency keys.
- [ ] Conflicts have a documented resolution policy.
- [ ] Server acknowledgement and local persistence are represented separately.
- [ ] Account changes cannot expose or misroute pending data.

### User experience and operations
- [ ] Cached data's freshness is clear where it matters.
- [ ] The UI offers a meaningful action when manual intervention is needed.
- [ ] Background work uses platform-supported scheduling.
- [ ] Retry and sync outcomes are observable.
- [ ] Logs and metrics avoid secrets and unnecessary personal data.

### Testing
- [ ] Refresh failure preserves cached records.
- [ ] Offline writes survive recreation.
- [ ] Retry exhaustion and permanent failure are covered.
- [ ] Duplicate delivery and conflict behavior are tested.
- [ ] Account-switch and logout behavior are tested.
- [ ] Tests use fakes or controlled services rather than relying on real connectivity.

## 17. Summary

Offline-first error handling is about preserving useful behavior when the remote service is unavailable—not simply catching an exception and displaying a message.

1. Treat local data as the UI's stable source of truth.
2. Model data availability, connectivity, and synchronization separately.
3. Keep valid cached data when refresh fails.
4. Persist offline writes before reporting them as saved.
5. Use a durable outbox for operations that must survive process death.
6. Combine bounded retry with idempotency and conflict resolution.
7. Treat connectivity as a hint, not a guarantee.
8. Respect Android and iOS background-execution limits.
9. Protect cached data and scope it to the correct account.
10. Test the guarantees users actually depend on.

**A resilient offline-first app does not pretend the network never fails. It preserves user progress, communicates what is known, and recovers safely when connectivity returns.**
