## 1. Why Error Handling Matters in KMP

A Kotlin Multiplatform application can share domain logic, data access, and presentation state across Android, iOS, desktop, and other targets. That makes error handling an architectural concern: a failure created in shared Kotlin may eventually need to become a useful message, retry action, or recovery path in a platform-specific UI.

Without a deliberate model, the same failure can be handled differently in different places:

- One screen displays a raw exception message.
- Another converts every failure into “Something went wrong.”
- A third silently returns an empty list.
- An iOS caller receives an unclear interop error.
- A coroutine cancellation is mistakenly shown as a network failure.

The result is inconsistent user experience and difficult debugging.

A reliable strategy begins with a simple principle:

> **Represent expected failures explicitly, preserve unexpected failures for diagnosis, and translate errors at the boundary where their meaning changes.**

This chapter focuses on reusable patterns for shared Kotlin code. Platform-specific implementations can build on the same principles while adapting UI, logging, and interoperability to each target.

### What good error handling should achieve

| Goal | Practical meaning |
|---|---|
| Clarity | Callers can tell success from failure without guessing |
| Recovery | The application knows whether retry, sign-in, correction, or fallback is appropriate |
| Consistency | Shared business rules do not vary by platform |
| Diagnostics | Engineers can investigate failures without exposing sensitive data |
| Testability | Failure paths can be verified without relying on real network outages |
| Safety | Cancellation, security failures, and programmer defects are not swallowed |

Error handling is not about wrapping every line in `try/catch`. It is about choosing where failures should be represented, translated, propagated, or recovered.

## 2. What Counts as an Error?

Not every non-success outcome should be treated the same way. Distinguish expected operational failures from invalid application state and programming defects.

| Category | Example | Typical response |
|---|---|---|
| Network failure | No connection, timeout, DNS failure | Offer retry or offline behavior |
| Remote service failure | Server returns an error response | Map to a domain-relevant failure |
| Authentication | Session expired or credentials rejected | Refresh session or request sign-in |
| Validation | User input is invalid | Show field-level guidance |
| Missing data | Requested record no longer exists | Show an empty/not-found state or return safely |
| Storage failure | Database read/write fails | Recover if possible; otherwise surface a meaningful failure |
| Cancellation | User leaves a screen or a job is cancelled | Propagate cancellation; do not show it as an ordinary error |
| Programming defect | Broken invariant or invalid state | Preserve visibility, log safely, and fix the defect |

### Expected failure versus programmer bug

A network timeout is a normal event in a mobile application. It should be part of the application's expected control flow.

An impossible state caused by a broken invariant is different. Converting every such defect into a generic “network error” makes the system appear resilient while hiding the real problem.

A useful rule:

- Model failures callers can reasonably anticipate.
- Validate external input at boundaries.
- Avoid catching exceptions merely to keep the application moving.
- Do not turn unknown failures into success-shaped values.

### Empty data is not always an error

An empty search result can be a valid success:

```kotlin
suspend fun searchProducts(query: String): List<Product>
```

Returning an empty list may be correct when the request succeeded and no products matched. It is misleading if the server request failed and the repository silently returned `emptyList()`.

```text
Request succeeded, zero matches  → Empty state
Request failed                   → Error/retry state
```

This distinction is one of the most important habits in repository design.

## 3. The Error-Handling Layers

A layered KMP architecture should translate errors only when a layer can add useful meaning.

```text
┌─────────────────────────────────────────────┐
│ Platform UI                                 │
│ Friendly message · Retry · Sign-in · Help   │
└───────────────────────▲─────────────────────┘
                        │ UI state / UI action
┌───────────────────────┴─────────────────────┐
│ Presentation                                │
│ Loading · Content · Empty · Recoverable error│
└───────────────────────▲─────────────────────┘
                        │ Domain outcome
┌───────────────────────┴─────────────────────┐
│ Domain                                      │
│ Business rules · Use cases · Domain failures│
└───────────────────────▲─────────────────────┘
                        │ Data result / exception
┌───────────────────────┴─────────────────────┐
│ Data                                        │
│ API · Database · Cache · Platform services  │
└─────────────────────────────────────────────┘
```

**Data layer:** understands HTTP status codes, socket timeouts, database exceptions, serialization failures, and cache behavior. It should not expose raw HTTP response objects throughout the app.

**Domain layer:** understands business meaning: an account is locked, an order cannot be cancelled, a user lacks permission, or a resource no longer exists. Domain failures should not depend on Retrofit, SQL drivers, Android `Context`, or UIKit.

**Presentation layer:** turns outcomes into screen state and actions: retry, sign-in, field validation, not-found, or a refresh warning while old content remains visible.

**Platform UI:** chooses localization, accessibility announcements, dialogs, and native conventions. Shared code can expose a semantic failure; each UI can translate it into user-facing copy.

Do not pass raw exception messages directly to users. They may be technical, unstable, or contain sensitive details.

## 4. Exceptions, Result Types, and State

Kotlin offers several ways to represent failure. Choose based on the operation and the contract callers need.

### Option A: Exceptions

Exceptions are useful when a function cannot reasonably complete and its contract permits failure to propagate.

```kotlin
suspend fun loadProfile(): Profile
```

This API can throw. Callers must know which failures may occur and where they are handled. If normal network failures are represented only by undocumented exceptions, callers rely on knowledge that is not visible in the type signature.

### Option B: `Result<T>`

Kotlin's standard `Result<T>` represents success or failure:

```kotlin
suspend fun loadProfile(): Result<Profile>
```

```kotlin
repository.loadProfile()
    .onSuccess { profile ->
        // Use profile.
    }
    .onFailure { throwable ->
        // Translate or handle failure.
    }
```

`Result` is useful when callers primarily need a success value or a throwable. It does not define the application's error taxonomy automatically. The producing function must explicitly convert failures into `Result.failure(...)` if that is its contract.

### Option C: A domain-specific sealed result

When callers need to distinguish expected outcomes, a sealed type can make them explicit:

```kotlin
sealed interface ProfileOutcome {
    data class Success(val profile: Profile) : ProfileOutcome
    data object Unauthorized : ProfileOutcome
    data object NotFound : ProfileOutcome
    data object Offline : ProfileOutcome
    data object ServiceUnavailable : ProfileOutcome
}
```

```kotlin
when (val outcome = loadProfile()) {
    is ProfileOutcome.Success -> showProfile(outcome.profile)
    ProfileOutcome.Unauthorized -> requestSignIn()
    ProfileOutcome.NotFound -> showNotFound()
    ProfileOutcome.Offline -> showOfflineMessage()
    ProfileOutcome.ServiceUnavailable -> offerRetry()
}
```

This assumes those outcomes are part of the actual use-case contract. Avoid creating a large hierarchy for cases the application does not need to distinguish.

### Option D: UI state

UI state describes what the user can currently see:

```kotlin
sealed interface ProfileUiState {
    data object Loading : ProfileUiState
    data class Content(val profile: Profile) : ProfileUiState
    data object SignedOut : ProfileUiState
    data object NotFound : ProfileUiState
    data class Error(val canRetry: Boolean) : ProfileUiState
}
```

UI state is not necessarily the same as a repository result. A refresh can fail while previously loaded content remains visible. Model that deliberately instead of forcing every state into a single `Loading`/`Error` switch.

| Need | A reasonable choice |
|---|---|
| Failure is exceptional and should propagate | Exception |
| Simple success/failure wrapper is sufficient | `Result<T>` |
| Callers need known, typed business outcomes | Sealed result type |
| Represent what a screen currently renders | UI state |
| Streaming updates over time | `Flow<T>` carrying values or explicit state |

These approaches can coexist. A data source may throw a technical exception, a repository may map known cases to a typed result, and a ViewModel may convert that result into UI state.

## 5. Model Expected Failures with Sealed Types

Sealed types are useful in shared code because they define known cases that callers can handle exhaustively.

```kotlin
sealed interface AppFailure {
    data object NetworkUnavailable : AppFailure
    data object RequestTimedOut : AppFailure
    data object Unauthorized : AppFailure
    data object Forbidden : AppFailure
    data object NotFound : AppFailure
    data object ServiceUnavailable : AppFailure
    data object InvalidData : AppFailure
    data object Unknown : AppFailure
}
```

This is an illustrative model. Choose categories that matter to your use cases and observability needs rather than copying the list unchanged.

### Keep domain meaning separate from technical details

```kotlin
sealed interface CheckoutFailure {
    data object CartEmpty : CheckoutFailure
    data object AddressRequired : CheckoutFailure
    data object PaymentDeclined : CheckoutFailure
    data object InventoryChanged : CheckoutFailure
}
```

The UI does not need to know whether an inventory failure originated from an HTTP `409`, a database transaction, or a cache consistency check. That mapping belongs closer to the data boundary.

### Avoid string-based branching

Fragile:

```kotlin
if (exception.message?.contains("timeout") == true) {
    retry()
}
```

Messages may change, be localized, contain server text, or represent different causes. Prefer mapping known exception types and response codes to typed categories.

A sealed type is useful when a distinction changes application behavior. It is unnecessary to create a unique failure class for every low-level exception if the app treats them identically.

## 6. Build a Shared Result Model

A reusable result wrapper can make the success/failure contract consistent across repositories and use cases. The following is an application-level type, not a Kotlin standard-library type.

```kotlin
sealed interface AppResult<out T> {
    data class Success<T>(val value: T) : AppResult<T>
    data class Failure(val cause: AppFailure) : AppResult<Nothing>
}
```

```kotlin
sealed interface AppFailure {
    data object Offline : AppFailure
    data object Timeout : AppFailure
    data object Unauthorized : AppFailure
    data object NotFound : AppFailure
    data object InvalidResponse : AppFailure
    data object Unknown : AppFailure
}
```

The `out T` makes the result covariant, while `Nothing` allows `Failure` to be used as `AppResult<T>` for any `T`.

### Consume results explicitly

```kotlin
fun renderProfile(result: AppResult<Profile>) {
    when (result) {
        is AppResult.Success -> renderContent(result.value)
        is AppResult.Failure -> renderFailure(result.cause)
    }
}
```

A real UI layer would typically update observable state rather than call rendering functions directly, but the exhaustive branch illustrates the contract.

### Should every project create `AppResult`?

No. If standard `Result<T>` already meets the team's needs, another wrapper can add ceremony without value. A custom result model is worthwhile when it provides stable, typed failure categories and prevents technical exceptions from leaking across architectural boundaries.

Keep the contract consistent. Avoid having some repositories return nullable values, others return `Result<T>`, and others return unrelated wrappers without a clear reason.

## 7. Map Errors at Layer Boundaries

Low-level failures should be translated once, close to where the code understands their meaning. This avoids duplicated mapping logic across ViewModels and screens.

```kotlin
suspend fun loadProfile(): AppResult<Profile> {
    return try {
        val profile = remoteDataSource.fetchProfile()
        AppResult.Success(profile)
    } catch (cancelled: kotlinx.coroutines.CancellationException) {
        throw cancelled
    } catch (exception: java.io.IOException) {
        AppResult.Failure(AppFailure.Offline)
    } catch (exception: Exception) {
        AppResult.Failure(AppFailure.Unknown)
    }
}
```

This snippet is illustrative, not a complete network classification policy. `IOException` can represent multiple conditions; it does not always mean the device is offline. Map only what you can identify reliably.

A more detailed mapping may look like this:

```text
Transport timeout         → Timeout
Confirmed no connectivity → Offline
HTTP 401                  → Unauthorized
HTTP 404                  → NotFound, if meaningful for this endpoint
HTTP 503                  → ServiceUnavailable
Malformed response        → InvalidResponse
Unclassified failure      → Unknown
```

The mapping must respect the API contract. A `404` might mean “no search results” for one endpoint and “resource not found” for another.

### Preserve diagnostic context safely

A stable failure category helps application logic. Engineers may also need the original exception for logs or crash diagnostics. Keep those details in an appropriate observability path rather than exposing the raw exception to the UI. Never log access tokens, passwords, payment details, or other sensitive payloads.

Catch exceptions at boundaries where you can translate, recover, or add context. Avoid a catch-all around an entire application flow if it prevents cancellation and programming defects from remaining visible.

## 8. Handle Coroutine Cancellation Correctly

Coroutine cancellation is control flow, not an ordinary application failure.

A coroutine may be cancelled because the user leaves a screen, a parent job is cancelled, a newer request replaces an older request, or the application shuts down a task.

### Incorrect pattern

```kotlin
suspend fun loadItems(): AppResult<List<Item>> {
    return try {
        AppResult.Success(dataSource.loadItems())
    } catch (exception: Exception) {
        AppResult.Failure(AppFailure.Unknown)
    }
}
```

`CancellationException` is an exception and can be caught by this broad handler. Swallowing it can break structured concurrency.

### Better pattern

```kotlin
suspend fun loadItems(): AppResult<List<Item>> {
    return try {
        AppResult.Success(dataSource.loadItems())
    } catch (cancelled: kotlinx.coroutines.CancellationException) {
        throw cancelled
    } catch (exception: java.io.IOException) {
        AppResult.Failure(AppFailure.Offline)
    } catch (exception: Exception) {
        AppResult.Failure(AppFailure.Unknown)
    }
}
```

The exact exception mapping should be tailored to the data source. The important rule is to rethrow cancellation before handling ordinary failures.

Use `finally` for cleanup that must run when an operation exits:

```kotlin
try {
    performOperation()
} finally {
    releaseTemporaryResource()
}
```

Do not use cleanup code that blocks cancellation indefinitely. A timeout can surface as cancellation-related behavior depending on the API. Decide deliberately whether a specific timeout should be translated into a typed failure. Do not classify every `CancellationException` as a timeout: user-initiated and parent cancellation must remain cancellation.

## 9. Error Handling in Repositories and Use Cases

A repository should define a predictable contract. It should not silently change a failed operation into a successful value.

### Repository responsibilities

- Coordinate remote, local, and cache data sources.
- Map technical failures to stable data/domain-facing categories.
- Preserve cancellation.
- Decide whether a fallback is valid.
- Avoid exposing platform-specific implementation details.

### Use-case responsibilities

A use case applies business rules and coordinates domain operations. It may return a typed domain failure when a business precondition is not met.

```kotlin
sealed interface RenameAccountResult {
    data object Success : RenameAccountResult
    data object NameRequired : RenameAccountResult
    data object NameTooLong : RenameAccountResult
    data object UpdateFailed : RenameAccountResult
}
```

```kotlin
class RenameAccountUseCase(
    private val repository: AccountRepository
) {
    suspend operator fun invoke(name: String): RenameAccountResult {
        val normalized = name.trim()

        if (normalized.isEmpty()) {
            return RenameAccountResult.NameRequired
        }

        if (normalized.length > 60) {
            return RenameAccountResult.NameTooLong
        }

        return when (repository.rename(normalized)) {
            is AppResult.Success -> RenameAccountResult.Success
            is AppResult.Failure -> RenameAccountResult.UpdateFailed
        }
    }
}
```

This example intentionally shows a simple mapping. A real application may need to distinguish conflict, authorization, connectivity, and server failures rather than collapsing every repository failure into `UpdateFailed`.

### Fallbacks must be semantically correct

A cached response can be a valid fallback for a read operation when the product supports offline access. Returning a default account, empty cart, or empty list after a failed write is usually not a valid substitute for success.

Ask:

1. Does the fallback represent truthful data?
2. Will the caller know it is stale or incomplete?
3. Can the fallback violate a business invariant?
4. Is the fallback safe for this operation?
5. Should the failure remain visible for retry or diagnostics?

If the fallback changes the meaning of the operation, model it explicitly.

## 10. Avoid Error-Handling Anti-Patterns

### Anti-pattern 1: Swallowing errors

```kotlin
try {
    repository.saveProfile(profile)
} catch (_: Exception) {
    // Nothing happens.
}
```

The caller cannot tell whether the save succeeded. The UI may show success even though no change was persisted.

**Better:** propagate the failure or return an explicit outcome that the caller must handle.

### Anti-pattern 2: Returning fake success values

```kotlin
catch (_: Exception) {
    emptyList()
}
```

This turns a failed request into a successful empty response. The UI may show “No results” instead of “Could not load results.”

**Better:** return an explicit failure and reserve empty collections for successful empty data.

### Anti-pattern 3: Exposing raw exception messages

```kotlin
uiState.value = Error(exception.message ?: "Unknown error")
```

Technical messages are not stable user-facing copy and may leak implementation details.

**Better:** map to a semantic category and let the UI choose localized wording.

### Anti-pattern 4: Catching `Throwable` for normal recovery

`Throwable` includes serious runtime conditions that application code generally should not treat as recoverable operational failures.

**Better:** catch expected exception types. Use broad handling only at a deliberate process or reporting boundary, and never swallow cancellation.

### Anti-pattern 5: Parsing exception text

```kotlin
if (exception.message?.contains("401") == true) {
    signOut()
}
```

**Better:** inspect structured response information at the network boundary and map it to a typed failure.

### Anti-pattern 6: Duplicating mappings in every screen

If each screen knows how to classify `IOException`, HTTP errors, and serialization exceptions, changes become expensive and inconsistent.

**Better:** centralize technical mapping and expose a stable contract to presentation code.

### Anti-pattern 7: Treating every failure as retryable

A retry can help with a temporary timeout. It will not fix invalid input, a permission denial, or a declined payment.

**Better:** expose retryability or a recovery action only when the application has enough information to justify it. For writes, consider idempotency and duplicate-submission risk before automatic retries.

## 11. Testing Error Paths

Error handling is incomplete until failure behavior is tested. The happy path confirms that data can flow through the system; failure tests confirm that the application behaves honestly and recovers safely.

### Test the repository

Verify that:

- A successful data-source response becomes `Success`.
- Known transport failures map to the expected category.
- Relevant HTTP statuses are classified according to endpoint semantics.
- Malformed data is not mistaken for empty success.
- Cancellation is rethrown.
- Unknown exceptions do not leak raw messages into UI-facing results.
- Fallback data is used only when the contract permits it.

### Test the use case

Verify that:

- Invalid input returns the correct domain outcome.
- Valid input reaches the repository.
- Repository failures are mapped intentionally.
- The repository is not called when a precondition fails.
- Cancellation and unexpected failures follow the documented contract.

### Test presentation behavior

Verify that:

- Loading transitions to content on success.
- Failure shows a recoverable state when appropriate.
- Retry invokes the expected operation.
- Existing content is retained during a failed refresh when required.
- Authentication failures trigger the correct sign-in path.
- Cancellation does not show an ordinary error banner.

### Example test outline

```kotlin
@Test
fun invalidNameDoesNotCallRepository() = runTest {
    val repository = FakeAccountRepository()
    val useCase = RenameAccountUseCase(repository)

    val result = useCase("   ")

    assertEquals(RenameAccountResult.NameRequired, result)
    assertEquals(0, repository.renameCallCount)
}
```

This test assumes a fake repository and `runTest` from `kotlinx-coroutines-test`. Add the appropriate test dependencies and adapt the fake to your repository interface.

Prefer assertions on typed outcomes such as `AppFailure.Timeout` rather than implementation-specific exception messages. For UI tests, assert semantic state or expected user-visible behavior, not internal exception text.

## 12. Production Checklist

### Error model
- [ ] Expected failures have a clear, stable contract.
- [ ] Domain failures do not depend on platform-specific types.
- [ ] Empty success is distinct from failed retrieval.
- [ ] The model distinguishes failures only where behavior needs to differ.

### Layer boundaries
- [ ] Technical exceptions are mapped at a suitable boundary.
- [ ] Presentation code does not parse exception messages.
- [ ] Raw exceptions are not shown directly to users.
- [ ] Unknown failures remain diagnosable.
- [ ] Fallbacks preserve the truth and meaning of the operation.

### Coroutines
- [ ] `CancellationException` is rethrown when caught.
- [ ] Work has a clear coroutine-scope owner.
- [ ] Timeout handling is not confused with all cancellation.
- [ ] Cleanup is safe and does not block cancellation indefinitely.

### Security and observability
- [ ] Logs exclude secrets and sensitive payloads.
- [ ] User-facing messages are localized and actionable.
- [ ] Diagnostic events include useful, non-sensitive context.
- [ ] Retry policies account for operation semantics and duplicate writes.

### Tests
- [ ] Success and expected failure paths are covered.
- [ ] Unknown failures are handled intentionally.
- [ ] Cancellation behavior is tested.
- [ ] Retry and fallback behavior is tested.
- [ ] UI state transitions are verified.

## 13. Summary

Strong error handling makes failure explicit without making the entire application depend on low-level technical details.

1. **Model expected failures** instead of hiding them behind empty values or generic exceptions.
2. **Translate at boundaries** where technical details become meaningful application outcomes.
3. **Keep shared failures platform-neutral** so Android and iOS can render them appropriately.
4. **Separate repository results from UI state.** They answer different questions.
5. **Preserve coroutine cancellation.** Cancellation is not an ordinary failure.
6. **Do not expose raw exception messages** as user-facing copy.
7. **Use fallbacks only when they preserve the operation's meaning.**
8. **Test failure paths as deliberately as success paths.**

A mature application is not one that never fails. It is one that knows what failed, communicates the right level of detail, recovers when recovery is valid, and keeps unexpected defects visible to the team.
