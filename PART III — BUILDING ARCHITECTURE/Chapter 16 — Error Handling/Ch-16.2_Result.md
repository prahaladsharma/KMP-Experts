## 1. Why `Result<T>`?

In application code, many operations have two broad outcomes:

- The operation succeeds and produces a value.
- The operation fails and the caller needs to respond.

A conventional function may throw an exception when it fails:

```kotlin
suspend fun loadAccount(): Account
```

The signature communicates the successful value, but it does not show the failure contract. A caller may need to inspect documentation or implementation details to know what can go wrong.

With `Result<T>`, the return type makes the two broad outcomes visible:

```kotlin
suspend fun loadAccount(): Result<Account>
```

Kotlin's standard `Result<T>` represents either a successful value of type `T` or a failure represented by a `Throwable`.

This can be useful for:

- Repository calls that deliberately expose expected operational failures.
- Use cases that need to pass a success/failure outcome to a caller.
- Parsing and validation operations with a clear failure contract.
- Shared code whose callers run on Android, iOS, desktop, or other Kotlin Multiplatform targets.
- Composing transformations without repeating the same branching logic.

However, `Result<T>` is not automatically the right return type for every function. Use it when the caller benefits from receiving failure as data. For programming defects or failures that should propagate, throwing may be clearer.

> **Key idea:** `Result<T>` does not prevent failure. It makes a function's success/failure outcome explicit to its caller.

## 2. Understand Kotlin's Standard `Result`

Kotlin provides `Result<T>` in the standard library. It is a value wrapper that can represent success or failure.

```kotlin
val success: Result<Int> = Result.success(42)

val failure: Result<Int> = Result.failure(
    IllegalStateException("Account is unavailable")
)
```

The two outcomes are inspected with methods such as:

- `isSuccess`
- `isFailure`
- `getOrNull()`
- `exceptionOrNull()`
- `getOrElse { ... }`
- `getOrThrow()`
- `fold(onSuccess, onFailure)`

### Read a result

```kotlin
fun printResult(result: Result<String>) {
    if (result.isSuccess) {
        println(result.getOrNull())
    } else {
        println(result.exceptionOrNull())
    }
}
```

This works, but many applications can express the same intent more clearly with `fold` or the transformation methods covered below.

### What does failure contain?

A standard `Result` stores a `Throwable`, not an application-specific error enum. That gives it flexibility, but it also means the caller may need to map technical exceptions into a stable application-level category.

For example, a raw `IOException` is useful diagnostic context, but it does not necessarily tell the UI whether the user should retry, sign in, or correct input.

### `Result` is not a network library

The type itself does not:

- Make a request.
- Catch exceptions automatically.
- Retry a failed operation.
- Decide whether a failure is recoverable.
- Localize an error message.
- Preserve coroutine cancellation correctly by itself.

Those responsibilities belong to the function that creates the result and to the layers that consume it.

## 3. Define a Clear Contract

Before choosing `Result<T>`, decide which failures the function converts into a `Result.failure(...)` and which failures are allowed to propagate.

Consider a repository contract:

```kotlin
interface AccountRepository {
    suspend fun loadAccount(): Result<Account>
}
```

The contract should be documented so callers know what a failure means. For example:

- Known remote-service failures are returned as failures.
- A missing account may be represented as a failure or as a distinct domain outcome, depending on the use case.
- Coroutine cancellation is rethrown.
- Unexpected programming defects are not silently turned into ordinary operational failures.

This is more useful than returning `Result<Account>` while leaving every behavior undefined.

### A result is not always enough to express domain meaning

Suppose a sign-in operation can produce these outcomes:

- Credentials are invalid.
- The account is locked.
- Multi-factor authentication is required.
- The service is temporarily unavailable.

A `Result<Session>` can technically represent all of them as exceptions. But if callers must reliably distinguish these outcomes, a domain-specific sealed result may provide a clearer contract.

Use standard `Result<T>` when “success value or failure throwable” is a useful abstraction. Use a custom type when the set of business outcomes is part of the API itself.

### Avoid mixed contracts

A function should not sometimes return `Result.failure(...)`, sometimes return a fabricated default value, and sometimes throw the same expected failure without a documented reason.

Choose a consistent contract:

```text
Expected operational failure → Result.failure(...)
Successful operation         → Result.success(value)
Cancellation                 → Propagate cancellation
Unexpected defect            → Usually propagate or report at a deliberate boundary
```

The exact contract may vary by layer, but it should be intentional.

## 4. Create and Inspect Results

### Create a successful result

```kotlin
fun parseQuantity(raw: String): Result<Int> =
    runCatching { raw.trim().toInt() }
```

For `"12"`, the result contains `12`. For `"twelve"`, parsing fails.

`runCatching` catches any `Throwable`, so this compact form is appropriate only when that broad capture is acceptable. In coroutine code, it must not be allowed to swallow cancellation; a safer boundary is shown later.

### Create a failure explicitly

```kotlin
fun validateAccountId(id: String): Result<String> {
    if (id.isBlank()) {
        return Result.failure(
            IllegalArgumentException("Account ID must not be blank")
        )
    }

    return Result.success(id)
}
```

This is useful for illustrating the API, but do not make callers parse the exception message to identify validation errors. If validation failures are expected business outcomes, a typed domain result may be better.

### Get the value or a fallback

```kotlin
val displayName = result.getOrElse { error ->
    "Guest"
}
```

A fallback is appropriate only if it is semantically correct. A guest label may be a valid UI fallback; a fake account object after a failed account fetch could be misleading.

### Get a nullable value

```kotlin
val account: Account? = result.getOrNull()
```

This is concise, but it discards the reason for failure. Use it only when the caller genuinely does not need to distinguish failure causes.

### Rethrow the failure

```kotlin
val account: Account = result.getOrThrow()
```

`getOrThrow()` returns the success value or throws the stored exception. It is useful when adapting a result-based API back to a throwing API, but it moves the failure back into exception-based control flow.

## 5. Transform Successful Values

One of the most useful features of `Result<T>` is that it supports transformations without requiring an explicit `if` branch for every operation.

### `map`

`map` transforms a successful value. If the result is already a failure, that failure is carried forward.

```kotlin
val accountName: Result<String> =
    accountResult.map { account ->
        account.name
    }
```

Conceptually:

```text
Success(Account) ──map──▶ Success(account.name)
Failure(error)   ──map──▶ Failure(error)
```

This is helpful when the next operation is a pure transformation that does not itself return a `Result`.

### `mapCatching`

Use `mapCatching` when the transformation may throw and you want that thrown exception captured as a failure:

```kotlin
val normalizedEmail: Result<String> =
    emailResult.mapCatching { email ->
        normalizeEmail(email)
    }
```

The transformation runs only for success. If it throws, the output becomes a failure.

**Important:** `mapCatching` catches `Throwable`, so do not casually use it around suspending work or logic where cancellation must propagate. It is intended for a synchronous transformation inside the result pipeline.

### Do not use `map` to return another result

This creates a nested result:

```kotlin
val nested: Result<Result<Profile>> =
    accountIdResult.map { id ->
        loadProfileResult(id)
    }
```

Nested results are often harder to consume than necessary. If the transformation itself returns a `Result`, use an explicit composition helper or branch clearly.

Kotlin's standard `Result` API does not provide a built-in `flatMap` member in the same way some functional libraries do. You can define a small project-level helper if it makes the contract clearer:

```kotlin
inline fun <T, R> Result<T>.flatMap(
    transform: (T) -> Result<R>
): Result<R> =
    fold(
        onSuccess = transform,
        onFailure = { Result.failure(it) }
    )
```

Usage:

```kotlin
val profileResult: Result<Profile> =
    accountIdResult.flatMap { id ->
        loadProfileResult(id)
    }
```

This helper is synchronous because standard `Result` transformations are not suspending. For a suspend function, use an ordinary suspend function with an explicit branch rather than trying to call a suspend operation inside this helper.

## 6. Chain Operations with `map` and `fold`

A result pipeline is easiest to read when each transformation has one clear responsibility.

Imagine these functions:

```kotlin
fun parseAccountId(raw: String): Result<AccountId>
fun validateAccountId(id: AccountId): Result<AccountId>
fun formatAccountLabel(id: AccountId): Result<String>
```

They can be composed with a `flatMap` helper if your project defines one:

```kotlin
val labelResult =
    parseAccountId(rawId)
        .flatMap(::validateAccountId)
        .flatMap(::formatAccountLabel)
```

Each failure short-circuits the remaining transformations. That means later steps run only when the previous step succeeds.

### `fold`

`fold` handles both outcomes and returns a value from either branch:

```kotlin
val message: String = result.fold(
    onSuccess = { account ->
        "Welcome, ${account.name}"
    },
    onFailure = {
        "We couldn't load your account."
    }
)
```

Unlike `getOrNull()`, `fold` makes the caller handle success and failure in one expression. Unlike exposing an exception message, it lets the application choose a safe message.

### Use `fold` at a meaningful boundary

For example, a ViewModel or presenter can map a repository result to UI state:

```kotlin
val nextState = result.fold(
    onSuccess = { account ->
        AccountUiState.Content(account)
    },
    onFailure = { throwable ->
        AccountUiState.Error(
            message = mapToUserMessage(throwable)
        )
    }
)
```

Here `AccountUiState`, `mapToUserMessage`, and the account types represent application-level contracts. The important part is the boundary: technical failure becomes presentation state in one intentional place.

### Keep transformations readable

A long pipeline of nested lambdas can become harder to debug than a few named functions. Prefer composition when each step is simple and the overall flow remains obvious. Use explicit branching when it communicates the business rule more clearly.

## 7. Use `recover` Without Hiding Failure

`recover` transforms a failure into a successful value. It is useful when a fallback genuinely satisfies the function's contract.

```kotlin
val title: Result<String> =
    remoteTitleResult.recover {
        "Untitled"
    }
```

If the remote title fails to load, the result becomes a successful `"Untitled"` value.

`recoverCatching` is similar, but it captures exceptions thrown by the recovery transformation.

### When recovery is appropriate

Examples include:

- A non-critical display label has a safe default.
- A cache is explicitly allowed as a fallback for a read.
- A preference value can be replaced by a documented default.
- A best-effort analytics operation is intentionally non-blocking.

### When recovery is dangerous

Do not recover a failed payment by returning a fake receipt. Do not recover a failed write by pretending it was saved. Do not turn an authorization failure into an empty successful response if that would hide a security issue.

A good recovery policy answers:

1. Is the fallback valid for the business operation?
2. Does the caller need to know that fallback data was used?
3. Can the fallback be stale or incomplete?
4. Could the fallback create duplicate writes or inconsistent state?
5. Should the original failure still be logged or measured?

### Preserve stale-data meaning

If a cache is used after a network failure, callers may need to know that the value is stale. A plain `Result<T>` may not express this distinction by itself.

For that case, consider a richer return model:

```kotlin
data class LoadedValue<T>(
    val value: T,
    val source: DataSource,
    val isStale: Boolean
)

enum class DataSource {
    Network,
    Cache
}
```

This example represents successful data with metadata. The operation's failure contract can still be handled separately. The design should not force stale success and fresh success to look identical if the UI or business rules care about freshness.

## 8. Convert Exceptions at the Boundary

`runCatching` is a concise way to execute a block and capture thrown failures:

```kotlin
val result: Result<Profile> = runCatching {
    remoteDataSource.fetchProfile()
}
```

This can be reasonable for synchronous operations, but it captures `Throwable`, not just ordinary exceptions. That matters for cancellation and severe runtime conditions.

### Coroutine-safe boundary

When wrapping suspending work, preserve cancellation explicitly:

```kotlin
suspend fun fetchProfileResult(): Result<Profile> {
    return try {
        Result.success(remoteDataSource.fetchProfile())
    } catch (cancelled: kotlinx.coroutines.CancellationException) {
        throw cancelled
    } catch (exception: Exception) {
        Result.failure(exception)
    }
}
```

This is a pattern, not a complete policy. You may want to catch only known transport exceptions and map them to a stable failure category rather than returning every exception unchanged.

### Map technical exceptions into stable failures

If a repository returns standard `Result<T>`, its callers receive a `Throwable`. A mapper can classify known cases:

```kotlin
fun Throwable.toAppFailure(): AppFailure =
    when (this) {
        is java.net.SocketTimeoutException -> AppFailure.Timeout
        is java.io.IOException -> AppFailure.Network
        else -> AppFailure.Unknown
    }
```

This example is intentionally small. `IOException` does not prove the device is offline, and exception types differ by platform and networking library. Add mappings only when the distinction is reliable for your targets.

A platform-neutral common module should avoid importing JVM-only exception classes unless the mapping is deliberately placed in a JVM-specific source set. In `commonMain`, use common contracts or place platform-specific mapping behind an interface implemented in platform source sets.

### Never map by exception message

Fragile:

```kotlin
if (throwable.message?.contains("timeout") == true) {
    AppFailure.Timeout
}
```

Messages are unstable and may contain sensitive data. Prefer structured exception types or transport response metadata.

## 9. `Result` with Coroutines and `Flow`

`Result<T>` can be returned from a suspend function, emitted by a flow, or used when collecting a one-shot operation. The right choice depends on whether the operation is a single request or a continuing stream.

### One-shot suspend operation

```kotlin
suspend fun refreshAccount(): Result<Account>
```

A caller invokes it once and receives one outcome.

### A flow of results

```kotlin
fun observeAccount(): Flow<Result<Account>>
```

This means the stream may emit multiple success/failure values over time. Be precise about the semantics: does one failure terminate the upstream flow, or is the failure emitted as a value and collection continues? That behavior should be part of the API contract.

### Prefer explicit UI state for ongoing screens

For many screens, a state model is clearer than a flow of `Result<T>`:

```kotlin
sealed interface AccountUiState {
    data object Loading : AccountUiState
    data class Content(val account: Account) : AccountUiState
    data class Error(val canRetry: Boolean) : AccountUiState
}
```

A screen often needs to represent loading, content, and error simultaneously or retain old content during a refresh. `Result<T>` describes one operation's outcome; UI state describes the current presentation.

### Do not swallow cancellation in a flow

Broad exception operators and `runCatching` can accidentally turn cancellation into an ordinary failure. When handling errors in a coroutine pipeline:

- Preserve cancellation.
- Decide whether the flow should emit a failure or terminate.
- Keep retry policies explicit.
- Avoid retrying permanent failures endlessly.
- Test cancellation and upstream failure separately.

### Retry belongs to policy, not the type

`Result<T>` does not imply that retries are safe. Before retrying, consider:

- Whether the failure is transient.
- Whether the operation is idempotent.
- Whether the server may already have completed a write.
- Whether retry limits and backoff are needed.
- Whether the user should explicitly choose to retry.

A failed read and a failed payment submission should not automatically share the same retry policy.

## 10. Design Repository and Use-Case APIs

The repository should make its contract predictable. The use case should translate outcomes only when business meaning requires it.

### Repository example

```kotlin
interface ProductRepository {
    suspend fun getProduct(id: String): Result<Product>
}
```

The implementation owns transport and storage details. It should preserve cancellation and avoid treating failed retrieval as a successful default product.

### Use-case example

```kotlin
class GetProductUseCase(
    private val repository: ProductRepository
) {
    suspend operator fun invoke(id: String): Result<Product> {
        if (id.isBlank()) {
            return Result.failure(
                IllegalArgumentException("Product ID is required")
            )
        }

        return repository.getProduct(id)
    }
}
```

This is a minimal example. In a mature domain layer, invalid input may be better represented by a typed domain failure than by `IllegalArgumentException`, because validation is an expected outcome.

### Presentation mapping

```kotlin
suspend fun loadProduct(id: String) {
    uiState.value = ProductUiState.Loading

    val result = getProductUseCase(id)

    uiState.value = result.fold(
        onSuccess = { product ->
            ProductUiState.Content(product)
        },
        onFailure = { throwable ->
            mapFailureToProductUiState(throwable)
        }
    )
}
```

The snippet illustrates the flow, not a complete thread-safe state holder. In production, use the appropriate `StateFlow`, reducer, or platform presentation mechanism for your architecture.

### Do not leak transport details upward

A ViewModel should not need to know how a particular HTTP client represents a timeout. Map technical details near the data boundary and expose a stable failure contract.

If the caller needs to distinguish business outcomes, avoid flattening everything into a generic exception. A domain-specific sealed result can be more appropriate than standard `Result<T>`.

## 11. Standard `Result` or a Custom Result Type?

Both can be valid. The key is to choose based on what the caller needs to know.

| Question | Standard `Result<T>` | Custom sealed result |
|---|---|---|
| Can it represent success/failure? | Yes | Yes |
| Does failure carry a `Throwable`? | Yes | Only if designed to |
| Does it define business failure categories? | No | Can do so explicitly |
| Is it concise for simple operations? | Usually | May add boilerplate |
| Can `when` enforce known business outcomes? | Not directly for each failure reason | Yes, with sealed variants |
| Is it suitable for a generic utility API? | Often | Depends on the contract |
| Is it automatically cancellation-safe? | No | No; implementation must preserve cancellation |

### Use standard `Result<T>` when

- A function has a simple success/failure contract.
- The throwable is useful to the caller or a mapper.
- You want to use the standard library rather than invent another wrapper.
- The project has a consistent policy for mapping failures.

### Use a custom sealed result when

- Business outcomes are known and materially different.
- Callers should handle each outcome exhaustively.
- Exposing a `Throwable` would leak technical details across layers.
- The public API needs a stable contract independent of implementation exceptions.

### Avoid duplicate abstractions

Creating `AppResult`, `NetworkResult`, `Resource`, `Either`, `Outcome`, and `ResponseState` for the same purpose can make an architecture harder to understand.

Use multiple types only when they serve different responsibilities—for example, a repository outcome, a domain result, and a UI state may differ for good reasons. Document those differences.

## 12. Testing Result-Based Code

Test both outcomes, and verify the contract—not the internal wording of exceptions.

### Success test

```kotlin
@Test
fun successfulLoadReturnsAccount() = runTest {
    val expected = Account(id = "a-17", name = "Mira")
    val repository = FakeAccountRepository(
        result = Result.success(expected)
    )

    val result = repository.loadAccount()

    assertEquals(expected, result.getOrNull())
    assertTrue(result.isSuccess)
}
```

This is an illustrative test. Adapt the constructors, test framework, and fake repository to your project.

### Failure test

```kotlin
@Test
fun failedLoadPreservesFailure() = runTest {
    val cause = IOException("Connection reset")
    val repository = FakeAccountRepository(
        result = Result.failure(cause)
    )

    val result = repository.loadAccount()

    assertTrue(result.isFailure)
    assertSame(cause, result.exceptionOrNull())
}
```

### Test transformations

Verify that:

- `map` transforms success.
- `map` preserves an existing failure.
- `mapCatching` captures a thrown transformation exception.
- `recover` creates success only when the fallback is valid.
- `fold` invokes the correct branch.
- A custom `flatMap` helper propagates the first failure.

### Test cancellation explicitly

For suspending code, verify that cancellation is not converted into `Result.failure(...)`:

```kotlin
@Test
fun cancellationIsRethrown() = runTest {
    val repository = CancellationTestRepository()

    assertFailsWith<CancellationException> {
        repository.loadAccount()
    }
}
```

The test requires a fake whose implementation throws `CancellationException`. In a real coroutine test, also cover cancellation of the parent job and verify that child work stops as expected.

### Test UI mapping separately

Given a result or typed failure, assert the expected UI state:

- Unauthorized → sign-in state.
- Timeout → retryable error state.
- Not found → not-found state.
- Unknown failure → safe generic error state.

Do not assert that the app displays a raw exception message.

## 13. Common Mistakes

| Mistake | Why it is risky | Better approach |
|---|---|---|
| Assuming `Result` catches exceptions automatically | A throwing function can still throw before returning a result | Catch and convert failures at the chosen boundary |
| Using `runCatching` around suspending work without care | Cancellation may be swallowed | Rethrow `CancellationException` |
| Returning `getOrNull()` everywhere | The reason for failure disappears | Keep the result until the caller has made a deliberate decision |
| Using `getOrThrow()` immediately | Failure moves back to exception control flow | Use only when a throwing contract is intended |
| Parsing exception messages | Messages are unstable and may leak data | Map structured exception types or response codes |
| Treating every failure as retryable | Retries can be pointless or unsafe | Define retry policy by failure and operation |
| Recovering with fake data | The caller may believe a failed operation succeeded | Use only semantically valid fallbacks |
| Returning nested `Result<Result<T>>` | Call sites become awkward | Compose results with an explicit helper or branch |
| Using standard `Result` for every business outcome | Business meaning may be hidden in exception types | Use a sealed domain result when exhaustive cases matter |
| Duplicating result wrappers | Too many similar abstractions confuse the codebase | Keep one clear contract per responsibility |

## 14. Production Checklist

### API design
- [ ] Each result-returning function documents which failures become `Result.failure`.
- [ ] Expected failures are not inconsistently thrown and returned.
- [ ] Business outcomes are typed when callers need to distinguish them.
- [ ] Standard `Result` and custom result types each have a clear purpose.

### Correctness
- [ ] Cancellation is propagated.
- [ ] No failed operation is silently converted into fake success.
- [ ] Fallbacks are semantically valid.
- [ ] Retry policy considers idempotency and transient failure.
- [ ] Exception messages are not used as control-flow identifiers.

### KMP boundaries
- [ ] `commonMain` does not accidentally depend on JVM-only exception classes.
- [ ] Platform-specific error mapping is isolated behind common contracts where needed.
- [ ] Shared failures can be mapped to localized platform UI messages.
- [ ] Error details exposed to Swift or other consumers are deliberate and stable.

### Testing and observability
- [ ] Success, expected failure, and unknown failure paths are tested.
- [ ] Cancellation behavior is tested.
- [ ] Transformation and recovery behavior is tested.
- [ ] Logs preserve useful diagnostics without sensitive data.
- [ ] User-facing UI never relies on raw exception text.

---

## 15. Summary

Kotlin's standard `Result<T>` is a useful building block for explicit success/failure contracts, but it is not a complete error-handling architecture.

Remember these principles:

1. Use `Result<T>` when callers benefit from handling failure as data.
2. Define which failures are returned and which are allowed to propagate.
3. Use `map`, `fold`, and recovery operations to make simple transformations clearer.
4. Avoid nested results; compose result-returning operations deliberately.
5. Preserve coroutine cancellation, especially around `runCatching` and broad exception handlers.
6. Translate low-level exceptions into stable application meaning at the correct boundary.
7. Use custom sealed outcomes when business cases need exhaustive handling.
8. Test cancellation, recovery, and failure paths—not only success.

A good result contract lets callers respond to failure without guessing, while keeping technical details out of places that do not need them.
