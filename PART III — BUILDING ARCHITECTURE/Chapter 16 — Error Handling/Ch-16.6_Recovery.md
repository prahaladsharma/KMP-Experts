## 1. What Recovery Means

Recovery is the controlled response that lets an application continue, restore a valid state, or guide the user after a failure.

It can mean:

- Returning cached data when a refresh fails.
- Refreshing expired credentials through a supported authentication flow.
- Reopening a database connection after a transient failure.
- Resuming synchronization from durable pending work.
- Reconstructing UI state after process recreation.
- Asking the user to correct invalid input.
- Rolling back a failed local transaction.
- Replaying an idempotent operation after an uncertain result.
- Falling back to a supported feature when an optional dependency is unavailable.

Recovery is not always automatic. Some failures require user input, a new permission, a corrected request, or a server-side decision.

### A basic recovery flow

```text
Operation fails
      │
      ▼
Classify the failure
      │
      ▼
Is there a safe recovery path?
      │
      ├── No ──► Return a meaningful failure state
      │
      ▼
Execute the recovery action
      │
      ▼
Did recovery succeed?
      │
      ├── Yes ──► Continue with valid state
      │
      └── No ───► Stop, report, or request user action
```

The most important constraint is **safety**. Recovery must not make the data less correct, repeat a non-idempotent side effect, conceal a security problem, or continue work after cancellation.

## 2. Classify Failures Before Recovering

Different failures require different recovery actions. A generic “catch and try again” policy often makes a problem harder to diagnose.

| Failure category | Possible recovery | Avoid |
|---|---|---|
| Temporary network error | Bounded retry or cached data | Infinite retries |
| Expired access token | Supported credential refresh, then one bounded replay | Replaying forever |
| Invalid input | Return field-level validation feedback | Retrying unchanged input |
| Serialization mismatch | Reject invalid payload and report diagnostic context | Silently substituting arbitrary defaults |
| Database transaction failure | Roll back; retry only if known safe | Assuming partial writes were committed |
| Stale local data | Refresh or label the data stale | Presenting stale data as authoritative |
| Permission denied | Explain and request permission if appropriate | Repeatedly invoking a denied capability |
| Missing local record | Re-query, recreate only if valid, or report not found | Creating duplicate records automatically |
| Server conflict | Reconcile using domain rules | Blindly overwriting either side |
| Coroutine cancellation | Stop promptly and propagate cancellation | Treating cancellation as a recoverable error |
| Programming defect | Surface diagnostics and fix the defect | Catching everything and returning fake success |

### Make recovery policy explicit

A useful policy answers:

1. What failed?
2. Is the failure expected and understood?
3. What state is still trustworthy?
4. What recovery action is safe?
5. How many recovery attempts are permitted?
6. What happens if recovery also fails?

A typed failure model helps keep this decision consistent across repositories and use cases.

```kotlin
sealed interface AppFailure {
    data object NetworkUnavailable : AppFailure
    data object SessionExpired : AppFailure
    data object InvalidInput : AppFailure
    data object Conflict : AppFailure
    data object StorageUnavailable : AppFailure
    data object Unknown : AppFailure
}
```

These categories are illustrative. Define them around your domain and map platform-specific exceptions at the appropriate boundary.

## 3. Recovery Is Not the Same as Hiding an Error

Consider this implementation:

```kotlin
suspend fun loadBalance(): Balance =
    try {
        api.fetchBalance()
    } catch (failure: Exception) {
        Balance(amount = 0.0)
    }
```

It returns a value, but the value is fabricated. A network failure now looks like a real zero balance. This is not recovery; it is a loss of correctness.

A safer design preserves the distinction between valid data and failure:

```kotlin
sealed interface BalanceLoadState {
    data class Success(val balance: Balance) : BalanceLoadState
    data object Unavailable : BalanceLoadState
    data object RequiresAuthentication : BalanceLoadState
}
```

The exact cases depend on the product. The principle is general: do not manufacture a successful domain value merely to avoid showing an error.

### Recovery must preserve meaning

- A missing list is not necessarily an empty list.
- A failed payment is not necessarily an unpaid payment.
- A timed-out write is not necessarily rejected by the server.
- Cached data is not necessarily fresh data.
- A locally saved change is not necessarily server-confirmed.
- A cancelled task is not necessarily a failed business operation.

When the outcome is uncertain, model that uncertainty rather than guessing.

## 4. A Recovery Decision Model

A recovery policy can be represented as a decision table.

| Condition | Action | Terminal outcome |
|---|---|---|
| Transient failure and budget remains | Retry with backoff | Success or exhausted retry |
| Network read failed but cache is valid | Return cached data and mark stale | Usable content with stale status |
| Session expired and refresh is supported | Refresh credentials once, then replay safely | Success or authentication required |
| Input invalid | Return validation details | User corrects input |
| Local transaction failed | Roll back and report failure | No partial local commit |
| Write outcome unknown | Query status or retry with same idempotency key | Reconciled outcome |
| Version conflict | Apply domain merge or ask the user | Resolved or needs attention |
| Cancellation received | Stop and propagate cancellation | Cancelled operation |
| Unknown defect | Preserve diagnostic context and fail visibly at the right boundary | Investigated defect |

### Recovery should have a budget

A recovery path may include several operations. For example, an API call may fail due to an expired token, trigger one token refresh, and then replay the original request. This should not turn into an unbounded cycle of refresh and replay.

Set limits for:

- Number of recovery attempts.
- Total elapsed time.
- Number of credential-refresh attempts.
- Number of reconciliation queries.
- Number of automatic conflict-resolution attempts.

When a budget is exhausted, return a meaningful state or ask for user action.

## 5. Recovering with Kotlin Result

Kotlin's `Result<T>` represents success or failure of a computation. Its operators are useful for mapping failures and providing fallback values when that fallback is valid.

### Map a failure

```kotlin
fun parseCount(raw: String): Result<Int> =
    runCatching { raw.toInt() }
        .recoverCatching { failure ->
            if (failure is NumberFormatException) {
                0
            } else {
                throw failure
            }
        }
```

This example is valid only if zero is a legitimate default for the particular count. If malformed input must be shown to the user, returning zero would misrepresent the input. A fallback is a product decision, not automatically a good recovery choice.

### Use a domain fallback

```kotlin
suspend fun loadPreferences(): Result<Preferences> =
    runCatching {
        remoteSource.fetchPreferences()
    }.recoverCatching { failure ->
        if (failure is IOException) {
            localSource.readPreferences()
        } else {
            throw failure
        }
    }
```

This illustrates cache fallback. It assumes the local preferences are valid and that `Preferences` has a meaningful offline representation. In production, keep the failure category and freshness metadata visible if they matter to the caller.

### Be careful with `runCatching` in suspend code

`runCatching` catches `Throwable`, which includes coroutine cancellation exceptions. Wrapping suspending work in `runCatching` can therefore accidentally turn cancellation into an ordinary `Result.failure`.

For cancellable coroutine work, use an explicit boundary that rethrows cancellation:

```kotlin
suspend fun <T> runSuspendCatching(
    block: suspend () -> T
): Result<T> =
    try {
        Result.success(block())
    } catch (cancelled: CancellationException) {
        throw cancelled
    } catch (failure: Exception) {
        Result.failure(failure)
    }
```

This helper catches ordinary `Exception` values while preserving cancellation. It should not be used to hide programming defects; callers should decide which failures are expected and recoverable.

## 6. Recovery with Coroutines

Coroutine recovery must respect structured concurrency and cancellation.

### Preserve cancellation

```kotlin
suspend fun refreshData(): RefreshOutcome =
    try {
        remoteSource.refresh()
        RefreshOutcome.Success
    } catch (cancelled: CancellationException) {
        throw cancelled
    } catch (failure: IOException) {
        RefreshOutcome.TemporarilyUnavailable
    }
```

This example maps a known I/O failure to an expected outcome. A production implementation should distinguish network connectivity from other I/O failures if the product needs that precision.

### Recover at a meaningful boundary

A repository may convert expected network failures into stable domain outcomes. A ViewModel may translate those outcomes into UI state. Neither layer should indiscriminately catch every throwable and claim success.

```text
Platform / networking exception
             │
             ▼
Data source boundary
Map transport details
             │
             ▼
Repository
Apply cache and recovery policy
             │
             ▼
Use case
Enforce domain constraints
             │
             ▼
ViewModel
Expose actionable UI state
```

### Timeouts are not proof that a write failed

If a coroutine times out while awaiting a server response, the server may still have processed the request. For reads, retry may be straightforward. For writes, recover through idempotency keys, an operation-status endpoint, or reconciliation when available.

### Do not use broad cancellation suppression

Avoid patterns such as:

```kotlin
// Avoid: cancellation can be swallowed.
try {
    performWork()
} catch (failure: Exception) {
    return fallbackValue()
}
```

If `performWork()` is cancelled, returning a fallback can make the caller believe the operation completed normally. Catch cancellation separately and propagate it.

## 7. Recovering Flow Streams

A Flow pipeline can recover from an upstream failure, but recovery changes stream behavior. Make that behavior explicit.

### Emit a fallback state

```kotlin
fun observeDashboard(): Flow<DashboardState> =
    remoteDashboardSource.observe()
        .map<Dashboard, DashboardState> { dashboard ->
            DashboardState.Content(dashboard)
        }
        .catch { failure ->
            if (failure is CancellationException) throw failure

            emit(DashboardState.Unavailable)
        }
```

This example assumes `Dashboard`, `DashboardState`, and the source flow are defined in the application. It emits a fallback state when upstream collection fails. In a typical Flow pipeline, downstream collector exceptions are not caught by the upstream `catch` operator.

### Prefer a local stream for offline-first content

For content that should remain visible offline, a stronger pattern is to observe the local database and refresh it separately:

```kotlin
fun observeDashboard(): Flow<Dashboard> =
    dashboardLocalSource.observeDashboard()
```

A refresh use case updates the local database on success. The UI receives updates through the local stream, while refresh status is exposed separately.

This avoids turning a remote stream failure into the end of the only source of UI content.

### Recovering a long-lived stream

For a WebSocket or other long-lived connection, recovery may require reconnecting. Use bounded backoff, cancellation-aware delays, and an explicit connection state. Decide whether events can be replayed, whether missed events can be fetched from a cursor, and whether reconnecting can duplicate side effects.

A reconnect is not a complete recovery strategy unless the application also handles missed data and duplicate delivery.

## 8. Cache Fallback and Stale Data

Cache fallback is one of the most useful recovery techniques for mobile applications, but the cache must be trustworthy for the intended use.

### Define freshness rules

A cached item can have several relevant timestamps:

```kotlin
data class CachedValue<T>(
    val value: T,
    val lastSuccessfulRefreshEpochMillis: Long?,
    val lastLocalUpdateEpochMillis: Long?,
    val freshness: Freshness
)

enum class Freshness {
    Fresh,
    Stale,
    Unknown
}
```

This model is illustrative. Freshness should be derived from a defined policy, not set arbitrarily.

### Fallback rules

Use cache fallback when:

- The local data is valid and belongs to the current account.
- The feature permits use of stale data.
- The UI can communicate the data's freshness when necessary.
- The cached representation is not known to be corrupted or invalidated.
- Security policy allows the data to remain available offline.

Do not use cache fallback when the action requires current authoritative state. For example, cached stock availability should not be treated as proof that an item can still be purchased.

### Keep the failure visible without blocking the user

A refresh can fail while the cached content remains usable. The UI can keep showing content and expose a message such as:

> Showing saved information. The latest update is unavailable.

This communicates the state without discarding valid data or implying that a refresh succeeded.

## 9. Recovering from Partial Failure

A workflow can contain multiple operations, and some may succeed before another fails.

For example, a profile screen may load profile details, preferences, and recommendations. If recommendations fail, it may still be useful to show the profile and preferences.

### Independent operations

When operations are independent, model partial success explicitly:

```kotlin
data class DashboardData(
    val profile: Profile?,
    val preferences: Preferences?,
    val recommendations: List<Recommendation>,
    val recommendationsUnavailable: Boolean
)
```

This is an illustrative model. Nullable fields and status flags should reflect actual domain meaning; a richer sealed state may be clearer for more complex workflows.

### Do not confuse partial success with transaction success

For independent reads, partial rendering can be appropriate. For a multi-step write that must be atomic, partial success may violate a business invariant. Such a workflow may need a database transaction, a server-side atomic operation, a saga with compensating actions, or an explicit pending state.

### Compensation is not rollback

A database transaction can often roll back uncommitted local changes. A remote side effect that has already happened may not be reversible by simply throwing an exception.

For multi-step distributed operations, design compensating actions deliberately. For example, if one step reserves inventory and a later step fails, the system may need to release the reservation through a separate command. That compensation can fail too, so it must be observable and recoverable.

## 10. State Repair and Data Reconciliation

Sometimes retrying the original operation is not enough. Recovery requires discovering the actual state and bringing it back into agreement.

### When reconciliation is needed

- A write timed out and its result is unknown.
- A local database update succeeded but a remote acknowledgement was not saved.
- A background worker was terminated mid-sync.
- A server and client hold different versions of an entity.
- A pending operation was delivered more than once.
- A local cache contains records that the server has since deleted.

### A reconciliation workflow

```text
Detect uncertain or inconsistent state
                 │
                 ▼
Identify the affected entity / operation
                 │
                 ▼
Query authoritative state or operation status
                 │
                 ▼
Compare local and remote versions
                 │
       ┌─────────┴─────────┐
       ▼                   ▼
  Can merge safely?     Needs a decision
       │                   │
       ▼                   ▼
Apply and persist     Record conflict and
the resolved state    request resolution
       │                   │
       └─────────┬─────────┘
                 ▼
        Record final outcome
```

### Use versioning when available

Version numbers, ETags, server revisions, or change cursors can help detect stale updates and identify which state is newer according to the server's contract.

Do not assume local wall-clock timestamps are sufficient for conflict detection. Device clocks can drift, and timestamps may not express causality.

### Make repair idempotent

A reconciliation job can be interrupted and run again. Applying the same repair twice should not create duplicate records or repeat irreversible side effects. Persist progress and use stable identifiers where the workflow needs to survive process death.

## 11. UI-Level Recovery

Recovery is complete only when the user can understand the current state and the next available action.

### Separate content state from operation state

A screen can display content while a refresh is failing. Represent those states separately rather than replacing the entire screen with a single error.

```kotlin
data class ProfileScreenState(
    val profile: Profile?,
    val isInitialLoading: Boolean,
    val isRefreshing: Boolean,
    val message: String?,
    val requiresSignIn: Boolean
)
```

This is a minimal example. Production state should avoid contradictory combinations—for example, `requiresSignIn = true` while showing private cached content from an account that has signed out.

### Match the recovery action to the failure

| UI condition | Useful action |
|---|---|
| Temporary refresh failure with cached content | Keep content; offer retry |
| Initial load failure with no cached content | Show error and Retry |
| Invalid form field | Highlight the field and explain the correction |
| Session expired | Offer sign-in or a supported reauthentication flow |
| Permission required | Explain why and offer a permission action when appropriate |
| Conflict requiring user choice | Show the conflicting values and available choices |
| Pending offline change | Show pending status and keep the local change visible |
| Permanent rejection | Explain what must change rather than offering endless Retry |

### Avoid automatic recovery loops driven by UI recomposition

In declarative UI frameworks, rendering can occur frequently. Do not start network recovery work directly in a composable body or on every state update. Trigger work through a well-defined lifecycle-aware effect, ViewModel event, or use case so a recomposition does not repeat side effects.

### Preserve state across recreation

For work that must survive process death, persist the operation or state in durable storage. Saved UI state can restore small presentation details, but it is not a substitute for a database-backed pending-operation queue.

## 12. Recovery Across Kotlin Multiplatform Targets

KMP lets teams share domain-level recovery rules while keeping platform-specific behavior behind clear boundaries.

### Good candidates for shared code

- Domain failure types.
- Recovery policy decisions.
- Retry and reconciliation rules.
- Repository contracts.
- Mapping remote DTOs into domain models.
- Offline queue state transitions.
- Deterministic conflict resolution.
- Tests for recovery decisions.

### Platform-specific concerns

- Database driver configuration and platform storage protection.
- Connectivity monitoring implementation.
- Background scheduling and execution constraints.
- Secure credential storage.
- OS-specific permission flows.
- Platform-specific networking exceptions.

### Keep abstractions focused

```kotlin
interface SyncScheduler {
    suspend fun scheduleSync()
}

interface SessionRecovery {
    suspend fun refreshSession(): SessionRecoveryOutcome
}
```

These are example contracts, not required abstractions for every app. Use them only when shared business logic needs to request a platform capability or when multiple implementations genuinely exist.

### Android recovery

For durable work, use a platform-supported scheduler such as WorkManager where appropriate. A worker should be safe to execute again, persist its progress, and translate retryable failures into the scheduler's retry mechanism rather than maintaining an endless in-memory loop.

### iOS recovery

Background execution is opportunistic and constrained by the operating system. Persist pending operations and make synchronization resumable. Do not assume that a coroutine will continue running after the app is suspended or terminated.

### Shared policy, native execution

The shared layer can decide **what** needs recovery. Platform code often decides **when** durable background work can run. Keep those responsibilities separate.

## 13. Observability and Recovery Signals

A system that recovers silently can still be unhealthy. Measure recovery behavior so that frequent failures do not disappear behind successful fallbacks.

### Useful signals

- Failure category and affected operation.
- Recovery action selected.
- Recovery attempt count.
- Recovery success or exhaustion.
- Time from initial failure to recovered state.
- Cache fallback frequency and age of served data.
- Reconciliation and conflict counts.
- Pending outbox size and oldest pending-operation age.
- Credential-refresh success rate.
- Background worker retries and terminal failures.

### Structured event example

```text
operation=refresh_profile
failure_category=timeout
recovery_action=serve_cache
recovery_attempt=1
recovery_outcome=cache_available
```

This is an illustrative event. Use stable, low-cardinality categories. Do not include credentials, personal data, raw request payloads, or sensitive exception messages.

### Distinguish user-facing and diagnostic messages

User-facing text should explain the state and next action. Diagnostic telemetry should help engineers identify the root cause. Do not expose stack traces or internal service details directly in the UI.

### Alert on repeated recovery

If most requests succeed only after repeated retries, or the outbox grows continuously, the application may be masking a service incident. Recovery metrics should help distinguish resilience from a persistent underlying failure.

## 14. Testing Recovery Paths

Recovery paths often contain more edge cases than the happy path. Test them explicitly with fake repositories, controlled clocks, deterministic retry policies, and test dispatchers.

### Essential scenarios

| Scenario | Expected result |
|---|---|
| Remote read fails; valid cache exists | Cached data remains visible with accurate freshness |
| Remote read fails; no cache exists | Meaningful initial-load failure state |
| Credential refresh succeeds | Original safe request is replayed within a bounded policy |
| Credential refresh fails | Authentication-required state is returned |
| Coroutine is cancelled | Cancellation propagates; no fallback is reported as success |
| Local transaction fails | No partial state is committed |
| Write response is lost | Reconciliation or idempotent replay prevents duplicate effects |
| One independent dashboard request fails | Other valid sections can still render |
| Distributed workflow step fails | Defined compensation or pending state is recorded |
| Conflict cannot be merged | State is preserved for explicit resolution |
| Recovery budget is exhausted | Operation stops with an actionable result |
| Process dies during synchronization | Durable work can safely resume |

### Example: preserve cancellation

```kotlin
@Test
fun cancellationIsNotConvertedIntoFallback() = runTest {
    val result = runCatching {
        runSuspendCatching {
            throw CancellationException("Cancelled")
        }
    }

    // The inner helper rethrows cancellation rather than returning
    // Result.failure. Assert the behavior at the appropriate boundary.
    assertTrue(result.isFailure)
}
```

This test illustrates the cancellation boundary, but the outer `runCatching` captures the cancellation for assertion purposes. Production suspend code should not use that outer wrapper to suppress cancellation. A more direct test can use `assertFailsWith<CancellationException>` around the helper invocation.

### Example: test a recovery decision

```kotlin
@Test
fun transientFailureUsesCacheWhenAvailable() = runTest {
    val cachedProfile = profile(id = "profile-1")
    val repository = FakeProfileRepository(
        cached = cachedProfile,
        refreshFailure = IOException("Temporary failure")
    )

    val result = repository.loadProfile()

    assertEquals(cachedProfile, result.profile)
    assertEquals(Freshness.Stale, result.freshness)
}
```

The names in this example represent test fixtures and a domain result defined by the application. The assertion verifies the behavior users depend on, rather than a specific internal call sequence.

### Avoid flaky recovery tests

- Do not use real network outages to test a retry policy.
- Avoid real-time delays when virtual time or injected delays are available.
- Make clocks and random jitter controllable.
- Verify attempt limits and terminal outcomes.
- Test process restart and duplicate delivery for durable workflows.
- Use integration tests for server idempotency and API contract behavior.

## 15. Common Anti-Patterns

| Anti-pattern | Why it fails | Better approach |
|---|---|---|
| Return fake success after any exception | Hides invalid or missing data | Return a typed failure or valid fallback |
| Catch `Exception` without rethrowing cancellation | Converts cancellation into ordinary success/failure | Handle `CancellationException` separately |
| Retry every failure | Repeats permanent failures and can amplify incidents | Classify failures and bound recovery |
| Refresh credentials indefinitely | Creates an authentication loop | Limit refresh/replay and return sign-in state |
| Use stale cache for authoritative actions | Can violate business rules | Require fresh server validation where needed |
| Retry uncertain writes with new identifiers | Can create duplicate effects | Reuse idempotency keys or reconcile |
| Assume rollback undoes remote side effects | Distributed effects may already be committed | Use compensation and durable workflow state |
| Catch errors inside every layer | Loses context and duplicates policy | Recover at a clearly owned boundary |
| Start recovery from every UI render | Repeated side effects and unnecessary traffic | Trigger recovery through explicit lifecycle-aware events |
| Hide all recovery activity | Makes chronic failures invisible | Record metrics and terminal outcomes |
| Treat partial success as full success | Can leave business state inconsistent | Model partial outcomes explicitly |
| Store pending work only in memory | Process death loses user intent | Persist durable work before acknowledging it |

## 16. Production Recovery Checklist

### Classification and policy
- [ ] Expected failures are classified into stable categories.
- [ ] Permanent failures are not automatically retried.
- [ ] Recovery actions are safe for the affected operation.
- [ ] Retry and recovery budgets are bounded.
- [ ] Unknown defects remain diagnosable.

### Correctness
- [ ] Fallback values are valid for the domain.
- [ ] Stale data is not presented as fresh.
- [ ] Cancellation is propagated.
- [ ] Local transactions preserve atomicity.
- [ ] Uncertain writes use idempotency or reconciliation.
- [ ] Partial failures are represented honestly.
- [ ] Compensation is designed for distributed side effects where needed.

### Architecture and platform
- [ ] Recovery policy has a clear owner.
- [ ] Shared KMP logic is separated from platform scheduling.
- [ ] Durable work survives process death.
- [ ] Credential refresh cannot loop indefinitely.
- [ ] UI rendering does not trigger repeated recovery side effects.

### Observability and tests
- [ ] Recovery attempts and outcomes are measured.
- [ ] Cache fallback and stale-data age are observable where useful.
- [ ] Sensitive information is excluded from logs.
- [ ] Cancellation, exhausted budgets, and permanent failures are tested.
- [ ] Reconciliation, idempotency, and process restart behavior are covered.
- [ ] User-facing states provide an appropriate next action.

---

## 17. Summary

Recovery is the discipline of returning an application to a valid and understandable state after something fails.

1. Classify the failure before choosing a recovery action.
2. Keep valid cached data when it is safe and useful.
3. Use fallbacks only when they preserve domain meaning.
4. Preserve coroutine cancellation.
5. Bound retries, credential refresh, and reconciliation.
6. Treat partial failures and uncertain writes explicitly.
7. Use idempotency and durable state for recoverable workflows.
8. Keep shared KMP policies separate from platform execution constraints.
9. Make the resulting state clear to the user.
10. Measure recovery so that persistent failures remain visible.

**Recovery is successful when the application preserves correctness, protects user intent, and provides a clear next step—even when it cannot restore service immediately.**
