## 1. Why Retry Exists

Distributed systems fail temporarily. A mobile app may lose connectivity in an elevator, a server may be briefly overloaded, or a connection may reset while a request is in progress.

A retry gives an operation another chance to succeed after a failure that is likely to be transient.

Common candidates include:

- Temporary network disconnection.
- Connection reset or a transient transport error.
- Rate limiting, when the service's retry guidance is respected.
- A temporary service-unavailable response.
- A short-lived contention or resource-busy condition.
- A database operation that failed due to a transient lock or availability issue.

Retry is not a universal fix. It cannot repair invalid input, expired permissions, malformed payloads, or a business rule that rejects an operation.

### The retry decision

A useful policy asks four questions:

1. **Is this failure likely to be temporary?**
2. **Is this operation safe to repeat?**
3. **How many attempts and how much elapsed time are acceptable?**
4. **What should happen when the retry budget is exhausted?**

```text
Operation fails
      │
      ▼
Classify the failure
      │
      ├── Permanent ───────► Return/propagate failure
      │
      ▼
Is repeating the operation safe?
      │
      ├── No ──────────────► Do not retry automatically
      │
      ▼
Retry budget remains?
      │
      ├── No ──────────────► Return/propagate failure
      │
      ▼
Wait using backoff + jitter
      │
      ▼
Try again (unless cancelled)
```

The goal is resilience without creating unnecessary load, duplicate side effects, or long delays for the user.

## 2. Decide Whether a Failure Is Retryable

Retry classification should be explicit. Avoid retrying every exception just because the operation failed.

| Failure | Usually retry? | Reason |
|---|---|---|
| Temporary connection reset | Often | The next connection may succeed |
| Request timeout | Sometimes | The server may still be processing the request |
| HTTP 429 | Often, with limits | Respect `Retry-After` and service policy |
| HTTP 503 | Often, with limits | Service may recover shortly |
| HTTP 400 | Usually not | Request is typically invalid |
| HTTP 401 | Not blindly | Refresh credentials if supported, then retry under a bounded policy |
| HTTP 403 | Usually not | Repeating without changed authorization rarely helps |
| HTTP 404 | Depends on endpoint | May be permanent or reflect eventual consistency |
| Serialization/schema error | Usually not | Repeating the same invalid payload will not fix it |
| User cancellation | No | Cancellation should stop the operation |
| Business-rule rejection | No | A retry does not change the business state |
| Unknown exception | Avoid by default | Treating unknown failures as transient can hide defects |

These are starting points, not universal HTTP rules. Endpoint semantics and service contracts matter.

### Represent the decision in code

```kotlin
fun isRetryable(failure: AppFailure): Boolean =
    when (failure) {
        AppFailure.NetworkUnavailable,
        AppFailure.TimedOut,
        AppFailure.ServiceUnavailable -> true

        AppFailure.Unauthorized,
        AppFailure.Forbidden,
        AppFailure.InvalidRequest,
        AppFailure.InvalidResponse,
        AppFailure.Unknown -> false
    }
```

This assumes the application has defined these `AppFailure` cases. Model the categories that matter to your application, and keep the policy easy to test.

### Keep retry classification separate from retry execution

The classifier answers **whether** another attempt is allowed. The retry executor controls **when** and **how often** it happens. Keeping these responsibilities separate avoids embedding policy throughout repositories, ViewModels, and networking interceptors.

## 3. Retry Budgets and Attempt Counts

A retry policy needs a clear limit. Unlimited retries can waste battery, keep screens loading indefinitely, amplify an outage, and create duplicate side effects.

Define whether `maxAttempts` includes the first attempt. This chapter uses **total attempts**, including the initial call.

For example:

- `maxAttempts = 1`: no retry; one initial attempt.
- `maxAttempts = 3`: initial attempt plus at most two retries.
- `maxAttempts = 4`: initial attempt plus at most three retries.

### Attempt budget is not the whole budget

Also consider:

- **Elapsed-time budget:** the operation should not retry past its deadline.
- **User-experience budget:** a foreground action should not remain blocked too long.
- **Request budget:** repeated attempts should not overload a service.
- **Battery/data budget:** mobile devices may be on constrained networks.
- **Concurrency budget:** many simultaneous operations should not all retry aggressively.

A policy can stop when either the attempt count or deadline is exhausted.

```text
Retry allowed only when:

attemptsUsed < maxAttempts
AND elapsedTime < operationDeadline
AND failure is retryable
AND operation is safe to repeat
AND coroutine is still active
```

For foreground actions, it may be better to stop automatic retries quickly and offer a visible Retry action. Background synchronization can use a longer bounded schedule, provided the platform's scheduling rules and product requirements are respected.

## 4. Backoff Strategies

Backoff controls how long the client waits before another attempt.

### Constant delay

Wait the same amount between attempts.

```text
Attempt 1 ── fail ── wait 1s ── Attempt 2
Attempt 2 ── fail ── wait 1s ── Attempt 3
```

Easy to understand, but multiple clients can keep hitting a struggling service at the same rate.

### Linear backoff

Increase the delay by a fixed amount.

\[
d_n = \min(d_{\max}, d_0 + (n - 1)k)
\]

Where:

- \(d_0\) is the initial delay.
- \(k\) is the increase per retry.
- \(d_{\max}\) is the maximum delay.
- \(n\) identifies the retry number, beginning at 1.

### Exponential backoff

Multiply the delay after each failed attempt.

\[
d_n = \min(d_{\max}, d_0 \times 2^{n-1})
\]

For an initial delay of 500 ms and a cap of 8 seconds:

| Retry number | Delay before jitter |
|---:|---:|
| 1 | 500 ms |
| 2 | 1,000 ms |
| 3 | 2,000 ms |
| 4 | 4,000 ms |
| 5 | 8,000 ms |
| 6 | 8,000 ms |

Exponential backoff reduces request pressure during an outage. In practice, combine it with jitter and a maximum delay.

### Use safe arithmetic

Repeatedly multiplying a large duration can overflow. Production code should cap the delay before it grows beyond the supported maximum, and should validate that all configured durations are non-negative.

## 5. Why Jitter Matters

Imagine thousands of devices receive a failure at the same moment. If every device waits exactly one second, they all retry together. This can create a **thundering herd** and prolong the outage.

Jitter adds randomness to spread requests across time.

A simple full-jitter strategy chooses a random delay from zero up to the calculated exponential-backoff cap:

\[
d_n = U(0, \min(d_{\max}, d_0 \times 2^{n-1}))
\]

Here \(U(0, x)\) is a uniformly distributed random value between zero and \(x\).

Other strategies exist, including equal jitter and decorrelated jitter. The best choice depends on the client population and service guidance. The essential point is to avoid every client retrying at the same fixed instants.

### Inject randomness

Inject a random-delay strategy rather than hard-coding global randomness inside business logic. This makes tests deterministic and lets the application choose a platform-appropriate implementation.

```kotlin
fun interface RetryJitter {
    fun delayMillis(capMillis: Long): Long
}
```

A production implementation can choose a value in the allowed range. A test implementation can return a fixed value, such as zero, to make the expected schedule predictable.

## 6. A Small Reusable Retry Helper

A reusable helper should own the attempt loop and delay, while the caller provides retry classification. The following example uses total attempts and a delay strategy supplied by the caller.

```kotlin
import kotlinx.coroutines.CancellationException
import kotlinx.coroutines.delay

suspend fun <T> retrying(
    maxAttempts: Int,
    shouldRetry: (Exception) -> Boolean,
    delayBeforeRetryMillis: (retryNumber: Int) -> Long,
    block: suspend () -> T
): T {
    require(maxAttempts >= 1) {
        "maxAttempts must be at least 1"
    }

    var attempt = 1

    while (true) {
        try {
            return block()
        } catch (cancelled: CancellationException) {
            throw cancelled
        } catch (exception: Exception) {
            val attemptsExhausted = attempt >= maxAttempts

            if (attemptsExhausted || !shouldRetry(exception)) {
                throw exception
            }

            val retryNumber = attempt
            val waitMillis = delayBeforeRetryMillis(retryNumber)
                .coerceAtLeast(0L)

            attempt += 1
            delay(waitMillis)
        }
    }
}
```

### Example usage

```kotlin
suspend fun fetchProfileWithRetry(): Profile =
    retrying(
        maxAttempts = 3,
        shouldRetry = ::isTransientNetworkException,
        delayBeforeRetryMillis = { retryNumber ->
            when (retryNumber) {
                1 -> 500L
                2 -> 1_000L
                else -> 2_000L
            }
        }
    ) {
        profileApi.fetchProfile()
    }
```

`isTransientNetworkException` is an application-defined classifier; its implementation depends on the networking library and target. The delays shown are illustrative. In production, prefer a capped backoff with jitter and respect any service-provided retry timing.

### Why this helper is intentionally small

It:

- Counts the initial call as attempt one.
- Does not retry non-retryable exceptions.
- Rethrows cancellation.
- Uses cancellable coroutine `delay`.
- Propagates the last failure after attempts are exhausted.
- Lets the caller define classification and delay policy.

It does not automatically understand HTTP response headers, idempotency, operation deadlines, or server-specific semantics. Those concerns belong in the policy or the operation boundary.

## 7. Retry with Kotlin Coroutines

Coroutine-aware retry should suspend rather than block a thread.

### Use `delay`, not `Thread.sleep`

```kotlin
delay(1_000L)
```

`delay` suspends the coroutine without blocking the underlying thread and is cancellable. `Thread.sleep` blocks a JVM thread and is not a portable common-code retry mechanism.

### Cancellation must stop retries

If the parent scope is cancelled during a backoff delay, `delay` throws cancellation and the coroutine stops. Do not catch that cancellation and continue the loop.

### Add an overall deadline

An attempt limit alone may not bound total elapsed time if each attempt itself can take a long time. Use an operation timeout where supported by the coroutine APIs in your project:

```kotlin
suspend fun fetchWithDeadline(): Profile =
    withTimeout(5_000L) {
        retrying(
            maxAttempts = 3,
            shouldRetry = ::isTransientNetworkException,
            delayBeforeRetryMillis = { retryNumber ->
                250L * retryNumber
            }
        ) {
            profileApi.fetchProfile()
        }
    }
```

This is an illustrative example. Choose the deadline based on the endpoint, user experience, and timeout configuration of the networking client. The coroutine timeout does not necessarily terminate remote server processing, and client cancellation does not guarantee that the server did not complete a request.

### Do not stack independent retry loops blindly

If the HTTP client retries three times and the repository retries three times, one logical operation may produce up to nine network attempts. Nested retry policies can multiply traffic and latency.

Choose one primary retry owner for each failure class. If multiple layers must retry, calculate the combined worst-case attempts and elapsed time explicitly.

## 8. Retry with `Flow`

Flows support retry operators for upstream failures. These are useful for streams that can meaningfully restart after a transient error.

### `retry`

```kotlin
fun observeConnection(): Flow<ConnectionState> =
    connectionDataSource.observe()
        .retry(retries = 3) { cause ->
            cause is IOException
        }
```

This retries upstream collection up to the configured retry count when the predicate returns `true`. The exact count semantics differ from the `maxAttempts` convention used by the helper above: `retry(retries = 3)` permits up to three retries after the original collection attempt.

### Add a delay with `retryWhen`

```kotlin
fun observeConnection(): Flow<ConnectionState> =
    connectionDataSource.observe()
        .retryWhen { cause, attempt ->
            val retryAllowed =
                cause is IOException && attempt < 3

            if (retryAllowed) {
                delay(backoffMillis(attempt.toInt() + 1))
            }

            retryAllowed
        }
```

This example assumes `backoffMillis` is a project-defined function and that the attempt value is safely converted for the chosen policy. Production code should avoid unsafe numeric conversions and add jitter where appropriate.

### Important flow considerations

- Retry restarts the upstream flow; it does not resume from an arbitrary point unless the source supports that behavior.
- A cold flow may repeat its upstream side effects on each collection attempt.
- Cancellation should not be converted into a normal retryable failure.
- Infinite retry may be appropriate for a long-lived stream only when it is bounded by lifecycle cancellation and includes sensible backoff.
- A flow that repeatedly fails should expose status or telemetry so users and operators can distinguish “connected” from “continually reconnecting.”

For UI state, consider emitting a connection or synchronization status rather than silently hiding every failed reconnect.

## 9. Retry at the Correct Architecture Layer

A layered KMP application should avoid scattering retry loops throughout the codebase.

```text
                 ┌─────────────────────┐
                 │ UI / ViewModel      │
                 │ User-triggered retry│
                 └──────────┬──────────┘
                            │
                 ┌──────────▼──────────┐
                 │ Use case            │
                 │ Business policy      │
                 └──────────┬──────────┘
                            │
                 ┌──────────▼──────────┐
                 │ Repository           │
                 │ Stable outcome       │
                 └──────────┬──────────┘
                            │
                 ┌──────────▼──────────┐
                 │ Remote/local source  │
                 │ Transport-specific   │
                 └─────────────────────┘
```

### Networking client

Use client-level retry only for failures it can classify correctly and for operations that are safe to repeat. Client libraries may already implement connection recovery or protocol-specific behavior.

### Repository

A repository is often a suitable owner for retrying a remote read because it understands the data source and can map the final failure into a stable result. Do not retry every repository method by default.

### Use case

The use case can own a business-level retry decision when it coordinates multiple operations or needs to enforce an overall deadline. Avoid repeating low-level networking logic here.

### ViewModel or UI

A user-triggered Retry button is not the same as an automatic retry loop. The UI should communicate the failure and let the user retry when that is the right product experience.

### Background worker

A background worker should use the platform's scheduling and backoff facilities where appropriate. Persisted work may outlive a screen or process, so do not rely on an in-memory coroutine loop for durable scheduling.

**Rule:** Give each retry responsibility a clear owner, and document whether its count refers to attempts or retries.

## 10. HTTP Retry Policies

HTTP retry behavior depends on method semantics, endpoint behavior, response status, headers, and service guarantees.

### Respect `Retry-After`

A service may provide a `Retry-After` header, commonly with a delay or an HTTP date. When the server gives retry guidance, interpret it according to the HTTP client and protocol requirements. Do not retry earlier than required by the service's policy. Also apply an application-level maximum wait or stop and surface the failure when the wait exceeds the operation's deadline.

### Retry status codes selectively

Some systems retry 429 or selected 5xx responses. This is not a universal list. Read the API contract, and consider whether the response body or headers explain a permanent failure.

### Timeouts are ambiguous

A client timeout does not prove that the server did not execute the request. The server might have committed a write but the response may have been lost. That is why operation safety and idempotency must be considered before retrying.

### Avoid retrying validation and authorization errors blindly

- A 400 response usually requires a corrected request.
- A 401 may need a controlled credential-refresh flow, not repeated identical requests.
- A 403 usually requires changed authorization.
- A 404 depends on the endpoint and consistency model.

Do not treat every non-success HTTP response as an exception without a clear policy. Some HTTP clients return response objects for error statuses, so the retry classifier must handle the actual result type used by the client.

## 11. Idempotency and Retrying Writes

An operation is **idempotent** when repeating it has the same intended effect as performing it once.

For example, setting a preference to `dark` is naturally idempotent:

```kotlin
suspend fun setTheme(theme: Theme) {
    settingsApi.updateTheme(theme)
}
```

Repeating the same assignment should leave the same final value.

An operation that creates a new payment, order, or shipment may not be idempotent. Repeating it can create duplicates unless the server provides an idempotency mechanism.

### Safer write retries

Before automatically retrying a write:

1. Determine whether the operation is naturally idempotent.
2. Check whether the server supports an idempotency key or operation identifier.
3. Reuse the same key for attempts belonging to the same logical operation.
4. Confirm the server's deduplication scope and retention window.
5. Distinguish “request definitely failed before processing” from “outcome unknown.”
6. Reconcile with the server if the outcome is ambiguous.

An idempotency key is not useful if the client generates a new key for every retry. The key must identify the same logical operation across attempts.

### Do not promise exactly-once behavior from retries alone

Networks can lose responses, clients can be killed, and workers can run more than once. Robust systems commonly combine at-least-once delivery with server-side deduplication, idempotent state changes, or reconciliation.

For critical writes, “retry until success” is not a complete consistency strategy.

## 12. Offline-First Apps and Background Work

A mobile app often needs different retry policies for foreground interactions and background synchronization.

### Foreground request

For a screen load:

- Use a short, bounded automatic retry policy if the failure is likely transient.
- Avoid keeping the UI blocked for too long.
- Preserve existing content where useful.
- Show an actionable error state when the budget is exhausted.
- Let the user initiate another attempt.

### Background synchronization

For durable work:

- Persist the work request if the operation must survive process death.
- Use the platform's work scheduler and backoff policy when appropriate.
- Require network connectivity only when it is a real prerequisite.
- Make the operation safe for duplicate execution.
- Record attempts and the final outcome.
- Avoid implementing a long `delay` loop that keeps a process alive unnecessarily.

In Android, WorkManager supports retry and backoff for work that returns a retry result. Its scheduling behavior is controlled by the system and is not an exact timer. Shared KMP business logic can define failure classification, while the Android worker translates that policy into WorkManager's supported behavior.

On iOS and other targets, use the appropriate platform scheduling APIs for durable background work. Do not assume that a coroutine kept in memory will continue running after the application is suspended or terminated.

### Cache fallback is not the same as retry

If a network read fails, returning valid cached data may improve availability. Make the state clear: cached content can be displayed while a refresh is pending or has failed. Do not disguise stale content as a successful fresh response when freshness matters.

## 13. Observability and Retry Metrics

A retry policy should be measurable. Otherwise, a system can quietly spend most of its time retrying while dashboards show only final successes.

Track metrics such as:

- Attempts per logical operation.
- Retry success rate.
- Final failure rate after the retry budget.
- Time spent waiting in backoff.
- Total operation latency.
- Failures grouped by stable category and endpoint.
- Rate-limit responses and compliance with `Retry-After`.
- Duplicate-operation or idempotency-key conflicts.
- Background work age and retry exhaustion.

### Log the attempt context

A useful event might include:

```text
operation=fetch_profile
attempt=2
max_attempts=3
failure_category=timeout
backoff_ms=750
will_retry=true
```

This is illustrative structured logging. Avoid logging credentials, personal data, raw payloads, or arbitrary exception messages as metric dimensions.

### Avoid high-cardinality metrics

Do not use raw exception messages, request IDs, or user IDs as metric labels. Use stable failure categories for metrics and keep sensitive or high-cardinality details in a controlled diagnostic channel only when needed.

A rising retry success rate can indicate that retries are recovering transient failures. A rising attempt count or retry exhaustion rate may instead signal a backend incident, poor timeout settings, or a client regression.

## 14. Testing Retry Behavior

Retry tests should not wait through real seconds or rely on real networks. Inject the delay strategy, use coroutine test utilities, and assert the observable contract.

### Test retry then success

```kotlin
@Test
fun retriesTransientFailureAndEventuallySucceeds() = runTest {
    var calls = 0

    val result = retrying(
        maxAttempts = 3,
        shouldRetry = { it is IOException },
        delayBeforeRetryMillis = { 0L }
    ) {
        calls += 1
        if (calls < 3) throw IOException("Temporary failure")
        "success"
    }

    assertEquals("success", result)
    assertEquals(3, calls)
}
```

### Test that permanent failures are not retried

```kotlin
@Test
fun doesNotRetryPermanentFailure() = runTest {
    var calls = 0

    assertFailsWith<IllegalArgumentException> {
        retrying(
            maxAttempts = 4,
            shouldRetry = { false },
            delayBeforeRetryMillis = { 0L }
        ) {
            calls += 1
            throw IllegalArgumentException("Invalid request")
        }
    }

    assertEquals(1, calls)
}
```

### Test exhausted attempts

```kotlin
@Test
fun propagatesFailureAfterMaximumAttempts() = runTest {
    var calls = 0

    assertFailsWith<IOException> {
        retrying(
            maxAttempts = 3,
            shouldRetry = { true },
            delayBeforeRetryMillis = { 0L }
        ) {
            calls += 1
            throw IOException("Still unavailable")
        }
    }

    assertEquals(3, calls)
}
```

### Test cancellation

```kotlin
@Test
fun doesNotRetryCancellation() = runTest {
    var calls = 0

    assertFailsWith<CancellationException> {
        retrying(
            maxAttempts = 5,
            shouldRetry = { true },
            delayBeforeRetryMillis = { 0L }
        ) {
            calls += 1
            throw CancellationException("Cancelled")
        }
    }

    assertEquals(1, calls)
}
```

These tests assume `kotlinx-coroutines-test`, Kotlin test assertions, and the retry helper shown earlier. Add tests for:

- Delay progression and caps.
- Jitter bounds using deterministic injected randomness.
- Deadline exhaustion.
- `Retry-After` handling.
- HTTP classification.
- Idempotency key reuse.
- Flow retry count and cancellation.
- Worker behavior after process restarts.
- Platform-specific networking behavior.

## 15. Common Anti-Patterns

| Anti-pattern | Why it is risky | Better approach |
|---|---|---|
| Infinite immediate retries | Can overload the client and server | Bound attempts and add backoff |
| Retrying every exception | Repeats permanent failures and may hide defects | Use an explicit classifier |
| No jitter | Many clients retry simultaneously | Add jitter to backoff |
| Retrying non-idempotent writes | Can create duplicate side effects | Use idempotency keys or reconciliation |
| Ignoring `Retry-After` | Can violate service guidance and worsen rate limiting | Respect server-provided timing |
| Nested retry loops | Multiplies attempts and latency | Assign clear retry ownership |
| `Thread.sleep` in coroutine code | Blocks a thread and is not portable common code | Use cancellable `delay` |
| Swallowing cancellation | Work continues after it should stop | Rethrow cancellation |
| Retrying forever in a UI request | User waits without a clear outcome | Use a bounded policy and visible retry action |
| Treating cache fallback as fresh data | Misleads the user about freshness | Expose freshness and sync status |
| Testing with real delays | Slow, flaky tests | Inject timing and use virtual time |

## 16. Production Checklist

### Policy
- [ ] Retryable failures are explicitly classified.
- [ ] The attempt count includes or excludes the initial call by documented convention.
- [ ] Attempts and total elapsed time are bounded.
- [ ] Backoff has a maximum delay.
- [ ] Jitter prevents synchronized retries.
- [ ] Server retry guidance is respected.

### Safety
- [ ] The operation is safe to repeat.
- [ ] Writes use idempotency keys or another duplicate-prevention strategy where needed.
- [ ] Ambiguous outcomes are reconciled rather than blindly repeated.
- [ ] Coroutine cancellation stops both attempts and waiting.
- [ ] Nested retry layers have a calculated combined budget.

### Architecture
- [ ] Each retry policy has a clear owner.
- [ ] Shared KMP code avoids platform-specific retry dependencies unless isolated behind an abstraction.
- [ ] Foreground and durable background work use suitable policies.
- [ ] Cache fallback is distinguishable from fresh success.
- [ ] Final failures map to stable application outcomes.

### Quality
- [ ] Success-after-retry, permanent failure, and exhausted-budget cases are tested.
- [ ] Cancellation is tested.
- [ ] Delay and jitter behavior can be tested deterministically.
- [ ] Retry metrics are recorded with low-cardinality labels.
- [ ] Logs exclude secrets and sensitive payloads.

---

## 17. Summary

Retries can improve resilience, but only when they are controlled by a clear policy.

1. Retry failures that are likely to be temporary.
2. Confirm that repeating the operation is safe.
3. Bound both attempts and elapsed time.
4. Use exponential backoff with jitter when appropriate.
5. Respect service-provided retry guidance.
6. Preserve coroutine cancellation.
7. Avoid multiplying retries across layers.
8. Protect writes with idempotency or reconciliation.
9. Use platform schedulers for durable background work.
10. Measure retry behavior and test it without real waiting.

**A good retry policy protects the user from temporary failure without turning a small failure into a larger outage.**
